## 1. 🔑 まず、こちらの読み違えを 1 つ訂正する

P4 の実地棚卸し(#283 のコメント 2026-08-28)は、こう書いた:

> **`REQUEST_BODY_REWRITE` は「1 操作 = 1 エントリの read-modify-write + `expectHash` 1 本」**
> ── **2 エントリを 1 操作で更新する形が存在しない**。前提ごと作り直しになる

⚠ **これは半分外れている。**

板の上でカードを動かすとき、**書き換わるのは板自身の本文 1 本だけ**である
── 置かれた相手のノートは 1 バイトも変わらない(参照しているだけ)。
つまり **既存の「1 操作 = 1 エントリ」はそのまま成立する**。

🔴 **本当に作り直しになるのは、板の上から「置かれた相手の中身」を編集したいとき**だけ
(板の上でチェックを付ける / 題名を直す)。そこは §6 の **W5** に切る。

🔑 この訂正で設計の重さが 1 段変わる ── 「storage の書込経路を広げる」話ではなく、
「**板の本文の記法を決める**」話に戻る。

## 3. 決めること ① ── 位置と結び付きをどこに書くか

### 推薦: **板の本文(PKC-Markdown)の記法に書く**(P4 の `:::format{.pkc-place …}` を土台に)

| 案 | 位置の在り処 | JSON 裁定 | 1 操作 1 エントリ | 旧ビルドが読めるか |
|---|---|---|---|---|
| **A 板の本文の記法**(推薦) | 板の本文 | ✅ 守る | ✅ 成立 | ✅ **ただの markdown として読める** |
| B 新しい body 形式(行指向 DSL) | 板の本文 | ⚠ JSON ではないが、**2 つ目の本文文法**を作る | ✅ | ⚠ 旧ビルドは意味を解さない |
| C `relations` に属性列を足す | DB | 🔴 schema 変更 | 🔴 崩れる(2 エントリ更新) | 🔴 **危険**(下記) |

🔴 **C は PKC2 が実際に事故を起こした形**である。PKC2 の不変条件 5(2026-07-26):

> とくに危険なのは **「読み側に合流処理を足して両立させる」型の変更**
> (`__rel__:` / `__order__:` サイドカー):新ビルドでは正しく動くので test が全部通り、
> **旧ビルドでだけ静かに欠損する**(relations が 0 件に見え、保存すると実際に消えた)

⚠ **PKC2 の `relations` には属性列が無く、PKC3 にも無い**(実測:
`schema.ts` の DDL は `cid / id / from_lid / to_lid / kind / created_at / updated_at`)。
足すのは schema 変更であり、この罠の顔をしている。

### ⚠ A を採ると決まること

- **板 = `whiteboard` archetype のノート**。body は PKC-Markdown
- 置かれた 1 枚 = **1 つの format 塊**(`:::format{.pkc-place entry=… x= y= w= h=}`)
- **書き戻しは板の本文だけ**(`REQUEST_BODY_REWRITE` を 1 本、既存の門と `expectHash` のまま)
- **アセットも同じ形**で置ける(塊の中に `![](asset:…)` を書く ── 実測で hydration は
  正常に働き、ObjectURL も表示の寿命終端で返る)

## 4. 決めること ② ── **掴む以外の道を最初から用意する**

🔴 **PKC2 はこれで動線を失った。** ランチャーの並び替えは元々 **◀▶ ボタン**だったのを
2026-07-17 に DnD 主体へ刷新し、**ボタンを撤去した** ── その後 touch 対応を足したが、
効くのは「hover で隠れたボタンを出す」だけで、**並び替えは DnD しか無いまま**である。

**最低 3 本を同時に出す**:

1. **掴んで動かす**(P4 の機構をそのまま ── slop / clamp / 見た目の復元 / 2 本目の指の拒否)
2. **キーボード**(選んで矢印。粗く動かす修飾キー)
3. **数値で入れる**(情報ペインか、右クリックから)

⚠ ③ の置き場は**見え方が変わる**ので、入れる前に画面の言葉で user へ出す。

## 5. 決めること ③ ── テンプレートコンポーネントとは何か

PKC2 の前例は 2 つ、どちらも**半分だけ**当たっている:

| 前例 | できること | 足りないこと |
|---|---|---|
| `/tmpXX`(雛形) | **本文へ字を貼る** | 保存先が flag の JSON 文字列(⚠ container ではない) |
| `structure-dsl` | **テキスト 1 枚で folder 階層を作る** | **中身も配置も作れない** |

🔑 ホワイトボードで要るのは**その中間** ── 「**板の一部(複数の塊 + 位置)を 1 枚の字として貼る**」。
板の本文が markdown なら、**テンプレート = 板の本文の断片**でよい。
= **既存の雛形機構がそのまま使える**(新しい保存先を作らない)。

## 6. 置かれたコンテナの中身をどう描くか ── 🔴 **過去の裁定を覆す提案**

user の言葉は「**各レンダリング結果コンテナ**を自由に配置」── つまり
「ノートの題名の札」ではなく「**描かれた結果そのもの**」を置きたい、と読める。

⚠ **PKC3 の P4 は「展開はしない」と裁定済み**である(2026-08-19 Q1。
`place-board.ts` の docstring に明記)。**#529 はその裁定を覆す提案**になる。

覆すなら、PKC2 の transclusion が持っていた制約を**そのまま引き継ぐ**
(PKC2 が実際に必要だと分かって入れたもの):

- **深さ ≤ 1**(埋め込みの中の埋め込みはリンクへ降格)
- 埋め込み subtree の **id は全部剥がす**(host の目次ジャンプと衝突する)
- 埋め込み内のチェックボックスは**読み取り専用**(← ⚠ W5 まではこの形)
- 自己埋め込み・循環はリンクへ降格

## 7. 測ることを先に決める(user 指示 2026-08-03)

この形に乗せると即座に破綻する。PKC3 の P4 は既に「掴んでいる間は style だけ動かす」形。
