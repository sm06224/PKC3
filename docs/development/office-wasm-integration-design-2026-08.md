# Office wasm を PKC3 本体へ組み込む(設計、2026-08-10)

> 🔴 **user 裁定 2026-08-10(不可侵)**
>
> 「**入れる / なんのためにやったと思ってる / ただし、実行したい人が手動で設定した際に
> 追加ダウンロードと idb とか opfs に配備して、以降の起動はローカルからにしてください /
> また、新規作成後に PKC に保存する導線、PKC の添付をもとに編集、上書きもできるように
> しましょう / と、思ったけど、うまくいかない場合は、ローカルとかを介してユーザーが
> できればいいです / 少なくとも閲覧はしーむれすたいけんにしたいなぁ**」

⚠ この裁定は **#88 の「閲覧優先で実装 / 可能なら独自ビルドしてしまえ」の続き**であり、
選定のやり直しではない。engine は既に焼けている(`office-wasm-selection-2026-08.md` §3.9〜§3.15)。

## 0. 裁定を要件へ落とす

| # | user の言葉 | 要件 |
|---|---|---|
| R1 | 実行したい人が**手動で設定**した際に | **既定では何も起きない**。設定画面で明示的に有効化したときだけ取得が始まる |
| R2 | **追加ダウンロード**と idb とか opfs に**配備** | 約 93MB を 1 回だけ取得し、**ローカルに保管**する |
| R3 | **以降の起動はローカルから** | 2 回目以降は network に出ない |
| R4 | **新規作成後に PKC に保存する導線** | LO で作った文書を PKC3 の添付として保存できる |
| R5 | **PKC の添付をもとに編集、上書き** | 既存添付を開いて編集し、**同じ添付へ書き戻す** |
| R6 | うまくいかない場合は**ローカルを介して** user ができればいい | R4/R5 が詰まったら、**書き出し → 手で添付**の逃げ道を必ず用意する |
| R7 | 少なくとも**閲覧はシームレス** | 添付を押したらその場で見える。別モード・別画面へ飛ばさない |

🔑 **優先順位は R7 > R5 > R4**。閲覧が滑らかでないなら、編集ができても意味がない。

## 1. 取得元 ── ここだけは実測で道が塞がっている

🚫 **GitHub Release 資産を JS から取ることはできない**(選定 doc §3.15 で実測)。
ACAO を 1 つも返さず OPTIONS は 405 なので、`fetch` は `TypeError` になる。
⚠ **coi-serviceworker はこれを救わない**(あれは COOP/COEP であって CORS ではない)。

したがって取得元は次の 2 つだけで、**両方を用意する**(R6 の「逃げ道」はここに効く):

| 経路 | 中身 | いつ使うか |
|---|---|---|
| **A. 同一 origin から取得** | PKC3 の配信元のサブパス(`/office/` 等)に一式を置く | 既定。押すだけで済む |
| **B. 手元の zip を選ぶ** | user が release から落とした zip を **file picker で読ませる** | A が無い / オフライン / 社内配布。⚠ **CORS の外**なので必ず通る |

🔑 **B を「保険」ではなく一級の導線にする。** A は配信環境に依存するが、B はしない。
⚠ B は user が 93MB を手で扱うので、**取り違え検出のため sha256 を必ず照合する**
(選定 doc §5 の `wasm-pack-store` の規約:「壊れを検出する材料を捨てない」)。

## 2. 置き場 ── IDB Blob(OPFS ではない)

user は「idb とか opfs」と言ったが、**IDB Blob を採る**。理由:

- 既に**同型の前例が 2 つ**ある(`pkc3-assets` / `pkc3-diagram-cache`)。3 例目として同じ規約で書ける
- `URL.createObjectURL(blob)` → `fetch` で **heap に載せずに流せる**
  (不可侵「ゼロコピー・生成物の即破棄」に沿う)
- OPFS は **storage worker が sqlite の lease を握っている**。同じ面に大物を同居させると、
  quota 逼迫時の挙動がノートの本体に波及する ── **分けておくほうが安全**

保存するのは **gz のまま**(`soffice.wasm.gz` 50.6MB + `soffice.data.gz` 26.4MB)。

- 置き場の実容量が **約 93MB → 約 77MB** で済む
- 起動時に `DecompressionStream('gzip')` + `WebAssembly.instantiateStreaming` で
  **解きながら compile**(実測 4,041ms / 288 exports、148MB を heap に載せない)

```
IDB store: pkc3-office-pack
  key            = 'lo-wasm-qt6'
  { version, sha256, files: { 'soffice.wasm.gz': Blob, 'soffice.data.gz': Blob,
                              'soffice.js': Blob, 'qtloader.js': Blob,
                              'soffice.data.js.metadata': Blob, 'fonts/*.ttf': Blob },
    fetchedAt, source: 'url' | 'file' }
```

⚠ **自動更新はしない**(§5 の規約)。設定画面に「確認 → 取得 → 差し替え」と
**削除**を置く。R3(以降はローカルから)は、この store を見るだけで満たされる。

## 3. 走らせ方 ── **別窓で開き、閉じたら消える**

> 🔴 **user 裁定 2026-08-10(追補。不可侵)**
>
> 「**ちなみに別タブでも構いません / 見やすければいいのだ / 同じ窓にこだわると、
> PKC の編集をしながら資料を読むとかできませんし**」

⚠ 当初は「添付 preview の器に iframe で出す」と書いていた。**この裁定で差し替える。**
理由は user の言うとおり ── **同じ窓に押し込むと、資料を読みながら PKC を編集できない**。
そして技術的にも別窓のほうが素直である:

| | iframe(旧案) | **別窓(採用)** |
|---|---|---|
| 版面の広さ | 添付ペインの中だけ | **窓いっぱい**。資料が読める |
| 編集しながら読む | できない | **できる**(並べる) |
| CPU の分離 | ⚠ 同じ process を共有しうる ── LO が重い間は本体も詰まる | 別の最上位文書。**分かれやすい** |
| 破棄 | `iframe.remove()` | **窓を閉じる**(realm ごと消える) |
| COEP の入れ子 | 親の分離条件を満たす必要がある | 各窓が自分のヘッダで成立 |

### なぜ「捨てられる境界」が要るのか(理由は変わらない)

1. **常駐 780MB**(実測)。開いている間だけの費用にしないと「業務画面」に置けない
2. 不可侵「重い処理はワーカーへ / アイドルで kill と解放」── ところが
   **LO は worker へ出せない**。Qt6 の wasm plugin は
   `val::global("window"/"document")` を **12 file・25 箇所**で叩いており、
   DOM を持たない worker では動かない(選定 doc §3.10)
3. emscripten の module は**同じ realm では解放しきれない**

🔑 したがって「worker へ出す」の代わりに **realm ごと捨てられる境界**を用意する。
別窓はその境界として iframe より強い。

```
PKC3 本体(窓 A)            Office(窓 B = office/host.html)
  ├ ノートを編集し続けられる     └ LibreOffice(この窓の main thread)
  └ postMessage で往復          × 閉じる = 780MB が還る
```

### ⚠ 別窓ゆえに確かめる必要があること

- **`window.open` は user の操作から呼ぶ**(でないとポップアップ遮断に遭う)
- **`window.opener` が生きるか** ── COOP `same-origin` は*別 origin*の opener を切る。
  同一 origin・同一 COOP なら browsing context group を共有するので残るはずだが、
  **保存の往復(R4/R5)がここに乗る**ので実測する
- **窓が既に開いているときは使い回す**(2 つ立てて 1.5GB にしない)
- **本体を閉じた / 再読込した**ときに、開きっぱなしの Office 窓が孤児にならないこと

### 閲覧の「シームレス」は何を指すか(R7 の読み直し)

**添付を押したら、余計な手順なしで読める状態になる**こと ── 同じ窓に描くことではない。
- 添付の器には「Office で開く」を置き、押したら**その場で窓が開いて文書が出る**
- 未配備なら、器に**設置カード**を出す(⚠ 勝手に取得を始めない = R1)

## 4. 面の作り ── 既存の器に出す(新モードを作らない)

不可侵「目指す姿は業務画面 ── 同じものが常に同じ場所にある」に従う。

- 閲覧(R7): 添付の preview の器 `[data-pkc-field="attachment-preview"]` に**その場で**出す。
  ⚠ **別モード・別画面へ飛ばさない**(#88 の「その導線はダメです / PDF を閲覧したい
  わけじゃない」と同じ轍)
- 未配備のとき: preview の位置に**設置カード**(「Office 表示を使うには一式が要ります」+
  取得ボタン + 手元の zip を選ぶ)。⚠ **勝手に取得を始めない**(R1)
- 編集(R5): preview の「編集」で iframe を編集可へ。保存で**同じ添付を上書き**
- 新規(R4): ランチャに「Office 文書を新規作成」。保存で**添付として PKC に入る**

## 5. 保存の実装 ── UNO を使わず、**FS を読む**

LO wasm の embind API に依存しない。実測で通っている手順がある(選定 doc §3.12):

1. `Ctrl+S` を送る(LO 自身に保存させる)
2. `Module.FS.readFile('/work/<name>')` で**バイト列を読む**
3. そのバイト列を PKC3 の添付として書き戻す

⚠ 実証済み: 打鍵したあと `Ctrl+S` → `bytes 98,647 / 目印 138 件`を読み出せた。
🔑 UNO/embind に手を出さないので、**上流のビルド構成に縛られない**。
⚠ ただし「保存できたか」を **戻り値では判定できない** ── 保存前後で
**FS 上の mtime とバイト長が変わったこと**を確認してから書き戻す(黙って古い版を
上書きしない)。

## 6. R6 の逃げ道(必ず作る)

- 取得が通らない → **手元の zip を選ぶ**(§1 B)
- 書き戻しが通らない → LO の「名前を付けて保存」で**端末へ書き出し**、
  PKC3 側の通常の添付追加で入れる
- ⚠ 逃げ道は**設定画面の奥ではなく、詰まったその場に出す**
  (「うまくいかない場合は、ローカルとかを介してユーザーができればいい」)

## 7. 切り替えの扱い ── flag ではなく **設定**

不可侵「flags は最大 15 個 + 各 flag に畳む条件の宣言必須。**正規設定(settings)と分離する**」。
Office 表示は **user が恒久的に選ぶもの**であって、畳む予定のある実験ではない。
したがって **settings 側**に置く(15 枠を食わない)。
⚠ URL クエリで有効化する裏口は**作らない**(不可侵「クエリパラメータを抜け穴にしてはいけない」)。

## 8. 段取り(1 段ずつ着地・1 段ずつ計測)

| 段 | 中身 | 単独で言えること |
|---|---|---|
| **O1** | `office-pack-store`(IDB Blob / sha256 / 取得 A・B / 削除) | 「93MB を 1 回だけ取り、以後ローカルから読める」 |
| **O2** | `office/host.html` + **別窓**の生成・使い回し・破棄 | 「開いて閉じたら 780MB が還る」(**実測して示す**) |
| **O3** | 添付 preview で**閲覧**(R7) | 「添付を押したらその場で見える」 |
| **O4** | 編集 → **同じ添付を上書き**(R5) | 「往復してもデータが壊れない」 |
| **O5** | **新規作成 → PKC に保存**(R4) | 「作って入れられる」 |
| **O6** | 逃げ道の仕上げ(R6)と設定画面 | 「詰まっても user が抜けられる」 |

⚠ **O2 の「還る」は必ず測る。** 不可侵「効くのは定常」── 開閉を繰り返して
RSS が戻らないなら、この設計は成立していない。`steady-probe.mjs` の対照群のやり方を使う。

  smoke 全 100 spec が緑(`require-corp` だと外部画像が全部死ぬ)
