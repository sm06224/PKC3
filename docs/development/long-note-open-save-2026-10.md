# 長いノートで「開く・保存する」のたびに全体を作り直す所(#1467 段 5。設計 doc ── 実装なし)

⚠ **この doc は測定と設計だけ。** `src/` は 1 行も変えていない。推薦(§6)に進むかどうかは、
§6 の「最初の 1 手」(プロトタイプでの常駐メモリの実測)を見てから決める。

- 測った版: main `66837c12`(#1544 着地後)。`npm run build` した `dist/` を `vite preview` で配って測定
- 前提: #1467 の段 1〜4(差分描画・図の差し替えの 1 コマ化・ホイールの引っかかり・打鍵中の先読み停止)は着地済み

## 0. 要約

**原因(3 行)**

1. 編集に入る時、読む面の DOM は**捨てられる**(`detail.ts:2120-2121` `region.textContent=''` + `dropSkeleton()`。
   `bodyView = EMPTY_VIEW` に戻る ── `detail.ts:837`)。保存・取消で戻る時は**空の面から全部作り直す**。
   行の確定(Tab)で効いている塊の差分は、**編集中の別の DOM**(ライブエディタ)に対するもので、読む面とは共有していない。
2. 作り直しは `applyBlocks(host, html, EMPTY_VIEW)` → `intact()` が `view.blocks.length === 0` で偽
   (`apply-blocks.ts:127`)→ **`replaceAll`**(`:59`)。しかも本文は毎回ワーカーで全文を描き直している
   (`detail.ts:1763`。結果の再利用は無い)。
3. 時間の大半は JS ではなく**最初のレイアウト**(`detail.ts:1829` `scroller.scrollTop = …` が強制する)。
   20,000 行・図入りの保存で 1 本の long task 903 ms のうち **678 ms がこの 1 行**。内訳は §3。

**推薦**: 読む面の DOM を編集のあいだ**捨てずに `content-visibility: hidden` で持ち越す**(§5-A)。
戻る時は同じ DOM に差分(`applyBlocks`)を当てる。見え方は同じ節点を使うので変わらず、
保存・取消の再構築と、保存後の図の再接続(長い task で 1.2〜1.5 秒)が消える見込み。
**ただし常駐メモリが増える**(編集中だけ、読む面の節点ぶん ── §5-A)ので、**最初に実測する**(§6)。

## 4. 原因 ── 保存で全体を作り直す経路

「本文の構造が変わっていないのに、なぜ全体か」の答え: **構造が変わったかどうかを比べる相手(前の DOM)が、
編集に入った時点で無くなっている**。

1. **編集に入る**: `renderCore`(`detail.ts:1118`)→ `renderEditor`(`:2104`)が `region.textContent = ''`(`:2120`)
   と `dropSkeleton()`(`:2121`)。`dropSkeleton` は `bodyHost = null` と `bodyView = EMPTY_VIEW` に戻す(`:824-837`)。
   読む面の DOM・図の器・その画像は全部ここで捨てられる(捨てるのは設計:`disposeLends()` が借りた URL を返す)。
2. **保存 / 取消で戻る**: `COMMIT_EDIT`(`app-state.ts:6433`)は `phase` を `ready` に戻す。
   `renderCore` の指紋(`mode !== 'editor'` を要求する比較、`detail.ts:1237` 付近)は
   `mode === 'editor'` なので一致せず、`renderView`(`:1259`)へ。`fresh`(`:1296`)が真 → 骨組みから組み直す(`:1304`)。
3. `renderView` は `this.markdown.render(shown, opts)`(`:1763`)で**全文を毎回ワーカーに描かせる**。
   `MarkdownClient.render`(`markdown-client.ts:94`)に結果の再利用(メモ)は無い。
4. 届いた HTML を `applyBlocks(host, html, this.bodyView)`(`:1633`)に渡すが、`bodyView` は `EMPTY_VIEW`。
   `intact()`(`apply-blocks.ts:126`)は `view.blocks.length === 0` なら偽(`:127`)→ `replaceAll`(`:203`)。
   差分(`patchSegment` / `diffBlocks`)は**前の塊の列があるときだけ**効く。
5. 作り直した DOM の全部に `hydrateFigures` / `hydrateAssetRefs`(`:1640` 付近)と、後処理(`:1675`〜`:1745` 付近)が走り、
   最後に `restoreScroll()`(`:1746`)の `scrollTop` 代入が**最初のレイアウトを強制**する。

**確かめたこと / 確かめていないこと**

- 行の確定の差分(`row-swap.ts:432` `applyBlocks(this.host, html, this.view, [])`)は**ライブエディタ自身の host と view**に
  当たる。読む面の `bodyView`(`detail.ts`)とは別物 ── **共有していない**。(読んで確かめた)
- `BODY_PERSISTED` の ack が読む面を**もう一度**描き直す経路は無い。指紋が `body === this.lastBody` で止める
  (`detail.ts` の冒頭の注記にも同じ規律)。trace でも保存後の大きな task は 1 本だけ。
  ⚠ ただし**描画の呼び出し回数そのものは数えていない**(task の本数と指紋の読みからの推定)。
- 「開く」(別のノートを選ぶ)も `skeletonLid !== lid` で `fresh` になり、同じ経路(§4-2 以降)を通る。
  ただし**開く側は、比べる前の DOM が元から無い**ので、保存と同じ直し方では効かない(§5)。

## 5. 候補(3 + 1)

共通の条件: **見え方は 1 ドットも変えない**(CLAUDE.md「見え方を変える判断は user のもの」)。

### A. 読む面の DOM を編集のあいだ持ち越し、戻る時に差分を当てる ★推薦

**やること**: `renderEditor` で読む面の host を**捨てずに** `content-visibility: hidden` にして region に残す
(`contain-intrinsic-size` は 0 ── 場所を取らない)。`bodyView`・図の控え・借りた URL も手放さず、`{lid, 描いた本文, 描いた設定の鍵}` の札と
一緒に持つ。戻る時:

- 本文も設定の鍵も同じ(変更なしの保存・取消) → **ワーカーも呼ばず**、`content-visibility` を戻すだけ。
- 本文が変わった → ワーカーで描き、**持ち越した `bodyView` に対して `applyBlocks`**(既存の差分)。変わった塊だけ作り直す。
- 札が合わない(別のノート・設定の鍵が違う・外から本文が変わった・コンテナが変わった)→ 捨てて今までどおり作り直す。

**見込み(プロトタイプ無しの見積もり ── 測ったのは土台の挙動だけ)**

| 測ったこと(`ff20000` / `plain20000`、DOM を出した後の 3 回) | 値 |
|---|---|
| 読む面を `display:none` にして**戻す**までの時間(= 作り直しの配置コストに近い) | 517〜781 ms / 761〜832 ms |
| `content-visibility:hidden` にして**戻す**までの時間(配置の記憶が使われる) | 164〜259 ms / **51〜56 ms** |

- 変更なしの保存・取消: 1.0〜1.5 秒 → **0.1〜0.3 秒前後**(ワーカーの往復 0.4〜0.5 秒と、再接続の長い task 1.2〜1.5 秒も無くなる:
  同じ `<img>` を持ち越すので)。
- 変更ありの保存: ワーカーの往復は残る。主スレッドは変わった塊の分だけ。
- **開くには効かない**(比べる前の DOM が無い)。

**見え方**: 変わらない(同じ節点を戻す)。**変わるのは**: 編集中は読む面が見えない(今もそう)/ ページ内検索・読み上げは
持ち越した側に当たらない(`hidden` は検索・アクセシビリティの木から外れる ── 仕様上そう扱われるが、**この製品での確認は未実施**)。

**リスク**

1. 🔴 **常駐メモリ**。編集中は読む面の節点が**追加で**生き続ける。測れたのは節点の数だけ:

   | ノート | 読む面 | 編集中(ライブエディタ) | 持ち越すと追加される割合 |
   |---|---|---|---|
   | `ff20000` | 66,059 | 117,373 | +56% |
   | `plain20000` | 36,284 | 71,335 | +51% |

   ⚠ **RSS / ネイティブのメモリ**は §6「最初の 1 手の結果」で測った(2026-10-11、増分は ±数 MB)。以下はその前の記述。founding の「ゼロコピー・生成物の寿命の終端で即破棄」と、
   user の「継続使用の常駐メモリが効く」(2026-08-03)に照らして**いちばん重い項目**。持ち越すのは「編集している間」だけで、
   別のノートへ移る / 閉じる / 取り消さずに離れる で必ず捨てる ── 寿命の終端は「その編集が終わるまで」と書ける。
   それでも**増える**ので、§6 の最初の 1 手で実測してから判断する。
2. **ほかの検索が持ち越した側に当たる**。読む面の host を `querySelector('.pkc-md-rendered…')` で探す箇所
   (binder・smoke・ツールバー)が、編集中も DOM に残った host に当たりうる。数え上げが要る(未実施)。
3. **図の観測**(`mermaid-hydrate` の IntersectionObserver / 先読み)は `hidden` の間に動かさない作法が要る。
4. **スクロール位置**: `hidden` の host は高さが 0 になる(= 親の `scrollTop` が丸められる)。戻る時の位置戻し(`restoreScroll` /
   `captureReadAnchor` の仕組み)を通す ── 既にある部品を使う。
5. ブラウザ: `content-visibility` に未対応の環境では**今の経路に落とす**(安全側)。Firefox / Safari の挙動は**未測定**。

**要る test**

- unit(`apply-blocks` / `detail` の描画): 編集に入って変更なしで戻ると ① `markdown.render` が**呼ばれない** ② `bodyHost` と
  各塊の**節点の同一性が保たれる**(`===`)。1 行だけ変えて戻ると、**変わった塊だけ**節点が新しく、ほかは同一。
- **札の網羅(N 個の門は N 個目だけが鳴る場面を N 通り)**: 別のノート / 設定の鍵(`allowExternalImages` / `interactiveDates` /
  `colorSwatches` …)/ 外からの本文変更(`REMOTE_BODY_CHANGED` / `BODY_REWRITTEN`)/ コンテナの切り替え / 添付の本文 ── それぞれ**作り直しに落ちる**。
- 寿命: 別のノートへ移る・取消・閉じる で**持ち越しが捨てられる**(節点数が元へ戻る。借りた URL が返る)。
- smoke(実ブラウザ): 保存の前後で **`scrollHeight` と先頭 400 塊の高さの合計が等しい** / `scrollTop` が戻る /
  図の `<img>` が**同じ節点で、再焼きが起きない**(`createObjectURL` の回数が増えない)。
- 変異試験: 札の比較を 1 つ外す → 古い本文が出る、を 1 件ずつ殺せること。

### B. 描画を画面の近くだけにする(窓化。画面の外は高さの分かった空の器にする)

**やること**: 画面に近い塊だけ配置を作り、遠い塊は**実測済みの高さ**を持つ器にする
(`content-visibility:auto` + 塊ごとの `contain-intrinsic-block-size`。高さは前に描いたときの実測)。

**なぜ `content-visibility: auto` の素の試行は失敗したか(今回、現行 main で再実測)**:
塊の高さの見積もり(`auto 24px`)が実寸と合わず、**文書の高さそのものが変わる**。

| ノート(`.pkc-md-rendered > *` に `content-visibility:auto; contain-intrinsic-block-size:auto 24px` を当てた) | `scrollHeight` 通常 → 試行 | 最下端へ送った後 | 先頭 400 塊の高さの合計 |
|---|---|---|---|
| `ff20000` | 274,478 → **76,246**(−72%) | 80,487(まだ動く) | 49,424 → 14,414 |
| `plain20000` | 347,791 → **186,937**(−46%) | 188,876 | 22,600 → 11,420 |

- 1 回ずつ・load 6〜8 の中で測った。**時間は参考(保存 2,054 → 1,307 / 1,332 → 812 ms)**。高さは負荷に依らない。
- 実寸に近づければ高さの食い違いは減るが、**見積もりだけで完全には合わない**: 画面に入って初めて配置された塊の高さが、記憶した高さと
  1px でも違えば文書の高さが動き、送り位置が揺れる。また `content-visibility` を効かせている間は**布置が独立の箱になる**ので、
  塊の中の子の余白の相殺(`h2` の上の余白が前の塊の下の余白と相殺する、など)が**外と切れる**場合がある ── 画素が動く原因の候補
  (⚠ この点は本 doc では**画素で確かめていない**。この段の依頼文は、以前の試行で「画素も変わった」と報告している)。
- 塊の高さの記憶は**幅・字体・テーマ・画像の読み込み**で無効になる(窓の幅を変えただけで全部ずれる)。

**見込み**: 配置が画面近くだけになるので、20,000 行でも開く・保存・編集に入るが同じ桁で下がる(上の試行の保存: 2,054 → 1,307 / 1,332 → 812 ms。高負荷下の 1 回ずつ)。
**開く・編集に入るにも効く**のが A との違い。
**リスク**: 見え方(高さ・余白・送り位置)が動く ── 「見え方は変えない」に正面から当たる。行の確定は以前の試行で悪化した(今回は再測定していない)。
**要る test**: 全塊の高さ・余白を窓化の有無で突き合わせる差分ハーネス(`perf-measurement` §2 の型。被覆: 見出し・表・コード枠・引用・
リスト・数式・図・折りたたみ)、幅を変えた後の再測定、送り位置のずれの上限、画素の比較。

### C. 画面の近くを先に作り、残りを数コマに分けて足す(スライス)

**やること**: `replaceAll` を「画面の位置の前後の塊 → 残りを rAF / idle ごとに数十塊ずつ」に分ける。`readAnchor`
(`restoreScroll` の目印の仕組み)で、上に足された分の送り位置のずれを打ち消す。

**見込み**: 総量は減らない(むしろ微増)が、**1 本の long task が 903 / 3,004 ms → 数十 ms の列**になり、
画面に出るまで・入力を受けるまでが速くなる。**開く・保存・編集に入るの全部に効く**。
**見え方**: 最終の姿は同じ。**途中**はスクロールバーの長さが伸びる(今は一瞬で全長)。
**リスク**: 分けて足す間に本文が変わったとき(保存の直後に再保存)の整合/ 図の観測の順番/ 検索の塗り(`syncSearchJump`)が途中の DOM を見る。
**要る test**: 分割の途中で次の描画が来ても最後に正しい姿になる(世代)/ 送り位置が動かない/ 全塊が出揃った後は A/B なしの DOM と同一。

### D. 読む面とライブエディタの DOM を 1 つにする(参考。推薦しない)

編集の面の下絵(`previewOpts` の `sourceLineAnchors`)と読む面で、描画の HTML が違う(行番号の印・押せる印の有無)。
同じ DOM を両方に使うには描画の仕様を統合する必要があり、**1 PR の主題を超える**。A が効かなかったときの次の手として記録だけ残す。

## 6. 推薦と、覆る条件

## 10. 段 6: 戻す 0.3 秒の内訳と、買えた分(2026-10-11)

条件(覆る条件 2「戻すのが 20,000 行で 0.3 秒を超える」)の内訳を trace で取った。`n20000`(20,001 塊)・変更なしの保存・フル Chromium・箱が静かなとき。
「押してから 2 フレーム後の描画まで」は 435〜540 ms(§9 の 0.71〜0.79 秒は、箱が他の仕事と同居していた回の値)。

| 区間(click の task 約 330 ms + その後) | 値 | 内訳 |
|---|---|---|
| 編集の面を外す(`remove`) | 約 82 ms | 純粋な取り外し 約 35 ms + **焦点を持つ帯を外すときの強制配置 約 35〜45 ms** |
| 配置(`restoreScroll` の `getBoundingClientRect`)| 約 60〜80 ms | 20,000 個の子を持つ器の再配置(**器だけを出し入れしても** 67〜83 ms ── 下の床) |
| スタイル再計算 | 約 20 + 23 ms | 器を出した分と、段組みの見張りの採寸 |
| 本文のスキャン類 | 約 50 ms | `querySelectorAll` が 5 ms 前後 × 10 本、読了時間・タグの走査(いずれも本文の字を読む) |
| PrePaint / Paint / Commit / HitTest | 約 60 + 32 + 17 + 25 ms | 6 万個の layout 物体の最初の描画 |
| その後 5 フレーム | 1 フレーム約 47 ms | 先頭へ戻るボタンと進捗バーの `transition`。描画の後で、測った時間には半分しか入らない |

**床**: 読む面の器を `content-visibility` だけで隠し→戻す実験(ページ内で直に切り替え)で、配置 67〜83 ms・戻して描画まで 162〜237 ms。
つまり `n20000` で 0.3 秒に収めるには、床の 0.17〜0.24 秒 + 編集の面を外す 約 0.06 秒を、ほぼ全部ゼロにする必要がある。
床を下げるには塊ごとの `content-visibility:auto`(§5 で高さのずれで棄却済み)か、子の数を減らす(塊を束ねる)しか無い ── どちらも見え方・記法の扱いに触れる。

**入れた物**: 編集の面を外すとき、**焦点を持つ節点(押した保存ボタンの帯)を最後に外す**(`removeEditorFace`)。
焦点のある節点を外すとブラウザが先に配置を払うので、20,000 行の編集欄が居る間に払うと、その配置も丸ごと払われる(trace で `remove` の中に Layout 35 ms)。
重い物を先に外すと、この強制配置は消える(`remove` 82 → 59 ms)。ただし後の配置がその分を引き取るので、正味の効きは小さい。

| 測定(押してから描画まで、中央値(範囲)、n) | main | 段 6 |
|---|---|---|
| `n20000` 変更なしの保存(箱が静か〜load 1 前後) | 472 ms (439〜655) n=6 | 448 ms (408〜542) n=6 |
| `ff20000` 変更なしの保存(load 1.5 以下の回のみ) | 333 ms (303〜650) n=5 | 284 ms (260〜342) n=4 |

⚠ 範囲が重なる ── 向きは一貫して「速い」だが、1 回ごとの揺れ(±100 ms)より効きが小さい。**効いたと言い切れるのは `remove` 内の強制配置が trace から消えたこと**まで。

**試して捨てた物(測った)**
- 編集の面を `display:none` にして次のフレームの後に外す: 戻しが **遅くなった**(A 764 / 681 ms vs 542 / 507)。`display:none` で 20,000 行の layout 物体を捨てる再計算が 128 ms かかり、外すより高い。
- 編集の面を `HELD_STYLE`(`content-visibility:hidden`)にして後で外す: さらに遅い(979 / 772 ms)。
- `transition` を切る(先頭へ戻るボタン・進捗バー): 後ろの 5 フレームの 47 ms ずつは消えるが、押してから描画までは変わらない(509 vs 472 ms、揺れの内)。見え方が変わるので入れない。
- 読了時間・タグ・見出しの走査の直前の答えの memo: 買えるのは 1 描き直し 20〜45 ms だが、`reading-time.ts` の注釈が「別のノートへ移っても前の本文を握り続ける」ので置かないと決めている(2026-10-10)。それを覆す根拠が無いので入れない。

**結論**: `ff20000`・`plain20000`(5,000 塊)は 0.3 秒前後。`n20000`(20,001 塊)は 0.45 秒前後で、0.3 秒には届かない。届かせるには床を下げる変更(塊を束ねる / 塊ごとの `content-visibility`)が要り、user の判断(見え方・段組みの扱い)。

## 11. 編集の面にも「画面の外を配置しない」を付ける(依頼 28 = B を測り直して覆す。2026-10-25)

**何を変えたか**: 5,000 行を超えるノートだけ、ライブエディタ(`editor-live`)の直下の塊にも `data-pkc-long-note`(= `content-visibility:auto` +
