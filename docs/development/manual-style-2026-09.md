# マニュアル執筆規約(user レポート #779 §6 を 2026-11-23 に改定)

> **なぜ要るか(user の言葉)** ── 「**構造を直しても、書き方が変わらなければ 3 日で
> 2 万字ずつ元に戻る。**」

⚠ **正本は `docs/manual.md` 1 本**である(`src/adapter/ui/render/help.ts` が `?raw` で
焼き込む)。この doc は**その書き方**を決めるだけで、**残件は持たない**
(burn-down は issue に在る)。

🔑 **マニュアルは「いまの画面の使い方」だけを書く**。更新の履歴はお知らせ
(`src/features/notice/notice-log.ts`)と `CHANGELOG.md` に在り、開発者向けの仕組みは
`docs/development/` に在る。マニュアルは「利用者が手を動かすために読むもの」に絞る。

## 節の型

```
### 〈名詞か標準の操作名で言い切る見出し〉

> 一行で:  この節で何ができるか(1 文)

**手順**
1. …

**つまずきやすい点**      ← 無ければ枠ごと省く

関連: 〈節〉 / 早見表: 〈表〉
```

🔑 **型が効く理由は 2 つ**:

1. **足す場所が一意に決まる** ──「一行で」が書けるなら既存節の改稿。書けないなら新設。
   判定が機械的になるので、**足す場所に迷って末尾へ積む動機が消える**
2. **読み飛ばせる** ── 全節が同じ順序なら、2 節目からは「手順だけ見る」ができる

⚠ **節の長さに字数の上限は無い**(旧 条 9 は廃止した。下の「廃止した条」)。長さは
「1 つの話題が 1 つの節に収まっているか」で決め、全体の規模は全体の上限(下)で抑える。

## 規約(2026-11-23 改定)

### 見出し

1. **見出しに日付を入れない。** 悪い「数式(2026-09-06 に足しました)」/ 良い「数式を書く」。
   ⚠ 日付は 1 か月で意味を失い、見出しだけが長く残る
2. **節番号を振らない。** ⚠ 前に挿入したくなったとき `4-0b` が生まれる。順序は目次が示す
3. **見出しは簡潔な名詞か、標準の操作名で書く。** 良い「ノートを作成する」「表」「SQL 画面」。
   - 長さは **20 字以内を目標、30 字を超えない**(機械の上限は 30 字)
   - **読点「、」を入れない**(2 つ言いたいなら節を割るか、片方を本文へ送る)
   - **終わりに置かない言い方**: 「〜を知る」「〜を確かめる」と、「〜のとき」「〜たとき」で終わる断片
     (「困ったとき」も名詞に言い換える。末尾のかっこの補足は外して判定するので、補足で逃げられない)
   - ⚠ かっこの補足(「ノートを作成する(Ctrl + N)」)も字数に数える ── 補足は本文の先頭へ
4. ~~「そのほか」という見出しを作らない~~ ── **廃止した**(下の「廃止した条」)
5. **見出しは H4 まで**(章 H2 / 節 H3 / 小節 H4)。H5 は使わない。
   **H1〜H4 が全部在ることは求めない**(章立てを組み替えた結果 H4 が無くなっても違反ではない)
6. **同じ名前の見出しを 2 つ作らない。** ⚠ 検索で引いたとき区別できない

### 本文

7. **新機能は「追記」ではなく「該当節の改稿」。** 型の「一行で」が書けるなら既存節に収める。
   書けないときだけ節を新設し、**章の流れ順に挿入する。末尾に足さない**
8. **ガイドに一覧を書かない。早見表に説明を書かない。**
9. **記号は 🔴 ⚠ 🔑 の 3 種のみ。** ⚠ は「失う・取り消せない」文にだけ付ける。表の升の印はデータなので数えない
10. **独自の語は用語集に登録してから使う**(`src/features/ui-terms.ts` の `STANDARD_TERMS` /
    `BANNED_TERMS` と、マニュアルの「言葉の意味」が正本)。造語を本文で言い換えない
11. **本文に日付の印を入れない。** `(2026-11-22)` `(2026 年 9 月に追加)` のような括弧つきの日付と、
    括弧なしの「2026-08-28 に変えました」「2026-09-04 まで」のような**日付 + 経緯の助詞・語**は書かない。
    いつ変わったかは、お知らせと `CHANGELOG.md` が持つ
12. **経緯を書かない。** 「以前は」「従来」「旧バージョン」「かつて」「〜になりました」のような、
    変わる前を知っている人にしか通じない書き方はしない。**いまどうなっているか**だけを書く
13. **いまの画面の位置で書く。** 画面下のバー(ステータスバー・状態バー)は廃止した。
    「画面の下に」「ステータスバー」「状態バー」とは書かず、いまの位置
    (左のバーの「メッセージ」ボタン・浮き札・左ペインのタブ など)で書く
    (「画面の下に常設のバーはありません」のような打ち消しは対象外。「上のタブ」は左ペイン・スマホの
    タブの正しい呼び名なので対象外)
14. **利用者に要らない開発者向けの仕組みは削除する**(付録へ移さない)。実装の経緯・内部の構造・
    設計判断は `docs/development/` に書く。マニュアルから消すだけで、移す先は用意しない

### 画面に出る字の逐語の引用は対象外

条 11・12・13 の検査は、**画面に出る字をそのまま引いた所**を見ない。画面の字は実装が決めるもので、
マニュアルが書き換えてよいものではないため(例: 画面が「n 件をゴミ箱へ移しました」と出すなら、そう引く)。
対象外にするのは次の 4 つ:

- 鉤括弧「…」/『…』の中
- インラインコード `…` の中
- **太字の画面の字**(「。」を含まない太字。1 文ぜんぶを太字にしたものは引用と見なさない)
- 機能の名前(「旧版 PKC の zip を取り込む」の「旧版」は経緯語ではないので、語の一覧に入れない)

⚠ 引用の外に書いた位置の案内(「画面の下に **「…」** と出ます」)は、引用の中身ではないので数える。

### 全体の規模

- **目標: 2,000〜2,800 行 / H3 は約 100 個。**
- **機械の上限(最終): 3,500 行 / H3 150 個。**
- 目標は「読み切れる量」の目安で、上限は暴走を止める門である。上限を超える足し方をするときは、
  先に既存の節を削る・畳む。

| 旧 条 9 | 1 節 = 600〜800 字・「覚えること」は 4 個まで | 字数に合わせて節を割ったせいで、**1 つの話題が小さな節に砕け**、見出しが増えて全体が膨らんだ(H3 が 680 個)。長さではなく話題の単位で切る |

## 門の形(移行期は終わった)

マニュアルの書き直し(2026-11-24)で、違反は 0 件になった。いまの門は次の 2 種類:

- **違反の件数**(長い見出し・読点の見出し・禁止の語尾・日付の印・古い位置の言い方・経緯の言い回し)は
  `tests/manual-style.test.ts` の `BASELINE`(= 0 件)と**等値**で見る。1 件でも出たら落ちる
- **規模**(行数・H3 の数)は `FINAL` の上限(3,500 行 / 150 個)**以下**で見る。`BASELINE` の行数・H3 は実測の記録
- 検査の関数は `tests/helpers/manual-style.ts` の**純粋関数**で、自前の原稿(31 字の見出し・
  「、」入りの見出し・囲みの中の違反)にも当てて**効いていること**を見る
- 囲みは ``` と ~~~ を、開きと同じ字・開き以上の長さで閉じるものとして読む(4 つの ```` の中の ``` は閉じではない。
  リストの字下げの中の囲みも囲み)。⚠ 見出しは **ATX 形式(`# 題`)だけ**を数える
- ⚠ 見出しを探す test は、見出しの**正確な字**に頼らない(題名にキーワードを含む節を段を問わず探す /
  本文の 1 文から節を探す)。章立てを組み替えても、守る中身は同じまま通る
