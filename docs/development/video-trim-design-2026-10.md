# 画面収録の前後を削る(#683 段②b)── 設計

> 裁定の出どころ:#1163 のコメント(Gemini による裁定。user の委任に基づく。2026-10-10〜11)。
> 本 doc は**設計と測定だけ**(doc-first)。製品コードは 1 行も書いていない。
> 音の切り出し(段②a)の設計は `audio-trim-design-2026-09.md`、実装は `src/features/audio/webm-opus.ts`。

## 0. 要約(3 行)

1. 画面収録(webm = VP8 の映像 + opus の音)も、音と同じ「**ここから / ここまで → この範囲で切り出す**」で、**新しい添付が 1 つ増え、元は残る**。
2. 映像は「前の完全な絵(キーフレーム)」からしか復号できないので、**始まりの数秒だけ**を作り直し(WebCodecs)、その先は**元のバイトをそのまま繋ぐ**。WebCodecs が無いブラウザは、**一番近い手前のキーフレームから**切る(始まりが少し早くなると伝える)。
3. これから録る物は、**キーフレームの間隔を 2 秒に詰めて**録る(測定: 既定は約 4.4 秒、詰めると 2.0 秒。ファイルは +17%、ただしこの試料は映像が毎フレーム全面変化するため過大 → §9)。

## 1. 画面で何が起きるか(user の言葉で)

録った画面収録を一覧(音/動画の面)で再生する。ここまでは今も同じ。

1. 見ながら **「ここを始まりにする」「ここを終わりにする」**(裁定文では「ここから」「ここまで」と略されている物。**製品の字は今の音のボタンのまま**。§12 Q1)を押す。押した所に時刻が出る。
2. **「この範囲で切り出す」** を押す → 新しい添付が 1 つ増える(元はそのまま)。押している間は「この範囲を切り出しています…」でボタンは押せない(音と同じ)。
3. 終わると、一覧に新しい動画が 1 行増え、そのまま再生できる。

### 1.1 ブラウザによって違う所(押せるのに壊れている、を作らない)

| 状況 | 画面 |
|---|---|
| 始まりを**細かく**切れる(WebCodecs の VP8 が使える) | 何も増えない。音と同じ。始まりは押した所ぴったり |
| 細かく切れない(WebCodecs が無い / VP8 が使えない) | 「この範囲で切り出す」を押すと確認が出る:<br>**「お使いのブラウザでは先頭を細かく切れません。一番近い区切りから切り出します」 [切り出す] [やめる]**(裁定の文言)<br>[切り出す] = 手前の区切りから始めて切り出す(始まりが押した所より**早く**なる)/ [やめる] = 何も作らない |
| 録画の形が切れない(webm 以外、VP8 以外、など) | ボタンを**出さず**、理由を 1 行その場に書く(音と同じ流儀。`trimUnavailableText`) |

- 確認の字に**早くなる長さ**を足す案(「始まりが約 3 秒早くなります」)を出す。キーフレームの位置は走査で分かるので、押す前に言える(§12 Q2。裁定の字は変えない前提で、追記の提案)。
- 「区切り」= キーフレーム。画面の字にはカタカナを出さない(裁定の字のまま)。
- 🔑 確認は**この 1 回だけ**。やめたら何も起きない(元も、新しい添付も増えない)。

## 2. 容器と符号化の事実(実測 = この箱の Chromium 141)

測定は §9 の probe。録った物は `MediaRecorder` の**既定設定**(`new MediaRecorder(stream)` ── 現行の `media-capture.ts` と同じ)で、canvas 640×360 + 音(WebAudio の 440Hz)を 20 秒。

### 2.1 Chrome の webm の中身(実測)

| 項目 | 実測 | 設計への効き方 |
|---|---|---|
| mime | `video/webm;codecs=vp8,opus` | 既定が VP8。VP9 は `isTypeSupported` で true だが**既定ではない** |
| 既定のビットレート | 映像 2,500,000 bps / 音 128,000 bps | 250MB の 1 本 ≒ 約 13 分(12 時間は約 57 本に割れる)。**切り出しは 1 本の中だけ**(§12 Q3) |
| `Segment` / `Cluster` の大きさ | 全部**不明**(8 バイトの全 1) | 容器の大きさでは飛べない。**ブロックを頭から順に読み進める**(音と同じ作り)。`Cluster` は約 1 秒(24 個/20 秒) |
| `SeekHead` / `Cues` / `Duration` | **全部無い** | 作り直す索引が無い。出力にも `Cues` は付けない(元と同じ形)。`Duration` は書く(§4.5) |
| 音のブロック | `SimpleBlock`(`0xa3`)、フラグ `0x80`(全部キー扱い) | 現行の音の切り出しがそのまま読める |
| 🔴 **映像のブロック** | **`BlockGroup`(`0xa0`)の中の `Block`(`0xa1`)**。フラグは常に `0x00`。**差分フレームにだけ `ReferenceBlock`(`0xfb`)が付く** | 🔴 **キーフレーム = `ReferenceBlock` を持たない `BlockGroup`**。`SimpleBlock` のキーフラグでは**見つからない**(実測: 映像 464 個 / `ReferenceBlock` 459 個 / キー 5 個) |

🔴 これは**事前の想定と違った**(「`SimpleBlock` のキーフラグを読む」と考えていた)。ffmpeg や Firefox の書く webm は `SimpleBlock` + キーフラグ `0x80` で書くことが多い(**未測**)ので、読み取りは**3 つの印を全部**見て、食い違えば**フレーム本体の印**を正とする:

1. `SimpleBlock` のキーフラグ(bit 0x80)
2. `BlockGroup` に `ReferenceBlock` が**無い**
3. 🔑 **VP8 のフレーム先頭 3 バイトの `frame tag` の bit 0 = 0 が「キーフレーム」**(RFC 6386 §9.1)。実測で **②と一致**(キー 5 個の時刻が同じ)

### 2.2 キーフレームの間隔(実測)

20 秒の既定録画で、VP8 のフレーム印から数えたキーフレームの時刻:

```
既定:                         0.01  4.49  8.63 12.94 17.56   → 間隔 4.48 / 4.14 / 4.32 / 4.62 秒(平均 約 4.4 秒)
videoKeyFrameIntervalDuration=2000: 0.01 2.02 4.04 6.05 8.07 10.08 12.09 14.11 16.11 18.14 → 間隔 2.00〜2.02 秒
videoKeyFrameIntervalCount=60:      0.01 2.65 5.26 7.65 9.85 12.46 15.06 17.38 19.68       → 間隔 2.2〜2.64 秒(60 フレーム。実効 約 24fps)
```

- 🔑 **既定の間隔は約 4.4 秒 = 2 分の画面収録で約 27 個のキーフレーム**。裁定の「前の区切りまで戻る」は、最悪 **約 4〜5 秒早くなる**。
- 録画側のキーフレーム間隔の指定は、この Chromium では**効く**(次節)。
- ⚠ **画面の中身が静かな録画では間隔が伸びうる**(エンコーダの設定次第。**未測**)。走査で実際の間隔を測って使う(想定しない)。

### 2.3 `MediaRecorder` の指定の可否(実測 + 未確認)

- `new MediaRecorder(stream, { videoKeyFrameIntervalDuration: 2000 })` と `{ videoKeyFrameIntervalCount: 60 }` は、**この Chromium 141 では両方とも読み取られ**(options の getter で確認)、上の表のとおりキーフレーム間隔が変わった。
- 仕様の出どころ:W3C **MediaStream Recording** の `MediaRecorderOptions` の 2 メンバ(`videoKeyFrameIntervalDuration`(ミリ秒)/ `videoKeyFrameIntervalCount`(フレーム数))。⚠ **この箱は外部の仕様 URL に届かない**(egress 制限 403)ため、**仕様の該当節の確認は未了**。Firefox / Safari の対応も**未確認**。
- 🔑 指定しても**非対応のブラウザは無視するだけ**(辞書のメンバは未知なら読まれない)。**失敗しない**ので、「対応を検出して出し分ける」必要は無い。ただし**効いたかどうか**は録り終えてから走査で分かるだけ(§8 段 ②b-3)。
- どちらを使うか:🟢 **`Duration`(ミリ秒)**を推す。理由 = フレーム数指定は**実際の fps が落ちると間隔が伸びる**(実測: 24fps で 2.2〜2.6 秒)。時間指定は 2.00〜2.02 秒に収まった。

## 3. キーフレームの話(なぜ「始まりだけ作り直す」のか)

VP8 のフレームは 2 種類。**キーフレーム**=単独で完結した 1 枚。**差分フレーム**=前のフレームとの差(単独では絵にならない)。

```
時刻 →   K0 d d d d d d d d  K1 d d d d d d d d  K2 ...
                     ↑ 切りたい所(cut)
```

- cut を含む塊(K0 から K1 の手前まで)の差分フレームは、**K0 から順に復号しないと絵にならない**。
- 単純に K1 から始めると、**始まりが cut より最大で 1 塊ぶん遅くなる**(= 押した所より先が切れてしまう)。K0 から始めると**早くなる**。どちらも「ぴったり」ではない。
- 🔑 だから裁定は 2 通り:
  - 細かく切れる:cut〜K1 の手前だけを**新しいキーフレームから作り直す**(=始まりぴったり)。K1 以降は元のまま。
  - 切れない:K0 から始める(始まりが早い)。

### 3.1 何を作り直し、何をそのまま繋ぐか

```
元:       [K0 d d d d d d d d][K1 d d d d d d d ...... d d d d][K9 d d d]
切り出し:        ↑cut                                  ↑end
新:   [N d d d ][K1 d d d d d d d ............. d d d d]         N = cut の絵を新しいキーフレームにしたもの
        └ 作り直し(復号 → 符号化)┘└─ 元のバイトをそのまま繋ぐ ─┘
```

- 🔑 **終わり(end)は作り直さない**:end の手前のフレームは、**同じ塊の中で順に並んでいる**だけなので、end の位置で**やめる**だけでよい(end より後ろの差分フレームは要らない)。終わりは**フレーム単位でぴったり**。
- cut と end が**同じ塊の中**(K1 より前に end がある):cut〜end だけを作り直す。
- cut が**ちょうどキーフレーム**:作り直しは**不要**(全部そのまま繋ぐ)。
- cut の後ろに K1 が**無い**(最後の塊):cut〜end を作り直す。

## 4. アルゴリズム

入力 = 元の `Blob`(1 本 最大 250MB)・`startMs`・`endMs`(再生機の `currentTime` ── 鳴らしたときの時刻。音と同じく**頭に札(`CodecDelay`)が付いた物をもう一度切る**ときの補正を使う)。

### 4.1 走査(1 回、頭から)

`Blob.slice` を **8MB 程度の窓**で順に読み、ブロックのヘッダだけを追う(**中身の bytes は覚えない**):

- `Segment` → `Info`(`TimestampScale`)→ `Tracks`(映像: `V_VP8`・`PixelWidth` / `PixelHeight`・`TrackNumber` / 音: `A_OPUS` は段②a の読み取りを流用)→ `Cluster` の列。
- `Cluster` の大きさが**不明**でも読める(中に降りるだけ。次の `Cluster` の id で終わりと分かる ── 音の読み取りがもう同じ作り)。
- 各ブロックについて**(トラック番号, 時刻ms, ファイル内の位置, 大きさ, キーフレームか)**だけを**配列**に残す。1 本 250MB でもブロックは約 3 万個、1 個 約 40 バイト = **約 1.2MB**。🔑 **bytes は持たず、索引だけ持つ**。
- 🔑 end の後ろの `Cluster` に入ったら**走査をやめる**(終わりを過ぎた所は読まない)。
- キーフレーム判定は §2.1 の 3 つの印。食い違う場合は VP8 の `frame tag`(ブロックの先頭 3 バイトだけ読む)を正とする。
- ⚠ 走査は**読むだけ**で、250MB なら IO は最大でも 250MB。ブロックのヘッダだけを小さい `slice` で刻んで読めば削れるが、`Blob.slice` の往復が増えるので**まず窓読みで測る**(§9)。

### 4.2 切る位置を決める

- 映像の `K0` = cut 以下で**最も近いキーフレーム**、`K1` = cut より後ろで**最初のキーフレーム**(end 以下に限る)。
- `end` = end 以下の**最後の映像フレーム**まで(その次のフレームの時刻が終わりの時刻)。
- 🔴 **映像の差分フレームが 1 つでも K0 から欠けたら、その先は絵が壊れる** → K0 から end まで**連続**して残す(途中を抜かない)。
- 🔴 VP8 の `show_frame = 0`(表示しない参照フレーム。`frame tag` の bit 4)が混ざる場合がある。復号器は出力を出さない。**そのフレームの時刻の扱い(次のフレームと同じ時刻になる)を見て**索引に載せる(**未測**。実測した録画では 0 個)。

### 4.3 作り直す部分(始まり〜K1 の手前)

細かく切れる経路:

1. `VideoDecoder`(`codec: 'vp8'`)を `configure` し、**K0 から順に**フレームを `decode` する。
2. 出てきた `VideoFrame` のうち、**時刻が cut より前**の物は**すぐ `close()`**(溜めない)。
3. **cut 以降 K1 の手前**の物は `VideoEncoder`(`codec: 'vp8'`、`width/height` は元の `PixelWidth/Height`、`bitrate` = 元の映像のその区間の実効値、`framerate` = 元の平均)へ渡す。**1 枚目だけ `keyFrame: true`**。渡したら `close()`。
4. 🔑 **背圧**:`encodeQueueSize` / `decodeQueueSize` が 8 を超えたら待つ。同時に生きている `VideoFrame` は**10 枚前後**で一定(1080p なら約 30MB、4K でも約 120MB)。**GOP 全体を貯めない**。
5. 符号化の出力(`EncodedVideoChunk`)から**バイトを取り出して**新しい `Cluster` に詰める(新しい 1 枚目がキー、残りが差分。`ReferenceBlock` は**付けない/付ける**を元の流儀に合わせる ── 元が `BlockGroup` 型なら同じ型で書く。§4.5)。
6. 🔴 **コーデックの条件を揃える**:VP8 には「別の設定を持つ入れ物」(`CodecPrivate`)が無い。揃えるのは**解像度**(元と同じ。違うと `TrackEntry` の値と食い違う)と**色空間**(`VideoFrame` が引き継ぐ)。**fps の揃え**はフレームの時刻を**元の時刻のまま**渡して、符号化器に任せない。
7. 🔑 K1 から先は**元のバイト**なので、作り直した最後のフレームから K1 へは**参照が繋がらない**(K1 はキーフレームで、前を参照しない)。= 継ぎ目で画が壊れない。
8. 画質:作り直した塊だけ 2 世代目の符号化になる。**目に見える差が出るかは未測**。ビットレートを元の実効値より**少し高め**(+20%)に置く案を、測定の上で決める(§9)。

細かく切れない経路(フォールバック): 4.3 を飛ばし、**K0 から end まで全部そのまま繋ぐ**。始まりは K0 の時刻になる。

### 4.4 音のそろえ

映像の始まりを `T0`(細かい経路 = cut、フォールバック = K0 の時刻)とする。

- 音は**現行の `trimWebmOpus` の考え方**で `T0` から `end` まで(前置き 80ms・`CodecDelay` で頭を捨てる・最後の block だけ `BlockGroup` + `DiscardPadding`)。
- 🔴 **映像と音を同じ物差しで 0 起点に直す**:出力の映像の最初のフレームが 0、音は `T0` を 0 とする。音の packet は 60ms 刻みなので、`T0` の手前から始まる packet が 0 より**前**に来る(最大 約 140ms)。
  - 🔴 **ここは未測の最大の不確かさ**:`CodecDelay` による頭の捨てを、**映像付きの `<video>`** が音の時刻のずらしとして**どう解釈するか**(Chrome が音を `CodecDelay` ぶんだけ遅らせる/捨てるだけか)。音だけの `<audio>` では段②a で `duration` が合うことを確認済みだが、**映像との同期は別問題**。
  - 計画:②b-1 で**自作の録画**(映像が一定間隔で点滅し、音が同時にビープ)を切り、**点滅とビープのずれ**を `<video>` の再生と `AudioContext` の解析で測る。許容 = 音が映像より **遅れる側に 125ms 以内 / 進む側に 45ms 以内**(放送の同期許容 ITU-R BT.1359)。
  - 外れたら:`CodecDelay` を使わず、**音の最初の packet を T0 以降の最初の境目**に取る(音は最大 60ms 遅れる = 許容内)。この案は**測定の結果で選ぶ**。

### 4.5 書き出し(新しい webm)

```
EBML ヘッダ(DocType webm)
Segment(大きさ 既知)
  Info      TimestampScale=1000000 / MuxingApp,WritingApp='pkc3' / Duration=<ms>
  Tracks    映像 TrackEntry(元のバイトを写す。TrackUID だけ新規でも可)/ 音 TrackEntry(段②a の作り + CodecDelay)
  Cluster…  作り直した頭の Cluster(メモリ上、数秒ぶん)
  Cluster…  ④ 元の Cluster のうち 丸ごと範囲内の物:ヘッダ(id + 大きさ + 新しい Timecode)だけ新規、中身は元の bytes
  Cluster   K1 を含む Cluster / end を含む Cluster:範囲外のブロックを落として組み直す(1 秒ぶん)
```

- 🔑 **④が肝**:`Cluster` の中のブロックの時刻は **`Cluster` の `Timecode` からの相対**なので、**時刻を 0 起点に直すには `Timecode` 1 つを書き換えるだけ**で、中の bytes は触らない。**元の `Blob.slice(...)` をそのまま部品にして新しい `Blob` を作る** = ゼロコピー(250MB を読んで書き直さない)。
  - 元の `Cluster` は大きさが**不明**なので、新しいヘッダも不明(8 バイトの全 1)で出し、次の `Cluster` の id が終わりを示す ── 元と同じ形。
  - 🔴 組み直す 2 つの `Cluster`(K1 を含む物と end を含む物)は、中のブロックを**ブロック単位で拾い**、新しい `Cluster` に並べ直す。この 2 つは bytes を一時的にメモリに載せる(各 約 1 秒 = 約 330KB)。
- 結果は `Blob`(部品の列)として**ワーカーから返す**。🔑 `Blob` は参照として渡る(構造化複製)ので、**250MB を ArrayBuffer にして transfer する必要が無い**。音の切り出しは結果を `ArrayBuffer` で返していたが、映像は大きいので `Blob` で返す。
  - ⚠ この `Blob` が**元の `Blob` の部品を指している**間は、元が生きている必要がある。保存先(添付の store)へ書き終えたら参照は要らない。→ 添付にする口(`asset-store`)が `Blob` をそのまま受けられるかを確かめる(**未確認** ── §12 Q5)。
- `Duration` は**自分で計算して直接書く**(出力の長さが分かっているので `withRecordedDuration` の壁時計は要らない)。= 開くと `duration` が `Infinity` にならず、終わりへ飛べる(2026-10-10 に録画で確認した性質を、切り出し結果にも持たせる)。

### 4.6 メモリの計画(250MB の 1 本)

| 何 | 量 | 方針 |
|---|---|---|
| 元のバイト | 250MB | 🔴 **一度に持たない**。`Blob.slice(…).arrayBuffer()` を 8MB の窓で読み、ヘッダを見たら捨てる |
| 索引 | 約 1.2MB(約 3 万ブロック) | 持つ |
| 復号された `VideoFrame` | 同時 約 10 枚(1080p で 約 30MB) | 背圧で上限を固定 |
| 作り直した出力 | 数秒ぶん(数百 KB〜数 MB) | メモリ |
| 出力の本体 | 元の `Blob` の部品 | **参照だけ**(コピーしない) |
| ピーク | **約 50〜150MB**(主に `VideoFrame`) | 250MB を `arrayBuffer()` で丸ごと読む音の作り(`trimAudio`)は**映像には使わない** |

⚠ 現行の `trimAudio` は `await job.blob.arrayBuffer()` で**全部を読む**。音の 1 本は小さいので問題にならなかったが、**映像で同じことをすると 250MB がヒープに載る**(不可侵: ゼロコピー)。**映像の切り出しは別の入口(別のジョブ型)にする**。

### 4.7 ワーカー

- 既存の `WorkerLease`(`src/adapter/platform/worker-lease.ts`)を使う。**遅延起動・起動待ちの間のジョブの保持・アイドルでの kill・飛んでいるジョブがある間は kill しない・kill 時に待っている依頼を reject** は機構が持つ(音の `AudioClient` と同じ)。
- 🔑 `VideoDecoder` / `VideoEncoder` は**ワーカーの中で使える**(段②b-2 で実測 ── 両ブラウザで通った。§9.1b)。使えなければ、**作り直しの部分だけ**メインスレッドへ出す(段②b-2 の実装。復号と符号化はブラウザが別スレッドで動かすので、メインが握るのは受け渡しだけ)。どちらでも使えなければフォールバックに落とす。
- ジョブ型を `trim-audio` と `trim-video` に分けるか、ワーカーを別にするか:**ワーカーは分ける**(音のワーカーを映像の長い仕事で塞ぐと、音の切り出しが待たされる)。`AudioClient` にならって `VideoClient` を置き、`AUDIO_WORKER_IDLE_MS` と同じ idle を使う(切り出しは続けて押される)。
- 進み具合:走査と作り直しは数秒かかる。**ボタンの字は音と同じ「この範囲を切り出しています…」**(進捗の数字は出さない ── 出すなら後の段)。

## 6. 録画側のキーフレーム間隔(段②b-3)

### 6.1 変更

`media-capture.ts` の `new Recorder(stream)`(`startCapture`)を、**画面収録(`kind: 'screen'`)のときだけ**:

```ts
new Recorder(stream, { videoKeyFrameIntervalDuration: 2000 })
```

とする(2 か所:初回と、250MB で切って次を始めるときの器)。音の録音には映像が無いので渡さない。

### 6.2 効いたかを確かめる

- 単体テストでは `Recorder` の fake に**渡された options を記録**させ、`2000` が渡っていることを見る。
- 実ブラウザ smoke では**録った webm を走査**してキーフレーム間隔を出し、**2.2 秒以下**を assert する(この Chromium での実測 2.00〜2.02 秒)。非対応のブラウザでは間隔が変わらない → その場合は assert でなく**診断で出す**(「効かない環境がある」と分かることが目的)。

### 6.3 ファイルの大きさへの効き

| | 映像のバイト(20 秒) | 全体 |
|---|---|---|
| 既定(約 4.4 秒間隔) | 973,319 | 1,326,434 |
| `Duration` 2000(2.0 秒間隔)| 1,195,239 | 1,557,105(**+17%**) |
| `Count` 60 | 1,053,445 | 1,410,133(+6%、ただし録れたフレーム数が違う: 497 対 464) |

🔴 **この数字は過大にも過小にもなる**:試料は画面全体が毎フレーム変わる合成の絵で、キーフレーム(約 1.8KB)が差分(約 2.1KB)より**小さい**という、実際の画面収録とは逆の性質。実際の画面収録は差分が小さく、**キーフレームの割合が増えるぶんは相対的に大きく効く**(キーフレームは差分の数十倍になりうる)。+17% の方向は変わらないが、**倍率は実画面で測り直すまで言えない**(§9)。

- 🔑 検算 = 動画の 250MB の分割(`partBytes`)が速く来る → 1 本の長さが短くなる(約 13 分 → 約 11 分の見込み。**未測**)。
- 帯の件数・本数の表示は実測の bytes を出すので、数字の整合は取れる。

### 6.4 既存の録画は書き換えない

不可逆なので触らない(`media-capture.ts` 冒頭の注記と同じ)。**既存の録画の切り出しは、間隔が約 4.4 秒のまま**(フォールバック時 最大 約 4〜5 秒早くなる)。お知らせ(`notice-log.ts`)には「これから録る画面収録は、細かく切り出しやすくなります(ファイルは少し大きくなります)」と書く(段②b-3)。

### 9.1c 段②b の実測(2026-10-11、#683。1080p / 4K・音と映像のずれ・ビットレートの式)

**どの版で測ったか**: Chromium 141(`/opt/pw-browsers/chromium` = フル版、headless、4 コア。測る前の負荷平均 0.3。⚠ `chromium_headless_shell` では測っていない)/ 製品の `cutVideo`・`scanVideo` を **本物の `Worker` の中**で回した(`vite build` の lib で `video-codec.ts` を 1 枚の IIFE にして Worker へ渡す。製品の `video-worker.ts` ではなく同じ中身を呼ぶ測定用の殻)/ 土台は `bec02c2d`。

**やり方**: 各設定を 3 回(rep ごとに並び順を回して交互に)。中央値(最小〜最大)。⚠ 合成の絵(細かい静止画を横へパンさせる = 動き補償が効く内容)なので、実画面の録画の代表ではない(§10.3)。

⚠ **元の動画の作り方が 2 つある**:
- `30fps` の元 = `VideoEncoder`(VP8)で作って自前で `webm`(`SimpleBlock`、音なし)に包む。キーフレームは 4 秒ごと(0 / 4 / 8 秒)。切る範囲は 4.3 秒〜11 秒 = 頭は **112 枚**(復号は 4 秒の手前のキーフレームから 120 枚)。
- `mr` の元 = `MediaRecorder` が実時間で録った物(音つき・実機と同じ容器)。⚠ **この箱の `MediaRecorder` は 1080p を 4〜18fps、4K を約 5fps でしか録れなかった**(software の符号化。n=1〜2)。30fps の 1080p / 4K が要るので、時間・メモリの測定は上の自作の元で行い、`MediaRecorder` は 360p(30fps が出る)で音と映像のずれ専用に使った。

#### 1. 作り直し(押した所ぴったり)の時間・メモリ(3 回ずつ。頭 112 枚)

| 項目 | 1080p(30fps、元 3.9Mbps) | 4K(30fps、元 15.4Mbps) |

| 判定 | 🟢 閉じ漏れ無し | 🟢 閉じ漏れ無し。⚠ 1 枚 12MB 級のフレームが 11 枚 + 符号化器の内部で RSS は +670MB まで上がる |

- 🔴 **同時に生きる `VideoFrame` は 11**(設計の上限は `MAX_LIVE_FRAMES = 10`)。`decodeQueueSize` を見る門は「復号器の中で処理中の 1 枚」を数えないため、上限は **10 + 復号器の中の 1 枚**になる。閉じ漏れではない(終わった後は 0)。コードの注釈の「10 枚前後」は正しく、「10 枚までに抑えてある」と書いた §9.2b は誤りだった(直した)。コードは変えない(1 枚の差で 4K でも +12MB)。
- 🔴 **所要時間が桁違いに遅い状態がある**(同じ入力・同じ設定で): 1080p が **11.4〜33.1 秒**(1 枚 102〜296ms)、4K が **47〜71 秒**(1 枚 423〜631ms)。ブラウザを起こした直後から遅い回があった(同じ 1080p の元を作る時間が 7.6 秒の回と 67 秒の回)。遅い間は renderer の CPU 時間が **約 8 倍**(46〜57 秒 vs 5〜7 秒)で、出力のバイトは速い回と同じ(画質も 1dB も違わない)。保険の 250ms の時計での起床は、遅い回で 25〜62 回(= 待ちの合計 6〜15 秒)、速い回は **0 回**。⚠ 遅い回の「1 枚が 250ms を超える長い待ち」の表れで、合図の取りこぼしかどうかは判定不能(速い回で 0 回なので、通常は合図で起きている)。steal は 1% 前後で、箱の他の仕事は無かった。**原因は判定不能**: `MediaRecorder` の録画・`AudioContext`・`<video>` の再生・画質の採取・音と映像のずれの採取を同じ page で先に走らせる切り分け 5 通りは、どれも再現しなかった(各 n=1)。速い状態と遅い状態が、ブラウザの起動ごと・同じ起動の中でも切り替わる。
  → 設計 §11 の「1080p/4K で作り直しが遅い(数十秒)」は **遅い状態では当たる**(4K の 4 秒の頭で 1 分前後)。速い状態では 4K の 4.4 秒(MediaRecorder の既定間隔)の頭が約 7 秒。進捗の表示は必須。実機でどちらになるかは **判定不能**(cowork で測る)。
- 🔴 **遅い状態の再現を試みた(2026-10-11、続報)**: 待ちの各経路に計数(起床の理由別・両方の待ち行列の長さを 100ms ごと)を一時的に入れ、1080p の作り直しを **ブラウザの起動 16 回で計 67 回**(`--lean` の 15 起動 × 4 回 = 60 のうち 1 起動は probe が 3 回目で止まり 2 回分 = 58 回、通常の形の 1 起動 × 9 回)回した(箱は静か、負荷平均 0.1〜0.7)。**遅い回は 0 回**: 全部 1716〜2346ms、250ms の時計での起床 0 回、`dequeue` 231 回(符号化器と復号器の合計)・符号化器の出力 111・復号器の出力 120 で毎回同じ、renderer の CPU 5.3〜7.0 秒。→ **遅い状態は再現しなかったので、原因は判定不能**。
  - **読んだ結果、待ちの作りに取りこぼしは見つからなかった**: `waitUntil` は条件を調べた同じ同期の流れで待ちを登録する(間に割り込む余地が無い)/ `live` や `encoded` が減る所・符号化器と復号器の出力・`dequeue`・失敗のすべてが `wake()` を呼ぶ。⚠ 取りこぼしが在っても 250ms の時計で進むので、**遅い回の「起床 25〜62 回」は「1 枚の処理が 250ms を超えた」でも同じ数になる**(1 枚 102〜296ms と合う)。取りこぼしの証拠にはならない。
  - **遅い状態は待ちの外にある可能性が高い**: 同じ遅い回で **元を作る側(待ちの作りが違う probe の自前の符号化)も 7.6 秒 → 67 秒に遅くなった**。製品の待ちを通らない物も同じ向きに遅いので、効いているのはブラウザの符号化器・復号器そのもの(CPU が 8 倍 = 内部の thread の空回り)と読むのが自然。
  - **ハードウェアか software かの切り替え(`hardwareAcceleration`)ではない**: この箱の Chromium 141 は `prefer-hardware` を **符号化・復号とも非対応**(`isConfigSupported` が false)と返し、`no-preference` と `prefer-software` は対応 = 常に software。⚠ 実機(GPU のある Windows / Mac)では別の可能性が残る(判定不能。cowork で測る)。製品の `configure` に `hardwareAcceleration` は渡していない ── 渡しても、この箱では速くならないと見るべき根拠(常に software)があり、実機では hardware を塞ぐ恐れがあるので、**変えない**。
  - probe に `--lean`(1080p の作り直しだけ回す。画質・ずれの採取を飛ばす)を足した。⚠ 同時に、終わった Worker の CDP session への問い合わせが返らず probe が永久に止まる穴(1 / 15 回で観測)を、2 秒で諦める形に直した。

#### 2. 音と映像のずれ(CodecDelay)

方法: 映像の白い点滅(0.4 秒)と音の 1kHz ビープ(80ms)を、同じ時計(AudioContext)で 4 回(元の時刻 2.4 / 6.4 / 10.4 / 14.4 秒)出す。切り出し後の動画を `<video>` で実時間再生し、`requestVideoFrameCallback` の表示時刻と、`MediaElementSource` → `AudioWorklet` のビープの立ち上がりを同じ時計で採って「ビープ − 点滅」を出す。出力の遅れは元と出力で同じなので、**出力 − 元の差が切り出しで増えたずれ**。元は 3 回再生した値で基準にした。元は 360p の `MediaRecorder` 録画(30fps、キーフレーム 4 秒ごと)。始まり 4.33 秒(作り直しの頭 = 約 3.7 秒)、終わり 15 秒。

| 対(元の時刻) | 場所 | 元の差(ms) | 出力の差(ms) | 増えたずれ(出力 − 元、ms) | n |
|---|---|---|---|---|---|
| 2(6.3 秒) | 頭(作り直し) | 68.3(61.9〜69.0) | 66.3(63.9〜71.4) | **−1.9**(−4.4〜+3.2) | 3 |
| 3(10.3 秒) | 尻(元のバイト) | 68.6(62.0〜69.3) | 66.6(64.0〜71.6) | **−2.0**(−4.6〜+3.0) | 3 |
| 4(14.3 秒) | 尻(元のバイト) | 68.7(62.1〜69.5) | 66.7(64.1〜71.6) | **−2.0**(−4.5〜+3.0) | 3 |

- 🟢 **増えたずれは ±5ms 以内**。頭(作り直した映像)も尻(元のバイト)も同じ。= 始まり以降の最初の packet を採る方式で、目に見えるずれは出ない。
- ⚠ **検出の限界**: 元の差そのものが 7ms 幅で揺れる(再生ごとの表示時刻の誤差)。`CodecDelay`(6.5ms)や `pre-skip` の 1 packet(20ms)が効くなら見えるはずの大きさだが、**6.5ms 単独は判定不能**。音の最初の 1 packet の捨て方による数 ms の差は、この計器では見えない。
- 対 1(元の 2.4 秒)は始まり(4.33 秒)より前なので出力に入らない。⚠ 別の予備の回(720p の `MediaRecorder`、始まり 2.3 秒で最初の対が出力の 0.1 秒に入った形、n=1)では、**始まり直後の対だけ +56ms**、他の対は +2〜−5ms だった。再生の頭の表示時刻が不安定なせいと読んだが**確かめていない**(切り出しの先頭の絵と音のずれが本当に在る可能性を捨てていない)。始まり直後 0.5 秒以内の対は、この計器では**判定不能**。
- 1080p / 4K の `MediaRecorder` 録画では点滅を拾えるフレーム数が足りず、**1080p / 4K でのずれは判定不能**(ずれは container の時刻の話で、画の大きさには依らない見込みだが、未測)。

#### 3. ビットレートの式(元の実測 × 1.2、下限 = 画素数 × 0.8bps)と継ぎ目の画質

出力の同じ番号(左上の 12bit の通し番号で対にした)のフレームを、元の同じフレームと比べた輝度の PSNR(dB)。⚠ 同じ設定の 3 回は 1 位まで同じ値(符号化が決定的)。再生は 0.5 倍速。**継ぎ目** = 作り直した頭の最後 → 元のバイトの最初のキーフレーム(出力の 3.65 秒 → 3.70 秒)。

| 設定 | 倍率 | 1080p 頭の最初(0 秒) | 1 秒 | 継ぎ目の直前(3.50 / 3.65 秒) | 継ぎ目の直後(3.70 秒〜) | 頭のバイト ÷ 元 |
|---|---|---|---|---|---|---|
| 式どおり(4.65Mbps) | ×1 | **32.3dB**(SSIM 0.951) | 42.1dB | **48.6 / 47.4dB** | 元のバイト(100dB 上限) | 1.53 |
| 半分 | ×0.5 | 29.6dB(0.916) | 35.2dB | 40.0 / 40.1dB | 同 | 0.77 |
| 2 倍 | ×2 | 37.6dB(0.982) | 46.6dB | 52.0 / 52.0dB | 同 | 2.20 |
| 4K 式どおり(18.3Mbps) | ×1 | 34.4dB(0.970) | 47.3dB | 53.2 / 53.2dB | 同 | 1.40 |

- 🟢 **継ぎ目で画は乱れない**: 継ぎ目の直前 47〜53dB、直後は元のバイトなので元と同一(輝度の誤差が 0 に近い)。さらに**隣り合う 2 枚の差(平均絶対差)** が継ぎ目をまたいでも元と同じ(1080p: 出力 12.61 / 元 12.60、4K: 15.16 / 15.12)= 時間方向の飛びも無い。
- 🟡 **作り直した頭の最初の 1 枚(キーフレーム)がいちばん粗い**: 1080p で 32.3dB(SSIM 0.95)、1 秒後には 42dB に上がる。細かい絵で最悪に近い内容なので、実画面ではもっと良い見込みだが**未測**。目に見えるかは、人の目で見ないと判定できない(**判定不能**)。倍率 2 で 37.6dB、頭のバイトが 2.2 倍(頭は最大でも 1 つのキーフレーム間隔 = 数秒分)になる。
- **式は変えない**: 元の 1.2 倍で継ぎ目は 47dB 以上、最初の 1 枚が粗いのは符号化器の立ち上がりの性質で、倍率を上げても 2 倍で +5dB。変えるなら最初の 1 枚だけ高くする案(符号化器が許すか未確認)で、画質の苦情が出てから。
- ⚠ 下限(画素数 × 0.8)は、`MediaRecorder` の 360p / 1080p の録画(元 0.65〜1.96Mbps)では下限が効いた(予備の 1 回、n=1: 1080p の `MediaRecorder` 録画で元の実測 0.65Mbps に対し式は下限の 1.66Mbps、頭のバイトが元の 1.9 倍。360p の録画では元 1.96Mbps に対し式 2.33Mbps で下限は効かず 1.2〜1.3 倍)。画面の止まった録画では頭が 2 倍近くまで増えうる。

#### 4. 同時に分かったこと

- `MediaRecorder` の `videoKeyFrameIntervalDuration: 4000` は、キャプチャのフレームが十分に来るとき(360p・30fps)は 4.03 / 8.06 / 12.10 / 16.10 秒で効いた。1080p(4〜18fps)・720p(6〜20fps)では **キーフレームが 1〜2 個しか入らない回があった**(n=各 1〜3)。②b-3 の録画側の間隔の約束は、遅い端末(録画のフレームが少ない)では守られない可能性がある。`videoKeyFrameIntervalCount` を `videoKeyFrameIntervalDuration` と併せて指定すると例外になった(メッセージは未確認、Chromium 141)。
- 実行の殻(Worker + `vite build`)とページ側の関数は `scripts/probes/video-trim-measure*.mjs`。出力の JSON(`--out`)に全回の生値が入る。

## 11. 危険と、計画が覆る条件

| 危険 | 影響 | 覆る/切り替える条件 |
|---|---|---|
| 映像付きで `CodecDelay` による音の頭の捨てが期待どおりに働かない | 音が映像からずれる | 測定で許容外 → 音を packet の境目に取る案(§4.4)へ |
| ワーカーの中で `VideoEncoder`/`VideoDecoder` が使えない | 細かい経路がメインに出る | ~~メインスレッドでは回さない~~ → **段②b-2 の実装は、作り直しの部分だけメインへ出す**(`VideoClient.scan` が `needs-codec` を受けたらメインで 1 枚通して測り、通れば作り直しだけメイン・組み立てはワーカー)。メインでも通らなければフォールバック(②b-1 の道)。理由:Chromium 以外でワーカーだけ WebCodecs が無い組み合わせを切り捨てない。メインが握るのは受け渡しだけ(復号・符号化はブラウザの別スレッド) |
| 1080p/4K で作り直しが遅い(数十秒) ── §9.1c: **遅い状態で 4K の頭 112 枚が 47〜71 秒**、速い状態で 5.9 秒 | 押した後の待ち | 進捗の表示を足す。それでも数十秒を超えるなら、細かい経路は**始まりが近い区切りの手前 0.5 秒以内のときだけ**にする案 |

| `Blob` の部品を指した結果が保存の口で扱えない | 250MB を ArrayBuffer にしてしまう | 保存の口を `Blob` を受けられる形にする(別の差分) |

| 既定のキーフレーム間隔が実画面で 10 秒以上になる | フォールバックで早くなる幅が大きい | 確認の字に実際の幅を出す(§1.1)ので誤認はしない。②b-3 で詰める |
