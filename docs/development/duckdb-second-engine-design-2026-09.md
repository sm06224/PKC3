## 2. 画面で何が起きるか

4. しばらく使わなければ**そっと畳まれ**、記憶を返す(次に押せばまた起きる)

⚠ **いまの引き方は 1 ドットも変わりません** ── 選ばなければ、これまでどおりです。

## 6. 作る物 ── 🔴 **engine を選べる継ぎ目は 0 件**

実地調査(2026-09-14)で数えた結果:

| | いま |
|---|---|
| SQL の面 | `src/adapter/ui/render/sql.ts`(**408 行**)。押し所は `run-sql` / `sql-to-note` / `set-sql-source` / `set-sql-text` |
| 走らせる鎖 | 押す → `RUN_SQL` → 字の門(`sql-guard.ts`)→ `REQUEST_SQL_RUN` → `runReadOnlySql` → **storage worker** |
| 🔴 engine の抽象 | **在りません** ── 安全装置(`PRAGMA query_only` / 歩数の門 / 字の白名簿)が**全部 sqlite の API に直結** |
| worker | storage worker は **`worker-lease` の対象外**(DB の錠を握るので常駐が要る) |

🔑 **だから DuckDB は別のワーカーにします**(storage worker に相乗りさせない)。
そして**使い捨ての規律**(遅延起動 / 溜め / アイドルで解放)に乗せる ──
⚠ **+182.5MB を常駐させない**ためです(実測で、畳むと **114.1MB 返ってきます**。
⚠ ただし **68.4MB は残りました** ── §10)。

### 🔴 安全装置は「写す」のではなく「作り直す」

⚠ sqlite 側の 3 つ(`PRAGMA query_only` / 歩数の門 / 字の白名簿)は
**sqlite 固有の API**なので、そのままでは効きません。DuckDB 側で同じ 3 つを
**別に作る**必要があります ── ⚠ ここを飛ばすと「**読むだけ**」の約束が破れます。

### ⚠ 組み合わせの矛盾を作らない

「相手 × engine」の 2 軸にすると、**成り立たない組み合わせ**が出ます
(例:添付の `.sqlite` を DuckDB で開く)。
🔑 **選べる engine を、選んだ相手で絞る** ── 矛盾を**画面から消します**
(user に「押せるのに効かない」を見せない)。

### 🔴 段④c で分かった、設計 doc に無かったこと

1. **拡張は必ず HTTP GET で取りに来る**(実測 2026-09-16、実ブラウザ 8 通り)──
   `registerFileBuffer` で器の中へ先に置いても素通りする。⚠ `blob:` に path は作れないので、
   🔴 **端末へ一式を入れてある user でも、拡張だけは毎回この PKC から読む** ──
   帰結として **電波が無いと `.parquet` / `.json` は開けない**。
2. **`.parquet` / `.json` には `_note` / `_lid` を足さない。** csv でそれを足す理由は
   「**sqlite 側と同じ SQL が通るようにする**」ことだが、この 2 つは
   **sqlite 側が存在しない**ので理由が消える。⚠ そして parquet / json は
   **列の名前を書いた人が決めている**形式なので、こちらで増やすのは驚きになる。
3. 🔴 **手持ちのファイルの控えが「1 回読んだら消える」形だった** ── 段② で DuckDB が
   **2 人目の読み手**になった時点で、**手持ちの `.csv` を DuckDB で引く道は死んでいた**
   (実測 2026-09-16。選んだ回が控えを消すので、走らせる回は必ず `null`)。
   🔑 終端を「読んだとき」から「**選ぶのをやめたとき**」へ移して直した。
4. **`sqlEngineHint` は sqlite の側でも「選べない」を返すようになった** ── それまで
   sqlite は**どの相手でも必ず選べた**ので、`resolveSqlEngine` の
   「選べないなら既定へ落とす」が**選べない値へ落とす**片手落ちを持っていた
   (⚠ そしてそれを `tests/features/sql-engine.test.ts` が**正しい仕様として pin していた**)。

🔑 **段① だけでも user の動機(分かち合いたい)は半分満たされます** ── DuckDB の文法が打てます。

## 11. 🔴 裁定 2026-09-15 ── **配り先は「PKC3 自身の Pages」**

⚠ **§9 の「A」とは別の問いです。** §9(エンジンを選ぶ欄を画面のどこに出すか)は
**まだ ⏸ のまま**です。ここで決まったのは **35MB の実体をどこから取ってくるか**だけ。

### ① user が何を求めていたのか

DuckDB も、sqlite や Office と同じように **オフラインで使えること**。
そのうえで PKC3 の柱(**勝手に外へ出ない**)を崩さないこと。

### ② そのとき何が問題だったのか

duckdb-wasm の素の姿は **実行時に外の CDN へ取りに行く**(parquet は
`https://extensions.duckdb.org/…`)── **オフラインで死ぬ**と**外へ出る**の
**両方**に当たる。

そして手本になる形が 2 つあり、**どちらから配るかで user に見える差が出た** ──
Office は**別 repo の Pages**(`sm06224/office-pack`)から配っているので、
そこへ相乗りすると **Office が使えない環境では DuckDB も道連れ**になる。

### ③ だから何を決めたか ── **PKC3 自身が配る**

| | どうする |
|---|---|
| 取りに行く先 | **PKC3 と同じオリジン**(`/dev/` を見ているなら `/dev/` の中) |
| 押す所 | **設定 → Office 表示 の隣に「DuckDB」**(Office と同じ見た目・同じ操作) |
| 置き場 | **IDB の Blob** |
| いつ取るか | **user が押したときだけ**(勝手に通信しない) |
| 取れなかったら | **理由を 1 行出す**(黙って失敗しない) |

🔑 **要点は「Office と配信経路を分けたこと」** ── 片方が落ちても、もう片方は生きる。

### 🔴 この裁定が連れてくる門 ── 先に書いておく

⚠ **35MB は `dist/` に置くが、precache には載せない。**
そのままだと `scripts/dist-inspect.mjs` が
**「precache に載っていない生成物がある」**で落ちる ── 2026-08-29 に
`portable-template.html` で**本番配布を実際に止めた**のと同じ形である。

🔑 **前例どおりにやる**:名指しで除外し、⚠ **外したぶんの門を置き直す**
── 除外した瞬間、その file は **0 バイトでも 100MB でも通る**ようになる
(tripwire を 1 つ撤廃したのと同じ)。別立ての予算を置き、
⚠ **その予算が渡っていなければ鳴らす**(optional にすると、呼び側が
渡し忘れた日に門ごと消える)。

### ⚠ 測って分かったこと(2026-09-15)

| | 値 | 引いた所 |
|---|---|---|
| npm の `@duckdb/duckdb-wasm` を展開した量 | 🔴 **142.5 MiB** | `npm view … dist.unpackedSize` = 149,377,663 |
| そのうち**配る**のは | **約 35 MiB**(素の版 `eh` だけ) | §1 の実測 |
| いま precache に載っている量(対照) | **137 file / 8.2 MiB** | `dist/precache.json` を実測 |

🔑 **だから同梱(precache)は採らない** ── 8.2 MiB が 43 MiB になり、
**DuckDB を選ばない user が 5.2 倍を払う**。
⚠ 「配る量は気にしない」(不可侵指示 2026-08-03)は生きているが、それは
**全 user が使う物**についての話であって、**選んだ人だけが使う物**を
全員へ配ってよい理由にはならない。

### ⚠ 段の切り方への影響(§7)

🔴 **段① から「precache に載せない形」で作る。** 普通に束ねると 35MB が
precache に入り、**後で外すときに上の門を踏む**。

## 12. 🔴 裁定 2026-09-15 ── **常駐させない。使うときだけ載せる**

### ① user が何を求めていたのか

DuckDB が**いつも居座る**ことを禁じた。使う瞬間だけ載り、使い終わったら**返す**こと。

### ② そのとき何が問題だったのか

⚠ **こちらの書き方が誤解を招いた** ── 「常駐が実測 +182.5MB なので置きっぱなしにしない」と
書いたので、**いま既に常駐しているように読めた**。
🔑 事実は「**`src/` に DuckDB を起こすコードは 1 行も無い**」(2026-09-15 実測。一致するのは
`DUCKDB_PRECACHE_SKIP` = precache に載せない印だけ)。+182.5MB は**起こしたときの実測値**である。

### ③ だから何をする ── 「使うときだけ」を **2 か所**に効かせる

| | いつ載るか | 使い終わったら |
|---|---|---|
| **35MB の実体** | DuckDB を初めて選んで押したとき | IDB に残す(次は取りに行かない)。⚠ 選ばない user は **0 バイト** |

**起動待ちのジョブを溜める** / **`idleMs` で kill** を持ち、いま **6 つのワーカー**が乗っている。
⚠ storage worker(sqlite)だけが対象外 ── DB の錠を握るので常駐が要る。
🔴 **DuckDB は storage worker に相乗りさせない**(相乗りさせると、この規律の外に出る)。

### 🟢 測った(2026-09-15)── **積み上がらない。残るのは 1 回目の代金だけ**

## 13. 🔴 段② を実装した(2026-09-15)── 測って決めた 4 つ

### ① user が何を求めていたのか

裁定 2026-09-15 の **A**(§9)= **SQL の面の「調べる相手」の隣に、どのエンジンで引くかを 1 つ増やす。
既定はいまの sqlite。** そして §12 の **常駐させない**。

### ② そのとき何が問題だったのか

段①b までで「起こす / 畳む / 目録を検める」は在ったが、**アプリからは 1 度も呼ばれていなかった**
(probe だけが呼んでいた)。⚠ つまり user には何も届いていない。

### ③ だから何を決めたか ── 実測が 4 つの判断を決めた

#### 🔴 (1) 相手は **csv / tsv だけ**にした(§7 の段① の字と違う)

§7 の段① は「相手は**この PKC のノートを写したもの**だけ」と書いてある。**そこから変えた。**

| | なぜ |
|---|---|
| ノートを写す | ⚠ 写す量と時間を**まだ測っていない**(§10 に書いたまま)。正本は sqlite の中に在る |
| 🟢 **csv / tsv** | bytes は**どちらの engine でも読む**ので、**写しが 1 バイトも増えない**。DuckDB の得意な形でもある |
| `.sqlite` / `.xlsx` | DuckDB から読むには**外の拡張**が要る ── §4 の柱と正面から当たる |

🔑 **これが分かったら覆る**:ノートを写す量と時間を測って、実用に足りると分かったとき。

#### 🔴 (2) 「外へ出ない」は **engine の門 1 つでは守れなかった**(実測)

実ブラウザで 3 通り測った(この箱・`@duckdb/duckdb-wasm@1.33.1-dev57.0`):

| 掛けた門 | 差し込んだ csv を読めるか | 遠くの file を読めるか |
|---|---|---|
| `autoinstall` / `autoload` を切る | 🟢 読める | 🔴 **読めてしまう** |
| `enable_external_access=false` | 🔴 **読めない**(差し込んだ物まで塞ぐ) | 🟢 塞がる |

⚠ 掛けないと**本当に外へ出る**:`read_parquet` は
`https://extensions.duckdb.org/v1.5.4/wasm_eh/parquet.duckdb_extension.wasm` へ XHR を出し、
`read_csv_auto('https://…')` / `FROM 'https://…'` / `ATTACH 'https://…'` は
**拡張を挟まずに**外へ出た(3 つとも `page.on('request')` で観測)。

🔑 **順番で解いた**(この順で実測済み):
**①拡張の自動取得を切る → ②相手を差し込む → ③`CREATE OR REPLACE TABLE … AS SELECT …` で
写し切る → ④`SET enable_external_access=false` で塞ぐ → ⑤そこから先が user の字。**

実測(塞いだ後):写した表の `SELECT` / `count` / `GROUP BY` は**全部通り**、
差し込んだ file の読み直しも、遠くの 3 通りも**全部断られ、外への要求は 0 件**。
🔴 そして **一度塞ぐと同じ器では二度と開けられない**
(「Cannot enable external access while database is running」)── **打つ人にも外せない**。
⚠ 写す代金は**実測 35ms**(3 行の小さな csv。行数が増えれば伸びる)。
⚠ **VIEW にしてはいけない** ── VIEW は打つたびに file を読み直すので、塞いだ後に引けない。

⚠ ①(拡張の自動取得)は **`SET …=true` で打ち直せてしまう**(実測)。
🔑 だから字の門(`duckdb-guard.ts`)が `SET` / `RESET` / `INSTALL` / `LOAD` を断る ── **対で効く**。

#### 🔴 (3) 返り値は **こちらで揃える**(倒さない)

上流には「開くときに double へ倒す」設定(`castBigIntToDouble` / `castDecimalToDouble`)が在り、
**実際に効いた**。⚠ ところが同じ実測で **HUGEINT が `1.2345678901234568e+29` になった** ──
30 桁が**静かに 17 桁へ落ちる**。🔑 だから**倒さずに、境界で揃える**(`features/query/duckdb-rows.ts`)。

実測した形(`table.toArray()` の 1 行目):

| 式 | `typeof` | 器 | `String(v)` |
|---|---|---|---|
| `count(*)` | **bigint** | BigInt | `"10"` |
| `sum(k)` / `HUGEINT` | object | **`[object Uint32Array]`** | 🔑 **正しい 10 進**(器が組む) |
| `DATE` / `TIMESTAMP` | 🔴 **number** | Number | 🔴 **`"1789430400000"`**(ミリ秒) |
| `[1,2]` / `{'x':1}` | object | `IntVector` / `Row` | `"[1,2]"` / `'{"x": 1}'` |

⚠ **自分で 32bit 4 つを組み直す初稿は間違いだった** ── `DECIMAL(n, s)` の**小数点を落とす**
(器は scale を知っていて、こちらは知らない)。🔑 まず器の `toString()` を使い、
器が素の並び(`"1,0,0,0"`)しか返さないときだけ組み直す。
🔴 日付は**列の型を見ないと見分けられない** ── だから `DuckDbRaw` は `types` を運ぶ。

#### 🔴 (4) 止める手は **畳むことだけ**(実測)

終わらない問い合わせの最中に `worker.terminate()` を呼んでも、
**10 秒待っても promise は pending のまま**だった(reject もされない)。
🔑 だから待ち手を解くのは**呼び側の時計**(`DuckDbLease.raceQuery`)── 30 秒で切って、
**ワーカーごと畳んで**止める。⚠ sqlite 側(8 秒)と値が違うのは**理由が違う**からである
(あちらはノートの DB を持つ worker なので、長引くと**保存が止まる**)。

### 🔴 実装の途中で見つけた、DuckDB と関係ない 1 件

`binder.ts` の `set-sql-source` は、相手の名前を **`selectedOptions[0].textContent`**
= **DOM の字**から採っていた。⚠ `lid` は state から来るので**どの test も落ちない**が、
名前だけが食い違うと、案内文も、拡張子で決まる振る舞い(= どの engine を選べるか)も
**前の相手の物**になる。🔑 名前は `entryMetas` / `sqlPage.guest` から引くように直した
(画面の字は最後の手段)。
⚠ これに気づけたのは、**happy-dom の `selectedOptions` が 2 回目以降の選択に追随しない**
(実測:`value` も `selectedIndex` も `selected` も効かない)という別の欠陥のおかげである。

## 16. 🟢 測った(2026-09-15)── **`blob:` からでも起きる**

段③ は「一式を **IDB の Blob** に置き、次からはそこから起こす」形なので、
`openDuckDb` に渡すのが**同一オリジンの path** ではなく **`blob:` の字**になる。
⚠ §11 で測ったのは path のほうで、**`blob:` は別物**である ── だから測り直した。

🔑 **worker を blob から起こすと、その worker の基点が blob になる**ので、
中で相対の解決をしていると壊れる ── そこがいちばんの懸念だった。

### 結果(実ブラウザ・5 走り)

| 測ったこと | 結果 |
|---|---|
| `new Worker(<worker の blob:>)` | 🟢 **5/5 で起きた**(同期例外も `error` も 0) |
| `db.instantiate(<wasm の blob:>)` | 🟢 **5/5 で通った** |
| `SELECT 42` | 🟢 5/5 |
| `registerFileBuffer` → `read_csv_auto`(日本語つき) | 🟢 5/5(「テスト」「二番目」が化けずに往復) |
| 🔴 **外への要求** | 🟢 **0 件 / 5 走り**(全部が同一オリジンか `blob:`) |

### 起こす時間 ── **差は読めなかった**

同じ走りの中で **path → blob → path** の順に測った(順序の効きを見るため):

| | サンプル | 平均 |
|---|---|---|
| path | 10 | **771.0ms** |
| blob | 5 | **757.2ms** |

⚠ **1 走りのブレ(624〜1056ms)のほうが、path と blob の差より大きい。**
向きも一定しない(5 走りのうち 2 走りは blob が遅い側、3 走りは速い側)。
🔑 だから言えるのは「**この測り方の分解能では、blob 化の追加コストは検出できなかった**」まで

- 🔴 **IDB から出した Blob そのもの**では測っていない ── 作ったのは
  `fetch → blob() → createObjectURL` である。器はどちらも `Blob` なので同じはずだが、
  **そこは測っていない**(段③ の実装で通す)
- **オフラインで**(電波を切って)起こせるか ── 測っていない
- 35MB を IDB へ**書く**時間と、端末の空き容量に当たったときの断り ── 測っていない
