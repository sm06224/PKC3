# 保存領域の太り方・片づけの所要を測る(#999 段①)

**状態:🔵 測定の記録**(2026-10-01)。画面は 1px も変えていない ── 足したのは読むだけの op
`storageGauge`(`protocol.ts` / `storage-worker.ts`)と、実ブラウザの probe
(`tests/probe/storage-gauge-probe.{html,mjs}`)だけ。⚠ `VACUUM` / `optimize` は**製品に口が無い**ので、
probe が `runReadOnlySql` の複文(先頭に `PRAGMA query_only = 0`)で打った(製品の画面はこの手を使わない)。

## 測った条件

| | 値 |
|---|---|
| ブラウザ | フル Chromium 141.0.0.0 / `headless_shell` 141.0.7390.37(Linux、4 コア / 16GB、`/opt/pw-browsers`)|
| 保存先 | OPFS SAHPool(`journalMode` = `truncate`、`tempStore` = 0 = 既定、page_size = 8192 ── 全部 `storageGauge` の実値)|
| (a)(b)の DB | 1,500 ノート × 本文 4KB(file 約 25 MiB)+ 100 回保存して「編集セッション後」にした状態から。1 経路 300 操作(`save` 等)|
| (c)(e)の DB | 本文 8KB のノートを file が目標に届くまで足し、**3 割を消した**(消しても file は縮まない = 返す対象)|
| 数字の読み方 | MiB。百分率の分母は**表の行ごとに書いた**(file 全体 or 測る前の file)。倍率は書かない |
| 実行 | 各ブラウザ 1 回。(a)(b)は byte 単位で**両ブラウザ同じ**(決定的な fixture)、時間だけ違う |

## 先に答え(5 つ)

| 問い | 答え |
|---|---|
| どの経路が主犯か | **file の大きさでは主犯は居ない**(300 操作で最大 +2.3 MiB = 測る前の file の 9.5%)。**worker の時間ではメッセージの追記**(処理の記録 = 5,000 節置き場)が **41 ms/操作**(本文の保存は 9 ms)|
| optimize で縮むか | **縮まない**(file は 0 byte 動かない)。**空きに変わる**だけ ── (b)で 4.6 → 12.1 MiB。縮むのは VACUUM |
| VACUUM は何秒か | 20 MiB = 0.3 秒 / 200 MiB = 2.3〜2.7 秒 / 1 GiB = **13〜18 秒**(別窓が待てる 10 秒を超える)|
| rowid は動くか | **動かなかった**(3 割消して穴だらけの DB で、rowid の集計・先頭・検索の当たりが全部一致。対照で rowid をずらすと検出される)|
| 途中で止めると | 🔴 **無傷ではない**。VACUUM の 20〜70% 地点で強制終了すると、開き直せない / 開けても読めない(下の(e))|

## (a) 経路ごとの太り方(N = 300、対照群 = 同じ時間だけ何もしない)

| 経路 | 所要 ms(1 操作)| file Δ | 空き Δ | 索引の段(測る前 → 途中の最大)|
|---|---|---|---|---|
| 対照(何もしない 12.3 秒)| — | **0** | **0** | 動かない |
| `save`(本文の保存)| 2,707(9.0)| +2.28 MiB | +0.36 | 8 → 17 |
| `save` + 履歴(`checkpoint`)| 2,329(7.8)| +2.32 | +0.34 | 8 → 17 |
| `appendMessage` 処理(上限 5,000 節 ≒ 750KB)| 12,348(**41.2**)| +1.48(**最初の 30 操作で出て以後 0**)| +0.84 | 9 → 9 |
| `appendMessage` メッセージ(上限 500 節)| 2,511(8.4)| 0 | −0.13 | 14 → 16 |
| `reorderEntry`(#984 の基準)| 1,063(3.5)| 0 | −0.07 | 8 → 8 |
| 削除 300 件 + ゴミ箱を空に | 2,090(7.0)| +1.34 | **+2.0**(終わりの空き 2.7 MiB = 終わりの file 29.2 MiB の 9.1%)| 9 → 11 |

- 分母: file Δ の百分率は「測る前の file 24.0 MiB(`save`)」。
- 🔑 file は**階段状**に増える(`save` の系列は 30 操作ごとに +0.1 / +0.7 / … / +2.3 MiB)。1 操作あたりの平均は**目安**で、規則ではない。
- 索引の段(`ftsSegments`)は FTS5 の自動結合で**増減する**(6〜17)── 差分の符号は当てにならない。**途中の最大**を見る。

## (b) FTS の optimize の前後(編集セッション 1,200 操作後の DB)

| 状態 | file | 空き(file に対する %)| 段 | 所要 |
|---|---|---|---|---|
| セッション直後(保存・履歴・追記・並べ替え・削除 各 300)| 34.4 MiB | 4.4 MiB(12.9%)| 14 | — |
| `optimize` 1 回目 | 34.4(**変わらない**)| 11.6(**33.6%**)| 1 | 407 ms |
| `optimize` 2 回目 | 同じ | 同じ | 1 | 19 ms(何もしない)|
| 続けて `VACUUM` | **22.8**(セッション直後の 66.3%)| 0 | 1 | 275 ms |

読み取れること: 1,200 操作後の file の **34%(4.4 + 7.2 MiB)が返せる**。そのうち **optimize が 7.2 MiB を空きへ移し、VACUUM が file を縮める** ── 片方だけでは足りない。

## (c)(d) VACUUM(3 割消した DB。前後の file の分母 = 消した直後の file)

| 大きさ(消した直後)| VACUUM だけ | optimize | optimize の後の VACUUM(file / 分母に対する %)|
|---|---|---|---|
| 20.9 MiB(空き 1.3 = 6.4%)| 0.26〜0.33 s → 19.5(**93.3%**)| 0.34〜0.44 s | 0.17〜0.22 s → 13.2(**63.3%**)|
| 201.7 MiB(空き 8.4 = 4.2%)| 2.3〜2.7 s → 193.0(**95.7%**)| 3.3〜3.4 s | 1.7〜1.8 s → 139.2(**69.0%**)|
| 1,001 MiB(空き 37.2 = 3.7%)| **13.1〜17.9 s** → 962.5(**96.1%**)| 17.4〜23.1 s | 9.2〜12.1 s → 698.0(**69.7%**)|

- 範囲は 2 ブラウザの最小〜最大(フル Chromium は遅い側)。**1 GiB まで**測った(箱の容量 24GB に余裕があった。4 GiB は測っていない)。
- 🔑 **VACUUM だけだと 4% しか返らない**(空きページ分)。FTS の古い段が残るので、**optimize を先に**打つと 30% 返る。
- **worker の常駐(プロセス木の Pss)**: VACUUM 中 +196 MiB(200 MiB 版)/ **+984 MiB**(1 GiB 版)── 約 **DB の大きさ 1 つぶん**。終わっても**戻らない**(wasm の heap は縮まない)。フル Chromium は worker を止めると 1,418 → 379 MiB に戻った。`headless_shell` は戻らなかった(1,341 MiB のまま)。
- **OPFS の使用量**: VACUUM 中 +192 MiB(200 MiB 版)/ +768 MiB(1 GiB 版)の**一時増**(`estimate().usage`)。⚠ 同じ profile に前の DB が残るので、見るのは差だけ。
- (d) 検索: rowid の集計(件数・和・最大・最小)・先頭 5 件の (lid, rowid)・5〜8 つの問い(大きさで数が変わる)の当たり(lid の集合)が、**3 つの大きさ × 2 ブラウザで全部一致**。🔑 対照として rowid を 100 万ずらすと 5〜7 項目が「違う」と出る(指紋が rowid に鈍くない)。`quick_check` は全部 ok。
- `storageGauge` 自身の所要: 1 GiB でも **8 ms 以下**(索引の段の代理 = `entries_fts_idx` の `count(DISTINCT segid)` が安い)。

## (e) VACUUM の途中で止める(200 MiB の DB。毎回作り直す。`SIGKILL` = renderer の強制終了)

| 止め方 | 止めた時点(VACUUM の何割)| 結果 |
|---|---|---|
| `Worker.terminate()` | 20% | **止まらない** ── 同期の VACUUM は最後まで走り、worker の錠が外れるまで 1.4〜2.3 秒(開き直しは 2〜3 回目で成功)。「worker を殺して中断」は成り立たない |
| `SIGKILL` | 2%(52ms)/ 10%(260ms)| 🟢 巻き戻った(殺す前と同じ file・同じ指紋・`quick_check` ok)|
| `SIGKILL` | **20 / 35 / 50 / 70%**(520〜1,820ms)| 🔴 **開き直せない**(`init` が `invalid fts5 file format (found 0, expected 4 or 5)` で 20 回とも落ちる)── 4/4。同じ 35・50% を**もう 2 回**やっても同じ(計 6/6)。`journalMode` を `delete` / `persist` に替えても 50% で同じ(大きな更新の 2,000ms も同じ)|
| `SIGKILL` | 90%(2,340ms)| 🟢 終わっていた |
| タブを閉じる(`page.close()`)| 20% / 50% | 20% は巻き戻り、**50% は開き直せない** |
| 対照: 全ノートの本文を書き換える 1 つの大きな更新(**終わるまで約 14〜16 秒**)| `SIGKILL` 150 / 400 / 800ms | 🟢 巻き戻った |
| 同上 | `SIGKILL` 1,000 / 1,500 / 2,000 / 3,000 / 5,000ms、`page.close()` 2,000ms | 🔴 **開けるが読めない**(6/6。`quick_check` に `Rowid … out of order` / `Freelist …`。製品が「読み込めません」の門を立てる)|
| 対照: 殺さずに待って普通に閉じる | — | 🟢 開き直せて全件書き換わり、`quick_check` ok(読み方が嘘でないことの確認)|

- `headless_shell` でも同じ並び(VACUUM 10% 巻き戻り / 50% 開けない、更新 2,000ms 読めない、待てば無傷)。
- 🔴 **VACUUM に限らない**: ふつうの大きな書き込みも、**主ファイルへの書き込みが始まった後**に止めると壊れた。journal の種類を替えても直らない。原因は未特定(下)。

## 読み取れないこと・測っていないこと

- **(f) 空きが足りないときの挙動は測っていない**(箱の OPFS を埋めるのは危険)。VACUUM の一時増(DB 1 つぶん弱)から、空きが DB の大きさを割る端末では**走らせてはいけない**と言えるが、実際に落ちたときの姿は未測。
- (e) は Linux の Chromium 141(headless)で、**実機のタブを閉じる動作ではない**。`SIGKILL` / `page.close()` が実機の閉じ方と同じ壊れ方をするかは未確認 ── 「壊れる」は**この環境での再現**であって、実 user の頻度ではない。
- 壊れの**原因は特定していない**(SAHPool の journal が復旧に使われていない可能性を疑うが、未検証)。🔴 これは VACUUM と独立の**既存の穴**の疑いで、#1007 の耐久性の話に属する(別 issue 候補。ここでは直していない)。
- 太り方は **300 操作・1,500 ノート**。数日〜数か月の連続使用ではない。履歴は +1 行の差分なので小さい(大きな書き換えの履歴は測っていない)。(b)の 1,200 操作は経路を順に回した合成で、user の実際の混ざり方ではない。
- 1 経路 1 回(ブラウザごと)。ただし (a)(b)は 2 ブラウザで byte 一致、(c)(e)は結論が一致。時間のばらつき(上の範囲)は 1 回ずつの揺れを含む。
- 4 GiB 超(#971)で wasm32 が VACUUM を通すかは未測。1 GiB で worker が +984 MiB 常駐した ── 2 GiB 級は heap の上限に近づく見込み(未測)。
- VACUUM / optimize 中に**保存が待たされる長さ**は直接測っていない(同期の 1 本なので、所要がそのまま待ち時間になる、は構造からの推定)。

## 段②③への含意(推薦。判断は段②で)

1. 自動に**縮める(VACUUM)まで入れてはいけない**: 約 600〜700 MiB を超えると別窓の 10 秒を超え、止まった場合の壊れ方が上のとおり。**索引の片づけ(optimize)も**数百 MiB で 3 秒超 ── 打つなら小さな単位(`automerge` / 段の少ない状態)に限る。
2. 先に直すのは**中断で壊れること自体**(別 issue)。
3. 太りの主因は「file が大きくなる」より「**メッセージの追記が worker を 41 ms 塞ぐ**」側 ── 段①の末尾の予告どおり、system 行を索引に入れない案(引き金に realm 条件)を別の裁定として出す価値がある(覆る条件: 追記の頻度が実使用で低いと分かる)。
