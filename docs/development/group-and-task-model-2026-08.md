# グループ概念とタスク化の設計(2026-08-19)

> user 指示(2026-08-19)
>
> **エントリやエントリグループをタスクとして扱えるようにするんです**
> **かつて要望したホワイトボードや onenote のような自由配置系グループオブジェクト
> エディタもエントリの関連やグループが必要になってくるので、グループ概念は必須です**

台帳は **#283**。本 doc は**設計と根拠**だけを持つ(やることは issue 側)。

決めるのは 2 つで、片方はもう片方の土台である。

- **(A) グループを第一級にする** ── entry の集まりを名前付きで扱える
- **(B) entry も group もタスクとして扱える** ── 状態・期日を持てる

そして (A) は、将来の**自由配置エディタ**(ホワイトボード / OneNote 風)が成り立つ前提でもある。

進め方は user 指示 2026-08-07(物量と試行と思考)に従い、**4 つの独立した立場**で案を起こし、
**3 つのレンズ**で採点し、最後に批評家を通した(read-only エージェント 13 本)。

## 1. 調べて分かった、設計の効き所

| 事実 | 根拠 | 効き方 |
|---|---|---|
| 🔴 `relations` に**属性の列が無い** | `schema.ts:59-67`(cid / id / from / to / kind / created_at / updated_at のみ) | **自由配置の座標は「メンバーである」という辺に付く情報**なので、いまの形では置き場が無い |
| 🔴 `structural` は移動のたびに**辺の行ごと作り直される** | `storage-worker.ts:622-636`(DELETE してから INSERT) | 辺に属性を載せると、**フォルダを移した瞬間に消える** |
| 🔴 UI からは**多重親を作れない**(同上の DELETE) | 同上 | 「重複所属」は structural では**構造的に表せない** |
| 多重親は取込でだけ生まれ、`entryOrder` 最小で 1 つに潰される | `features/relation/tree.ts:26-51` | 取込済みデータでは「並べ替えで居場所が変わる」経路が理屈上ある |
| タスクの材料は**既にある** | `entries` の `status` / `date` / `archived` + `idx_entries_status` / `idx_entries_date` | 封印した todo 由来。列は生きている |
| ただし **text は抽出しない** | `features/flavor/text-flavor.ts` が `NO_EXTRACT` | ふつうのノートに `status:` と書いても、いまは列に入らない |
| かんばん / カレンダーは `archetype !== 'todo'` を**最初に落とす** | `kanban-data.ts` / `calendar-data.ts` | 面に出すには、この 2 面の入口を作り替える必要がある |
| `:::format{x=… y=…}` は**今日のビルドがそのまま `data-pkc-x` を吐く** | `markdown-render.ts:2714-2728`(allowlist 無し) | 座標の記法は**新設ゼロ**で足りる |
| frontmatter の読み書きは揃っている | `frontmatter.ts`(parse / set / splice) | 記法側の実装コストが低い |
| 🔴 **`group` という概念は実装に 1 件も無い** | `src/features/relation/` は 4 file | 今回が最初 |

**3 レンズとも案4**。理由は好みではなく、次の 3 つがどれも実装で確かめられた事実だからである。

1. **静かに欠ける経路がゼロ**(互換レンズ)。5 種類の読み手 ── ①旧ビルドのタブが holder になる回
   ②旧ビルドが新アーカイブを復元 ③**旧ビルドが書いたアーカイブを新ビルドが復元** ④md ZIP / 可搬 HTML / docx

   ⚠ ③は 4 案とも自分では数えていなかった軸で、ここで順位が割れた。
   案1 / 案3 は「データの唯一の写しが、旧 writer の知らない場所に在る」ので③で構造的に落ちる。
2. **同じ形を既に 1 度着地させている**(方針レンズ)。タグ(#182)が
   「frontmatter key + 情報ペインの押せる札 + 集計面」で動いており、グループはその 2 例目になる。
3. **1 歩目が小さい**(実装レンズ)。P1 は純関数 1 file(~120 行)と既存 UI の複製で、
   **DDL・storage op・migration・スキーマ版のどれにも触らない**。

## 3. 推薦(案4)と、その中身

### 3.1 記法 ── これが正本

```yaml
---
tags: [プロジェクトA, 買い物]     # 所属(複数可)。⚠ **既存のタグをそのまま使う**
status: doing                     # 状態。生の文字列。「完了」の判定は `isDone` 1 か所
date: 2026-09-30                  # 期日
archived: true                    # 片付けた
---
```

グループの**表紙**(実体)は、`group: プロジェクトA` と書いたノート **1 件**。
表紙は entry なので、本文・状態・期日・履歴・添付・座標を**そのまま**持てる ──
🔑 **新しい record 型を 1 つも作らずに「第一級」を満たす**。表紙は**無くてもよい**。

🔑 **足す key は `group:` の 1 つだけ**(裁定 Q2)。所属は `tags:` を再利用する ──
「グループ」に求められている差は**表紙を持てること**だけで、束ね方そのものは
タグと同じである。`groups:` を別に作ると、frontmatter の名前で束ねる仕組みが
**3 系統目**になり、CLAUDE.md §7「同じ問いに答える口が 2 つある」を自分から作る。
🔑 **グループとは「表紙を持つタグ」である。**

**入れ子**は、表紙自身が `tags:` を持つこと。**重複所属**は配列がそのまま。
どちらも「許すために書く行が 0 行」である ── 制約を DB に持たないから。

### 3.2 自由配置(将来)

**板そのものが 1 つのノートで、その本文が正本**(裁定 Q1)。置く物は 2 種類:

```
:::format{#place-1 .pkc-place x=120 y=40 w=320 h=200 z=3}
### 買い出し                      ← ① 板で書いた付箋(中身がその場に在る)
- [ ] 牛乳
:::

:::format{#place-2 .pkc-place entry=abc123 x=460 y=40 w=280 h=160}
:::                               ← ② 既存ノートの札(題名 + 抜粋を出す)
```

**markdown 方言の新設はゼロ。** 今日のビルドが `data-pkc-x="120" …` を吐く
(`markdown-render.ts:2714-2728`。allowlist が無いので `entry=` もそのまま通る)。

🔑 **これが「位置の置き場」問題を解く。** 位置は「板 × ノート」の関係の属性に見えるが、
**板の本文に書けば関係テーブルは要らない** ── だから `relations` に属性列が無いことは
この案の障害にならない(案1 / 案3 を採る理由が 1 つ消える)。
⚠ **中身の展開(transclusion)はしない** ── ②は題名と抜粋の札で、開けば本体へ飛ぶ。
展開器は PKC3 に存在せず(`markdown-render.ts` は空の placeholder を出すだけ)、
作ると板が「本文の写し」を持つことになって正本が 2 つになる。

### 3.3 グループの状態は「独立」。集約しない

表紙の `status:` が唯一の正本。子の状態は **`3 / 7 完了` という数え上げだけ**を横に出す。

- 集約にすると、グループの状態は**どの本文にも書かれていない値**になる(「本文が正本」が最初に破れる)
- しかも判定が「表紙を描く所」と「一覧に出す所」に**別々に生える**(CLAUDE.md §7)
- 🔴 **自動で本文を書き換えない。** 「全部済んでいます。完了にしますか」を**押せるボタン**にする

### 3.4 folder / `structural` とは並存させる(統合しない)

| | folder / structural | グループ |
|---|---|---|
| 何 | **居場所**(1 つ・排他) | **所属**(複数可・非排他) |
| どこ | `relations` 表 | 本文の frontmatter |
| 移動 | 辺を作り直す | 本文の 1 行を splice |

統合しない根拠は 2 つとも実装に在る ── ①`writeParent` が移動のたびに辺を作り直すので、
structural に載せた属性は**フォルダを移すと消える** ②多重親が UI から作れない。

## 4. 🔴 先に塞ぐ土台(#284)

案4 は frontmatter に載せる。ところが**その土台に、既に出荷済みの無言のデータ消失経路がある**
(自分の probe で再現。#284 に実測を書いた)。

1. 既定の編集面は **live**(`editor-mode.ts:25`)で、**生 body を渡す**(`detail.ts:826`)。
   2 ペイン側は剥がしている(`:899` / `:904`)── **非対称**
2. 生 body を描くと frontmatter は `<hr>` + `<h2>` になり、**画面に出て、その場で編集できる**
3. 閉じの `---` が消えると `parseFrontmatter` は `found:false` / `meta:{}` / 🔴 **`warnings:[]`**
   ── **警告ゼロで全部消える**

いまの被害はタグ 1 種類だが、案4 は**この露出を全ノートへ広げる**。
🔑 **#284 を先に塞ぐことが、この設計の着手条件である。**

## 5. 着地条件(案4 を採るなら、同時に決めること)

1. **合流を黙らせない** ── 取込で既存の組名と一致したら「同名の組に合流しました: N 件」を出す
   (`pkc3-archive.ts` の `dangling-relation` 警告と同じ形)
2. **16KB 超を見せる** ── `parseFrontmatter` の `size_limit` 警告は**いまどの面にも出ていない**。
   「この本文は組に入りません」を情報ペインに出す
3. **突き合わせの規則を 1 つに寄せる** ── `tags.ts` は正規化 + 大小無視、`group-by.ts` は生値で、
   **今すでに 2 つある**。寄せずに出すと「同じ名前なのに 2 組に割れる」という直しようのない症状になる

## 6. できないこと(正直に)

- 🔴 **グループの改名が、全メンバーの本文書き換えになる**(N 件の保存・履歴・`updated_at`)。
  途中で失敗すると**半分だけ移った状態**になる ── 「本文が正本」を選んだ代償そのもの
- 🔴 **取込で同名グループが合流する**(lid は付け替わるが、名前は付け替わらない)
- 🔴 **グループごとの並び順を持てない**(`entryOrder` は container 全体で 1 本の数直線)。
  表紙に `order: [lid, …]` と書けば持てるが、それは lid 参照になり、
  **アーカイブ復元が body 中の `entry:` を書き換えない**という確定した穴を自分から呼び込む
- 🔴 **グループで絞るたびに全件走査**(`entries.status` / `date` の索引を 1 度も使わない)。
  ⚠ **件数別の実時間は測っていない** ── 速さが要るなら P2 で列(= 派生)を足す
- 🔴 **P1 ではかんばん / カレンダーに出ない**(2 面が `archetype !== 'todo'` を落とすため)
- 🔴 **本文の中のチェックリストは P1 では押せないまま**(描く面が 5〜7 あり、
  書き出した単一 HTML には store が無いので分岐が要る)── P1 は「ノート 1 件をタスクにする」まで
- 🔴 **入れ子の循環を作れてしまう**(深さ 8 で打ち切る。アプリは切らない)
- 🔴 **表記ゆれは検出できない**(`プロジェクトA` と `プロジェクトＡ` は別の組)
- 🔴 **可搬 HTML / docx にグループもタスク状態も出ない**(読む面が frontmatter を剥がすため)
- ⚠ **`YYYY-MM-DD` に厳密一致しない日付は黙って落ちる**(`todo-flavor.ts`)──
  いま todo だけの穴が、全 archetype の穴になる

## 7. 覆る条件(これが分かったら決め直す)

- **Q1**: 「札ではなく**中身をそのまま**板に出したい(本当の transclusion)」なら、
  展開器が要る。位置は板の本文のままでよいが、**正本が 2 つになる**問題を先に解く
- **Q2**: 「タグと組は**画面で完全に分けたい**(同じ名前でも別物として扱いたい)」なら、
  `tags:` の再利用をやめて別 key を作る ── ただし束ね方が 3 系統になる代償を払う
- **Q3**: `pkc3-archive.ts` の lid 付け替えが **body まで追随**するようになったら、
  id での同一性が安全に使える(いまは body の `entry:` を書き換えないので使えない)
- **5000 件級で集計面の実時間が使い物にならなかった場合** ── 派生列(索引)が必須になり、
  「DB はいつ捨ててもよい」という潔さが一部失われる(案が変わるのではなく、段階が増える)

## 9. 裁定(user 委任により決定。2026-08-19)

> user 指示 2026-08-19「**推薦通りで良い / その判断は全てあなたに委任する**」

⚠ 3 点とも **user の好みではなく、実装がどうなっているかで決まった**。
聞く前に読めば決まる問いだった、というのが今回の反省である。

### Q1 板に置くのは「付箋」か「既存ノート」か → **両方。板の本文が正本**

「既存ノートを置くなら位置は『板 × ノート』の属性になり、関係テーブルか新表が要る」と
書いたが、**それは位置を辺に持たせる場合の話**だった。**板の本文の記法に書けば**
関係テーブルは要らない(§3.2)。よって**選んだ案のまま両方載る**。
⚠ ただし**中身の展開(transclusion)はしない** ── 展開器が無く、作ると正本が 2 つになる。
既存ノートは**題名 + 抜粋の札**として置き、開けば本体へ飛ぶ。

### Q2 グループは tags と別概念か → **別概念にしない**

求められている差は「**表紙(実体)を持てる**」だけで、それは key 1 つ(`group:`)で足りる。
`groups:` を別に作ると、frontmatter の名前で束ねる仕組みが **3 系統目**になり、
「同じ問いに答える口が 2 つ」を自分から作る(CLAUDE.md §7)。
🔑 **グループ = 表紙を持つタグ。** P1 の実装量も大きく減る。

### Q3 同一性は「名前」か「不変の id」か → **名前**

- **タグが既に名前で出荷済み**なので、id を持ち込むと同一性の模型が 2 つになる
- id を本文に書くと、**アーカイブ復元が body の `entry:` を書き換えない**という
  確定した穴(`pkc3-archive.ts`)を踏む ── 壊れ方が**静か**な側へ倒れる
- 名前の代償(改名が N 件の本文書き換え / 取込で同名合流)は**見える**側の代償である

⚠ 代償は**緩和策つき**で受ける:
1. 改名は「まとめて置換」の **1 操作**として提供する(N 件を user に手作業させない)
2. 取込での同名合流は**警告を出す**(黙って合流させない ── §5 の着地条件 1 と同じ)
