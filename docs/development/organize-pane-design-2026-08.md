# 整理の面の設計(#240 / #241)── フォルダ主体・複数選択・D&D・2 ペインファイラ

> 作成 2026-08-17。**実装はまだ入れていない**(doc-first。裁定を仰ぐ点は §6)。

## 1. 何を作るか(user 指示 2026-08-17)

> **右ペインに削除ボタンがあるが使いにくい。まとめて消せない。そもそも左ペインの
> 一覧表示はあまり意味がない。フォルダ表示メインにしてフォルダをダブルクリックで
> 開くように変更、複数選択・範囲選択・D&D を導入すること**

> **アプリに 2 ペインタブファイラ(PKC 内の整理高度化のため)を組み込みで提供すること、
> PKC2 にあったコマンド機能はこの 2 ペインファイラの内部で使うこと**

台帳は #240(左ペイン)と #241(2 ペインファイラ)。**部品を共有する**ので 1 つの doc にする。

## 2. いまの実装(読んで確かめた事実)

| 事実 | 場所 |

| 移動は**選択の下に出る「移動」の選択肢**(`move-entry`)── 1 件ずつ | `filer.ts:99` |

### 🔴 いちばん効く 1 行

```ts
const scope = resolveFilerScope(state.selectedLid, state.entryMetas, state.relations);
```
`filer.ts:200` ── **「いまどのフォルダを見ているか」は `selectedLid` の純関数**である。

つまり現状は **「選ぶ」と「入る」が同じ操作**になっている。⚠ user の言う
「**ダブルクリックで開く**」は、この 2 つを**分けろ**という指示にほかならない ──
1 クリック = 選ぶ(入らない)、2 クリック = 入る。

⚠ そして**複数選択とも正面からぶつかる**: 選択が集合になった瞬間、
「選択 → 現在地」の写像は成り立たない(2 件選んだらどこに居るのか言えない)。

🔑 **したがって最初の 1 手は「現在地を状態として持つ」**である。これが無いまま
D&D やまとめて削除を足すと、**落とし先も削除対象も選択に引きずられる**。

## 3. 設計(推薦)

### 3-1. 現在地(`scopeLid`)を state に持つ

- `AppState` に `scopeLid: string | null` を足す(`null` = ルート)
- **`selectedLid` は消さない** ── 「いま開いているノート」であり、中央と右ペインの正本
- 面の遷移: 行を 1 クリック → **選ぶだけ**(中央が開く)/ フォルダを 2 クリック →
  `scopeLid` が変わる(中央は変えない)
- パンくずは `scopeLid` を動かす(いまは `DESELECT_ENTRY` を撃っている ── `binder.ts:933`)

⚠ **移行の注意**: いま「フォルダを 1 クリックすると入る」に慣れている動線が変わる。
お知らせに 1 行出す。

### 3-2. 選択を集合にする

- `selection: readonly string[]`(順序 = 選んだ順)+ `anchorLid`(範囲選択の起点)
- `selectedLid` は **集合の最後の 1 件**として維持する(= 既存の全面はそのまま動く)
  ── 🔑 これなら**中央・右ペイン・履歴・書き出しの経路を 1 つも触らずに済む**
- 修飾キー: `Ctrl/Cmd` = 足す・外す / `Shift` = `anchor` から範囲
- ⚠ **表示している並び順**で範囲を採る(#183 の並べ替えが効いている順)。
  データの順で採ると、目で見た範囲と違うものが選ばれる

### 3-3. まとめて削除は**ゴミ箱へ**

- 既存の `DELETE_ENTRY` を n 件ぶん撃つのではなく、**1 回の操作**として扱う
  (途中で失敗したときに「半分消えた」を作らない)
- 🔑 **戻せる**(ゴミ箱が既にある)ので、確認は「n 件をゴミ箱へ入れます」の 1 回でよい
- ⚠ **`purge-trash`(完全削除)はまとめて撃たせない** ── 元に戻せない操作を
  一括で撃てるようにするのがいちばん事故が大きい

### 3-4. D&D の意味を**落とす場所で分ける**

| 落とす場所 | 意味 |
|---|---|
| **フォルダの行の上** | そのフォルダへ**入れる**(親子の付け替え) |
| **行と行の隙間** | その位置へ**並べ替える**(#183 の手動順) |
| **パンくずの段** | その階層へ**出す** |

⚠ いま `move-entry` の選択肢が同じ仕事をしている ── **消さない**(キーボードだけの
動線であり、D&D が使えない場面がある)。⚠ マニュアルの「ドラッグ&ドロップは受けません」
(§5)は **2026-08-18(#250)に既に消えている** ── OS からの file の drop を
受けるようになったため(§7-1)。ここで足すのは**行と行の間の D&D**(PKC の中の
移動)であって、file の drop とは**受け口が別**である。

### 3-5. 2 ペインタブファイラ(#241)

- **同じ部品を 2 枚**置く(左右)。それぞれが `scopeLid` と `selection` を持つ
- **タブ**は各ペインが持つ(1 ペイン n タブ)
- 置き場は **中央の面の 1 つ**(`ViewMode` に足す)── 左の列は狭く、2 ペインは入らない
- 🔑 **左の列のフォルダ面は残す**(1 画面完結の主動線)。2 ペインは
  「腰を据えて整理する」ときに開く面である

### 3-6. コマンド機能の置き場(#241 後半)

user 指示は「**PKC2 にあったコマンド機能はこの 2 ペインファイラの内部で使う**」。
⚠ PKC2 は read-only 参照なので、**移すものを名指しで決めてから**着手する
(丸写し禁止 = 「流用 + 総合的見直し」)。§6 の裁定 5 で聞く。

## 5. 検証(この doc の時点で決めておく)

- **①の後**: 「1 クリックで入ってしまわない」を smoke で見る ──
  ⚠ 逆向き(2 クリックで入る)だけを見ると、**1 クリックでも入る実装**が素通りする
- **②の後**: 範囲選択は**表示順**で採れているか(並べ替えを変えてから Shift 選択する)
- **③の後**: ゴミ箱に n 件入り、**戻すと n 件戻る**(片道の実装が素通りしないように)
- **④の後**: 落とす場所 3 つを**別々に**当てる(1 つ通っただけで「D&D 実装」と言わない)
- 変異試験: 「修飾キーの判定を落とす」「表示順ではなくデータ順で範囲を採る」
  「まとめて削除が 1 件しか消さない」を当てて、落ちることを確かめる

## 6. 🔴 裁定 ── 2026-08-18 に決めたこと

> **user 指示 2026-08-18「実装を完了してください」**を受けて、§6 の 6 点は
> **調べたうえでこちらが 1 つずつ推薦を決め、その形で実装する**(判断の出し方
> 2026-08-08:「選択肢を並べて user に丸投げしない」)。
> ⚠ **user に見える仕様**なので、違えば言ってください ── 決めた形と**覆る条件**を各項に書きます。

| # | 決めたこと | 理由 | これが分かったら覆る |
|---|---|---|---|
| 1 | **`selection: string[]` を「印を付けたもの」の唯一の正本にする。`selectedLid`(= 開いているノート)は今の意味のまま触らない**。1 クリックは両方を動かし、`Ctrl` / `Shift` は `selection` だけ動かす | PKC2 の「選択の union」は user audit が**最悪の UX 事故**と記録し、呼び出し側ごとの `includeAnchor` という二重規則になっていた。末尾を自動同期する案も、`Ctrl+click` のたびに中央が開き直って `REQUEST_BODY` が n 回飛ぶ | user が「`Ctrl+click` でも中央を移したい」と言う場合 |
| 2 | **まとめて削除はゴミ箱行き。確認は 1 回。完全削除は一括で撃たせない**。まとめて復元は `bulk_id` 列を足さず、ゴミ箱の一覧に同じ複数選択を通す | 段②で作る規則を再利用すれば**判定が 1 本**で済む。schema 変更は migration と旧 DB 互換を連れてくるのに、買えるのは「同時に消した」という関係 1 つだけ | user が「同時に消したものは 1 ボタンで戻したい」と言う場合 |
| 3 | **D&D はまず「フォルダの上 = 入れる」と「パンくず = 出す」の 2 つ。隙間の並べ替えは段を分ける。ゴミ箱へのドラッグは入れない** | 前 2 つは既存 action にそのまま乗る(1 PR 1 主張)。隙間だけは「順序の付け方」という別主題で、`他のフォルダに触らない` 不変条件を壊しうる | user が「手動の並びは D&D で作りたい」を最優先と言う場合 |
| 4 | **一覧タブは残す。既定はフォルダにする。ただし同じ PR で「フォルダ面にも並び順を効かせる」を必ず入れる**。最後に使ったタブを覚える | user 指摘は「あまり意味がない」であって「消せ」ではない。かつ**効かない操作子を既定の面に出すのは無言の操作拒否**である | 平置き 15k の初回描画が許容外なら、既定変更の前に行再利用を入れる |
| 5 | **「コマンド機能」は構成コマンド(`mv` / `mkdir` / `rename` + dry-run)を 2 ペインの中に置く。コマンドパレットは移さない** | user 指示は「**PKC 内の整理高度化のため**」の 2 ペインと同じ文にある ── 構成コマンドはまさに整理の道具で、パレットはアプリ全体のランチャー(「2 ペインの内部で使う」理由が無い) | user の言う「コマンド機能」がパレットを指していた場合。⚠ その時も登録簿は `KEY_COMMANDS`(#256)1 本に寄せる |
| 6 | **2 ペインは中央の面**(`ViewMode` に 1 つ足す)。同じ段で死に値の `'filer'` / `'launcher'` を畳み、編集中に押したときの断り文を足す | 幅は中央にしかない。別ウィンドウ案は多タブの編集権(#177 / TabSync)の話を増やす | user が「整理しながら本文も見たい」と言う場合(置き場は変わらず、右ペインに開いているノートを出す形を併せて検討) |

### 実装の順(依存)

**①→②→(③ と ⑤ を同じ PR)→④→⑥→⑦**。
③ と ⑤ を同じ PR にするのは、どちらも「フォルダ面が主動線になる」という 1 つの主張の表裏だから
── ⑤ だけ先に出すと、**まとめて消せないままフォルダ面が既定になり**、user 指摘の
「まとめて消せない」がいちばん目立つ場所へ移る。
⚠ ④ は「入れる / 出す」と「隙間の並べ替え」で PR を割る(主張が 2 つ)。

## 6-b. 旧「裁定を仰ぐ点」(記録として残す)

1. **`selectedLid` を「集合の末尾」として残す**案でよいか(既存の面を触らずに済む)。
   それとも「開いているもの」と「選んでいるもの」を**別の名前**で持つか
2. **まとめて削除はゴミ箱行き**でよいか(= 戻せる。完全削除は一括では撃たせない)
3. **D&D の落とし先 3 つ**(フォルダの上 = 入れる / 隙間 = 並べ替え / パンくず = 出す)
   ── 3 つとも要るか、まず「入れる」だけでよいか
4. **左の列の既定タブをフォルダにする**(いまは一覧)。⚠ 一覧タブは**残す**前提でよいか
   (user 指摘は「あまり意味がない」であって「消せ」ではないと読んだ)
5. **コマンド機能として何を移すか** ── PKC2 のどの操作を指しているか名指しが要る
6. **2 ペインは中央の面**でよいか(左の列には幅が無い)
