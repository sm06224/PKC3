# P6d: PKC3 の書出し ── 設計(2026-08)

正本 doc §11 の P6 最終段。P6a〜P6c で「PKC2 から救出する」が成立したので、
残りは **PKC3 から出す**側。

> **前提(user 裁定 2026-07-30、不可侵)**: PKC3 export は **PKC2 にインポートしない**
> (一方通行)。だから PKC2 の形式に寄せる制約が無く、**素直な形を選べる**。

---

## 0. この段の芯 ── 「出す」は「読む」より壊れやすい

P6c(取込)は**壊れた入力をどう扱うか**が論点だった。P6d は違う。入力は自分の
DB なので壊れていない。**論点は 2 つだけ**:

1. 🔑 **常駐量**。PKC2 の書出しは container 全体を 1 個の巨大文字列に組み立てて
   いた(実測 +293MB 常駐)。user 指示「**ゼロコピー、生成とライフサイクル後の
   速やかな破棄を徹底**」(2026-07-27、不可侵)は、**この段で一番効く**
2. **出したものを自分で読み戻せるか**(round-trip)。PKC2 は writer と reader を
   別々に書いて食い違わせていた(拡張子ストリップの正規表現、`compact` /
   `compacted` の綴り違い、bit 11 を書くが読まない…)── P6c の調査で見た通り

---

## 1. 出す 3 形式

| # | 形式 | 何のためか | 中身 |
|---|---|---|---|
| 1 | **アーカイブ ZIP**(`.pkc3.zip`) | **バックアップ正本**。これさえあれば全部戻る | `manifest.json` + `container.json` + `assets/<key>` |
| 2 | **可搬 HTML**(`.html`) | 1 ファイルで配れる・その場で読める | `#pkc-data` に `{container, export_meta}` + 閲覧 UI |
| 3 | **md ZIP**(`.md.zip`) | **外に出す**(PKC3 を捨てても読める) | `<slug>.md` × N + `assets/<key>.<ext>` |

⚠ **①だけが可逆**。②は閲覧が主目的、③は**片道**(frontmatter に入らない情報は
落ちる)。3 つを同じ「書出し」ボタンに並べるなら、**どれが可逆かを UI で言う**
── PKC2 は light / full の別を書出し後の manifest にしか書いておらず、user は
「添付が入っていない ZIP」を後から見分けられなかった。

---

## 2. 🔑 常駐量の設計(この段の主題)

### 2-1. 全部 Blob の部品で組む ── 1 個の巨大バッファを作らない

`new Blob([a, b, c])` は **部品の参照を持つだけ**で、中身をコピーしない。
asset は `AssetBlobStore.get()` が **IDB の Blob をそのまま返す**(既にディスク側の
実体を指している)ので、**部品として並べるだけなら heap に載らない**。

```
アーカイブ ZIP = Blob([
  LH(manifest), manifest文字列,
  LH(container), container文字列,
  LH(asset1), <IDB の Blob をそのまま>,   ← ここが要点
  ...
  中央ディレクトリ, EOCD
])
```

⚠ **CRC-32 と長さだけは中身を舐めないと出せない**。ただし舐めるのは
`blob.stream()` 経由で 1 件ずつでよく、**同時に heap に載るのは 1 チャンク**。
P6c の reader が既に `crc32Update` を持っている(段①)ので**再実装しない**。

⚠ **local header に CRC を書く必要がある** = 書く前に舐める必要がある。
順序は「asset を舐めて CRC と長さを得る → その値でヘッダを作る → 部品を並べる」。
data descriptor(bit 3)を使えば舐めながら書けるが、**PKC3 の reader は
中央ディレクトリを正としつつ local header の署名を検査する**ので、素直に
2 パス(舐める → 組む)にする。**IDB の Blob を 2 回読むだけで、常駐は増えない**。

### 2-2. HTML も**流し込める**(base64 は 3 バイト境界で分割できる)

「単一 HTML は全部 base64 にするから必ず全量メモリに載る」は**誤り**。
base64 は 3 バイト → 4 文字の変換で状態を持たないので、**入力を 3 の倍数で
区切れば**、チャンクごとに符号化して連結した結果が全体符号化と一致する。

**実測で確認済み**(2026-08-02、node、ランダム 200 本 × 最大 5000 バイト):

| 分割 | 結果 |
|---|---|
| **3 の倍数** | 200 / 200 が全体符号化と**一致** |
| 3 の倍数でない(対照) | 200 / 200 が**不一致** ── 境界条件が本物であることの確認 |

⚠ 対照群を置いたのは、「一致した」だけでは**分割していないのと区別がつかない**
から(fixture のゼロ件次元と同型の罠)。

→ HTML export も `Blob([...文字列部品])` で組める。**常駐は 1 チャンク**。

### 2-3. 本文をどう取り出すか ── ここだけ穴が開いている

`store-port` の現状(`protocol.ts`):

| op | 単位 |
|---|---|
| `listEntryMetas` | 全件(**body を含まない**) |
| `getBody` | **1 件ずつ** |

⚠ **body を一括で取る op が無い**。5000 entry の書出しが 5000 往復になる。
`getBody` を N 回呼ぶのは「正しいが遅い」形で、**プライム・ディレクティブ的には
足すべき**(「効果が小さいからやらないではなく、積み上げた先に価値があるなら
小さかろうが積んでください」── user 指示)。

**提案**: `listBodies { cid, afterLid?, maxBytes }` を足す。
`importRevisionChains` の `REVISION_BATCH_BYTES`(4MB)と**同じ作法**
(postMessage に全量を載せない / 1 メッセージの合計バイト数で切る)。
⚠ **鎖と違って body は割ってよい**(1 entry = 1 独立単位)ので、
`batchChains` が持つ「割ると静かに落ちる」問題は無い。

## 3. 何を出すか(表ごと)

| 表 | アーカイブ ZIP | 可搬 HTML | md ZIP |
|---|---|---|---|
| `entries` | 全列 | 全列 | body → `.md`、他は frontmatter |
| `relations` | 全件 | 全件 | ⚠ **落ちる**(md に居場所が無い) |
| `revisions` | **鎖のまま**(下記) | 鎖のまま | ⚠ **落ちる** |
| `assets`(meta) | 全件 | 全件 | key → ファイル名のみ |
| asset bytes | `assets/<key>` 生バイナリ | base64 | `assets/<key>.<ext>` |
| `settings` / `flags` | ⚠ **出さない**(§5) | 出さない | 出さない |

### 3-1. revisions は**鎖のまま**出す(全文に展開しない)

P5c の履歴は **tip = `entries.body` / 過去 = 逆向きパッチ**。展開すると
N×M のバイト数になり、②の常駐設計が台無しになる。PKC3 export は PKC2 に
読ませない前提なので、**鎖をそのまま出して PKC3 が読み戻す**のが素直。

⚠ 帰結: **可搬 HTML の閲覧 UI は履歴を出せない**(パッチ適用が要る)。
P7 の Pages product で履歴まで見せたいなら、その時に**閲覧側へパッチ適用を
載せる**判断をする ── いま全文展開して常駐を捨てる理由にはならない。

### 3-2. md ZIP は**落ちるものを書き出す**

frontmatter に入らない relation / revisions は失われる。PKC2 は
「落ちた」ことを user に言わずに出していた(bundle 経由で thumbnail が
落ちる縁など)── PKC3 は **書出し前に「これは片道です」と言い、
manifest に落とした件数を刻む**。

## 4. 危険な縁 ── 静かに壊れうる箇所

各行を **断る / 言う / 仕様として受ける** のいずれかに倒す。

| # | 縁 | 扱い |
|---|---|---|
| A | **参照はあるが bytes が無い asset**(GC 途中失敗など) | `assets/` に入れず **manifest に missing として刻む + 書出し後に言う**。参照は壊れたまま温存(P6c §4-B と同じ規約) |
| B | **書出し中に user が編集する** | 書出しは **asset gate の内側**(取込・purge と排他)── P6b で確立済みの規約に合流。`phase !== 'ready'` なら断る |
| C | ファイル名の衝突(md ZIP、同題のノート) | `-2` を**拡張子の直前**に挿す(PKC2 と同じ規則 ── user の目に馴染む)。⚠ slug が空になる題名は `untitled` |
| D | 題名の非 ASCII | ZIP は **UTF-8 flag(bit 11)を立てて名前を書く**。⚠ P6c で「**bit 11 は読まない**・妥当な UTF-8 かで決める」と決めたので、**自分の reader で読み戻せる**ことは test で確かめる |
| E | **巨大 container** | 常駐が線形に増えないこと(§2)を**測ってから**言う。⚠ 「boot 窓だけで定常を語らない」── 書出し中の long task を測る |
| F | 空 container | **0 件の書出しを黙って作らない** ── 「取り込めたつもりで 0 件」の裏返し。断るか、0 件と明示 |
| G | asset key が content hash であること | ファイル名 = key なので **再取込で自然に畳まれる**(ZFS 発想がそのまま効く)。⚠ 64MB 超の採番 key(`hash === null`)は畳まれない ── 仕様として受ける |

### 3-3. 実装で決めたこと(段④ 着地時、2026-08-02)

| 決めごと | 内容 | なぜ |
|---|---|---|
| **本文の `asset:<key>` を相対パスへ書き換える** | `assets/<key>.<ext>` | 書き換えないと**外では画像が 1 枚も出ない** ── 「PKC3 を捨てても読める」が成立しない。片道形式なので書き換えてよい |
| **拡張子は mime から引く** | 既知 mime の表 + 未知は `.bin` | OS はほぼ拡張子で判定する。⚠ 嘘の拡張子を付けるより**開けない方がまし**なので未知は推測しない |
| **frontmatter は最小 + 元の frontmatter は残す** | `title` / `archetype` / `created_at` / `updated_at`(値がある時だけ) | 添付 entry の `attachment.*` を落とすと外で中身に辿り着けない。衝突時は**表の値が勝ち、勝った旨を注意に出す** |
| 🔴 **書くのは原文 splice。parse → 再構築をしない** | `spliceFrontmatterKeys` で PKC3 のキーだけ差し込む。`parseFrontmatter` は**読むだけ** | 組み直すとミニ YAML の未対応構文(ネスト / ブロックスカラー / 非 ASCII キー / コメント)が**無言で落ちる**。16KB 超の frontmatter では parser が諦めるので **frontmatter ごと本文まで削れた** `.md` が出る(review H-1 実測: 17,584 → 65 文字)。`frontmatter.ts` に既にこの規律が明記されていた |
| 🔴 **書き換えは*リンク/画像の宛先*だけ** | fence / inline code は飛ばし、宛先が `asset:` で始まるときだけ replace | 生テキストを舐めると、書式を説明したノートの本文や `https://…/asset:…/path` のような **URL が改変される**(review H-2 実測) |
| 🔴 **ファイル名は大文字小文字を同一視して一意化** | `Memo.md` / `memo.md` は衝突として扱う | macOS / Windows は同一視して展開するので、両方入れると**ノートが消える**(review H-3 実測: 3 件 → 1 件)。添付パスも同様 |
| **連番は base ごとに継続** | `Map<base, next>` | 毎回 2 から数え直すと同題 8000 件で O(k²)(実測 7.6 秒 → 159ms) |
| **同種の注意は上限 10 件 + 「ほか N 件」** | | 3000 件の `<li>` を作らない。⚠ ただし**黙って減らさない** |
| **添付 entry に参照行を 1 本足す** | `![name](assets/…)` / `[name](assets/…)` | 添付 entry の body は frontmatter だけなので、足さないと**空の `.md`** になる。本文が既に出しているなら足さない |
| **履歴は「本数」でなく「履歴を持つノートの件数」で言う** | `dropped.revision_entries` | 本数を数えるには entry ごとに `listRevisionMetas` を呼ぶしかなく、5000 件のノートで**数字 1 個のために 5000 往復**する。`listRevisionLids` は 1 往復で済む |
| **参照されていない添付は入れない** | 件数を注意に出す | 削除済みノートの添付が**人に配るファイル**に載る(段③ review H3 と同根)。⚠ アーカイブ側には入れない ── バックアップから添付を落とすのはデータ欠損 |
| **Windows 予約語を避ける** | `CON` → `CON-` | `CON.md` は Windows で作れない ── **展開できない ZIP** を作らない |
| **manifest に `reversible: false`** | + `note` の 1 行 | 「戻せない」を機械可読に刻む。後から見分けられない形にしない |

## 5. 出さないもの(意図的)

- **`settings`(正規設定)/ `flags`(実験)** ── 環境の設定であってデータではない。
  持ち出すと「別の端末で開いたら挙動が違う」を作る。⚠ user が明示的に
  「設定も移したい」と言ったら**別形式**で足す(データと混ぜない)
- **IDB の内部形式 / OPFS の sqlite ファイルそのもの** ── 別 origin で読めない
- **PKC2 互換の形** ── 一方通行(user 裁定)

## 6. 実装順(各段が単独で着地・単独で測れる)

| 段 | 内容 | なぜこの順か |
|---|---|---|
| ✅ ① | **ZIP writer**(`features/export/zip-writer.ts`)+ `listBodies` op | 全形式の土台。**reader(段①)と対で round-trip test が書ける** ── writer と reader を別々に書いて食い違わせた PKC2 の失敗を構造的に避ける |
| ✅ ② | **アーカイブ ZIP**(+ 復元)| 可逆な正本。①が通れば「自分の書出しを自分で読める」が成立する |
| ✅ ③ | **可搬 HTML** | §2-2 の流し込み。閲覧 UI は最小(P7 の Pages product が本番) |
| ✅ ④ | **md ZIP** | 片道。落ちるものを manifest と UI で言う |

🔑 **round-trip test を最初から回す**: 「書出し → 自分の reader で取込 → 元と一致」。
P6c の reader が既にあるので、**②が着地した時点で全形式の検品ができる**。
⚠ 一致の判定は「entries / relations / revisions / asset bytes の**中身**」で行う
(件数だけ見ると、中身が入れ替わっていても通る)。

## 6-2. 段② で決めたこと・残したこと(2026-08-02)

- **復元まで込みで着地させた** ── 「復元できないバックアップはバックアップではない」。
  書出しボタン → ダウンロード → 取り込み直し、を smoke で往復させている
- ⚠ **アーカイブ経路は PKC2 の convert を通さない**。body は既に PKC-Markdown なので、
  `fromPkc2` を通すと**二重変換で壊れる**。`restoreArchive` は lid / relation id の
  衝突回避と asset key の写しだけを行う
- 🔴 **履歴はまだ復元しない**(この段の限界。**ファイルには入っている**)。
  アーカイブは履歴を鎖のまま持つが、復元には逆向きパッチの意味論を worker の
  符号化側と突き合わせる必要がある ── 取り違えると**誤った履歴を書き込む**ので、
  書かない方がまだ回復できる。件数を warning に出している。**次段の仕事**
- **null の正規化は書出し側で行う**(`kind` の NULL → `'full'` / `mime` の NULL →
  `octet-stream`)── 読み手に「null かも」を持ち回らせない

### 🔴 レビューで覆った 2 点(2026-08-02)

**(1) カーソルは並び順と同じ複合キーでなければならない。**
`ORDER BY entry_order, lid` に対して `WHERE entry_order > ?` **単独**で続きを取って
いたので、**境界の順序値を共有する行が全部飛んでいた**。`entry_order` に UNIQUE は
無く、`app-state.ts:230` 自身が「trash 復元と CREATE の並行採番は重複しうる」と
明記している ── つまり**ゴミ箱から複数戻した直後にバックアップを取るだけで踏む**。
実証: 同じ entry_order の 5 件 → **1 件しか出ない**。
⚠ lid だけ持ち回って worker 側で順序値を引き直す形も駄目(その行が消えていると
位置が解決できず先頭から読み直して**重複**する)── カーソルは `{entryOrder, lid}` を
そのまま持ち回る。

⚠ **なぜ test をすり抜けたか**: round-trip test の stub が**配列 index で継続**して
おり、**実装のカーソルより正しかった**。stub が実装の欠陥を迂回していた ──
「スタブは実装の意味論を真似る」ことが要る。実 worker に当てる test を足した。

**(2) 「バッチごとに本文を手放す」は事実に反していた。**
entry ごとの JSON を**文字列のまま** `parts` に積んでいたので、`finish()` まで全
entry の本文が heap に残る。実測で **本文の総量ぶん(96MB)heap が線形に増える**
ことが示された。→ バッチぶんを 1 個の Blob にして積む(文字列は次の周回で回収される)。
🔑 **「コピーしない設計」を主張したいなら、主張どおりに測る**

- 可搬 HTML の閲覧 UI → **読めるだけ**に留める(段③)

(以下は当時の記録)

   `p6c-zip-import-design-2026-08.md` §5-④ で「**実体が手に入らなければ
   着地させない**」と決めてある(PKC2 に読む実装が無く round-trip の参照実装が

3. **md ZIP の frontmatter に何を載せるか** ── 最小(title / archetype / 日付)か、
   PKC3 の全メタか。**外で読む**のが目的なので最小を推すが、user の使い方次第
4. **可搬 HTML の閲覧 UI をどこまで作るか** ── P7 の Pages product と重複する。
   P6d では「読めるだけ」(一覧 + 本文 render)に留めるのを推す
