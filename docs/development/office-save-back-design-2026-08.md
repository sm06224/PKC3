# Office で編集した文書を PKC へ書き戻す(#88 / O4)── 設計

> 🔴 **user 裁定 2026-08-11**:「**保存したら旧版と差し替えるべきです /
> そうでなくては PKC のマークダウンからの参照が崩れます**」

この裁定で、前案(「添付ノートの frontmatter だけ新しい key へ向け直す」)は
**棄却**された。理由は user の言うとおりで、本文に書かれた `asset:<key>` 参照が
**古い bytes を指したまま**残るからである。

以下は「参照が崩れない」を満たす形を、実装できる粒度まで落としたもの。

---

## 1. 何が難しいか ── key は中身から決まる

PKC3 の添付 key は **content addressing**(`key = f(sha256(bytes))`。
user 指示 2026-08-01「ZFS と同じ発想」)。したがって:

> **bytes が変われば key も変わる。同じ key に別の中身を書く操作は、
> この設計には存在しない。**

「差し替え」を実現する道は 2 本しかない。

### 案 A: key を保ったまま bytes を上書きする

一見いちばん素直だが、**dedupe が壊れる**。

`attach.ts` は「入ってくる bytes の hash から key を作り、その key が既に在れば
put を省く」で重複を消している。key `K`(= `f(H1)`)の中身を `H2` の bytes で
上書きすると:

| 後から起きること | 結果 |
|---|---|
| **元の file をもう一度添付する** | hash は `H1` → key は `K` → 「既に在る」と判断 → put を省く → 新しいノートが **編集後の中身を指す** |

⚠ これは**中身の取り違えが、静かに、恒久的に固定される**形である
(CLAUDE.md「壊れを検出する材料を捨てない ── 誤りが自己証明されて固定される」)。
救うには dedupe を「key の有無」から「key + hash の一致」へ変え、
不一致のときの**別 key の割り当て規則**を作ることになる ── content addressing を
やめるのと同じである。**採らない。**

### 案 B: 新しい key に置き、**参照している側を全部書き換える**(推薦)

```
保存 → 新 bytes を新 key(= f(H2))で put
     → 旧 key を参照している **生きている本文** を全部 新 key へ書き換える
        ・添付ノートの frontmatter(attachment.asset_key / size / hash)
        ・ほかのノートの本文にある asset:<旧key> / pkc://<cid>/asset/<旧key>
     → 旧 bytes は **消さない**(下記 §3)
```

user から見た振る舞いは「差し替え」そのものになる ── **どこから参照していても、
次に見たときは新しい中身が出る**。key は内部の識別子なので user には見えない。

---

## 2. 🔴 いちばん危ないところ ── 「広く拾う」と「狭く当てる」を混ぜない

CLAUDE.md の既存規律(実際に 1 度踏んでいる):

> 「どれを含めるか」は false-keep 側(広く拾う)、「どこを書き換えるか」は
> 誤爆しない側(狭く当てる)── 片方の規則をもう片方に流用すると、誤差が
> **データ欠損の向き**へ反転する。

`features/asset/asset-ref-scan.ts` は **わざと広い**(key を substring で探す /
2 回 unescape する)。GC が「まだ使われている」を見落とすと**実データが消える**からで、
誤差は keep 側にしか出さない設計になっている。

**この規則を書き換えに流用してはならない。** 散文の中に key が偶然現れただけの
場所まで置換してしまう。書き換えは**狭く当てる**(`asset:<key>` /
`pkc://<cid>/asset/<key>` という**構文**で拾い、原文 splice する)。

### 取りこぼしたらどうなるか ── **欠損ではなく、古いまま**

狭い書き換えが escape 済みの綴り(`asset:ast\-key`)を落としたとする。
そのノートは**旧 key を指したまま**になる。しかし §3 のとおり旧 bytes は生きているので、
**壊れるのではなく「そこだけ古い版が出る」**。⚠ そのうえで:

> 書き換えのあとに**広い規則でもう一度走査**し、旧 key を指したままの本文が
> 残っていたら **件数を user に出す**。黙って「差し替えました」と言わない。

これで「静かに古いまま」を作らない。

## 3. 🔴 旧 bytes をどう持つか ── 台帳を作る(2026-08-11 の裁定)

> user:「**アセットの履歴は全バイトにならざるを得ないよね?ならば容量 Limit と
> 世代 Limit の両方を制約にしたい / 明示的スナップショットと自動履歴は
> 区別したい(フォークのように)**」

### なぜ全バイトなのか

本文(テキスト)の履歴は**パッチの鎖**で持っている(P5c)。バイナリにはそれが効かない ──
`.docx` / `.xlsx` / `.pptx` は ZIP なので、1 文字直すだけで**圧縮ブロックごと全部変わる**。
差分を取っても縮まないので、**1 版 = 1 バイト列まるごと**にならざるを得ない。

### 🔴 初版の設計は上限を持っていなかった(これが穴だった)

この doc の初版は「旧 bytes は revisions の snapshot が参照しているので消えない」と書いた。
それは**上限が無いという意味**である:

```
テキストの履歴は 100 世代まで保つ
  5MB の .docx を 100 回保存  →  500MB
 50MB の .pptx を 100 回保存  →  5GB
```

しかも user はそれを**制御できない**(テキスト履歴の副作用として貯まるので、
どの画面にも出てこない)。**採らない。**

### 採る形 ── 添付の版を明示的な台帳で持つ

### 🔴 置き場は **添付ノートの frontmatter**(新しい保管庫を作らない)

```
attachment.history:
  ['2026-08-11T04:00:00Z|auto|ast-xxx|123456|', '…|pinned|ast-yyy|98765|初稿']
```

別の保管庫(IDB / sqlite の新テーブル)に置く案から**乗り換えた**。frontmatter だと
3 つが**タダで手に入る**:

| | 別の保管庫 | frontmatter |
|---|---|---|
| GC が「まだ使われている」と分かるか | **判定を書き足す**(片方だけ見るとフォーク先の現物が消える) | **key が本文に出るので、既存の広い走査がそのまま拾う** |
| バックアップ(`.pkc3.zip`)に入るか | 入れる処理が要る | **本文なので入る** |
| 版の増減そのものの履歴 | 無い | **テキスト履歴に残る**(いつ pin したかも追える) |

⚠ とくに 1 行目 ── §「フォーク」で書いた「判定を 2 か所で見る必要がある」危険が、
**そもそも発生しない**。
⚠ 制約: frontmatter が持てるのは**平たい値の配列**まで(オブジェクトの配列は不可)。
なので 1 版 = 1 行の区切り文字列にする。**ラベルは最後**に置き、`|` を含んでよい
(4 個目までで分割し、残りをラベルにする ── 逃がし文字を作らない)。

### 🔴 列には「過去の版」だけを入れる

**いまの版は `attachment.asset_key` に在り、列には入れない。**
こうすると「いまの版は絶対に落ちない」が**規則ではなく構造**になる ── 落としようがない。

### 🔴 台帳から外すことと、bytes を消すことは別

上限で版を**列から外しても、bytes はその場では消さない**。その `assetKey` は
別のノートの本文・別の添付の台帳・フォーク先の「いまの版」が**まだ指しているかも
しれない**からである。⚠ 実際に消すのは既存の「使っていない添付を消す」だけ ──
判定はそこ 1 か所のまま(規則を 2 本にしない)。誤差は **keep 側にしか出ない**。

| | 自動履歴(`auto`) | 明示スナップショット(`pinned`) |
|---|---|---|
| いつ増えるか | 保存で書き戻すたび | user が「この版を残す」を押したとき |
| **世代 Limit** | 1 添付あたり **5 世代**(既定) | 掛からない |
| **容量 Limit** | 添付の履歴 **合計 200MB**(既定) | 掛からない |
| 溢れたら | **古い自動履歴から落ちる** | 落ちない |
| 使用量の表示 | 数える | **数える**(上限の外だが、見えないと積む) |

- 🔴 **いまの版は絶対に落とさない**(上限の対象は「過去の版」だけ)
- 🔴 **2 つの Limit は設定にする** ── user 指示「予算は手違いの検出であって、
  サイズを守らせる規律ではない」と同じ扱いで、**引き上げられる形**にする
- 既定 5 / 200MB の根拠: Office 文書は 0.1〜5MB が大半 / 200MB は Office 一式(77MB)と
  同じ桁で、ブラウザの quota に対して十分小さい。⚠ **出発点であって規律ではない**

### 🔑 これでテキスト履歴とバイトが切り離せる

台帳が「生きている参照」になるので、添付のバイトの寿命は**台帳が決める**。
テキスト履歴の副作用ではなくなる。

⚠ 帰結: 古いテキスト履歴へ戻したとき、その本文が指す添付の版が**上限で既に
落ちていることがある**。そこは**既にある表示**(`data-pkc-asset-missing` /
「添付が見つかりません」)に落ちる ── 新しい壊れ方を作らない。

### 🔀 スナップショットから**フォークする**(裁定 2026-08-11「可能なら B でやってくれていい」)

pinned な版に **「この版から新しい添付を作る」** を付ける。押すと:

```
新しい添付ノート(新 lid)ができ、その版の assetKey を指す
  → 題名は「<元の題名>(<ラベル or 日付>)」
  → 以後、元のノートと新しいノートは **独立に育つ**
```

🔑 **bytes は複製されない。** content addressing なので、両方が**同じ blob を指すだけ**
── 追加コストはほぼゼロである(これが「可能なら」の答え: 可能で、しかも安い)。

⚠ **帰結: blob の寿命は「参照している全部」で決まる。** 上限で版を落とすときは、
その `assetKey` を **① 生きている本文 ② すべての添付の台帳** のどちらかがまだ
指していないかを見てから消す ── 片方だけ見ると、フォークした先の現物が消える。
🔑 判定は既存の広い走査(`asset-ref-scan.ts`)に**台帳を足すだけ**にする
(規則を 2 本にしない)。

⚠ フォークした先の台帳は**空から始まる**(その版が「いまの版」になるだけで、
元の履歴は引き継がない)── 引き継ぐと同じ bytes が 2 つの台帳で二重に数えられ、
容量 Limit の意味が壊れる。

## 4. 経路(どこに何を置くか)

```
[別窓 host.html]                    [PKC3 本体]
  LO が /work/<name> へ保存
    ↓ FS の mtime/size を監視
  bytes を読む
    ↓ 放送 saved { name, bytes }
                                    OfficeWindow が受ける(既に実装済み)
                                      ↓
                                    書き戻しの判断(新 module)
                                      ・hash → key
                                      ・put(新 key が未知なら)
                                      ・旧 key を指す本文を集める(広い走査)
                                      ・狭い規則で splice して persist
                                      ・書き換え残りを数えて報告
```

| file | 役割 | 新規 / 既存 |
|---|---|---|
| `public/office/host.html` | 保存を検知して bytes を放送する | 既存に追記 |
| `src/features/asset/asset-ref-rewrite.ts` | **狭く当てる**書き換え規則 | 🆕 |
| `src/adapter/platform/office/office-save-back.ts` | 判断(put → 書き換え → 報告) | 🆕 |
| `src/features/flavor/attachment-versions.ts` | 版の台帳(読み書き / 上限で落とす)── **純関数** | 🆕 |
| `src/adapter/state/app-state.ts` | 本文を差し替える要求 / ack | 既存に追加 |
| `src/adapter/state/store-effects.ts` | disk から読んで splice して persist | 既存の `REQUEST_TILE_UPDATE` と同型 |

⚠ `main.ts` には**判断を置かない**(原文 pin の test しか無い面である)。

### 保存の検知(host 側)

LO の保存は wasm の MEMFS へ落ちる。`FS.stat(path)` の `mtime` / `size` を
1 秒ごとに見て、**変わってから 1 tick 落ち着いたら**読む(書き込み途中を掴まない)。

⚠ 「Ctrl+S を外から撃つ」形にはしない ── LO の保存経路を外から起こす手段が
無く、押せたつもりで何も起きない導線になる。**user が LO の中で保存する**のが起点。

## 5. 守る主張(test で pin するもの)

1. 🔴 **空の保存で添付を壊さない**(既に `OfficeWindow` で 1 段止めている)
2. 🔴 **書き換えは狭く当てる** ── 散文に偶然現れた key を置換しない
3. 🔴 **広い走査で残りを数える** ── 書き換え残りがあれば件数を出す
4. 🔴 **旧 bytes を消さない** ── 履歴からの復元が生きる
5. 🔴 **中身が同じなら何もしない**(hash が同じ = 保存しただけで内容は不変)
6. 🔴 **編集中・整理中は書き戻さない**(既存の gate と同じ扱い)
7. 添付ノートの **題名と lid は変わらない**
8. 🔴 **世代 Limit と容量 Limit の両方が効く** ── 片方だけでは 50MB × 5 世代が通る
9. 🔴 **いまの版は絶対に落ちない**(上限は「過去の版」にしか掛からない)
10. 🔴 **`pinned` は上限で落ちない**。ただし**使用量には数える**(見えないと積む)
11. 🔴 **フォーク先が指している bytes を落とさない** ── 上限の判定は
    「生きている本文 + すべての台帳」で見る(片方だけ見るとフォーク先が壊れる)
12. 🔴 **フォークで bytes を複製しない**(同じ blob を指すだけ)

## 6. user に見える変化(マニュアル / お知らせ)

- Office の窓で保存すると、**PKC の添付がその場で新しくなる**
- 本文に貼った参照(`asset:…`)も**一緒に新しくなる**
- 古い版は **5 世代 / 合計 200MB** まで残る(どちらも設定で変えられる)。
  溢れたら**古い自動履歴から落ちる**
- **この版を残す**を押した版は、上限で落ちない(使用量には数える)
- **この版から新しい添付を作る**(フォーク)── その版を指す別のノートができ、
  以後は独立に育つ。⚠ **中身は複製されない**ので容量は増えない
- ⚠ 書き換えられなかった参照があれば、**件数を出す**
