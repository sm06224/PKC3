# UI 点検 ── 「業務画面」はどこまで届いているか(2026-08-04、Full HD 実測)

> user の問い: 「PKC3 の UI 設計に**電子カルテの見た目**を導入するようにしているが、
> 率直に言ってどう思うか」

## 0. 測り方

- **1920×1080 / dpr 1** の実 Chromium(persistent profile)で、**中身のある状態**を作って撮った
  ── ノート 12 件(表・図・箇条書きを含む)+ フォルダ / 表 / ログ 各 1 件 = 計 15 件
- 撮った面: 起動直後(空)/ 一覧+ノート / 図のあるノート / 編集中 / 設定 / フォルダ / アプリ / 端末風テーマ
- **pageerror・console.error は 0 件**(見た目の問題であって、壊れているのではない)
- ハーネスは使い捨て(`scratchpad/visual-fullhd.mjs`)。⚠ 常設するなら nightly 側へ

## 1. まず言葉の確認 ── リポジトリに「カルテ」は 1 度も出てこない

`grep -rn "カルテ"` は **0 件**。実際に書いてあるのは user 指示 2026-08-03 の
**「業務画面」**で、その中身は 5 つ ── 高密度だが詰まっていない / 同じものが常に同じ場所にある /
1 画面で完結する / マウスだけで完結しキーボードは近道 / **地は無彩色、色は情報にだけ**。

つまり **「電子カルテ」は指示語ではなく、user が実物として思い浮かべている像**だと受け取りました。
そのうえで率直に答えます。

## 2. 率直な意見

### 方向は正しい。ただし**いまの画面はまだ「業務画面」ではない**

**方向を支持する理由**: ノートアプリの大半は逆(chrome を隠す / ハンバーガー / モーダル多用)へ行き、
**件数が増えると操作が遅くなる**。「常に同じ場所」「隠さない」は、増えても遅くならない数少ない作法です。
PKC3 が P8 でメニューを畳むのをやめ、3 列固定にしたのは正しい判断だと思います。

**それでも「まだ業務画面ではない」と言う理由**: 業務画面が高密度を許されるのは、
**どの区画も毎回使う生きた情報を載せている**からです。いまの PKC3 は逆で ──

> **要らない所が広く、要る所が空いている。**

Full HD で数えた実測がそれを示します(grid は `minmax(200px,18vw) 1fr minmax(220px,20vw)`):

| 区画 | 幅 | 実際に載っているもの |
|---|---|---|
| 左(一覧) | 346px | **題名だけ**(日付も更新も状態も無い) |
| 中央(本文) | 約 1190px | 上詰め。ノート 1 件で**下に 600px 前後の白** |
| 右(情報) | **384px** | 4 行(題名 / 種類 / 作成 / 更新)+ ボタン 3 個。**うち 2 行は「—」** |

384px を 4 行に使っておいて、そのうち半分が空欄です。電子カルテがこの使い方をしたら、
それは**カルテの良い所ではなく悪い所**を写しています。

### 「カルテらしさ」は見た目からは来ない

電子カルテが成立しているのは、① 訓練された人が ② 毎日 8 時間 ③ 固定スキーマの記録を入れるからです。
個人のノートアプリにはこの 3 つが**どれも無い**。だから**見た目**(帯・小さい字・詰めた格子)を
写すと、密度の不快さだけが移ります。写すべきは規則で、私が要ると思うのは 3 つだけです:

1. **同じ情報は常に同じ場所にある**(→ 既に達成済み。3 列固定・モードで動かない)
2. **行は走査できる**(→ **未達**。題名しか無い行は目で追えない)
3. **面は用途で区切られ、区画は満たされている**(→ **未達**。右列が空、中央が広すぎ)

## 3. 良かったところ(変えないほうがよい)

- **3 列が編集に入っても動かない**。編集開始で列幅が変わらないのは実測で確認した
- **主要な導線を隠していない**。取り込む / バックアップ / 閲覧用 HTML / Markdown が常に見える
- **編集が左原文・右プレビューの 2 面**で、図が焼き上がった PNG として即座に出る
- **書式パネルが文字ラベル**(見出し1・太字・表・図…)。アイコンだけより業務画面に合っている
- **端末風の緑をテーマの 1 つへ降ろした判断**は正しい。既定の無彩色+濃緑 1 色は落ち着いている

## 4. 見つけた問題(優先度順)

### 🔴 P1. 情報列が嘘をついている(**バグ**)

作成・更新が**常に「—」**。原因は実装にあります:
`app-state.ts:991` が `createdAt: null` を入れ、worker が `datetime('now')` を刻むので、
**その値は次の boot まで主スレッドに戻ってこない**。

実測で確認: 作った直後は `—`、**再読込すると `2026/08/04` が出る**。
つまり user が今日書いたノートの情報列は、今日のあいだ空欄です。
→ 確定時に worker が刻んだ値を返して集約へ載せる(**S**)。

### 🔴 P2. 絵文字アイコンが方針と正面から衝突している

`icons.ts` は 📄📁🚀📥💾🌐📝🧹📎✏🗑 …。絵文字は **多色で、色も形も OS 依存**です。
user 指示は「**地は無彩色、色は情報にだけ**」── 絵文字は情報を持たない所に色を撒くので、
**この 1 か所だけで方針が破れている**。加えて 🚀(アプリ)は業務画面の語彙ではありません。
→ 単色の線画(inline SVG + `currentColor`)へ置換(**M**。数は 20 個ほど)。

### 🟠 P3. 一覧の行が走査できない

行は「種別チップ(絵文字)+ 題名」だけ(`sidebar.ts:149-153`)。
**日付が無いので、どれが最近かが分からない**。15 件でも分からないので、
500 件では一覧が機能しません。
→ 行を「題名 / 右端に更新日(細字)」の 1 行 2 情報にする(**S**。P1 の値が要る)。

### 🟠 P4. 右列が空、中央が広すぎ

- 右 384px に 4 行 → **幅を詰める**か、**載せるものを増やす**かの二択
- 中央は読み幅の上限が無い(`app.css` に本文向けの `max-width` が無い)。
  Full HD では 1 行が 1190px まで伸び、日本語で 70 文字を超える ── 読みにくい
→ ① 本文の読み幅を上限つきに(全角 45 文字前後)。**ただし表・図・コードはフル幅**
  ② 空いた右側に「関係」「添付」「履歴の直近」を載せる(= A-7 と合流)。または右列を 260px へ(**S**)

### 🟠 P5. 保存の導線が二重で、語彙も違う

編集中の画面に **同時に 4 つ**出ています ── 上に `保存` / `キャンセル`、下に `保存して解放` / `編集を破棄`。
同じことを 2 か所で、違う言葉で聞いている状態です。業務画面で最も嫌われる形です。
→ 1 か所に寄せ、語彙を 1 つに(**S**)。⚠ どちらを残すかは「押す場所」の一貫性で決める

### 🟡 P6. 設定がワーカーのログ

設定画面の中身は **配色 1 つ + ワーカー計器 + ジョブのログ**。user 向けの設定が 1 個しかありません。
→ user 向け(配色 / 既定の種類 / 追記の挙動 / 履歴数)と開発者向け(計器)を分ける(**S**)

### 🟡 P7. 初回起動の中央が完全な白紙

1190×1000px に**何も無い**。右列だけが「左の一覧から選ぶと…」と言っています。
→ 中央に「新規で作る / 取り込む」の 2 択を置く(**S**)

### 🟡 P8. 「一覧」タブと「フォルダ」タブがほぼ同じ

同じ 15 件が並ぶ。違いは階層とゴミ箱の有無だけで、しかも行の見た目が違います
(一覧は種別チップ付き、フォルダは無し)。P8 段⑤ で「上の帯と左ペインのかぶり」を解消したのに、
**タブ間に別のかぶりが残っている**。
→ 役割を分ける(一覧 = 全件+絞り込み / フォルダ = 階層専用)か、統合する(**S**)

### 🟡 P9. 細部

- 編集中のテキストエリアの**緑の枠が太い**(彩度の面積が大きい)── 1px + 内側の淡色へ
- **「図を保存」の位置が図と揃っていない**(図の左端 x=360 に対しボタン x=762)
- 下部の操作バーが **2 行に不均等に折り返す**(3 個 + 2 個で幅がばらつく)

## 5. 改善案のまとめ(選択用)

| # | 案 | 効く方針 | 見積り |
|---|---|---|---|
| 1 | 作成・更新を確定時に返す(**バグ修正**) | 画面が嘘をつかない | S |
| 2 | 絵文字 → 単色線画アイコン | 地は無彩色、色は情報にだけ | M |
| 3 | 一覧の行に更新日を入れる | 行が走査できる | S |
| 4 | 本文に読み幅の上限(表・図は除く) | 高密度だが詰まっていない | S |
| 5 | 右列を詰める or 中身を足す | 区画を満たす | S |
| 6 | 保存導線を 1 か所・1 語彙に | 迷わせない | S |
| 7 | 設定を user 向けと計器に分ける | 1 画面で完結 | S |
| 8 | 初回起動に案内を置く | 迷わせない | S |
| 9 | タブのかぶりを解く | 同じものは 1 か所 | S |
| 10 | 細部(枠・ボタン位置・折返し) | 詰まっていない | S |

⚠ **1 → 3 → 4 → 5 の順**を薦めます。1 が無いと 3 が作れず、4 と 5 は対になっている(中央を締めた
ぶんを右へ回すか、右を削って中央へ返すか)ので、続けて決めるほうが手戻りが少ない。

## 6. 結論

**「電子カルテの見た目」を目標にすること自体は薦めません。** 写すと density の不快さが移ります。
ただし **user が本当に言っている「業務画面」の 5 条件は正しく、続けるべき**です。

いま足りないのは見た目の様式ではなく、**区画が仕事をしていないこと**の 3 点 ──
① 行に日付が無い ② 右 384px が空 ③ 中央に読み幅が無い。
この 3 つを埋めれば、様式を足さずに「業務画面らしさ」は出ます。

⚠ そして絵文字は落としてください。**あれが唯一、方針と正面から矛盾している要素**です。
