# Office のストレージを PKC にする(#205 / #88 の O4・O5)── 2026-08-16

> 🔴 **user 指示 2026-08-16(不可侵)**:
> 「**全て PKC を動線にしたい / PKC をストレージとして使用するイメージです**」
>
> これは先行して聞いた 2 点(別名保存の扱い / 新規文書の題名)への回答であると同時に、
> **設計の枠そのものを決めた指示**である ── 「保存を検知して PKC へ写す」ではなく、
> **Office から見えるファイルシステムが PKC である**。

## 0. 何を決めたいか

LO wasm の **開く / 保存 / 別名で保存 / 新規作成**が、すべて PKC のノートを相手にする形。
⚠ ここで決めるのは**土台の選び方**であって、UI の細部ではない。

## 1. 事実(実測。推測ではない)

### 1-1. いま保存は wasm の中で完結して消える

| 手 | 観測(2026-08-15、配布中と同版で 2 回) |
|---|---|
| Ctrl+S(新規文書) | LO 内蔵の Save ダイアログ。`Look in: /home/web_user`、ツリーは `Computer` と `web_user` **のみ** |
| Enter | MEMFS の木が 37 → 38 件。**`/home/web_user/Untitled 1.odt`(8,666 B)が出現** |
| Ctrl+Shift+S | 同じダイアログ・同じ行き先 |

🔴 **ブラウザのダウンロードの口はコードに無い** ── `showSaveFilePicker` / `showOpenFilePicker` は
`soffice.js` / `qtloader.js` / **`soffice.wasm` 本体**のいずれにも **0 件**
(空振り防止の対照群として `registrymodifications` / `web_user` は同じ grep でヒットする)。
→ **窓を閉じれば消える。**

### 1-2. PKC → Office の往路はコピー、復路は無い

```
IDB Blob → main.ts で Uint8Array 化(heap に載る)→ BroadcastChannel(構造化複製)
        → host.html が FS.writeFile('/work/<name>') → LO
```
復路は 1 本も無い。`planSaveBack`(純関数)は**呼び出し元 0 件**のまま全 test 緑だった。

### 1-3. 🔴 いまの一式に積んである FS は **MEMFS だけ**(2026-08-16 実測)

配布中の `soffice.js` を数えた:

| | 件数 |
|---|---|
| `MEMFS` | 1 |
| `WORKERFS` | **0** |
| `IDBFS` | **0** |
| `NODEFS` | **0** |
| `FS.mount` | 1 |
| `createLazyFile` | 1 |

🔑 **`FS` は JS から触れる**(`host.html` が既に `FS.writeFile('/work/…')` を呼んでいる)。
→ **JS 側で独自の FS を登録することは、焼き直さなくてもできる**(WORKERFS 自身も純 JS)。

### 1-4. ⚠ ただし FS の read は**同期**である

Emscripten の FS は `stream_ops.read` が同期。PKC の bytes は **IDB(非同期)**なので、
**そのままでは遅延読み込みができない**。WORKERFS が Blob を扱えるのは
`FileReaderSync` を使うからで、**それは worker の中でしか使えない**。

## 2. 道は 3 本

### (a) 全部を先に MEMFS へ載せる

窓を開くときに Office 添付を全部 `FS.writeFile` する。

- ✅ 焼き直し不要・実装が最短
- 🔴 **heap に全部載る**。添付上限は 250MB なので、集めた人ほど破綻する
- 🔴 「ゼロコピー・生成物のライフサイクル終端での即破棄」(user 指示 2026-07-27、不可侵)と正面衝突

### (b) 独自 FS を JS で登録し、**開く直前に材料を渡す**

`FS.mount` に自前の node_ops / stream_ops を登録して `/pkc` を生やす。
一覧(名前・大きさ・日付)は PKC の meta から作り、**bytes は開く直前に親から transfer** して
その 1 件だけ heap に置く。閉じたら捨てる。

- ✅ **焼き直し不要**(`FS` は既に触れる)
- ✅ 一覧は meta だけなので軽い ── 1000 件あっても bytes は 0
- ⚠ **同期 read の壁**: LO のダイアログで選ばれた瞬間に bytes が要る。
  → 「一覧に出す = meta」「選ばれたら read が来る」ので、**read が来た時点で bytes が無いと落ちる**。
  回避は ①よく使う分を先に載せる ②`FS` の read を**待たせられる形**にする(要調査)
- 🔴 **ここが唯一の未検証点**であり、道の成否を決める

### (c) WORKERFS を積んで焼き直す

`-lworkerfs.js` を足して焼く。Blob を**コピーせず**マウントでき、`FileReaderSync` で同期 read できる。

- ✅ **ゼロコピーの不可侵指示にそのまま乗る**(bytes は Blob のまま)
- ✅ 上流の仕組みなので自前の FS を保守しなくてよい
- 🔴 **read-only** ── 保存側は別に要る(書き込みは MEMFS の `/pkc-out` を watch する形)
- 🔴 **焼き直しが要る**(1 ビルド ≒ 4 時間)
- ⚠ **LO のファイル I/O が pthread の worker で走るか**が前提。走らないなら `FileReaderSync` が使えない ── **未検証**

## 3. 推薦(1 つ)

> **(c) を本線にし、(b) の調査を先に 1 回だけ回す。**

理由:

1. **user の不可侵指示(ゼロコピー)に素直に乗るのは (c) だけ**である。(a) は明確に反する。
2. (b) は焼き直し不要で魅力的だが、**同期 read の壁が未解決**で、そこが崩れると設計ごとやり直しになる。
   ⚠ 「たぶん待たせられる」で実装に入るのは、2026-08-14 に 7 回転を溶かした型
   (**上流を読まずに推測でレバーを回した**)と同じである。
3. (c) の弱点(read-only)は**実害が小さい** ── 保存は別経路(`/pkc-out` を watch)で成立し、
   それは (b) でもどのみち必要になる。

**先に回す 1 回の調査**(これで道が決まる):
- LO wasm の **ファイル I/O がどのスレッドで走るか**を実測する
  (pthread の worker なら `FileReaderSync` が使える = (c) 成立)
- `FS` の `stream_ops.read` を**非同期に待たせられるか**を実測する(= (b) の成否)

⚠ **どちらも「1 job = 1 主張」で測る。** 同じ実験に 2 つを載せない。

### 覆る条件

- (b) の同期 read が**待たせられる**と実測できたら、**焼き直し不要**なので (b) が勝つ
- LO の I/O がメインスレッドで走ると分かったら、(c) は成立しないので (b) か (a) へ倒れる

## 5. 危ないところ

1. **放送は全タブに届く** ── 素直に購読すると 2 タブで添付が 2 回作られる(#177 の follower と噛み合わせ)
2. **`host.html` は bundle されないので unit が 1 件も届かない**。smoke の pack は数十バイトの偽物なので
   **MEMFS の監視は smoke でも走らない** ── 検証は**実 LO を積んだ probe しか手が無い**
3. **観測点**は「放送を出した」ではなく「**添付の key が変わり、本文の `asset:` が新しい key を指した**」まで見る
   (`planSaveBack` が誰からも呼ばれないまま 2,000+ tests が緑だった前例)
4. **窓の使い回し**(`location.replace`)は**未保存を無警告で捨てる** ── 書き戻しを足すと
   「読み物を差し替えた」から「**編集を捨てた**」へ意味が変わる
