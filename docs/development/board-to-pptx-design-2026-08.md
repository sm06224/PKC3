## 3. 段の切り方

## 4. 段① の設計

### 4.1 何を読むか

板の塊(`.pkc-place`)の**開き行の属性**と**中身**:

```
:::format{.pkc-place x=120 y=64 w=240 h=96}
### 課題
- 見積もりが出ていない
:::
```

- `x` / `y` … 板の左上からの px
- `w` / `h` … 塊の大きさ(⚠ 省略時の既定は描画側の規則に合わせる ── **数え直さない**)
- 中身 … そのまま `<p:txBody>` の段落へ(既存の `lineXml` を使う)

### 4.2 座標の換算(EMU)

DrawingML の単位は **EMU**(English Metric Unit)= 914400 EMU / inch。
板は px なので **96 dpi 換算**で `EMU = px * 9525` とする。

⚠ **決めること**: 板が既定のスライド(既存の `pptx.ts` のスライド寸法)より
大きいとき、①縮めるか ②はみ出させるか ③スライドを分けるか。
🔑 **推薦は ①縮める**(1 枚に収める)── 叩き台なので**全体が見える**ほうが価値が高い。
⚠ 縮めるときは**縦横比を保つ**(文字だけ相対的に大きくなるのは許容する)。

### 4.3 どのスライドへ載せるか

既存の `splitIntoSlides` は見出しでスライドを切る。
🔑 **板の塊は「1 枚の板 = 1 スライド」**にする ── 板は 1 つの絵なので、
途中で切ると意味が壊れる。⚠ 板の直前の見出しがあれば、それをそのスライドの題にする。

### 4.4 検査(空振りさせない)

- 🔴 **書き出した `.pptx` を開いて `<p:sp>` の `<a:off>` が板の `x=` と対応する**ことを見る
  ── ⚠ 「`<p:sp>` が在る」で止めない(既存の文字の塊も `<p:sp>` なので、
  **それに満たされる**。CLAUDE.md §1「範囲が広すぎて別物に満たされる」)
- 🔴 **板を 2 つ置いて、2 つの `<a:off>` が違う**ことを見る(1 つだと位置を
  無視しても通る)
- ⚠ **対照群**: 板でない普通の段落は、これまでどおりの位置(自動レイアウト)に出る

## 5. ⚠ やらないこと / 決めていないこと

- 🚫 **新しい描画アプリを持ち込まない** ── 位置が本文の外に出ると、板は
  PKC の外へ持ち出せなくなる(「本文が正本」が壊れる)
- **逆方向(Office → PKC)** ── user 自身が「これから検討かね?」と保留にしている
- **Word 側(`docx.ts`)** ── 同じ橋が要るかは未調査
- **図形の色・線** ── 段① では `<a:noFill/>` のまま(既存の文字の塊と同じ)

# 段③ の設計(2026-09-14 追記)── 板どうしを線で繋ぐ

> 2026-09-14 に**段②(形を選べる)が着地**しました(main `000a123` の 1 つ前、PR #910)。
> この節は、そのとき「ここから設計が重くなる(繋ぎ先の同一性が要る)」と書いた**段③**の設計です。

## 7. 🔴 「繋ぎ先の同一性」は、思っていたより小さい問題でした

実装を全数で読んで、**重いと思っていた理由が 2 つとも崩れました**。

### 7.1 CLAUDE.md の戒めは、ここには当たらない

CLAUDE.md(2026-08-19 の裁定)にこう在ります:

> ③ 名前か id か → **名前**(タグが既に名前で出荷済み。id を本文に書くと、
>   復元が body を書き換えない既知の穴を踏む = **静かに壊れる**側へ倒れる)

🔑 **禁止の目的は「復元が追随できない参照を作るな」**です。あの裁定が相手にしていたのは
**ノートをまたぐ参照**(グループの id を、別のノートの本文が指す)── 片方のノートを
履歴から戻しても、**もう片方は直らない**。だから静かに壊れます。

⚠ **ここは違います。** 線と、繋がれる 2 枚の板は、**同じ 1 つの本文の中**に在ります。
本文を復元すれば 3 つとも**同時に**戻るので、**追随できない参照が原理的に作れません**。

🔑 これは CLAUDE.md の「**戒めは対象ではなく目的に照らして検算する**」の実践です ──
「id を本文に書くな」と読むと止まりますが、目的で読むと**同じ本文の中なら通ります**。

### 7.2 記法は既に id を持っている(新しい記法を足さない)

`block-directive-attrs.ts` が Pandoc 風の `{#id .class}` を**既に解釈**し、
`markdown-render.ts` が `id="…"` として出します。

⚠ **PKC3 に「システムが id を発行して本文へ書き込む」前例は 0 件**です(実測)──
いま在る id は全部 ①既に別の理由で在る lid の再利用 か ②本文に書かず毎回導出する slug。
🔑 だから**ここが 1 例目**になります。だからこそ 7.1 の検算が要りました。

## 8. 記法

```
:::format{#a .pkc-place x=40 y=40 w=200 h=100 shape=round}
はじめ
:::

:::format{#b .pkc-place x=320 y=40 w=200 h=100 shape=diamond}
判断
:::

:::format{.pkc-line from=a:right to=b:left line=elbow}
:::
```

🔑 **`from=` / `to=` / `line=` は汎用のループを通る**ので、DOM には**自動で**
`data-pkc-from` / `data-pkc-to` / `data-pkc-line` が出ます(段② の `shape=` と同じ)。
⚠ つまり書くのは**描く側だけ**です。

⚠ **線は「置いた物」ではありません** ── 座標を持たず、**2 枚の板の位置から毎回引く**。
🔑 だから**板を動かせば線も付いてきます**(座標を書くと、動かしたときに置き去りになる)。

### 8.1 🔴 **アンカー(接続点)**── user 裁定 2026-09-14 で足りないと分かった所

user 裁定(こちらの解釈、2026-09-14):**線の形は 1 つに決めず選べるようにする。
まっすぐと直角だけでなく曲線(ベジェ)も要る。そして、これがコネクタである以上、
線を繋ぐ先=アンカー(接続点)が要る ── 線を束ねるためにも。**

🔴 **こちらの 1 稿目には、アンカーが 1 つも無かった。** `from=a to=b` は
「**どの板に**繋ぐか」しか持っておらず、「**その板のどこに**繋ぐか」が書けません。
⚠ 帰結は 3 つとも user が見る所で出ます:

| アンカーが無いと | 画面で何が起きるか |
|---|---|
| 繋ぎ先が板の中心しか無い | 線が**板の上を横切って**中心まで刺さる |
| 🔴 **束ねられない** | 3 本が同じ板へ来ても**バラバラの所**に当たる(user が言った「線を束ねる」ができない) |
| 向きを指定できない | 「右から出て左へ入る」が書けない ── **直角の折れ方が決まらない** |

🔑 **だから板は 4 つの接続点を持ちます**(PowerPoint と同じ考え方):

```
        top
         │
 left ──[板]── right
         │
       bottom
```

> 🔴 **1 稿目は「5 つ(+ center)」と書いていたが、誤りだった**(2026-09-15 に実測)。
>
> ⚠ ①**この節自身の被害の表と食い違う** ── 表の 1 行目が
> 「繋ぎ先が板の中心しか無い → 線が**板の上を横切って**中心まで刺さる」と、
> **中心こそが被害**だと書いている。
> ⚠ ②そして**形式に中心が無い**。四角へ `idx` 0〜7 の線を出して LibreOffice に
> 読ませたら:
>
> | idx | どこに付いたか |
> |---|---|
> | 0 / 1 / 2 / 3 | 上 / 左 / 下 / 右 |
> | 🔴 **4〜7** | **(0, 0) に落ちた**(= 解決できず、線が壊れる) |
>
> 🔑 つまり `center` は**コネクタとして書けない** ── 画面だけ中心に刺して
> 書き出すと、**PowerPoint では線が原点へ飛ぶ**(画面と配った先が食い違う、
> いちばん気づけない壊れ方)。
> 🔑 だから `:center` は**受けずに、理由を言って断る** ── 黙って無視すると
> 「書いたのに効かない」になり、user は綴りを間違えたと読む。
> ⚠ 実装(`place-line.ts` の `PlaceAnchor`)は最初から 4 つで、
> **doc の側だけが間違っていた**。

- 綴りは **`from=<id>:<接続点>`**(`a:right`)。⚠ **省いてよい** ── 省くと
  **いちばん近い接続点**をこちらが選びます(手で書かせない)
- 🔑 **同じ接続点へ来た線は、そこで束ねます** ── 1 点に集めるので、
  「どこから来たか」が読める(user 裁定の「束ねるためのアンカー」がこれです)
- ⚠ **接続点は板の属性ではありません** ── **線の側**に書きます。
  板は位置と大きさしか持たないので、**板を書き換えずに繋ぎ替えられます**

### 8.2 線の形(3 つ。**線ごとに選べる**)

| `line=` | 画面で何が出るか | 既定 |
|---|---|---|
| `straight` | **まっすぐ 1 本**。どこへ動かしても必ず届く | 🟢 **これ**(省いたとき) |
| `elbow` | **直角に折れる**(横 → 縦 → 横)。配線図の見た目 | |
| `curve` | 🆕 **曲線(ベジェ)** ── 接続点の向きへいったん出てから、相手の接続点の向きへ入る | |

⚠ **`curve` は接続点と対で効きます** ── 出る向き・入る向きが決まって初めて
「ふくらみ方」が決まります(だから §8.1 が先に要ります)。
🔑 **既定を `straight` にする理由**:省略して書いたときに**必ず届く**形だからです
(`elbow` は折れ場所しだいで板の上を通り、`curve` は向きが要る)。

## 9. 身元をどう振るか(3 案)

| | どうやって指すか | 🔴 困る所 |
|---|---|---|
| **A** user が手で `#a` と書く | いまの記法のまま | 毎回手で書くのは**動線として重い** |
| **B** 掴んで繋いだ瞬間に振る | 板から板へ引くと、`#a` `#b` と `from=`/`to=` が**まとめて書かれる** | **PKC3 で 1 例目**(7.2) |
| **C** 中身の 1 行目(名前)で指す | id を 1 つも足さない | 🔴 **同じ字の板が 2 枚あると決まらない** ── 板は「はじめ」「判断」のような**短い字**になりがちで、重複は避けられない |

🔑 **推薦は B(振る)+ A(手でも書ける)**。C は**重複が原理的に避けられない**ので採りません。

### ⚠ 重複したらどうするか(コピペは避けられない)

板ごとコピーすれば `#a` が 2 枚になります。🔑 **壊れない側へ倒します**:

- **読む側**:同じ id が 2 つ在ったら**先に出たほう**を採る(線は 1 本だけ繋がる)
- **書く側**:振るときに**本文の中を見て、重複しない字を選ぶ**(`a` → `a2`)
- ⚠ **本文は壊れません** ── 繋がらない線が 1 本出るだけで、字も板も失われない

⚠ ③④⑥ を**素通りさせる**のは、既存の一貫性に合わせるためです(板そのものが

## 11. PowerPoint へ(`<p:cxnSp>`)

⚠ **前例は 0 件**です(`cxnSp` は repo 全体で、この doc の見出し 1 件だけ)。

pptx の図形 id は**その回の書き出しの連番**(`base + 100 + n`)で、**恒久の id ではありません**。
🔑 だから**本文の id → その回の番号**の対応表をその場で作り、`stCxn` / `endCxn` に書きます。

⚠ **実測してから進めます** ── 1 本の線を吐いて、**LibreOffice Impress と PowerPoint の
両方で開くこと**を確かめる(開かなければ、線は画面だけにして pptx は段③ から外す)。

### 11.1 🟢 実測しました(2026-09-15)── **LibreOffice は「コネクタ」として読む**

⚠ まず**道具が欠品していた** ── この箱には `libreoffice-core` しか無く、Impress の
filter が入っていなかった(このまま測ると**対照群ごと落ちて「開けない」と読む**)。
`apt-get update` してから `libreoffice-impress` を入れて測り直した。

**測り方**:製品の `buildPptx` で板 2 枚の `.pptx` を作り、`slide1.xml` の `</p:spTree>`
の直前に `<p:cxnSp>` を 1 つ**注入した版**と**しない版**を作って、
`--convert-to fodp`(平たい ODF)へ落として**LO が何として読んだか**を見る。

🔑 観測点は **大きさではなく `draw:connector` の件数**にした ── 大きさは
「増えた」としか言えない(CLAUDE.md §4)。

| | `draw:connector` |
|---|---|
| **対照群**(注入しない) | **0 件** |
| 注入した版 | **在る** |

そして読まれた中身が、ただの線ではなく**繋がっている**ことまで出た:

```
draw:type="line"
draw:start-shape="id1"  draw:start-glue-point="1"
draw:end-shape="id2"    draw:end-glue-point="3"
svg:x1="15.832cm" … svg:x2="19.008cm"
```

🔑 **`stCxn` / `endCxn` の `idx` は、四角では `0=上 / 1=左 / 2=下 / 3=右`** ──
`stCxn idx="3"`(右)と `endCxn idx="1"`(左)を書いたら、座標が
**板 1 の右端(3413760+2286000 EMU = 15.83cm)から板 2 の左端(6842760 EMU = 19.01cm)**
にぴたりと落ちた(= 意図どおり)。
⚠ LO の内部の glue-point 番号は **1 / 3 と入れ替わって**出るが、**座標は合っている**
── 内部の番号づけが違うだけなので、こちらの `idx` を裏返してはいけない。

### 11.2 🔴 自前の接続点(`custGeom` + `cxnLst`)は**入るが、線がそこから出ない**(実測 2026-09-15)

user 裁定 2026-09-15 で「辺の真ん中だけでは足りない」となったので、
**書き出しでも 5 つ目以降の接続点を使えるか**を測った。

| 測ったこと | 結果 |
|---|---|
| 自前の接続点一覧を図形に持たせられるか | 🟢 **持てる。** 9 点を宣言したら LO が読んだ一覧は**宣言と 1 つ違わず一致**(`952500 0 / 0 476250 / 952500 952500 / 1905000 476250 / 476250 0 / 1428750 0 / 0 238125 / 1905000 714375 / 238125 0`)。9 本の線も**それぞれ別の点**に繋がった(glue point の id 4〜12) |
| 5 つ目以降(`idx` ≥ 4)へ繋げるか | 🟢 **繋がる。** ⚠ **対照群**(同じ file の中の preset の四角に `idx=4`)は **(0,0) へ潰れた** ── 「4 つまで」は**形の側の制限**であって、線の仕組みの制限ではない |
| 形は保てるか | 🟢 **保てる。** 自前の点を持たせた「丸」は、preset の丸と**同じ枠**(6307〜11599 × 4994〜7640)に同じ丸として出た |
| 🔴 **線は宣言した点から出るか** | 🔴 **出ない。** 9 本が **3 か所(枠の角)**にしか出ない。⚠ **対照群**(preset の丸の 8 点)は **8 点とも正確**に出る ── 計器のせいではない |
| 逃げの向き(`ang`)のせいか | ❌ **違う。** 4 辺ぶんの正しい向き(上 270° / 左 180° / 下 90° / 右 0°)を入れ直しても**1 バイトも変わらなかった** |

## 13.1 🟢 もう 1 段の裁定(2026-09-15)── **中点の中点 + 控えめな曲線**

こちらが出した設問は「接続点の出し方」と「曲線の形」の 2 つで、どちらにも

### 決まったこと ①接続点(→ §8.1 / 段③b で着地)

user が求めていたこと(こちらの言葉で):**4 辺の真ん中だけでは足りない。
必要に応じてその中点、さらにその中点、と細かくできること。出し方はマウスを
乗せた所を起点にしてよい。そして、同じ 2 枚を結んでいても、経路が明確に同じ
ではない繋がりが在るので、それを別の物として描けること。**

| どう受けたか | どこ |
|---|---|
| 接続点を **`辺 + 分数`** にした(`right@1/4`。分母は 64 まで) | §8.1 |
| 同じ 2 枚の間の線を **`k/(n+1)` で散らす**(1 本なら真ん中のまま) | §8.1 |
| **同じ所を指した線はそこで束ねる**(2026-09-14 の裁定と両立する) | §8.1 |
| **マウスを乗せて点を出す / さらに中点を出す**動き | 🔜 **段③d**(掴んで繋ぐ)と一緒に作る |

⚠ **こちらで決めたこと**(裁定の外側なので、違えばそう言ってください):
散らし方を **均等**(`k/(n+1)`。2 本なら 1/3 と 2/3)にした ── 「中点の中点」は
**書ける点**の話で、**自動で散らすとき**は均等のほうが見て読めるからです。
記法はどちらも書けるので、後から変えられます。

### 決まったこと ②曲線(→ 段③c。まだ着地していない)

user が求めていたこと(こちらの言葉で):**曲がり方は控えめにする。ただし、
曲がる位置を縦線か横線のどちらかに固定できるようにして、図の動線を単純にできること。**

🔑 **だから段③c は 2 つ持つ**:
1. **`line=curve` は控えめにする**(接続点の向きへ少しだけ出て、すぐ相手へ向かう)
2. 🆕 **`bend=` を足す** ── `bend=v:320` なら **縦線 x=320 の所で曲がる**、
   `bend=h:240` なら **横線 y=240 の所で曲がる**。書かなければ 2 点の中間で曲がる。
   ⚠ `line=elbow` にも同じように効く(曲がる位置は「形」とは別の軸である)

⚠ **狙いは「何本かの線が同じ幹を通る」こと** ── 同じ `bend=v:320` を書いた線は
同じ縦線の上で折れるので、配線図のように揃う(これが user の言う「動線の簡易化」)。
