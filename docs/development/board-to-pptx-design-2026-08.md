## 4. 段① の設計

### 4.1 何を読むか

板の塊(`.pkc-place`)の**開き行の属性**と**中身**:

```
:::format{.pkc-place x=120 y=64 w=240 h=96}
### 課題
- 見積もりが出ていない
:::
```

- `x` / `y` … 板の左上からの px
- `w` / `h` … 塊の大きさ(⚠ 省略時の既定は描画側の規則に合わせる ── **数え直さない**)
- 中身 … そのまま `<p:txBody>` の段落へ(既存の `lineXml` を使う)

### 4.2 座標の換算(EMU)

DrawingML の単位は **EMU**(English Metric Unit)= 914400 EMU / inch。
板は px なので **96 dpi 換算**で `EMU = px * 9525` とする。

⚠ **決めること**: 板が既定のスライド(既存の `pptx.ts` のスライド寸法)より
大きいとき、①縮めるか ②はみ出させるか ③スライドを分けるか。
🔑 **推薦は ①縮める**(1 枚に収める)── 叩き台なので**全体が見える**ほうが価値が高い。
⚠ 縮めるときは**縦横比を保つ**(文字だけ相対的に大きくなるのは許容する)。

### 4.3 どのスライドへ載せるか

既存の `splitIntoSlides` は見出しでスライドを切る。
🔑 **板の塊は「1 枚の板 = 1 スライド」**にする ── 板は 1 つの絵なので、
途中で切ると意味が壊れる。⚠ 板の直前の見出しがあれば、それをそのスライドの題にする。

### 4.4 検査(空振りさせない)

- 🔴 **書き出した `.pptx` を開いて `<p:sp>` の `<a:off>` が板の `x=` と対応する**ことを見る
  ── ⚠ 「`<p:sp>` が在る」で止めない(既存の文字の塊も `<p:sp>` なので、
  **それに満たされる**。CLAUDE.md §1「範囲が広すぎて別物に満たされる」)
- 🔴 **板を 2 つ置いて、2 つの `<a:off>` が違う**ことを見る(1 つだと位置を
  無視しても通る)
- ⚠ **対照群**: 板でない普通の段落は、これまでどおりの位置(自動レイアウト)に出る

## 5. ⚠ やらないこと / 決めていないこと

- 🚫 **新しい描画アプリを持ち込まない** ── 位置が本文の外に出ると、板は
  PKC の外へ持ち出せなくなる(「本文が正本」が壊れる)

- **図形の色・線** ── 段① では `<a:noFill/>` のまま(既存の文字の塊と同じ)

# 段③ の設計(2026-09-14 追記)── 板どうしを線で繋ぐ

> 2026-09-14 に**段②(形を選べる)が着地**しました(main `000a123` の 1 つ前、PR #910)。
> この節は、そのとき「ここから設計が重くなる(繋ぎ先の同一性が要る)」と書いた**段③**の設計です。

## 7. 🔴 「繋ぎ先の同一性」は、思っていたより小さい問題でした

実装を全数で読んで、**重いと思っていた理由が 2 つとも崩れました**。

### 7.1 CLAUDE.md の戒めは、ここには当たらない

CLAUDE.md(2026-08-19 の裁定)にこう在ります:

> ③ 名前か id か → **名前**(タグが既に名前で出荷済み。id を本文に書くと、
>   復元が body を書き換えない既知の穴を踏む = **静かに壊れる**側へ倒れる)

🔑 **禁止の目的は「復元が追随できない参照を作るな」**です。あの裁定が相手にしていたのは
**ノートをまたぐ参照**(グループの id を、別のノートの本文が指す)── 片方のノートを
履歴から戻しても、**もう片方は直らない**。だから静かに壊れます。

⚠ **ここは違います。** 線と、繋がれる 2 枚の板は、**同じ 1 つの本文の中**に在ります。
本文を復元すれば 3 つとも**同時に**戻るので、**追随できない参照が原理的に作れません**。

🔑 これは CLAUDE.md の「**戒めは対象ではなく目的に照らして検算する**」の実践です ──
「id を本文に書くな」と読むと止まりますが、目的で読むと**同じ本文の中なら通ります**。

### 7.2 記法は既に id を持っている(新しい記法を足さない)

`block-directive-attrs.ts` が Pandoc 風の `{#id .class}` を**既に解釈**し、
`markdown-render.ts` が `id="…"` として出します。

⚠ **PKC3 に「システムが id を発行して本文へ書き込む」前例は 0 件**です(実測)──
いま在る id は全部 ①既に別の理由で在る lid の再利用 か ②本文に書かず毎回導出する slug。
🔑 だから**ここが 1 例目**になります。だからこそ 7.1 の検算が要りました。

## 8. 記法

```
:::format{#a .pkc-place x=40 y=40 w=200 h=100 shape=round}
はじめ
:::

:::format{#b .pkc-place x=320 y=40 w=200 h=100 shape=diamond}
判断
:::

:::format{.pkc-line from=a:right to=b:left line=elbow}
:::
```

🔑 **`from=` / `to=` / `line=` は汎用のループを通る**ので、DOM には**自動で**
`data-pkc-from` / `data-pkc-to` / `data-pkc-line` が出ます(段② の `shape=` と同じ)。
⚠ つまり書くのは**描く側だけ**です。

⚠ **線は「置いた物」ではありません** ── 座標を持たず、**2 枚の板の位置から毎回引く**。
🔑 だから**板を動かせば線も付いてきます**(座標を書くと、動かしたときに置き去りになる)。

### 8.1 🔴 **アンカー(接続点)**── user 裁定 2026-09-14 で足りないと分かった所

user 裁定(こちらの解釈、2026-09-14):**線の形は 1 つに決めず選べるようにする。
まっすぐと直角だけでなく曲線(ベジェ)も要る。そして、これがコネクタである以上、
線を繋ぐ先=アンカー(接続点)が要る ── 線を束ねるためにも。**

🔴 **こちらの 1 稿目には、アンカーが 1 つも無かった。** `from=a to=b` は
「**どの板に**繋ぐか」しか持っておらず、「**その板のどこに**繋ぐか」が書けません。
⚠ 帰結は 3 つとも user が見る所で出ます:

| アンカーが無いと | 画面で何が起きるか |
|---|---|
| 繋ぎ先が板の中心しか無い | 線が**板の上を横切って**中心まで刺さる |
| 🔴 **束ねられない** | 3 本が同じ板へ来ても**バラバラの所**に当たる(user が言った「線を束ねる」ができない) |
| 向きを指定できない | 「右から出て左へ入る」が書けない ── **直角の折れ方が決まらない** |

🔑 **だから板は 5 つの接続点を持ちます**(PowerPoint と同じ考え方):

```
        top
         │
 left ──[板]── right      + center(真ん中)
         │
       bottom
```

- 綴りは **`from=<id>:<接続点>`**(`a:right`)。⚠ **省いてよい** ── 省くと
  **いちばん近い接続点**をこちらが選びます(手で書かせない)
- 🔑 **同じ接続点へ来た線は、そこで束ねます** ── 1 点に集めるので、
  「どこから来たか」が読める(user 裁定の「束ねるためのアンカー」がこれです)
- ⚠ **接続点は板の属性ではありません** ── **線の側**に書きます。
  板は位置と大きさしか持たないので、**板を書き換えずに繋ぎ替えられます**

### 8.2 線の形(3 つ。**線ごとに選べる**)

| `line=` | 画面で何が出るか | 既定 |
|---|---|---|
| `straight` | **まっすぐ 1 本**。どこへ動かしても必ず届く | 🟢 **これ**(省いたとき) |
| `elbow` | **直角に折れる**(横 → 縦 → 横)。配線図の見た目 | |
| `curve` | 🆕 **曲線(ベジェ)** ── 接続点の向きへいったん出てから、相手の接続点の向きへ入る | |

⚠ **`curve` は接続点と対で効きます** ── 出る向き・入る向きが決まって初めて
「ふくらみ方」が決まります(だから §8.1 が先に要ります)。
🔑 **既定を `straight` にする理由**:省略して書いたときに**必ず届く**形だからです
(`elbow` は折れ場所しだいで板の上を通り、`curve` は向きが要る)。

## 9. 身元をどう振るか(3 案)

| | どうやって指すか | 🔴 困る所 |
|---|---|---|
| **A** user が手で `#a` と書く | いまの記法のまま | 毎回手で書くのは**動線として重い** |
| **B** 掴んで繋いだ瞬間に振る | 板から板へ引くと、`#a` `#b` と `from=`/`to=` が**まとめて書かれる** | **PKC3 で 1 例目**(7.2) |
| **C** 中身の 1 行目(名前)で指す | id を 1 つも足さない | 🔴 **同じ字の板が 2 枚あると決まらない** ── 板は「はじめ」「判断」のような**短い字**になりがちで、重複は避けられない |

🔑 **推薦は B(振る)+ A(手でも書ける)**。C は**重複が原理的に避けられない**ので採りません。

### ⚠ 重複したらどうするか(コピペは避けられない)

板ごとコピーすれば `#a` が 2 枚になります。🔑 **壊れない側へ倒します**:

- **読む側**:同じ id が 2 つ在ったら**先に出たほう**を採る(線は 1 本だけ繋がる)
- **書く側**:振るときに**本文の中を見て、重複しない字を選ぶ**(`a` → `a2`)
- ⚠ **本文は壊れません** ── 繋がらない線が 1 本出るだけで、字も板も失われない

## 11. PowerPoint へ(`<p:cxnSp>`)

⚠ **前例は 0 件**です(`cxnSp` は repo 全体で、この doc の見出し 1 件だけ)。

pptx の図形 id は**その回の書き出しの連番**(`base + 100 + n`)で、**恒久の id ではありません**。
