- 箱: 4 コア / 16GB / Chromium(`/opt/pw-browsers/chromium` = chromium-1194)/ headless / 計った日 2026-10-02

## 1. 何を比べたか(対照群を先に)

| 腕 | 中身 |
|---|---|
| **対照(`off`)** | 同じ板・同じ枠(320 × 240)で**本文を頼まない** = 題名の帯だけ。測りたい操作(中身の描画)以外は全部同じ |
| **全部描く(eager)** | 開いたときに全部の枠へ中身を出す(W3-① の作り)。余白を 1,000,000px にして「全部が近い」にした版 |
| **近づいた枠から(今)** | 画面から 800px までに近づいた枠から中身を描く。一度描いた枠は離れても捨てない |

**台の次元**(ゼロ件の次元は「測っていない次元」なので書く):枠は 4 列に敷き、置くノートは
本文の長さが 3 通り(短い ≈ 800 字 / 中 ≈ 3,000 字 / 長い ≈ 12,000 字 ── 4,000 字で切れる)・全部に表とチェック、
**4 枚に 1 枚が mermaid の図**、5 枚に 1 枚が**本文に貼った画像**(同じ添付)、8 枚に 1 枚が**画像の添付ノート**
(1 件ずつ違うノイズ画像 ≈ 130KB)。⚠ **この台に chart と数式は 0 件**(常駐・応答の数字には入っていない。形の実測は §6 の末尾に別に書いた)。⚠ 枠の大きさは 320 × 240 だけ(振っていない)。

**計器の自己検査**(各回の先頭。鳴らなければ測らずに落ちる):既知の 300ms の詰まりが long task と心拍(4ms)に出ること
(出た: 305ms)/ 100MB を触ったら Pss が 60MB 以上動くこと(出た: +99.8MB)。

⚠ **Pss の読み落としを除いている。** `/proc/<pid>/smaps_rollup` を読めなかった 1 プロセスが 0 になる走査が時々あり、
その標本だけ **85〜100MB 低く出る**(プロセス数は 8 のまま)。Pss / Rss が 0.47 未満(正常は 0.50〜0.59)の標本は
**数え漏れ**として除いた(表の「有効」の数)。

## 2. 常駐(Pss、MB。**板を端から端まで 2 往復し、各回の後に 4 秒静止**した後)

「圧迫後」= ブラウザへメモリ圧迫の通知(`Memory.simulatePressureNotification` critical)を送って解放させた後。
ブラウザは解放したメモリをすぐ OS へ返さないので、「普通に使っているとき」(往復後)と「残っている分」(圧迫後)を分ける。

| N | 対照 往復後 / 圧迫後 | 全部描く 往復後 / 圧迫後 | 近づいた枠から 往復後 / 圧迫後 | 差(近づいた枠から − 対照)往復後 / 圧迫後 |
|---|---|---|---|---|
| 10 | 448 / 444 | (10 枚は全部が最初から近いので同じ) | 485 / 473 | **+37 / +29** |
| 40 | 461 / 457 | 526 / 511 | 524 / 506 | **+63 / +49** |
| 100 | 473 / 464 | 580 / 553 | 583 / 555 | **+110 / +91** |
| 200 | 480 / 458 | 629〜668 / 610 | 662 / 605 | **+182 / +147** |

(中央値。有効な標本 1〜3 件ずつ。全部描くの N = 10 は 1 回が自己検査で落ち、もう 1 回は標本が欠けたので省いた。)

🔑 読み:
- **枠 1 枚あたり約 0.6〜0.75MB**(N = 40 → 200 の傾き: 往復後 +119MB / 160 枚 = 0.74MB、圧迫後 +98MB / 160 枚 = 0.61MB)。
  固定費(mermaid・markdown の部品を読む分)が約 30MB。**枠の数に比例して増える**。
- **「近づいた枠から」は、一度全部を通ると「全部描く」と同じ常駐になる**(捨てないので当然 ── 583 対 580、662 対 668)。
  開いた直後は近い枠(20 枚)だけなので軽い。
- 内訳の参考(捨てる版・N = 100・6 往復の範囲): 文だけの板 501〜520MB / 図を足す 550〜567 / 画像を足す 532〜559 /
  全部入り 559〜595。**図と画像の枠が重い**(対照との差が文だけの約 2 倍)。

⚠ long task は 50ms 未満を落とすので**心拍の最大空き**を併せて見ている(最大空き = いちばん長く返ってこなかった時間)。
⚠ 「初回に落ち着くまで」は**中身を出した枠の数が最後に増えるまで**。近づいた枠からでは近い枠(20 枚)だけが対象。

🔑 読み:
- **開く時間は「全部描く」だと枠の数に比例して伸びた**(N = 200 で 7.4 秒。開き直しは主スレッドが 0.7 秒固まる)。
  **近づいた枠からにすると、初回 1.1 秒・開き直し 83ms**(対照の 74ms と同じ桁)。
- **板を送る間の最大空きは逆に増えた**(N = 200 で 61 → 97ms)。描く仕事が「開くとき」から「送りながら」へ散ったため。
  50ms を超える long task は 1 回の板で 0〜5 件。送るたびに固まる形ではない。

## 4. 「見えていない枠の中身を捨てる」は **捨てない**(測った結果)

依頼の「常駐が N に比例して増えるなら、見えていない枠の中身を捨てる」を、**実装して測った**:
画面から外れて 1.5 秒たった枠を器ごと捨て(貸出・図の URL も返す)、近づいたら控えから描き直す版。

| N = 200・往復後の常駐(MB) | 往復 1 | 2 | 3 | … | 8 | 14 | 圧迫後 |
|---|---|---|---|---|---|---|---|
| 全部描く(8 往復) | 672 | 667 | 652 | | 640 | | **501** |
| **捨てる版**(8 往復) | 629 | 653 | 714 | | 820 | | 633 |
| **捨てる版**(14 往復) | 630 | 661 | 684 | | 823 | 819(9 往復目の 838 から 762 まで下がる鋸歯) | 628 |

- **捨てる版は、板を往復するほど常駐が増えた**(N = 200 で 1 往復あたり約 25MB。14 往復で 760〜840MB の鋸歯)。
  全部描く版は 640〜650MB で止まる。JS heap は 76MB のまま ── **増えたのはブラウザ側の控え**。
- 原因の読み:**枠を作り直すたびに画像を新しい URL で読み直す**(8 往復で ObjectURL を 1,424 本作って 1,414 本返した)。
  返した URL の画像のデコードの控えは、圧迫の通知を送っても残った(圧迫後 633MB 対 501〜610MB)。
- 捨てて得られる分(圧迫後 30〜45MB)は、**捨てない版の圧迫後のぶれ**(501〜610MB。同じ構成の 3 回)に埋もれる。
- 文だけの板(図・画像なし)を捨てる版で 6 往復しても増えなかった(518 → 501MB)── **増えるのは図と画像を作り直す分**。

→ **捨てない。** 一度描いた枠は、離れても器・図の URL・貸出を持ち続ける(別のノートへ移るときに全部返す ──
ObjectURL を表示の寿命の終端で返す規律はそのまま)。常駐は「一度でも近づいた枠の数」で決まり、開いた直後は軽い。

**`content-visibility: auto` も測った**(全部描く版・cap 200・N = 100 / 200):往復後の常駐は変わらない(579 対 583 /
655 対 676)。開き直しの最大空きは 403 → 162ms / 432 → 203ms に縮んだが、板を送る最大空きは 40 → 54ms / 53 → 74ms に増えた。
**採らない**(常駐に効かない / 「近づいた枠から」が開き直しの固まりを既に消している / 描画の包含で枠の持ち手が切れる恐れ)。

## 5. 決めた定数

| 定数 | 値 | 根拠(上の表) |
|---|---|---|
| `PLACE_BODY_CAP`(板のために持つ抜粋の数) | **40 → 200** | 40 のままだと、N = 100 で**どの枠に中身が出るかが開くたびに変わった**(初回 40 枚・開き直し 80 枚。頼む数を上限で切り、手放した物を頼み直すため)。200 なら N = 100 / 200 で全部に出る(出た枠 100/100・200/200)。持つのは切った本文なので最大 200 × 4,000 字 ≒ 1.6MB。⚠ **測ったのは N = 200 まで** ── 板 1 枚で中身が出るのは先頭から 200 枚まで |
| `PLACE_BODY_CLIP`(切る字数) | **4,000 のまま** | 1,500 / 4,000 / 12,000 を N = 40(近い枠 20 枚)で比べた:圧迫後の常駐は 492 / 495〜499 / 497〜498MB(差は誤差内)、節点は 1,936 / 2,590 / 3,016 個、**開き直しの最大空きは 51〜71 / 86〜115 / 132〜158ms**。常駐は動かないが、12,000 は開くたびに +50〜70ms 固まる。1,500 は 3,000 字のノートを途中で切る。4,000 は 3,000 字を全部出し、1,500 より +20〜30ms で済む |
| `PLACE_ENTRY_DEFAULT_W` × `_H`(既定の大きさ) | **320 × 240 のまま** | **大きさは振っていない**(測ったのは 320 × 240 だけ)ので動かす根拠が無い。常駐の差は枠の数と中身(図・画像)で出ており、枠の面積の効きは測っていない |
| `PLACE_NEAR_MARGIN`(中身を描き始める余白) | **800px(新規)** | 枠 320 × 240 で、画面 1 つ分ほど手前から描く。⚠ **この値は振っていない**(800 で測った)。開く時間と送る間の空きの釣り合いは上の §3 |

⚠ 4,000 字の測定は「捨てる版」の構成で採った(近い枠の描画と節点の数は「近づいた枠から」と同じ)。

## 6. 測っていない次元(正直に)

- chart・数式の枠の**常駐と応答**(台に 0 件。⚠ 形は下の「後から測った形」)/ 枠の大きさ(320 × 240 のみ)/ 余白の値(800 のみ)/ N = 200 より大きい板
- **実機**(DPR・遅い端末・実フォント)/ **製品ビルド**(dev の minify なし)/ 2 つ目のブラウザ(headless_shell)
- 「一度全部を通った板」の常駐が頭打ちか増え続けるか(捨てない版は 8 往復で 640〜650MB に止まったが、それ以上は測っていない)

### 後から測った形(2026-10-02、#529。chart・数式。⚠ 常駐ではなく**枠に収まるか**だけ。probe は repo の外)

- **chart**:`emb`(320 × 240 の枠)の図は 290 × 166。ところが**原文の `<pre>`(35 px)が図の下に見え**、枠の中身が
  scrollHeight 217 > clientHeight 184 で**原文のせいだけでスクロールバーが付いた**(→ 掃除で原文の面を外して直した)。
- **数式**:`emb` は 302 × 184 に収まる。長い式は式自身が横に送る(scrollWidth 1437 / 見える幅 290)。
- **`auto`(大きさ指定なし)の塊**:長い式で塊が 1614 px になり、面が横に 734 px 溢れる(`max-width: none`)。未対応(別件)。
