## 🔴 勝った案も、3 つの角度から**全部壊せた**(そして 3 つとも「直せる」)

⚠ **機械の判定は「やり直し」と出た**(過半が refute したため)が、**中身を読むと違う** ──
3 本とも**方式そのもの**ではなく**書き方の穴**を指しており、3 本とも具体的な直しを添えている。
🔑 だから方式 A を保ち、**3 つの穴を設計に織り込む**。

### 穴① 断られた書込が「いちばん新しい控え」になり、別の窓の本文を古い字で上書きする

この repo には**多重タブの楽観検査**が既に在る(`storage-worker.ts:1802-1804` / `:2802-2805`)──
`expectHash` が食い違うと **1 バイトも書かずに** `conflict` で断る(#178 の実体)。

⚠ 控えを「応答の**前**」に積むと、**断られた書込も控えに残る**。後日それを「いちばん新しい行」
として穴埋めに使うと、**別の窓が正しく保存した本文を、古い本文で上書きする**。

🔑 **直し**:控えの行に **成功 / 拒否 / 未確定** の **3 値**を持たせ、穴埋めは
**成功 > 未確定** の順で採り、**拒否は採らない**。
⚠ **真偽 2 値にしない** ── 「まだ返事が無い」と「断られた」が同じ顔になり、この穴がそのまま戻る
(`store-proxy.ts:126-129` の `EditGrant` が同じ理由で 3 値になっている)。

### 穴② 使い捨ての cid の控えが、誰にも消せずに残り続ける

OPFS の handle を他のタブが握っていると、init は**例外を投げずに `memory` へ退避する**
(`container-rebuild.ts:29-40` に 2026-09-18 の実ブラウザ実測が表で載っている)。
そのとき `resolveContainer` は**その回かぎりの新しい cid** を発行する。

🔴 sqlite 側は閉じれば消えるが、**控えだけは IDB なので残る** ── そして追い出しが
「器ごと」だと、**二度と書かない cid は二度と掃除されない**。

🔑 **直し(門を 2 つ置き、片方だけで成立させない)**:
1. **孤児の cid を掃く** ── `asset-gc.ts:50-57` の `strayBlobKeys` と同じ形。
   ⚠ 誤差の向きも同じに倒す:**生きている cid の一覧が空なら 1 件も消さない**(`asset-gc.ts:51`)。
2. **上限を「器ごと」から「この端末全体」へ** ── いまの案は cid で割るので、
   **cid が増えた分だけ天井も増える**(= 天井が無いのと同じ)。

### 穴③ 掛け所が、壊れが実際に作る穴と**ずれている**

`rescueEntries` は区画ごとに **1 本の SELECT で題名も本文も同時に取る**ので、
区画が落ちると **`skipped` として丸ごと飛ぶ**(`storage-worker.ts:3672-3689`)──
**題名ごと 1 件も返らない**。

⚠ ところが案は `bodyMissing`(**題名は在るが本文が無い**)の所にだけ控えを掛けていた。
🔴 `bodyMissing` は**壊れでは起きない** ── 2 周する回のブレでしか出ない
(`container-rebuild.ts:110-116` に自分で書いてある)。
🔴 そのうえ zip は**欠けたことを画面の字に 1 つも出さない**(件数は `metas.length`)。

🔑 **直し**:控えは **`listEntryMetas` の側**へ足す(題名ごと足す)。そして
**「控えから足した件数」を別の列で持ち**、書き出しの 1 行に出す
── ⚠ `entries` に混ぜると「sqlite から拾えた数」が水増しされ、**壊れ方の判断材料が消える**。
⚠ 埋める規則は**純関数 1 つ**にし、1 周の `collectRescued` と 2 周の `rescueArchiveSource` の
**両方がそれを呼ぶ** ── 2 通り書くと、2 つのボタンで戻る件数が食い違う。

## 画面で何が起きるか(⚠ ここが user の裁定)

**新しいボタンは足さない。** 増えるのは**設定の 1 行**と、既に在る 2 つのボタンの**戻る量**である。

```
中身が壊れていないか調べる
  この端末に、直近の編集の控えが 12 件あります(最後は 9/18 14:32)
  [ 壊れていないか調べる ]  …
```

控えが取れていない端末では:

```
  ⚠ この端末では控えを取れていません
```

壊れた日に押すのは、**いままでと同じ 2 つ**:

| 押す物 | いま | 控えが入ると |
|---|---|---|
| **中身を残して、作り直す** | 拾えた行だけ戻る | **読めなかった所に居たノート**も、控えの本文で戻る(いまは**題名ごと居ない**) |
| **拾って、戻せる形で書き出す** | 本文が読めなかった所に「⚠ 読み出せませんでした」と書かれる | そこが**控えの本文に替わる** |

⚠ **合流は「穴埋めだけ」** ── sqlite から読めた本文は **1 件も上書きしない**。
🔑 理由:拾った行は**時刻を持たない**(`created_at` / `updated_at` が `null`)ので、
**どちらが新しいか言えない**。⚠ **言えないほうを勝たせない。**

⚠ 「中身を捨てる」の窓には「**控え 12 件もここで消えます**」と出す(添付で既にやっている形)。

## 🔴 この方式で守れない所(先に書く)

- **持ち歩ける 1 枚(portable)では守りにならない** ── そこでは **sqlite 自身が IndexedDB に在る**
  (`db-image-store.ts:1-6`)。同じ入れ物なので「別の入れ物だから生き残る」が成り立たない。
  ⚠ #1007 にこの carve-out は 1 行も無かった。
- **ブラウザのデータを消されたら一緒に消える** ── IDB も OPFS も同じ origin の「サイトのデータ」。
  **別の入れ物ではあるが、別の寿命ではない。**
- **タブを閉じる瞬間の 1 件は残らないことがある** ── 完了を待たない設計なので。
  ⚠ **いちばん欲しい 1 件が落ちる**向きの失敗である。
- **壊れたことに気づく契機は変わらない** ── 控えは**戻す道具**であって、**気づかせる道具ではない**
  (それは段①)。

## 測ってからでないと言えないこと

⚠ **「待たないから体感に載らない」は設計の主張であって、実測ではない。**

1. 控え**あり / なし**の 2 群で、**打鍵から反映まで**と long task を比べる(対照群を揃える)
2. 常駐は `smaps_rollup` の **Pss をプロセス木で**採る(heap だけ見ると storage worker を数え落とす)
3. 本文の**大きさの分布**(1 MB の上限が実際に何 % を弾くか ── `body_chars` が sqlite に在る)
4. 8 MB / 500 件が、実際の 1 日の編集回数に対して**何日ぶんを覆うか**
5. タブを閉じる瞬間に、控えが**どれくらいの割合で書き切れるか**

## これが分かったら覆る

- 実測で**打鍵から反映までが目に見えて遅くなる**なら、置き方(応答の前に積む)を変える
- user の実機の `integrity_check` が「**特定の表 / 索引だけ**が繰り返し壊れる」を示したら、
  段②より先に**そこを直す**(#1007 の「engine を見直す側へ倒す条件」)
- 控えが**1 件も埋められない**壊れ方(rc 11 が控えの鮮度より速い)なら、周期を見直す
