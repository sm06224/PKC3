## 0.0 🔴 裁定(user 2026-08-07。不可侵)

> 「**記法の縮小と簡単に言うが、ユーザーの動線を縮小することを忘れるなよ**」

**縮小はやらない。** 2026-08-06 の条件つき OK は、この裁定で**縮小しない側へ確定**した。

**確定した読み方**:

- **記法 1 つ = user の書き方 1 つ**。落とせば「書けたものが書けなくなる」──
  §1 で数えた 84 も、§6 の「落とす議論の対象外」も、**全部 keep** である
- 段数・維持コスト・受理方言の一貫性は**こちら側の都合**であり、動線と交換してよい物ではない。
  §3 が「縮小の正当化を維持コストと一貫性に置ける」と書いたのは、この裁定で**閉じた**
- ⚠ §1.1 の「どこにも出てこない記法 15」を**削除候補として蒸し返さない**。
  正しいラベルは「**移植の穴**」であり(§3 反駁 2)、台帳から消すと復元の手がかりが失われる

**では何をやるか** ── 記法を 1 つも失わない整理だけを買う:

| # | やること | 状態 |
|---|---|---|
| ① | 目次が本文と別の実装で見出しを読んでいる(§2 の実バグ 4 件) | ✅ 着地済み(#86) |
| ② | **§4 の「段を素通りさせる」** ── 本文に無い記法の段を走らせない。**出力は 1 バイトも変えない** | 実施する |
| ③ | ライブエディタの釣り合い(`live-editor-balance.test.ts` の `ok:false`)── **落ちている動線を戻す**側なので、この裁定と同じ向き | 実施する |

⚠ §5 の「先に決めることが 6 つ」は**縮小をやる場合の前提**だった ── 縮小をやらないので
**6 つとも不要**になった(⓵ 記法の正本 doc の権威順だけは、他の判断でも使うので残す)。

## 0. 結論を先に(調査時点の記述。上の裁定と同じ結論)

> **記法の縮小は、いま着手すべき仕事ではない。** 裁定は貰っているが、
> **裁定の前提が 3 つとも成り立たなかった。**

③は縮小をやるなら**その前に**要る。

| # | やること | なぜ先か |
|---|---|---|
| ① | **目次(TOC)が本文と別の実装で見出しを読んでいる**のを直す | 実バグ 4 件が出ている(§2)。記法を 1 つも減らさずに user の損が消える |

⚠ **この doc は実装を含まない。** 裁定を貰うための材料である。

## 2. 調査中に見つかった実バグ 4 件(私が自分で再実測した)

🔴 **これが今回いちばん価値のある収穫である。** どれも「目次が本文と**別の実装**で
見出しを読んでいる」ことから来ており、`extractHeadingsFromMarkdown` を直接呼ぶ
test は **1 件も無い**。

### ① 見出し番号を付けると、目次を押しても飛ばない

```
入力: heading-number 有効 + `# 第一` + `:::toc{depth=2}`
本文の見出し id → "1-第一"
目次のリンク先   → "#第一"        ← 飛ばない
```

目次の文字列は前処理**前**の原文から作られる(段 9 で nav HTML を完成させる)のに、
見出し id は採番**後**に作られる。⚠ user が手書きした `[戻る](#第一)` も同じ理由で切れる。
⚠ 書き出した HTML の `#slug` と、PKC2 取込のログ permalink 書換も同じ slug に載っている。

### ② `%%隠す%%` は本文からは消えるが、目次に出る

```
入力: `# 見出し %%隠す%% つき`
本文の h1 id  → "見出し-つき"                 ← 隠れている
目次の項目    → "見出し %%隠す%% つき"        ← 漏れている
目次の slug   → "見出し-隠す-つき"            ← id とも不一致 = 飛ばない
```

### ③ `%%%` ブロックの中の見出しも目次に出る

```
入力: `%%%` / `## 隠したはずの見出し` / `%%%`
目次の項目 → "隠したはずの見出し | 出る見出し"
```

⚠ さらに **markdown ZIP 書き出しは原文をそのまま書く**ので、隠した本文はそこにも残る。
「隠す」の約束が**面ごとに違う**。

### ④ 行頭寄せの付いた見出しは目次から落ちる

```
入力: `||## 中央見出し` + `## ふつうの見出し`
目次の項目 → "ふつうの見出し"        ← 中央寄せの見出しが消えた
```

### そのほか、確認できた食い違い

| 事実 | 実測 |
|---|---|
| 書き出す HTML の `.pkc-*` 規則 | **10 個**(`app.css` は **71 個**)── `==印==` / ルビ / 圏点 / `_N` / `:::note` / `:::quote` などは**書き出した HTML で装飾が付かない** |
| `@media print` | `app.css` に **0 件**(書き出し側に 2 件だけ)── 画面からの印刷に印刷用 CSS が無い |
| `+++` の改頁 | `.pkc-section-break` は罫線と余白だけ。`:::break{kind=page}` も同じ `<hr>` に落ちる ── **改頁はいまどの面でも起きていない** |
| 早期 return | `markdown-render.ts` に **0 件** ── 42 段すべてが記法の有無に関わらず全文を走る |
| ライブエディタの囲い走査 | `/^:::([A-Za-z][\w-]*)/` で**名前を問わず** `:::` を囲いと見る。名前表は `{'toc'}` の 1 個だけ |

## 3. 私の縮小案は 3 つのレンズすべてに反駁された

調査のあと 55 項目の keep / fold / drop 案を作ったが、3 体の反駁がそれぞれ
**16 / 16 / 12 項目**を崩した。崩れ方に型があるので、そこだけ残す。

### 反駁 1 ── 記法を落とすと、ライブエディタが**今より壊れる**

囲いの走査(`source-blocks.ts`)は **renderer と無関係に** `:::name` を一律に囲いと見なし、
閉じ(無ければ EOF)まで 1 塊に飲む。一方 `buildBlockPartition` は
「描画側の最上位塊の個数」と「畳んだ範囲の個数」が合わなければ `ok:false` を返し、
**全文 textarea へ落ちる**。

いまは renderer 側も同じ名前を 1 塊に畳んでいるので釣り合っている。
**記法を落とすと renderer 側だけ literal に変わり、釣り合いが必ず壊れる。**

実測で確認された釣り合いの状態:

| 組合せ | いま |
|---|---|
| `:::callout` / `:::admonition` / `:::if` / `:::frontmatter` / `:::body` / `:::code` | **ok = true**(drop すると false へ退行) |
| `:::quote` > `:::section` / `:::format{.a}` > `:::details` / `:::.hl` / `::: {.hl}` / `:::foo`(未知名) | **すでに ok = false**(今日から壊れている) |

私の案は「記法ごと畳めばライブエディタの食い違いも消える」と書いていた ── **逆だった**。

### 反駁 2 ── 「移植していない」を「記法として存在しない」と書いた型が 6 件

`caps` の renderer 12 種 / `notation:` / `:::heading` 等 4 種 / `:::frontmatter`・`:::body` /
card・embed / Tier 1 ── いずれも根拠が **PKC3 の実装と使用数**で、出典側の status
(✅ / 🔄 / 📝 / 正式実装予定)に触れていない。

🔴 これは **2026-08-06 に user から revert を受けた事故と同じ構造**である
(corpus の註記を根拠に実装を変えた件)。この書き方をすると**移植の穴が記法台帳から
消える**ので、後から「元々無かった」ことになって復元の手がかりが失われる。

具体的に出典と食い違っていた点:

| 私が書いたこと | 出典 |
|---|---|
| Tier 0 / Tier 1 を drop、Tier 2 を keep | catalog では **Tier 0 と Tier 1 こそが simple 列**、Tier 2 が formal 列。しかも user 裁定(2026-05-25)で明示 OK 済 |
| ルビ `[[ruby:…]]` を canonical keep | 正本は **❌ 廃止**(移行先 `[base\|読み]`)。しかも PKC3 は後継形を実装していない ── 正しいラベルは「**廃止形の暫定受理**」 |
| `:strong:` 等 formal 4 種を simple へ fold | canonicalization spec は `canonicalize(simple) → formal` の 1:1 写像を定め、**canonical = formal** と明言。user 裁定 Q6 も同じ向き ── 私の案は**逆走**していた |
| `:::if{format=…}` を drop(「PKC3 に docx 出口が無い」) | 値集合は **html \| markdown \| docx** の 3 値で、PKC3 は markdown 出口を持つ。「永久に不可視」は記法の性質ではなく `processIfBlocks(..., 'html')` と**第 3 引数を固定した実装の帰結** |
| 行中 `:align:` の chip が「意味不明」だから drop | 規約は「**hint chip(default 非表示)**」と規定 ── 見えているのが規約違反で、直すのは CSS 1 規則 |
| caps override は「doc に分類が無い」 | doc は在る(§7.2.0 に 2 層 cap と override 経路)。正しい根拠は「**PKC3 が override 経路を移植していない**」 |

そして横断的な誤り: **どの版を正本とするか宣言していなかった。**
私は 7 か所で v3 を「規約」と引いたが、v3 自身が v4 を後継と明記し、v4 が
「supersedes v3」と宣言している。v3 に載っていない記法は、v3 だけを見ると
「実装が勝手に生やした余分」に見える ── 私の Tier 0/1 drop と `:::if` drop は
**まさにその読み方から出ていた**。

### 反駁 3 ── 1 パス化の算術と、その正当化が両方おかしい

| 私の主張 | 実際 |
|---|---|
| 縮小だけで段 42 → 26 | 内訳に入れた `processAdmonitionAliases` は **keep と決めた 8 短名を処理している当の関数** ── 段は 1 本も減らない。到達点は **27** |
| 全文スイープ 11 → 3 | 後処理 12 段が全文 HTML スイープであることを勘定していない。実数は **23 前後 → 20 前後** |
| goldens は 2 件動く | fold/drop 対象を含む golden は **25 件中 8 件**。分岐の受け皿(`pkc3Diverges`)は既に 4 件埋まっているので、縮小をやると **12/25 が「PKC3 の自己申告」**になる ── Q1 の唯一の安全網を先に半分無効化することになる |
| `alignMap` producer 3 → 2 で阻害要因が減る | 残るのが**壊れている方の対**。`:::paragraph{align}` の鍵は最終段の行挿入でずれ、remap する処理がどこにも無い |
| 段数を買い物にする | user の不可侵指示は「**効くのは定常**」= 常駐メモリと操作の応答。段数はその代理指標にすぎず、しかも **定常はすでに底に着いている**(direction doc の実測で long task 0 本 / heap 横ばい)。引いた 0.339 vs 0.352 ms/KB は**方言の有無で入力を変えた対照**で、両群とも 42 段すべてが走っている ── **段数を変えた測定ではない** |

🔑 したがって、縮小の正当化を「速くなる」にも「段が減る」にも置けない。
置けるのは **維持コスト・受理方言の一貫性・ライブエディタとの釣り合い**である。

## 4. 見落としていた選択肢 ── 段を消さずに素通りさせる

`markdown-render.ts` に `if (!text.includes(…)) return` 型の早期 return は **0 件**
(grep で確認)。42 段すべてが、その記法が本文に 1 文字も無くても全文を走る。

つまり **「段を消す」以外に「段を素通りさせる」という買い物が実在する**のに、
`direction-ir-vs-html-2026-08.md` §2 Q1 の 3 択(やらない / 1 パスに畳む / 骨組みを作る)にも
私の案にも入っていなかった。

- **記法を 1 つも失わない**(user の損が 0)
- **goldens が 1 バイトも動かない**(出力が同じなので、安全網を無効化しない)
- 危険は「素通りの判定を間違えると、その記法が黙って効かなくなる」1 点だけ
  ── これは記法ごとに 1 本の test で pin できる形である

⚠ ただし**これも「速くなる」とは言えない**(§3 のとおり定常は底に着いている)。
買えるのは「本文に無い記法のために走る仕事が消えること」であって、
体感を主張するなら測ってからにする。

## 5. 縮小をやるなら、先に決めることが 6 つ

> ⚠ **2026-08-07 の裁定で縮小はやらないと決まった**(§0.0)ので、この 6 つは**不要**である。
> ⓵(記法の正本 doc の権威順)だけは縮小と無関係に使うので、そこだけ生きている。
> 以下は記録として残す。

順番が大事である。**上から決めないと下が決まらない。**

### ⓵ 記法の正本はどの doc か

候補の権威順(調査の結論):

1. **user 裁定 / user 指示のタグが付いた doc**(そのトピックについてのみ最上位)
2. `docs/spec/pkc-markdown-complete-spec-v4.md`(記法ごとに canonical / 🔄 / 📝 / ❌ を
   貼る**分類体系を持つ唯一の doc**。97 項目を網羅)
3. catalog(`notation-redesign-2026-05/01-notation-catalog.md`)
4. `markdown-dialect-for-ai-authors-v3.md`(v4 に supersede されている)

⚠ これを宣言しないと、以下の全項目が**解釈で通せる**ようになる。

### ⓶ 縮小の線を「マニュアルの約束 + データ契約」に置くか

`docs/manual.md`(513 行)が user に約束しているのは
**fence 一式・脚注・`:::toc`・行頭寄せ 5 形・`:::paragraph{align}` / `:::format{align}`・
frontmatter globals** だけである。

一方 `==印==` / ルビ / 圏点 / `_N` / `__ 字下げ` / `:::note` / `:::figure` / `[@id]` /
`%%` / `:sup:` / `+++` / `:::details` / `:::quote` / タスクリストは
**マニュアルに 1 件も載っていない**(grep 0)。

項目ごとに 84 個の verdict を積むより、**この線を先に引く**ほうが速くて堅い。

### ⓷ 合格線を何で置くか

段数で置くか、応答とメモリを測って置くか。⚠ 段数で置くなら
「単位の付け替えだけで通せる gate」にならない定義が要る(§3 で実際にそうなっていた)。
⚠ **§4 の「素通りさせる」案を選択肢に入れるか**も、ここで一緒に決まる。

### ⓸ goldens の契約を何件まで自己申告に落とすことを認めるか

- 縮小の影響は **25 件中 8 件**
- 分岐の受け皿はすでに 4 件埋まっている → 縮小後は **12/25 が自己申告**
- ⚠ **harvest スクリプトは PKC2 の renderer を import する**ので、縮小後に再実行すると
  PKC2 の出力へ戻る = **更新の道具として使えない**。残る道は手編集だけ
- ⚠ そして縮小の安全網(goldens / CSS parity の CORPUS)を**縮小の当事者が編集する**ので、
  この PR では変異試験も「意図した変異」になって効かない ── **第三者の網を先に置く**

### ⓹ 「隠す」の約束をどの面まで守るか

現状は面ごとに違う:本文では消える / **目次には出る** / **markdown ZIP には原文が入る** /
添付 GC はコメント内の `asset:` も keep 側に数える。
「隠す記法は不可侵」を決めるなら、**どの面まで隠すのか**を決めないと不可侵の内容が定まらない。

### ⓺ Q2(docx を戻すか)を先に閉じるか

裁定の条件は「**正規形を iR のために残す必要がなければ**」である。
canonical formal(`:strong:` / `:emphasis:` / `:code:` / `:strike:` / `:autoref:` /
`:caption:` / `:::break`)の fold は**この条件の解除が前提**なので、
Q2 を閉じるか「formal は iR 用ではない」と明示裁定を貰う必要がある。

## 6. 縮小をやらなくても動かないもの(参考)

反駁を通しても「落とす議論の対象外」として残ったもの。将来の裁定のときに使う。

- **隠す記法**(`%% %%` / `%%%` / `:::comment`)── 落とすと**隠していた本文が漏れる**。
  他の fold は「誤りが見える方が良い」で正当化できるが、ここだけ逆向き
- **リンク scheme**(`asset:` / `entry:` / `pkc://`)── データ契約。`asset:` は添付 GC の
  到達性判定そのもので、落とすと bytes が復元不能に消える
- **frontmatter 一式** ── 全 flavor の保存形(記法ではなくスキーマ)
- **fence 一式** ── マニュアルの約束かつ spreadsheet flavor の保存形。mermaid は
  「描いたら焼く」不可侵指示の入口
- **markdown-it 本体の設定** ── goldens 25 件の byte 一致契約がこの上に載る
- **日本語組版の 4 点**(ルビ / 圏点 / 空行 `_N` / 字下げ `__`)── 使用数が少なくても
  代替が無い。北極星の「必要十分」= 日本語の本文が組めること
- **行頭アライン 5 形** ── マニュアルが typo 3 形の受理まで明記して約束済。
  実装は 1 正規表現なので縮小しても段が減らない = **買える物が無い**
- **見出し slug と目次** ── 外に配った HTML の `#slug`・PKC2 のログ permalink 書換が
  全部これに載る(§2 の実バグの当事者でもある)
- **`neutralizeSentinels`**(入口の PUA 無効化)── sentinel 方式の唯一のガード
