## 0. 何を決めたいか

PKC2 との**最大の落差**が「Word / PowerPoint に出せない」ことである。
出口を作るにあたり、**どの道を通すか**を 1 つ選ぶ。user 裁定が要るのはここだけ。

## 1. 事実(実地調査 2026-08-15。推測ではない)

### 1-1. PKC2 は 2 系統・3 実装で作り、片方だけ成功した

| 系統 | 形式 | 依存 | 結果 |
|---|---|---|---|
| AST 経由 | `.docx` / `.pptx` | `docx` 361KB + `pptxgenjs` 269KB + jszip 96KB = **725.5KB** | 多数の欠落を抱えたまま着地(下記) |
| 手書き OOXML | `.xlsx` | **依存 0**(文字列で XML + store-only ZIP) | **唯一、実パーサで読み返す test がある** |
| ブラウザ印刷 | PDF | 0 | 動くが、日本語フォント埋め込みは**していない**(`@font-face` 0 件) |

🔴 **PKC2 の docx / pptx で実際に落ちていたもの**(すべて**黙って**落ちる):
mermaid 等の図は**原文が等幅で出る** / 数式は OMML でなくただの斜体 / ルビは近似 /
SVG 画像は消える / **全画像が 480×360 に固定**(縦横比を見ない) / TOC・ヘッダ・
フッタ・ページ番号・core properties は無し。
そして **pptx は画像が 1 枚も出ない** ── `container` を渡す呼び出し元が**存在しない**
(docx 側は同じ見落としを 1 度踏んで直した。pptx は smoke が無かったので残った)。

🔴 **速度・メモリは 1 度も測られていない**(`bench-results/` に export の計測 0 件、
worker 化 0 件 = `Packer.toBlob` はメインスレッド)。「重い」という記録があるのではなく、
**測っていない**。

### 1-2. PKC2 の構造的な失敗は「レンダラが 2 本ある」こと

画面・印刷は markdown-it 系(4,191 行)、書き出しは AST 系(1,238 + 1,118 行)。
**「Word で直した」が PDF に届かない / その逆も届かない**。記録された不具合のほぼ全部が
この土台の上に乗っている。

### 1-3. PKC3 にいま在るもの / 無いもの

**在る**:
- 書き出しの土台が 1 本(`ArchiveSource` / `exportArchive` / `zip-writer` / 添付の包含判定 /
  ファイル名 / ObjectURL の寿命管理)
- **貼れる HTML**(`features/export/clipboard-html.ts`)── **すでに Word へ貼る経路**
- 塊 ↔ 原文の対応(`splitTopLevelBlocks` + `buildBlockPartition` + `SourceRange[]`)
- 図のラスタ(PNG・IDB キャッシュ)とベクタ(SVG は書き出し時だけ)
- 印刷 CSS と紙面(`@page` の `size`)。**PDF は「印刷から」出せる**(smoke が 3 枚以上を pin)
- worker-lease(遅延起動 / バッファ / アイドル kill)

**無い**:
- 🔴 **AST**。`renderMarkdown` は**文字列 → 文字列**で、前処理 23 段が PUA sentinel を挟むため、
  **`md.parse` の token は最終文書を表していない**
- 🔴 **ZIP の deflate**(書き側は store 固定。読み側は deflate を読める)
- 🔴 **LO wasm に「開く」以外を頼む口**(`--convert-to` の呼び出し 0 件。`saved` メッセージは
  型と parse だけ在って**送り手も受け手も無い**)
- `@page` の余白・柱・頁番号(`size` のみ)

## 2. 道は 3 本ある

### (a) 画面の HTML を Office が読める形に寄せる
Word は HTML を開ける。`clipboard-html.ts` が既に**貼れる HTML** を作っている。
- 利点: **レンダラが 1 本のまま**。実装量 M。今日の資産の延長
- 欠点: 段組・改頁・ヘッダフッタの制御が弱い。pptx にはならない

### (b) 手書き OOXML を、**画面と同じ HTML から**組む
PKC2 で唯一成功した形(xlsx)を、docx へ広げる。材料は AST ではなく
**塊分割された HTML 断片**(`splitTopLevelBlocks`)。
- 利点: 依存 0 / **レンダラは 1 本のまま**(画面と同じ出力を写す)/ 段組・改頁・
  ページ番号まで自分で出せる / worker へ丸ごと逃がせる
- 欠点: 実装量 L。写像の網羅は**記法の数だけ**要る(ただし**落ちたら断る**形にできる)

### (c) LibreOffice wasm に変換させる
すでに 77MB の一式を配っており、Writer / Calc / Impress が動いている。
- 利点: 忠実度は最も高い。pptx / xlsx / PDF が同じ口で出る
- 欠点: **未検証の穴が多い** ── wasm ビルドに headless 変換の経路があるか未確認 /
  MEMFS から読み出す口が無い / 受け渡しが **BroadcastChannel = コピー**(ゼロコピー指示と
  唯一衝突している場所)/ 一式を入れていない user には出口ごと無い / 窓 1 つで約 750MB

## 3. 推薦(1 つ)

> **(b) を本線にする。ただし段階を切り、まず `.docx` だけ。PDF は印刷のまま。**

理由は 3 つ:

1. **PKC2 の失敗の根はライブラリではなく「レンダラ 2 本」だった。** (b) は画面と同じ
   HTML を写すので、**構造的に分岐しない**。(a) も同じ性質を持つが、段組・改頁・
   ページ番号という**帳票の core** が出せない
2. **依存を足さない選択が、たまたま最も強い test を生んだ**のが PKC2 の実績である
   (手書き xlsx だけが実パーサで読み返されていた)。⚠ これは「軽いから」ではない ──
   配る量は判断理由にしない(user 指示 2026-08-03)。**自分で組んだから、自分で
   読み返せた**という因果である
3. **(c) は魅力的だが、いま未検証の穴が 3 つある**(headless 変換 / MEMFS 読み出し /
   コピー経路)。**#156 の IME が 1 ビルド ≒ 4 時間の回転**であることを考えると、
   ここに本線を賭けるのは高い。⚠ ただし **(c) を否定しない** ── (b) が着地したあと、
   「pptx / xlsx は LO に任せる」は自然な次段である

### 覆る条件

- **LO wasm の headless 変換が動くと実測できたら**、pptx / xlsx の担当は (c) へ移す
  (docx も忠実度で上回るなら本線ごと移る)。⚠ この検証自体は (b) と**並行**でよい
- user が「Word より PowerPoint が先」と裁定したら、(b) の段階順を入れ替える
  (pptx の手書きは docx より重い ── その場合は (c) の検証を先に回す)

## 4. 段階(#187 にぶら下げる)

| 段 | 中身 | 落ちたときの断り方 |
|---|---|---|
| ① | 塊 → docx の写像(段落 / 見出し / 箇条書き / 表 / 引用 / コード / 水平線) | 写せない塊は**その場に理由を出す**(黙って落とさない) |
| ② | 画像(添付 + 図の PNG)。⚠ **縦横比を保つ**(PKC2 は全部 480×360 に潰していた) | 解決できない画像は alt を文字として残し、件数を返す |
| ③ | 紙面(`page-format` と同じ値)・改頁(`+++`)・ページ番号・見出しの段落書式 | ─ |
| ④ | worker へ逃がす(worker-lease の 5 本目)+ 大きい文書の実測 | ─ |
| ⑤ | `:::if{format=docx}` を**生かす** ── いまは `'html'` 固定で**永久に不可視**。
     Office 出口ができて初めて**落ちていた動線が戻る**(不可侵「記法を減らすことは
     user の動線を減らすこと」の逆向き) | ─ |

## 5. 検証の型(PKC2 の轍を避ける)

- 🔴 **生成物を開いて中を見る**。`.docx` を unzip し、**主張した部分の OOXML パートを
  名指しで読む**。⚠ PKC2 は `word/numbering.xml` を 1 度も読まなかったため、
  箇条書きの実装が**マニュアルの記述と食い違ったまま 3 ヶ月**残った
- 🔴 **経路ごとに smoke を持つ**。PKC2 の pptx が画像を 1 枚も出さないまま残ったのは、
  docx にだけ smoke があったからである
- 🔴 **速度とメモリを測る**(PKC2 は 0 件)。対照群は「同じ文書を HTML で書き出す」
