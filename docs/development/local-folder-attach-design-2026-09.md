## 1. 画面で何が起きるか

1. **パソコンのフォルダを開く…** を押す → OS のフォルダ選択が出る
2. 選ぶと、**そのフォルダの中の file が一覧で出る**
3. file を押すと **PKC のノートとして開く**(いつもの本文の面)
4. 直して **保存** を押すと、**パソコン側の元の file も書き換わる**
5. やめたくなったら **切る** を押す(次に開いたときは繋がっていません)

⚠ **消す口は置きません**(§4)。⚠ 繋いだことは**憶えません** ── 毎回選び直します
(#854 段② と同じ裁定。片方向の作り足しなので、煩わしければ後から「憶える」を足せます)。

## 3. 継ぐ作法(既に在る 2 本が決めている)

### ⚠ ① handle は **このセッションだけ**の記憶。どこにも保存しない

`local-office-files.ts:6-11` が理由まで書いています:

> 保存すると「昔どこかで開いたファイル」への書込権をアプリが黙って持ち続けることになる
> (user が意識していない同意の延命)。読み直したら紐づけが消えるのが**正直な寿命**である。

🔑 **フォルダでも同じ**にします。⚠ IndexedDB に入れれば「次も自動で繋がる」は作れますが、
それは**上の裁定と正面から逆**です(#854 段② の「毎回選び直す」とも揃います)。

### ⚠ ② handle を reducer に入れない

`app-state.ts:864` に明記:**`FileSystemFileHandle` は不透明で比較も複製もできない**ので、
純粋な reducer には入れない。🔑 state が持つのは**名前と lid だけ**で、handle は
`LaunchedFiles` と同じ形で**アダプタ側の Map** に置きます。

### ⚠ ③ 許可を求めるのは **user が押した流れの中**でだけ

`local-office-files.ts:98-99` が理由を書いています ── `requestPermission` は user の操作の
中でないと断られることがある。🔑 だから**押した流れの中で**確かめます。

## 4. 🔴 書けるようにすることの危なさ(と、4 つの守り)

⚠ ブラウザの書き込みは **既定で先に中身を空にしてから**書きます
(`launched-files.ts:135-137` に既に注意書きが在る)。⚠ そして **PKC の中のデータと違い、
パソコンの file は取り消せません**。

🔑 だから**作り方のほうで受けます**(user 裁定 2026-09-14 のコメントで宣言済み):

| 守り | 画面で何が起きるか |
|---|---|
| **上書きは必ず 1 度聞く** | 「○○.md を上書きします」と出て、押さなければ何も起きない |
| **削除は PKC からやらない** | 消すのは OS の file 画面で。PKC に「消す」を置かない |
| **空の本文で上書きしない** | 中身が空になる保存は、その場で断って理由を出す |
| **書けた / 書けなかったを必ず言う** | 黙って失敗しない(許可が切れた / 他で開かれている、など) |

⚠ **4 つ目は既に形が在ります** ── `WriteBackResult = { ok: true } | { ok: false; reason }`
(`launched-files.ts`)。理由を値で返す形なので、**握り潰される経路がありません**。

## 5. ⏸ 残っている 1 問 ──「見えた file を、どこに置くか」

> **つないだフォルダの中身を、いまのノートの一覧に混ぜますか。別の場所に出しますか。**

⚠ ここは**お好みが割れやすい所**なので、3 つを**画面の言葉**で並べます。

### A ── 一覧に混ぜる(「これは外にあります」の印つき)

| | |
|---|---|
| 画面 | いつものノートの一覧に、外の file が**印つきで並ぶ** |
| 🟢 良い所 | 「PKC の中に全部ある」感じになる。探す欄で一緒に引ける |
| 🔴 困る所 | **消したつもりがパソコンの file だった**、が起きる |
| ⚠ 作る量 | **大きい** ── 一覧は `filerRows`(`filer-list.ts:68`)が作り、場所は **`scopeLid: string | null`(PKC のノートの lid)**という 1 つの座標で表されている。外の path を混ぜるには**この座標系を作り直す**ことになり、`getStructuralChildren` / `DualTab` / 探す / 並べ替え / 履歴 / 書き出しの**全部**に「外か中か」の区別を通す |

### B ── 別の場所に出す(別のタブ / 別窓)

| | |
|---|---|
| 画面 | 「パソコンのフォルダ」という**別の面**に、繋いだフォルダの中身だけが並ぶ |
| 🟢 良い所 | 中と外が**目で見て分かれる**。いまの面は 1px も変わらない |
| ⚠ 作る量 | **小さい** ── 予定表 / 連絡先 / 音・動画 と**同じ形**(左のタブ + 別窓 + 塞がれたら左へ戻す)が既に在る |
| 🔴 困る所 | 直すときに**面を行き来する**(外の一覧 → 本文 → 外の一覧) |

### C ── **取り込んで、PKC のノートにする**(⚠ いま `launchQueue` がやっている形)

| | |
|---|---|
| 画面 | 一覧から押した file が**そのまま PKC のノートとして開く**。保存すると**元の file にも書き戻る** |
| 🟢 良い所 | 探す・並べ替え・履歴・書き出しが **1 つも変わらない**(ただのノートなので)。⚠ **書き戻しの道は既に出荷済み** |
| 🔴 困る所 | 「PKC の中にコピーが出来る」ので、**外と中が二重に在る**期間ができる |

### 🔑 推薦:**B を入口にして、C で開く**

- **入口は B**(別の場所)── 繋いだフォルダの一覧は**専用の面**に出す。
  ⚠ こうすると「消したつもりが外の file」が**原理的に起きません**(その面に消す口を置かない)
- **開いたら C**(取り込む)── 押した file は PKC のノートになり、**保存で元へ書き戻る**。
  🔑 ここは**既に動いている道**なので、新しく作るのは入口だけです

⚠ **A を推さない理由は「好み」ではありません** ── 上の表のとおり、
**一覧の座標系そのものを作り直す**ことになるためです(実測:`scopeLid` は
`filer-list.ts` / `dual-pane.ts` / `tree.ts` の 3 本に跨っています)。

🔑 **これが分かったら覆ります**:実際に使ってみて「外の一覧と本文を行き来するのが煩わしい」
となれば、**B の面の中に本文を出す**(2 ペインのように)側へ倒します。

## 8. ⚠ まだ測っていないこと

- **Chromium 以外**:Firefox は File System Access を持たず、Safari は制限つき
  ── 🔑 だから**押し所を出すかどうかを feature-detect で決める**(「押せるのに何も起きない」を作らない)
- **フォルダの中が多いとき**(1 万 file)の一覧の速さ ── `FileSystemDirectoryHandle.entries()` の
  実測は 0 件(使用例が無い)
- **権限がどれだけ持つか** ── handle をセッション限りにするので実害は小さいが、
  **1 回の作業の途中で切れるか**は測っていない
- **OPFS(PKC の DB)との相性** ── 同じ端末で両方を触ったときの割当・権限は未測
- **#532(セルフホスト)との順番** ── どちらも「PKC の外にある物をどう扱うか」なので、
  先にどちらを出すかは裁定が要る
