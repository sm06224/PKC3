## 1. PKC2 の実地調査(段⑦ の材料)

PKC2 を read-only で調べた(user 指示 2026-07-30。手は出していない)。
**流用ではなく総合的見直し**の判断材料として、数と欠陥を先に置く。

### 1.1 書式リボン ── 大きすぎて、既定で隠されていた

| 事実 | 根拠 |
|---|---|
| `format-panel.ts` 747 行。6 group / 操作 29 / 値ピッカー 6 / ダイアログ 1 | `FORMAT_GROUPS` = `format-panel.ts:487-577` |
| 可視クリック要素 **42**、ポップアップ内 option がさらに **28** | 同上 + `:379-465` |
| **既定では見えない**(`shell.format_panel_default_hidden_enabled` が既定 true) | `shell-flags.ts:399-407` |
| 書式ショートカット 5 個は **flag が既定 OFF** | `editor.format_shortcuts_enabled` |

作りすぎた結果、自分で隠した。user U-15「何でも button 化は悪い兆候」が
PKC2 自身の doc に記録されている(`vscode-grade-overhaul-2026-05/MASTER.md:251`)。

### 1.2 🔴 そのまま流用してはいけない欠陥(実測)

PKC2 の該当関数をそのまま node で走らせて確認した:

| 欠陥 | 実測 | 場所 |
|---|---|---|
| **インラインにトグル解除が無い** | `**hello**` + 太字 → `****hello****` | `wrapInline`(`format-panel.ts:47-56`、条件分岐ゼロ) |
| **見出しにトグル / レベル置換が無い** | `# hello` + H2 → `## # hello` | `prefixLines`(`:71-85`) |
| **脚注がハリボテ** | `/footnote` は `[^1]` を固定挿入。定義行も採番も無い(2 回使うと重複) | slash-menu |
| **図(mermaid)に挿入導線が無い** | fence を手打ちするしかない | src 全体 grep で 0 件 |

PKC2 の spec(`phase-beta-group-c-format-panel-spec-2026-05.md:363-364`)は
「`**hello**` + Bold → `hello`(toggle off)」と**書いてあった**。
実装が追いつかないまま、test にもトグル解除のケースが 1 件も無かった
── 「通っている test は、何も保証していないかもしれない」の実例。

### 1.3 🔴 最大の肥大要因 ── 同じ操作が 4 面に別実装で散らばる

書式リボン(29 op)/ スラッシュメニュー(31 cmd)/ snippet-toolbar(20 kind)/
コマンドパレット(inline 5 + テンプレ 14)が、**それぞれ独自のテーブル**を持つ。
PKC2 の spec は「共通の `FORMAT_OPERATIONS` registry を 1 つ持つ」と設計していたが、
**registry は作られなかった**。結果として:

- 左揃え `<|` は「レンダラ上 `|>` と同じ end へ写像され左揃えにならない」として
  リボンからは除外されたのに、**snippet-toolbar とコマンドパレットには生き残っている**(死んだ操作)
- 圏点は `^^text^^` が canonical と宣言済みなのに、2 面が旧形 `[[em:…]]` を挿入し続けている

### 1.4 残すべき資産(捨てない)

**純粋な変換ロジックと座標計算**は価値が高い ── 行拡張つき prefix トグル /
align 3 種排他 / リスト marker トグル + 採番連携 / pipe table の caret ベース構造編集 /
mirror-div のキャレット座標。いずれも DOM 非依存で、テストも厚い。

## 2. 段⑥(着地済み)── 書式パネル

**14 操作、常設、単一の正本**。

```
見出し1 見出し2 見出し3 | 太字 斜体 コード | 箇条書き 番号 チェック 引用 | リンク 表 図 コード塊
```

| 決めたこと | 理由 |
|---|---|
| 規則は `features/markdown/text-ops.ts` の `FORMAT_OPS` / `applyFormat` **だけ** | §1.3 の「4 面に散らばる」の再演を最初から塞ぐ。描画側は表を並べるだけ、binder は「選択を読む → 渡す → 書き戻す」だけ |
| **畳まない**(既定で見えている) | §1.1 の「作りすぎて隠す」の逆。14 個なら畳む必要が無い |
| 図案(絵文字)を付けない | 14 個並ぶと読めない。高さは CSS(`--row-h`)が揃える |
| 近道キーは Ctrl+B / I / K の 3 つだけ | 「キーボードは近道」── **パネルに無い操作をキーだけに置かない** |

### 2.1 🔴 印の**本数**で判定する(PKC2 の欠陥の修正)

`*` の連なりを数える。これがないと `**太字**` の内側で斜体を押したとき、
太字の印を 1 個ずつ剥がして `*太字*` にしてしまう(**押した人は斜体を付けたつもりなのに太字が消える**)。

- 太字(2 文字)は **2 本以上あれば自分のもの**
- 斜体・コード(1 文字)は **奇数のときだけ自分のもの**

結果:`**太字**` + 斜体 → `***太字***`、そこで斜体 → `**太字**` に戻る。

### 2.2 行頭の印は「付ける印」で判定しない

- 番号付きは付けた直後に `2. ` `3. ` になるので `1. ` では**二度と外せない** → `/^\d+\. /`
- `- ` はチェック `- [ ] ` の頭とも一致する → `/^- (?!\[[ x]\] )/`
  (除外しないと、チェック行に箇条書きを押した瞬間 `[ ] やること` に化ける)

### 2.3 やらなかったこと(意図的)

文字色 / 背景色 / 文字サイズ / 書体 / 表の行列編集 / 検索置換 / ルビ / 圏点。
どれも PKC2 には在るが、**14 個を超えると畳みたくなる**。畳んだ瞬間に
§1.1 と同じ場所に戻る。要るという判断が出たら、そのとき足す。

## 3. 段⑥(着地済み)── 追記

### 3.1 🔴 doc が先に嘘をついていた

`docs/manual.md:56` は「**ログ** = 追記型。`## <日時>` の節を末尾に足していきます(秒まで)」と書き、
`textlog-flavor.ts:3` も「追記 = 末尾への節 append(P3-5 で編集 UI が実装)」と書いていた。
**その UI は一度も存在しなかった。**

docs-parity test は緑のまま腐っていた ── pin していたのは「ログ」という**文言**だけで、
振る舞いの主張を縛っていなかった。今回 `APPENDABLE_ARCHETYPES` と
マニュアルの記述を突き合わせる test を足した。

### 3.2 🔴 追記専用の書込経路を作らない

PKC2 の追記は「専用 textarea + `QUICK_UPDATE_ENTRY` で直に store へ書く」形で、
**編集中は追記欄が出ない**ことで競合を避けていた(構造的な回避)。
PKC3 で同じ形を作ると、`START_EDIT` の draft と別経路の書込が競合し、
**追記した節が保存で黙って消える**(PKC2 側で実測して再現した経路)。

PKC3 は追記を**編集操作**にした:

```
閲覧中に「追記」を押す → START_EDIT → 編集欄の末尾に節を足す → カーソルを末尾へ
```

書込経路は `COMMIT_EDIT` 1 本のまま。履歴も普通の編集と同じ 1 件で、
「追記のたびに revision を積んで 100 件 cap に張り付く」問題も起きない
(PKC2 は追記のたびに無条件で revision を 1 件積み、保持上限も無かった)。

### 3.3 何を足すか

| 種類 | 足すもの |
|---|---|
| **ログ**(textlog) | `## YYYY-MM-DD HH:mm:ss` の節(秒まで) |
| **ノート**(text) | 空行だけ ── **見出しは足さない**(構造は書く人のもの) |

判定は `features/flavor/append-spec.ts` の 1 か所。
描画側(ボタンを出すか)と binder(何を足すか)が別々に育つと、
「ボタンは出るが何も起きない」がすぐ生える。

⚠ PKC2 の text 追記は「**章を選んで差し挟む**」までできた(user の明示指示由来)。
PKC3 は末尾追記だけにした ── 要るなら段⑦ 以降で。

## 4. 段⑦ 提案 ── スニペット(Text Blaze 相当)

### 4.1 Text Blaze の正体(調査)

3 層:

1. **短縮語 → テンプレート展開**(`/addr` と打つと住所が展開される)
2. **挿入時に埋める入力欄**(`{formtext}` `{formmenu}` `{formtoggle}` …)
3. **動的コマンド**(`{time}` `{if}` `{repeat}` `{import}`、外部連携は DB / URL 系)

発火の誤爆対策は**フォルダ単位の 3 択トリガ設定**
(① 前が語境界 ② 前後が語境界 ③ どこでも)。

### 4.2 PKC3 が**すでに持っている**もの

| Text Blaze | PKC3 の既存機構 | 違い |
|---|---|---|
| `{formtext}`(差し込み) | frontmatter `vars.x` → 本文の `{{vars.x}}` | **描画時**に展開(挿入時ではない) |
| `{if}` | `:::if{format=X}` の条件ブロック | 同上 |
| `{import}` | ─ | 無い |

つまり PKC3 に足りないのは **① 短縮語の展開**と **② 挿入時に埋める**の 2 つ。

### 4.3 置き場所(**裁定点 A**)

「どの entry がスニペットか」を**本文を読まずに**知る手段は archetype 列しかない
(archetype は常駐のリーン集約に入っており、ランチャーが同じことを既にやっている)。

- ⚠ `settings` 表は DDL に在るが、**worker に読み書きが 1 つも無い** ──
  「設定に置き場所を持たせる」設計は新しい protocol op と worker 実装を要求する
- ⚠ flag に入れるのは論外(PKC2 は 14 種のテンプレ本文を**文字列フラグ 1 本に JSON で**
  詰めて Flags インスペクタで手編集させていた。PKC3 の「flags は最大 15 個、
  正規設定と分離」と正面から衝突する)

**提案: 新 archetype `snippet`。本文は PKC-Markdown、短縮語は frontmatter。**

```markdown
---
abbr: addr
---
〒100-0000 東京都千代田区…
```

利点:
- **JSON 文字列 body を作らない**(不可侵指示)を守れる
- バックアップ・書き出し・取り込み・履歴・検索が**何も足さずに**通る
  (export は archetype で絞っていない)
- archetype を 1 つ足すコストは小さい ── 未知 archetype は text にフォールバックするので
  既存データは無傷、触るのは registry・作成の選択肢・ラベルの 3 箇所

### 4.4 発火(**裁定点 B**)

**提案: 短縮語 + `Tab`、および `/` のスラッシュメニュー。両方。**

理由 ── 短縮語は「覚えている人には最速」、スラッシュは「覚えていない人が探せる」。
片方だけだと、どちらかの人が使えない。

⚠ **Text Blaze の「自動展開」は採らない**。日本語入力では未確定文字列が
`value` に入るので、打った瞬間に展開する形は誤爆が避けられない(§5 の実測)。

### 4.5 挿入時に埋める(**裁定点 C**)

**提案: `${…}` をプレースホルダにし、挿入後に最初の 1 個を選択。`Tab` で次へ。**

- `$` は PKC-Markdown で**未使用**。`{{…}}` は `{{vars.x}}` に取られている
- **フォームダイアログは作らない** ── `form` アーキタイプは
  「機能を煮詰める前に作り込んで破綻した」ため封印中であり、
  Text Blaze 型のフォームダイアログはその**再演**になる。
  本文の中で Tab 移動するだけなら、新しい UI 面が 1 つも増えない

### 4.6 動的値(**裁定点 D**)

**提案: 最小 4 つだけ ── `${date}` `${time}` `${datetime}` `${cursor}`。**

計算式・条件分岐・繰り返し・外部連携(Text Blaze の Formula / If / Repeat /
DBSelect …)は**入れない**。「新機能を盛り込みすぎない」。
条件分岐が要るなら PKC3 は既に `:::if{}` を持っている(描画時)。

## 5. 🔴 IME の実測(段⑦ の前提)

headless Chromium で実測した(推測ではない):

| 観測 | 結果 |
|---|---|
| 変換中の `value` | **未確定の文字列が既に入っている** ── 「カーソル手前を読んで短縮語を探す」を変換中に走らせると未確定文字列を誤認する |
| 確定の瞬間の `input` | `inputType="insertCompositionText"` かつ **`isComposing=true`**。`compositionend` はその**後** |
| 素の ASCII 打鍵 | `inputType="insertText"` / `isComposing=false` |
| 変換中の Tab | `keydown key="Tab" isComposing=true` |
| 確定直後の Tab | `isComposing=false` |

したがって:

- 短縮語の探索は **`inputType === 'insertText'` のときだけ**走らせる(IME 由来を全部弾ける)
- `Tab` をトリガキーにするのは IME 的に安全(binder の既存ガード `if (ke.isComposing) return;` が両方を正しく捌く)
- ⚠ textarea の Tab は既定でフォーカス移動。**展開しないときに `preventDefault()` すると
  既存のキーボード導線を壊す** ── 短縮語が当たったときだけ止める

## 6. やらないこと(段⑦ の scope 外)

| 却下するもの | 理由 |
|---|---|
| フローティング / 選択追従の書式パネル | PKC2 が一度作り、**user 判断で scrap-and-build された履歴**がある。snippet-toolbar も v1〜v3 を「醜い + 使い勝手が悪い」で潰して v4 に落ち着いた ── 再発禁止 |
| テンプレ本文を flag に詰める | §4.3 |
| フォームダイアログ | §4.5 |
| 計算式 / 繰り返し / 外部連携 | §4.6 |
| コマンドパレット・snippet-toolbar・リボンの 4 面展開 | §1.3 の肥大要因そのもの。入口は「短縮語 + Tab」と「`/`」の 2 つに固定する |

⚠ **スラッシュメニューは 1 キーごとに全破棄・全再生成しない**。PKC2 は
`innerHTML = ''` → 45 項目を append を毎打鍵やっている(仮想化もインクリメンタル更新も無い)。
PKC3 の「常駐メモリと操作の応答で語る」方針では、ここは**測る対象**になる。

## 7. 段取り(裁定が出たら)

1. `snippet` archetype + frontmatter `abbr:`(作成の選択肢・ラベル・registry)
2. 展開の純関数(`features/markdown/snippet-expand.ts`)── `${…}` の走査と Tab 移動
3. 短縮語の探索(`inputType === 'insertText'` 限定)と `Tab` の分岐
4. スラッシュメニュー(短縮語と**同じ表**を引く ── 2 つ目のテーブルを作らない)
5. 変異試験:IME 経路 / Tab の素通し / `${}` の走査 / 表の二重管理が生えていないこと
