## 1. いま何が起きているか(実装から書き出す)

⚠ 散文で「分かりにくい」と言い直しても直らないので、**user が実際に踏む順**に書く。
根拠はすべて `file:line`(issue や過去 doc の記述は根拠に使っていない)。

### 1-1. 物語 A ── 「今日の予定を見たい」

1. 左の列の **アプリ**タブを押す(`render/browse.ts` の `BROWSE_TABS`)
2. タイル「カレンダー」を押す(`features/launcher/tiles.ts:192`)
3. `openViewTile`(`main.ts:246`)が **`window.open(url, '_blank', 'noopener')`** を撃つ
4. 🔴 **PKC がもう 1 つ立ち上がる** ── 別窓は `#pkc?view=calendar&container=…&entry=…`
   を読んで boot し、**左の列も中央も右の列も全部持っている**

> 🔴 **これが user の言う「もう一つPKCが開いて混乱する」の実体である。**
> 別窓は「カレンダー」ではなく **PKC そのもの**で、たまたまカレンダーを開いている。
> ⚠ しかも**選んでいるノートも編集中かどうかも 2 つに分かれる**ので、
> どちらの窓で何をしていたのかが user の頭の中でしか繋がらない。

5. ⚠ ポップアップが塞がれていたら、**中央の面**に出る(`openInPane`)──
   つまり**本文が消える**。これは #300 で user が名指しで断じた形である
   (「**メインの PKC の機能を阻害する方向で PKC のセンターペインを占有するな**」)

### 1-2. 物語 B ── 「このノートに日付を付けたい」

いまの**唯一の**書き口は、**カレンダーの日を押すこと**である
(`binder.ts:1557` の `calendar-set-date` → `SET_ENTRY_DATE`)。だから:

1. 日付を付けたいノートを**先に選ぶ**
2. カレンダーを開く(= 別窓が立つ / 本文が消える)
3. 日を押す

⚠ この面は自分でもそれが無理筋だと知っていて、帯にこう出している
(`render/calendar.ts:135`):

> **「日を押す前に、左の一覧からノートを選んでください」**

🔴 **カレンダーは「見る面」の顔をして、実体は「日付を書く道具」だった。**
だから見に行くだけの人にも「先にノートを選べ」と言う。

### 1-3. 物語 C ── 「やることを見たい」

1. アプリタブ → タイル「やることの板」→ また別窓
2. 盤面に出るのは **`task_total > 0` の全ノートの、全チェック項目**
   (`storage-worker.ts:461` の `TASK_CANDIDATE_WHERE` / `task-count.ts` の `listTaskItems`)
3. 🔴 **本文の体裁として書いたチェックリストも、1 行残らず札になる**

> 🔴 **これが user の言う「これはただのノイズ」の実体である。**
> 走査の docstring は「**少なく数えるのは害**」と書いて **superset(多め)**に倒しており、
> ⚠ **多めに倒す判断そのものは正しい**(候補の絞り込みとしては正しい)。
> 間違っていたのは、**候補をそのまま盤面に出したこと**である。

### 1-4. 数え直すと ── 予定の口は **2 つに割れている**

| | 単位 | どこに書く | どの面が読む |
|---|---|---|---|
| カレンダー(#276) | **ノート 1 件** | frontmatter の `date:` | `entries.date` 列 |
| 板(#277) | **本文の 1 行** | チェックリストの `- [ ]` | `task_total` 列 → 本文走査 |

🔴 **同じ「予定」に、単位も書き方も読み手も違う口が 2 つ在る。**

## 2. 🔑 2 つの苦情は、同じ 1 つの誤りである

①(別窓が混乱する)と②(札がノイズ)は別々の話に見えるが、**根は 1 つ**である ──

> 🔴 **どちらの面も、user が頼んでいない問いに、user が選んでいない場所で答えている。**

- カレンダーは「**この選んだノートに日付を書きたいか**」に答える。user は
  「**今日は何がある**」を知りたかった ── しかも**本文を退かして**答える
- 板は「**この容れ物の全チェック項目**」に答える。user は
  「**やることは何か**」を知りたかった ── 体裁のチェックボックスまで含めて答える

そして user が endorse した一文が、**両方の直し方を同時に言っている**:

> 「**日付を入れたチェックリスト、これが予定として機能する**」

これを設計の言葉に直すと 2 つになる ──

1. 🔑 **予定は「本文の、その行」に書く**(面へ行って書くものではない)
2. 🔑 **予定は「日付を持つもの」だけ**(全チェック項目ではない)

⚠ **①はカレンダーの置き場所を決める。** 書く仕事が本文へ移れば、カレンダーは
**読むだけの面**になる ── 読むだけの面は user を連れて行く必要が無いので、
**本文を退かす理由も、別窓を立てる理由も消える**。

⚠ **②は板の中身を決める。** 「日付を持つもの」で絞れば、体裁のチェックボックスは
最初から入ってこない ── **後から間引く仕掛けが要らない**。

🔑 したがって**この doc の設計は 1 行に畳める**:

> ## 🔴 予定は本文に書く。面はそれを映すだけ。

## 3. 🔴 カレンダーは「アプリ」ではない ── #300 との関係を先に片付ける

⚠ user は **2026-08-21 に「組み込みアプリを全部別窓で使えるようにしろ」と要望している**
(#300)。今回の①はそれと**逆向きに見える**ので、先に切り分ける。

**矛盾していない。** #300 が指していたのは **Office / PDF / タイマー / 連絡先**のような、
**それ自体が別のアプリケーションであるもの**である。カレンダーと板が別窓化に巻き込まれたのは、
**たまたま `ViewMode` だったから**にすぎない(`main.ts:246` の
`view: 'dual' | 'calendar' | 'kanban'` がその 3 つを同じ口に押し込んでいる)。

🔑 **境目はここに引く**:

| | 何か | 置き場 | 例 |
|---|---|---|---|
| **アプリ** | PKC の外から来た、**それ自体で完結する道具** | 🔴 **別窓**(#300 のとおり) | Office / PDF / タイマー / 連絡先 |
| **ノートの見方** | **自分のノートを別の角度から見ているだけ** | 🔴 **シェルの中**(本文を退かさない) | 予定 / 一覧 / フォルダ |

⚠ 見分け方は 1 つ:**それを閉じたとき、user が失うものは何か。**
Office を閉じれば Office が消える(別物なので当然)。
**カレンダーを閉じて自分のノートが見えなくなるのは、おかしい。**

⚠ 現状はタイル一覧で **`カレンダー` `やることの板` が `Office` と横並び**になっている
(`tiles.ts:229` の `builtin` 配列)── **画面がこの分類の誤りをそのまま出している**。

## 4. 設計

### 4-1. 記法 ── `@2026-08-19` / `@2026-08-19 14:00`(#292 の裁定を受ける)

user の②が「日付を入れたチェックリスト」を endorse したので、**行に日付を書く記法**が要る。
#292 で 2 本の独立したレビューが推薦していた **(a) `@` + 完全な日付形**を採る。

```markdown
- [ ] 見積を送る @2026-08-25
- [ ] 打ち合わせ @2026-08-25 14:00
- [ ] これは体裁のチェックリスト(日付が無いので予定ではない)
```

- 🔴 **受けるのは「`@` + 完全な日付形」だけ。** ⚠ `@1,500`(単価)や `@3`(個数)は
  日本語の業務文で普通に書かれる ── **`@` の次が数字なら日付**と字面どおり実装してはならない
- 🔑 既存記法と**文字レベルで排他**である ── 本文の札は **`@[card](entry:…)`** で
  `@` の直後は必ず `[`(`features/link/card-presentation.ts:70` の `CARD_RE` がそう書いてある)
- 時刻は**省略可**。付けるときは `YYYY-MM-DD HH:MM`
  (⚠ 空白 + `HH:MM` の後読みなので、`@2026-08-25` 単体と曖昧にならない)
- ⚠ **`📅 2026-08-19` / `[due:: …]` の寛容な読みは、この段では入れない。**
  理由は 1 つだけ:**まだ誰も書いていない形を読んでも、今日は何も買わない**。
  ⚠ 取り込み(Obsidian からの移行)で実際に要ると分かった時点で足す。
  🔑 **足すのも外すのも安いので、急ぐ理由が無い**

### 4-2. ③ 日付を入れる道具 ── **書式の帯のボタン**

> user:「**日付の記法としては入力がめんどくさいから、日付と時刻を簡単に入力できるし、
> ついてくるツールとか用意されてもいいかも**」

🔑 **置き場は書式の帯**(`render/format-bar.ts`)── **`置換` の隣に 1 つ**。

⚠ 「`@` を打ったらその場に出る」型(Obsidian の `date-trigger`)は**採らない**:

- PKC3 に**補完の機構が 1 つも無い**ので、この 1 件のために新設することになる
- ⚠ `@[card]` が**同じ 1 文字目**を使うので、1 打鍵目で衝突する
- 🔴 そして不可侵指示に正面から当たる ──「**マウスだけで完結し、キーボードは近道**」。
  打鍵でしか出ない道具は、**マウスの人には存在しないのと同じ**である

**押したら出るもの**(器は既存の `app-dialog.ts`):

```
┌────────────────────────────┐
│  今日   明日   今週末   来週    │  ← 1 押しで終わる(いちばん多い場合)
│  ────────────────────────  │
│  日付 [2026-08-25]  時刻 [  :  ] │  ← 端末の日付ピッカーをそのまま使う
│                    [ 入れる ]   │
└────────────────────────────┘
```

- 🔑 **格子を自作しない。`<input type="date">` / `<input type="time">` を使う** ──
  端末のピッカー・キーボード操作・地域の書式を**ただで引き継ぐ**
  (⚠ CLAUDE.md §10 の逆 ── ここは native を**置き換えていない**ので、
  ついでの性質を落とす心配が無い)
- 時刻は**空でよい**(空 = 日付だけ)
- 差し込みは **`insertText`**(`render/row-swap.ts`)── ⚠ `execCommand('insertText')`
  を通るので **`Ctrl+Z` で戻せる**
- 🔴 **閉じたら本文へ焦点を返す**(CLAUDE.md §10 の③後始末)。⚠ 返さないと、
  入れた直後にキーが全部死ぬ ── P8 段② で実際に踏んだ形である
- 近道は keymap に足す(`features/keymap.ts` は 42 コマンド + 割当変更 UI を持つ)

#### ⚠ ノート 1 件に日付を付ける口はどうなるか

1-2 のとおり、いまの唯一の口は**カレンダーの日を押すこと**である。カレンダーから
書く仕事を外すので、**代わりの置き場が要る**。

🔑 **右の列(情報)へ移す。** 規則は既に決まっている(`render/browse.ts` の表)──
**右 = 選んでいるもの**であり、ノートの日付はまさに**選んでいるノートの属性**である。
⚠ 同じピッカーを呼び、`SET_ENTRY_DATE` を撃つ(**action は既存のものをそのまま使う**)。

### 4-3. ① 見る場所 ── **左の列の 4 つ目のタブ「予定」**

🔴 **中央でも別窓でもなく、左の列に置く。**

理由は「そこが空いているから」ではない。**規則が既にそう決めている**
(`render/browse.ts:9` の表。P8 段⑤ で user 指摘から起こしたもの):

| 場所 | 扱うもの |
|---|---|
| 左 | **ノート全体** ── 探す・作る・入れる・出す・片づける |
| 中央 | **いま開いているもの** |
| 右 | 選んでいるもの |

**予定は「ノート全体を横断して見る」もの**なので左である。そして左の列は
**既にタブの束**(一覧 / フォルダ / アプリ)なので、**新しい機構が 1 つも要らない** ──
タブが 1 枚増えるだけで、スクロール位置の記憶も選択の意味論も既存のものが効く。

```
┌──────────┬──────────────────┬────────┐
│ 一覧 フォルダ    │                        │  情報   │
│ アプリ [予定]   │      本  文             │        │
│ ┌──────┐ │   （ここは 絶対に 消えない ）  │  日付   │
│ │ 8月    ‹ ›│ │                        │  [8/25] │
│ │日月火水木金土│ │                        │        │
│ │      1  2 │ │                        │  タグ   │
│ │ 3 4 5 6 7 8 9│ │                     │        │
│ │ … ㉕ …    │ │                        │  関係   │
│ └──────┘ │                        │        │
│ 今日            │                        │        │
│  ☐ 見積を送る    │                        │        │
│ 明日            │                        │        │
│  ☐ 14:00 打合せ  │                        │        │
│ この先          │                        │        │
│  ☐ …           │                        │        │
│ ▸ 完了(3)       │                        │        │
└──────────┴──────────────────┴────────┘
```

- 🔴 **本文は 1 度も消えない。** これが①への直接の答えである
- 🔑 **上は小さな月**(移動のため)。今日に印、予定のある日に点。押すと下が跳ぶ
- 🔑 **下は時間順の並び**(読むため)── **今日 / 明日 / 今週 / この先**。
  ⚠ **期限切れは「今日」に合流させる**(Apple の Today と同じ定義)──
  別の列にすると「見なくてよいもの」に見える
- **札を押す** → そのノートを中央に開く(既存の `select-entry` がそのまま効く ──
  左の列は元々そういう意味論である)。⚠ **その行まで送る**のは**新しい** ──
  ただし材料は在る(`markdown-render.ts` の `sourceLineAnchors` は本文の面で
  **既に有効**:`render/detail.ts:503` / `:1495`)
- **印を押す** → その行のチェックを反転する(既存の `TOGGLE_TASK` / `applyBodyRewrite`)
- 🔑 **完了は畳んで件数を出す**(`▸ 完了(3)`)── 2026-08-20 に板で決めた作法をそのまま使う
  (**畳むことと隠すことは違う**)

#### ⚠ 幅は足りるか(数える)

左の列は `minmax(200px, 18vw)`(`styles/app.css:62`)── 1920 で 345px / 1440 で 259px /
下限 200px。**7 列の月**は下限でも **28px/セル**で、1〜2 桁の数字なら入る。
⚠ **セルの中に予定を並べるのは捨てる**(いまの中央の面はそれをやっている)──
予定は**下の並び**が持つので、月は**日付と点だけ**でよい。

### 4-4. ② 何を出すか ── **日付を持つものだけ**

🔴 **既定で盤面に出るのは「日付を持つ行」と「日付を持つノート」だけ。**

| 出るもの | どこに書く |
|---|---|
| `- [ ] 見積を送る @2026-08-25` | 本文の行(4-1) |
| `date: 2026-08-25` を持つノート | frontmatter(既存) |

⚠ **1-4 で割れていた 2 つの口が、ここで 1 つの面に合流する** ── 単位は違う
(行 / ノート)が、user から見れば**どちらも「その日にあること」**である。

#### 🔴 日付の無いチェック項目は、**捨てない。畳む**

> 「**文章の体裁としてチェックリストを使いたい場面もある**」

⚠ しかし「体裁のつもり」と「日付を書き忘れたやること」は、**本文から見分けられない**。
🔑 だから **落とすのではなく、既定で出さない切替**にする ──
**「日付のない項目も出す」**(既定 **オフ**)。

- 既定:**ノイズが 0** ✅ user の②への直接の答え
- 1 押し:**いまと同じ全部の一覧が戻る**
  ⚠ ここで切替を置くのは「消してはいけないから」ではない ──
  🔑 **日付を書き忘れたやることが実在する**からである(体裁のつもりと区別が付かない以上、
  片方だけ選ぶと必ず取りこぼす)。切替なら**両方に答えられて、既定はノイズ 0** になる
- 🔑 仕掛けは新しくない ── `showDoneTasks` / `showArchived` と**同じ形の旗**である

⚠ **`task_total` の走査は変えない。** あれは「本文を読む候補を絞る」ための列であり、
**多めに数えるのが正しい**(`task-count.ts` の docstring が名指しでそう決めている)。
🔑 変えるのは**盤面に出す前の絞り**である ── 走査の規律には 1 行も触らない。

## 5. 捨てるもの(ゴーストの一覧)

> 「**既存機能の維持が頭をちらついているなら、それはただのゴーストだから無視しなさい、
> そもそもPKC2でもカレンダーは未完成**」

⚠ **user が名指しで「無視しろ」と言ったので、遠慮せず数え上げる。**
🔑 判定は 1 つ:**捨てたあと、user が「できなくなること」は何か。**

| 捨てるもの | 何だったか | 捨てたら user が失うもの |
|---|---|---|
| `ViewMode` の **`calendar`** | 中央を占める月の面 | 🔑 **無し** ── 4-3 の左タブが同じものを、本文を消さずに出す |
| `ViewMode` の **`kanban`** | 中央を占める板 | 🔑 **無し** ── 4-3 の並びが同じ札を出す。列(未完了/完了)は**行の印そのもの**なので、印を押せれば足りる |
| **カレンダー / 板のタイル**(`tiles.ts:192` / `:207`) | アプリ一覧の 2 枚 | 🔑 **無し** ── §3 のとおり分類が誤っていた |
| `openViewTile` の **`calendar` / `kanban` 経路** | 別窓を立てる配線 | 🔑 **無し**(`dual` は残す ── §7) |
| **`calendar-set-date`**(`binder.ts:1557`) | 日を押して日付を書く | ⚠ **書き口が 1 つ減る** → 4-2 で**右の列へ移す**(移すので失わない) |
| 帯の**「先にノートを選んでください」** | 選ばせるための指示 | 🔑 **無し** ── 選ばせる理由(書く仕事)が消える |

🔴 **PKC2 も未完成だったことを、言い訳ではなく設計の根拠に使う。**
PKC2 のカレンダーは `todo` アーキタイプ 1 件 = 1 予定で、**PKC3 では `todo` が封印中**
(`features/sealed.ts`)── つまり**同じ形を保っても中身が永久に空**である。
🔑 **保つ価値のある形が、そもそも存在しない。**

## 6. 変えない約束

1. 🔴 **`date:` frontmatter を残す**。`@` は**足す**のであって置き換えではない。
   ⚠ 理由は「不可侵だから」ではない ── **ノート 1 件が丸ごと予定である**書き方
   (会議のノート・その日の記録)は、行の日付では表せないからである。
   🔑 不可侵裁定 2026-08-07 が禁じているのは
   **こちら側の都合(段数・維持コスト・一貫性)と動線を交換すること**であって、
   **間違いを直すこと**ではない(user 指示 2026-08-23 の明示 ── 私の拡大解釈だった)
2. 🔴 **本文の全文走査を作らない**(#212 の穴)。走査は storage worker の中、
   絞りは `task_total` 列 ── **主スレッドへ運ぶのは札だけ**(不可侵指示 2026-07-27)
3. **抽出列を増やさない**(この段では)。行の日付は**札を組むときに本文から読む** ──
   ⚠ 読むのは既に読んでいるノートだけなので、**新しい読みは 1 件も増えない**
4. **クエリ言語を作らない**(Obsidian Tasks の 118 ページの Quick Reference がその失敗)
5. **完了は消さない。畳んで件数を出す**(2026-08-20 の裁定)
