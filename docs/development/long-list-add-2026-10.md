# 長い一覧で 1 件足すと、全行を作り直していた(#1087。実装つき)

- 測った版: main `a34686f1`(直す前)と、その上に `src/adapter/ui/render/filer.ts` の差分だけを載せた版(直した後)
- 測った場所: `npm run build` した `dist/` を `vite preview` で配り、実ブラウザ(chromium、headless、1440×900、4 コア)
- 材料: 平置き 5,700 件(題名と短い本文だけ。`.pkc3-full.zip` で取り込んだ)。**フォルダの表(既定の探し方)**に全部が出る形

## 1. 何が起きていたか

5,700 件ある状態で「+ ノート」を 1 回押すと、新しい行が見えるまで約 2.7 秒かかり、
renderer のメモリが一時的に +185〜190 MB 膨らんで、あとで GC が戻していた(保存が走る前の話)。

原因: `filer.ts` の `render()` は一覧の指紋(`metaSignature`)が動くと、`this.region.textContent = ''` で
**表ごと捨てて全行を作り直して**いた。ノートが 1 件増えれば指紋は必ず動くので、
平置き(root の直下 = 全件)では **増えた 1 件のために 5,700 行 × 約 4 ノード = 約 23,000 ノードを作り直す**。
file 冒頭の注にも「keyed 行再利用は平置き大 container が現実になったら計測してから入れる」と、この日のために残してあった。

## 2. 直し

`reconcileRows`(`filer.ts`)。表と tbody を持ち越し、行は指紋(題名・種別・日付・名前の打ち替え・親の名前)が
同じなら**同じ node のまま**並べ直す。選択と印は属性だけ合わせる。消えた行だけ外し、新しい行は入る位置へ差し込む。
見える結果(並び・選択・印・題名・焦点・スクロール位置)は変えない。

- 周りの帯(パンくず・移動の帯・ゴミ箱)は小さいので、これまでどおり作り直す。表だけ残す
- 焦点が持ち越した行に在るままなら `focus()` を撃ち直さない(撃つと見える位置へ動かされる)

## 3. 測定(5,700 件、1 件足す。直す前 B と直した後 A を交互に 3 組、毎回新しい profile)

計測: renderer プロセスの Pss(`/proc/<pid>/smaps_rollup`、40 ms 間隔のピーク − クリック直前の GC 後)/
CDP `Performance.getMetrics` の Script・Layout・RecalcStyle・Task の差 /
`PerformanceObserver('longtask')` / クリックから新しい行が DOM に現れるまで。

| 指標(3 回の値) | 直す前 B | 直した後 A |
|---|---|---|
| renderer Pss の一時増(MB) | 184 / 191 / 192 | 39 / 43 / 43 |
| クリック → 新しい行が見えるまで(ms) | 2753 / 2347 / 2989 | 1136 / 1124 / 1192 |
| 最長の long task(ms) | 1835 / 1613 / 2012 | 363 / 373 / 366 |
| long task の合計(ms) | 2508 / 2124 / 2693 | 840 / 848 / 891 |
| Layout(ms) | 844 / 651 / 782 | 307 / 299 / 327 |
| RecalcStyle(ms) | 852 / 784 / 1078 | 86 / 70 / 75 |
| Script(ms) | 290 / 288 / 266 | 145 / 142 / 174 |
| 既存の行が同じ node か(`rowNodeKept`) | 3/3 とも false | 3/3 とも true |
| DOM ノード数(前 → 後) | 23,099 → 約 23,440 | 同左 |

読み方:
- 向きはどの組でも同じで、範囲は重ならない。倍率は書かない(差し引きの値)
- JS ヒープ(`JSHeapUsedSize`)は 6〜12 MB で動かない。**増えていたのは DOM の native メモリ**で、JS ヒープを測る計器では見えない
- 直した後も約 1.1 秒残る。内訳は Layout 約 300 ms + RecalcStyle + Script で、残りは編集欄を開く側と、表(5,700 行)の再レイアウト。
  **この PR は触っていない**(§5)

## 4. 守っているもの

- `tests/adapter/filer-row-reuse.test.ts`: 足す / 途中へ足す / 消す / 並べ替えで既存の行が同じ node のままであること、
  題名・種類・日付が変わった行は作り直されて字が新しくなること(対照群)、選択と印が持ち越した行でも正しい 1 行にだけ付くこと、
  焦点を外さず `focus()` を撃ち直さないこと
- `tests/smoke/layout.smoke.spec.ts` の既存の「左の列のスクロール」の道中に 1 段足した(起動は増やしていない):
  32 件の状態で 1 件足し、新しい行が出て、既存の行に付けた目印が消えず、スクロール位置が動かない

## 5. やっていないこと・分かっていないこと

- 残りの約 1.1 秒の分解。表の再レイアウトは `content-visibility: auto` や仮想化の領分で、見え方(スクロールバー・Ctrl+F・焦点移動)に
  触るので別の判断にする
- 一時増のうち約 40 MB が何か(編集欄の初期化・2 つ目の表の再レイアウトのどちらも疑えるが、切り分けていない)
- 単一 HTML 版(portable)での実測。描画コードは同じだが、**この PR では測っていない**
- 「+ ノート」以外の経路(取り込み・削除・移動)の実測。単体 test は足す・消す・並べ替えを通している

## 6. レビュー応答(同じ PR の追加分)

- **打ち替え中の行は動かさない**: 焦点のある node を `insertBefore` で動かすと focusout が出て、打ちかけの名前が確定される。
  chromium と headless_shell の両方で、焦点のある行を動かすと焦点が外れ focusout が 1 回出て、兄弟の行を動かすと出ないことを実測した。
  そこで `reconcileRows` は打ち替え中の行を動かさず、手前の行を後ろへ退ける。
  この修正の途中で、描き直しの後始末(`focusedBefore` の戻し)が**行の中の欄から行へ焦点を奪い返す**ことも見つかった(unit が捕まえた)ので、行の中に焦点が在るときは戻さない
- **全選択は始まった回だけ**: 行を持ち越すようになったため、打っている最中の再描画でも欄は生きている。
  毎回 `select()` すると次の打鍵が打ちかけの字を置き換える。焦点と全選択は、欄が出た最初の回にだけ当てる(別のフォルダへ入ってから欄が出る経路でも当たる)
- 行の指紋から `formatStoredDate`(更新日の title)を外した。日付(年月日)だけの関数で、`formatListDate` と同じ値から決まるので、等価だった
  (時刻は title にも出ない)。外しても変異試験の結果は同じ
