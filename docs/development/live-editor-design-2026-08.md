## 0. 要約 ── 何を作るか、1 段落で

画面は**常に描画済みの文書**にする。いま直している塊(段落・見出し・表・fence …)だけが
原文の `<textarea>` に一時的に差し替わり、そこから出た瞬間(= 確定)に**その塊だけ**
描き直して差分で当てる。**打鍵ではレンダリングを 1 回も起こさない**。
2 列(原文 | プレビュー)の分割は畳み、閲覧と編集が同じ DOM・同じ CSS を使う
── これが「ビューワーとエディタを高度に合わせる」の実装である。

## 2. 🔴 着手前に測った(S0)── 設計が成立するかの判定

**恐れていた失敗**: PKC-Markdown は `breaks: true`(単独改行が `<br>`)なので、
**空行を打たない日本語の散文は丸ごと 1 段落 = 1 塊**になる。そうなると
「編集中の塊 = 文書ほぼ全部」に潰れ、機構は入るのに**見た目は今日と同じ**になる
── これは最も静かな失敗であり、**着手前に分かる**。

計器: `tests/bench/run-block-sizes.ts`(`npx vite-node` で実行)

### 測った結果(この repo の doc 25 件 = 人間が書いた長い日本語 markdown)

| 指標 | 中央 | p90 | 最大 |
|---|---|---|---|
| 1 文書の塊数 | **61** | 122 | 177 |
| **最大の塊が文書に占める割合** | **11.2%** | 17.0% | 21.6% |
| 1 塊あたりの原文行数(近似 = 行数 ÷ 塊数) | 4.0 行 | 5.5 行 | 6.1 行 |

**潰れている文書(最大の塊が 50% 以上): 0 件 / 25。** 塊が 2 個以下: 0 件。

### 最悪の場合の腕(同じ文書から**段落間の空行だけ**を落とす)

対照群は「測りたい違いだけが違うもの」なので、中身は同じで空行だけを取り除いた。

| 文書 | 塊(元 → 空行なし) | 最大塊の割合(元 → 空行なし) |
|---|---|---|
| rust-wasm-strategy | 176 → 169 | 8.0% → **8.0%** |
| p7-product-release-design | 177 → 142 | 7.6% → **7.7%** |
| user-reports-2026-08-05 | 78 → 64 | 16.1% → **16.1%** |
| docs/manual.md | 122 → 105 | 5.0% → **5.0%** |

**空行を落としても 8 / 8 が潰れない**(最大塊の割合 中央 8.0%)── 見出し・箇条書き・表が
塊を切るので、空行だけでは潰れない。

### ⚠ 測っていない次元(はっきり書く)

- **user の実ノートではない**。repo の doc 群は「人間が書いた長い日本語 markdown」なので
  散文の癖の代理になるが、**代理である**。
- **見出しも箇条書きも表も無い、空行も無い一枚の散文**は 1 塊に潰れる ── これは原理で
  あって測る必要が無い。その形のノートがどれだけ在るかは **user の実データでしか分からない**。
- golden 25 件は 72% が「潰れている」が、あれは**方言 1 個ずつの試験体**(構造上 1 塊)で
  あって実文書の代理ではない。⚠ ただし**集約**(`:::toc` / 脚注 / 採番)を持つのは
  golden 側だけ(repo doc は 0%)── 集約の扱い(§9 論点 B)は golden の側で効く。

**判定: 設計は成立する。** ただし上の「一枚の散文」の縮退は残るので、
`Ctrl+A` で全塊を差し替える形(= 今日の編集画面が本設計の縮退形)を必ず持つ(§6 S6)。

## 3. すでに直したもの(S1)── 今日起きている図の破棄

本設計とは独立に、**今日のプレビューで既に起きている**バグを 1 件直した。

`both` モードの fence(mermaid / html / csv)は「ソース / レンダリング切替」の
`<input id>` を持ち、その id を**中身から**決めていた ── ただし salt が
**token 添字**だった。すると図の**前**に段落を 1 つ足すだけで添字がずれ、id が変わり、
**図を含む塊の HTML が変わる**。`apply-blocks.ts` は塊 HTML の完全一致で差分を取るので
「その塊は変わった」ことになり作り直される ── **生きている `<img>` が捨てられて絵が
一度消える**(ObjectURL の作り直し + IDB の読み直し + decode)。

実測(同じ入力・図の前に段落 1 つを挿入):

```
直す前: diff = { prefix: 2, suffix: 1, middle: [挿入した段落, 図の塊], removed: 1 }
直した後: diff = { prefix: 2, suffix: 2, middle: [挿入した段落],       removed: 0 }
```

塊の差は **`pkc-rv-…` の値だけ**だったのに、図の塊がまるごと作り直されていた。

**直し方**: salt を「**同じ (lang, 中身) の fence の中で何番目か**」に変えた
(`nextFenceOccurrence`)。同じ内容の fence を区別するという当初の目的は保ったまま、
無関係な編集で id が動かなくなる。⚠ カウンタは `env`(render 1 回ぶん)に持つ ──
module スコープに置くと render を跨いで増え、id が毎回変わって元の病気に戻る。

pin: `tests/features/fence-id-stability.test.ts`(10 件)。
⚠ goldens 25 件は**動かない**(golden test が id を別名化して比べているため)。

### ⚠ 変異試験で 1 巡目に 2 件生き延びた(記録)

**原因はどちらも「fixture のゼロ件の次元」**だった ── 前に足していたのが**段落だけ**で、
「**同じ言語の別の fence**」を前に足す形が 1 件も無かった。そのため
「鍵に中身を混ぜない」変異が素通りしていた(鍵が `lang` だけになると、
別内容の図が 1 つ前に在るだけで数がずれる)。test を 2 件足して塞いだ。

もう 1 件は **等価変異**だった。「slot と wrapper で 2 回数える」変異が生き残ったので
test の穴かと思ったが、`<input id>` と `<label for>` は**どちらも同じ引数から作る**ので
対応は崩れず、鍵に中身が入っているので衝突もしない ── つまり**観測できる違いが無い**。
私が source に書いていた「2 回数えると label が自分を指さなくなる」は**嘘**だったので、
コメントを訂正した(変異を殺す test を足すのではなく、嘘を消すのが正しい対応)。

最終: **6 件中 5 KILLED / 1 等価変異 / SURVIVED 0 / NOT-APPLIED 0**。

## 4. 採る形 ── 行の入れ替え(row-level swap)

3 案(① 穴あき全文レンダー ② ブロック contenteditable ③ 行の入れ替え)を
独立に立て、**3 つのレンズ**(日本語入力 / 定常性能 / 設計との整合)で採点した。
perf と arch が ③ を最良とし、日本語入力のレンズだけが ① を上に置いた
── その差は「① が明示していた規則の有無」であって機構の優劣ではないので、
**規則は接ぎ木した**。

### 何が正本か

- **原文の正本は `state.openBody.body` 1 本**。差し替え中の textarea は
  「body の連続行スライスを映した窓」で、`commitRow(range, text)` が
  **本文書込の唯一の口**。
- 打鍵ごとの `UPDATE_OPEN_BODY` は**残す**。落とすと、キャンセルの新規判定 /
  再読込の予約 / 編集中の書き出しが**最大 3 秒古い本文**を見る。
- 画面は常に描画済み文書。閲覧と編集で DOM の世界を作り替えない
  (いま `detail.ts:403` が `region.textContent = ''` で全部捨てている)。

### 🚫 採らなかったもの

- **contenteditable**(案 ②)── この repo に前例が 0 件で、候補窓の位置・再変換・
  モバイル IME・自動修正がすべて未確認領域に入る。textarea なら**そこは platform 既定の
  まま**で、そもそも変えていないので守る必要がない。
- **穴あき文書を描く**(案 ①)── 合成した文書を描くと、link reference definition が
  穴に入るだけで**文書中の全リンクがリテラルに落ちる**。集約の例外表が活性領域の数だけ
  掛け算で増える。

## 5. 日本語入力の契約(実測に基づく)

⚠ **この節の 2 つは私が自分で実測した**(CDP `Input.imeSetComposition` ×3 →
`Input.insertText` で「にほん」→「日本」)。ここを間違えると**日本語だけ静かに壊れる**。

### 実測 1: 確定の瞬間の `input` も `isComposing === true`

```
compositionupdate data="日本"
input  isComposing=true  inputType="insertCompositionText"  data="日本"  value="日本"
compositionend  data="日本"  value="日本"     ← この後に input は来ない
```

🔴 **したがって本文の `input` に `if (e.isComposing) return;` を足してはならない**
── 確定した本文が state に入らず、次の打鍵まで欠損が残る。
**英数字入力では絶対に再現しない**(いま `binder.ts:713-717` にガードが無いのは**正しい**)。

### 実測 2: `compositionend` は「確定」ではない

変換を取り消した場合(候補を消した場合):

```
input  isComposing=true  data=null  value="日本"   ← 元に戻っている
compositionend  data=""   value="日本"
```

🔴 **`compositionend` の意味は「封印が解けた」だけ**。確定・保存・塊の切替の
引き金にしてはならない。

### 契約(守る規則)

1. `compositionstart` で活性塊を**封印**し、`composing = true`(**boolean 1 個**。
   深さカウンタや start/end のペア計数は禁止 ── DOM を触ると数が合わなくなり、
   固着した側に倒れると全打鍵が無視される)
2. 封印中に**しないこと**: textarea のノードを取り除く / 差し替える / 移動する、
   `value` に代入する、祖先の `innerHTML` に代入する、`focus()` を撃つ、活性塊を切り替える。
   ⚠ 変換中にノードが差し替わると `activeElement` が落ち、composition が
   **例外もイベントも出さずに死ぬ**(= 最終 DOM も state も正常に見える、検出手段の無い欠損)
3. 封印中に届いたパッチは、**封印ノードに重なるときだけ**保留(latest-wins で 1 件)。
   `compositionend` の次のフレームで `composing === false` を確認してから流す
4. `input` は `isComposing` で **return しない**(実測 1)
5. `compositionend` は確定の引き金にしない(実測 2)
6. `blur` が変換中に来たら**同期で確定しない**。`pendingCommit` を立てて
   `compositionend` の後に確定する
7. **安全弁**: `composing === true` なのに `activeElement` が当該 textarea でなくなったら、
   次の `focusout` / `selectionchange` で封印を解く(DOM を触られると
   `compositionend` が来ないことがあり、end を待つ実装は永久に固まる)
8. 確定の引き金(Esc / Tab / Ctrl+Enter)は先頭で `if (e.isComposing) return;`
   (既存の作法 `binder.ts:775, 842` と同じ)
9. **活性塊を移すときは textarea を作り直す**。同じノードを使い回して `value` を
   代入すると、native の取り消し履歴が前の塊の文字を保持したまま残り、
   Ctrl+Z で**別の塊の文字が現在の行へ流れ込む**(本文破壊)
10. プログラム的な文字挿入(書式バー)は `document.execCommand('insertText')` に寄せる
    (undo に載る)。⚠ 封印中は拒否する
11. `writeBack` が撃っている素の `Event('input')` を **`InputEvent` へ「直さない」**
    ── `inputType` が undefined であることが偶然守りになっている(知って触らない)

### ⚠ 測れない次元

- **再変換**(変換キー / 変換のやり直し)、`key="Process"`、IME がキーを食う挙動 ──
  CDP は本物の IME ではないので**この環境では再現できない**
- **候補窓が開いている最中の layout shift**(確定で周囲の塊が入れ替わる)── 原理的に測れない
- モバイル / タッチ IME

## 5.5 caret はどこに入るか(2026-08-05 追測。user 質問「コードブロックのような複数行に対する caret 位置が変わってしまうということ?」への答え)

**答え: 逆である。複数行のコードブロックは「正確に入れる」側で、難しいのは 1 行の中の装飾。**

### なぜ複数行が問題ではないのか

塊に入ると、その塊の**原文の行がそのまま**入力欄に入る。だから
「何行あるか」は難しさに関係しない ── 難しいのは「**描画テキストの n 文字目が、
原文の何文字目か**」という 1 行の中の話である。

### 実測 1: コードブロックは描画テキストが原文と **byte 一致**する

`<`・`&amp;`・バックティック・タブ・日本語を全部混ぜた fence で確かめた:

```
描画: "const a = \"<b>&amp;\" + `x`;\n\tif (a < 1 &…
原文: "const a = \"<b>&amp;\" + `x`;\n\tif (a < 1 &…
   → 一致: true
```

構文強調は `<span>` で包むだけなので**文字は変えない**。刻印も出ている
(`data-pkc-source-line="0" data-pkc-source-end="5"`)。
だから **クリック座標 → 原文の行と列**が求まる ── 実測で
「3 行目の『日本』の直後」を突いて **line 2 / col 4**(正解)を得た。

### 実測 2: 難しいのは 1 行の中の装飾

```
原文  : これは**太字**と[リンク](https://example.com)と`コード`です。   (45 文字)
描画  : これは太字とリンクとコードです。                                (16 文字)
```

描画テキストの 1 文字の移動が、原文では 10 文字の移動になりうる。
ここに写像が要る。

### 実測 3: その写像は **2 ポインタ**で作れる(9 例すべて正確)

規則: 描画テキストと原文を並べて歩き、**文字が一致したら両方進める / 違ったら
原文だけ進める**(その分が markup)。同期が切れたら**最後に同期した所へ戻す**。

| ケース | 結果 |
|---|---|
| `**太字**` / `~~打消~~` / `==印==` / `` `コード` `` | ✅ 正確 |
| `[リンク](url)` ── 描画の「リンク」直後 → 原文の `リンク` と `](` の間 | ✅ 正確 |
| `![alt](asset:…)` ── 描画に文字が出ない → 画像 markup の**手前** | ✅ 正確 |
| `A &amp; B` ── 描画は `A & B`(原文に無い形) | ✅ 正確 |
| `## **太字**の見出し` | ✅ 正確 |

### 実測 4: 外れる構文は **必ず手前へ丸まる**(誤差の向きを固定した)

描画テキストに「原文に無い文字」が現れる構文は同期を失う。そのとき着地する場所:

| ケース | 着地 |
|---|---|
| `{{vars.name}}` の置換(描画は `佐藤`) | `こんにちは ⟨caret⟩{{vars…` ── 置換の**手前** |
| 脚注の参照(描画は `[1]`) | `これは脚注[⟨caret⟩^a]…` ── 参照の**手前** |
| 見出しの自動採番(描画は `1. 章の題`) | 塊の**先頭** |
| CSV / mermaid の**描画された表・図**(描画テキストが原文と無関係) | 塊の**先頭** |

🔑 **最悪でも「塊の先頭」**= 元々の退避先と同じ場所である。前へ飛び越したり、
無関係な場所へ落ちたりはしない(2 ポインタが単調なので原理的に起きない)。
⚠ 採番と脚注は**こちらが生成した接頭辞**なので、長さが分かっている ──
先に剥がしてから 2 ポインタに掛ければ正確にできる(S7 の中身)。
⚠ 描画された表・図は、隠してある原文の `<pre>`(**byte 一致**)側で編集すればよい
── 既に「ソース / レンダリング切替」が在る。

### 実データでの割合(repo の doc 群、塊 1,840 個)

| 塊の種類 | 個数 | 割合 |
|---|---|---|
| 段落(装飾あり) | 652 | 35.4% |
| 見出し(装飾なし) | 464 | 25.2% |
| 段落(装飾なし) | 194 | 10.5% |

| 表 | 170 | 9.2% |

⚠ この表は「行の中に装飾が在るか」で分けた粗い分類である(箇条書き・表・引用の
**中身**にも装飾は在りうる)── 正確な数は range sidecar(S2)が入ってから出す。
言えるのは「**装飾を含む行は多数派ではないが、無視できる少数でもない**」まで。

## 5.6 行確定まで待つ / auto pair / 開放終端(user 提案 2026-08-05。**採る**)

> **user 提案(原文)**
> 「**行確定まで待てよ / それができないってこと? / auto pair と開放終端を検知したら、
> 一旦レンダリングは生の文字のままにして、行を色変え、閉じ終端がついた時点で
> レンダリング / これではいかんのか? / auto pair は開放終端をそもそも作りにくくする
> 機構であり、入力補助な**」

**できる。そしてこれが正しい形である。** 3 点に分けて答える。

### ① 「行確定まで待つ」── 既にそう設計している(合意)

§0 のとおり本設計は**打鍵ではレンダリングを 1 回も起こさない**。描くのは
「その行/塊から出た瞬間」だけ。だから「打ちかけの `**` が一瞬 bold になって
また戻る」というちらつきは**原理的に起きない**。ここは user 提案と同じである。

### ② auto pair ── **採る**(私の設計に無かった)

開放終端をそもそも作りにくくする入力補助。⚠ ただし日本語入力と噛み合わせる規則が要る:

- 🔴 **変換中は auto pair を撃たない**。変換中に閉じ記号を挿入すると
  composition が壊れる(§5 の契約 2「封印中に value へ代入しない」と同じ理由)
- IME で開き括弧(`「` `【` `(`)を確定した場合は、**`compositionend` の後**に
  閉じを補う(確定文字列の末尾を見る)。⚠ `compositionend` は「確定」ではないので
  (§5 実測 2)、`data` が空でないことを確かめてから
- 撃つのは **`document.execCommand('insertText')`** 経由(§5 契約 10)── undo に載る。
  直接 `value` に代入すると Ctrl+Z で戻せない飾りになる
- ⚠ **選択範囲があるときは囲む**(surround)、無いときは挿入。既存の書式バーの
  `applyFormat` が同じ判断を持っているので**規則を 1 本に寄せる**(2 つ書かない)

### ③ 開放終端の検知 → 生のまま + 行を色変え → 閉じたら描く ── **採る**

実測すると、**行内とブロックで壊れ方がまったく違う**ことが分かった。
user 提案はブロック側で決定的に効く。

#### 行内の開放終端: 見た目は原文と同じ(害は小さい / 色に価値がある)

| 打ちかけの原文 | 描画結果 |
|---|---|
| `これは**太字` | `これは**太字`(そのまま) |
| `` これは`コード `` | `` これは`コード ``(そのまま) |
| `これは[リンク](` | `これは[リンク](`(そのまま) |
| `これは==印` | `これは==印`(そのまま) |

⇒ 閉じていない行は**すでに原文どおりに見えている**。だから「生のままにする」は
実質すでに満たされている。**足りないのは「待っていることが見えない」こと** ──
いま user には「打ちかけ」と「literal な `**` を打った」の区別が付かない。
**行を色変えする**(= user 提案)がここを埋める。

#### 🔴 ブロックの開放終端: 閉じないと**後続を飲み込む**(ここが本題)

| 打ちかけの原文 | 描画結果 | 何が起きているか |
|---|---|---|
| ` ```js ` + `const a = 1;`(閉じ無し) | **完成したコードブロック** | fence が EOF で自分を閉じる ⇒ **以降の全文が code になる** |
| `:::note` + `中身`(閉じ無し) | **完成した callout** | 同じ ⇒ **以降の全文が callout の中身になる** |
| `\| a \| b \|`(区切り行なし) | 段落のまま | 表は `\|---\|` が来るまで表にならない |

⇒ ブロック開始記号を打った瞬間に、**まだ書いていない下の文書が丸ごと巻き込まれる**。
ここで「閉じ終端が付くまで生のまま」にするのが user 提案の最大の効き所である。
**auto pair の最優先対象もここ**(```` ``` ```` を打ったら閉じ ```` ``` ```` を同時に置く /
`:::x` を打ったら `:::` を置く)。

#### 検知の作り方(features 層・純関数)

`fenceTransition`(既存。§4 で export する)と `:::` の深さで**釣り合い**を見る。
行内は「対になる記号の数が奇数か」で足りる(``` ` ``` / `**` / `==` / `~~` / `[` `]` `(` `)`)。
⚠ **fence の中は数えない**(コードの中の `**` は装飾ではない)── 既存の
fence 走査を再利用する(2 本目の行パーサを書かない)。
⚠ 検知は **描くかどうかの判定にだけ**使う。原文には触らない。

### ④ 🔴 そして user 提案のおかげで、私の設計の**粒度が粗すぎた**ことが分かった

§9 論点 A で私は「外れたら**塊の先頭**へ丸める」と書いた。これは粗い ──
実測すると**行レベルの刻印は既に在る**:

```
p     line=0 end=2      ← 複数行の段落(breaks:true)
table line=4 end=7
tr    line=4 end=4      ← 🔑 表は**行ごと**に刻まれている
tr    line=6 end=6
tr    line=7 end=7
ul    line=9 end=11
li    line=9 end=9      ← 🔑 箇条書きは**項目ごと**
li    line=10 end=10
li    line=11 end=11
```

複数行の段落も `<br>` で行が分かれている(3 行 → `<br>` 2 本)ので、
**クリック位置より前の `<br>` を数えれば原文の行が正確に出る**。

⇒ **活性単位を「塊」から「クリックした行を含む最小の刻印要素」へ下げる**
(表の行 / 箇条書きの項目 / それ以外は塊)。これで:

- caret の退避先は「塊の先頭」ではなく **「その行の先頭」** ── 40 文字の行なので実害が小さい
- 40 行の表をクリックしても**表全体が生の文字列になったりしない**(1 行だけ入力欄になる)
- 🔑 **部分描画にはならない**。描く入力は**常に完全な文書**のままで、
  変えるのは「**当てる範囲**」だけ ── 既存の「スロット + pin」機構が
  塊単位ではなく**行単位**になるだけである(§7 契約 7-8。`pin` を配列で受けるのが効く)

## 6.9 入れ子の `:::` の既存バグを直した(2026-08-06)

ライブエディタが**開けない文書**を減らすために、描画側の既存バグを直した。
これは renderer のバグなので**閲覧画面にも効く**(ライブエディタ専用の修理ではない)。

### 何が壊れていたか

`processSectionBlocks` は「開いたら**最初に出会った `:::` まで**を中身にする」平坦な
走査だった。`:::section` の中に `:::note` を書くと:

1. 内側の開き行が**本文として素通り**して `<p>:::section{role=note}</p>` になる
2. 内側の閉じが**外側の閉じ**として使われる
3. 外側の閉じが最上位に残って `<p>:::</p>` として漏れる

⚠ これは `:::toc` が本文を飲んでいた件(user 報告 2026-08-05)と**同じ形**である ──
「1 個ぶんしか数えない走査」。

### 直し方

**開いている `:::` を stack で数える**。⚠ 数えるのは `section` に限らず
**すべての `:::name`** ── `:::details` なども閉じ `:::` を消費するので、自分の種類だけ
数えると他人の閉じを自分の閉じとして食う(混在した入れ子で同じ壊れ方をする)。
他人の開き / 閉じは**そのまま流す**(後段の `processDetailsBlocks` 等が自分で処理する)。

### ライブエディタへの影響

**入れ子の `:::` でも行の差し替えが開くようになった**(以前は分割の検証が落ちて
今日の編集画面へ退避していた)。⚠ 退避する条件は消えていない ── renderer が畳まない
`:::name`(例:**id 無しの `:::figure`**。id は必須で、無い形は意図的に literal 残し)
では走査だけが 1 塊に畳んで食い違うので、そこは開かない。
🔑 `scanContainers` に directive ごとの表を持ち込まない ── 「renderer が何を畳むか」の
判定が 2 か所になり、片方だけ古くなる。

### 🔴 変異試験で「下流だけ見ていた」ことが露見した(7 件中 2 件が生存)

1 巡目の test は `<details>` が在るか / 後続が section の外に在るかを見ていた。
どちらも**閉じを取り違えても成立する** ── 取り違えると後段の `processDetailsBlocks` が
**section の閉じごと `<details>` の中に巻き込む**ので、`<details>` は在るし後続も外に出る。
直した観測点は **タグの入れ子の順序**(`<section` → `<details` → `</details>` → `</section>`)。
⚠ CLAUDE.md「下流の結果だけを見る test は、別経路が救って変異を見逃す。**壊れる当の
振る舞いを直接見る**」の実例がまた出た。2 巡目は **7/7 KILLED**。

⚠ この修理で、**壊れた挙動を pin していた test 4 件が落ちた**(入れ子を「組めない本文」の
見本に使っていた)── 直った側を守るように反転させ、退避の見本は**別の実物**
(id 無しの `:::figure`)へ差し替えた。

## 7. 差分の契約(要点)

1. **行番号を DOM に焼かない**。`renderMarkdownWithRanges(text) → { html, ranges }` にする
   ⇒ `sourceLineAnchors` は据え置き = **goldens 25 件が 1 byte も動かない**。
   焼いたままだと、行数が変わる編集で差分が全滅する(`diffBlocks` は前後一致のみで
   LCS を持たない)
2. **行 → 塊は「分割(partition)」で持つ**。⚠ **範囲は単調でない**(脚注セクションは
   末尾の塊なのに定義行を指す)ので `end = 次の start − 1` を無条件に使わず、
   走査で組む。覆えなければ**行差し替えを開かない**
3. **由来の無い塊は「導出物」と名前を付ける** ── 実測で `footnotes-sep` /
   `<section class="footnotes">` / `<nav class="pkc-toc-formal">` の **3 種に限る**。
   クリックしても差し替えず、それを生む原文行へ案内する
4. **frontmatter のずれは 1 か所だけに持つ**(`fmOffset`)。PKC2 はこの換算を
   消費側に手書きで散らして事故った
5. **突合は鍵 2 本**: `identity` = 塊の原文スライス / `paint` = 塊の HTML。
   ⚠ 同内容の塊が反復する文書では identity が退化するので、出現順で区別し、
   退化したら前後一致へ**フォールバックする**(keyed が今より悪くなる経路を残さない)
6. **hash は塊あたり 2 lane = 64bit**。32bit だと 2,000 塊台で誕生日衝突が実用域に入り、
   衝突は「変わったのに変わっていないと判定」= **古い塊が画面に残る**向きに壊れる
7. **活性塊は当てる直前に定数スロット HTML に差し替え、textarea をその孫に置く**
   ⇒ host の `childNodes` が動かないので、`intact()` を**緩めずに**異物を差分の外へ出せる
8. **崩れたときの回復は 5 段**(`intact()` false → 全置換 / 分割の検証失敗 → 行差し替えを
   開かない / hash は identity と併用 / worker の世代不一致 → 全量へ退化 / 封印中は保留)
9. **プレビュー失敗時に `BlockView` を戻す**(いま戻していないので、次のパッチで
   全置換に落ちる ── S2 で同時に塞ぐ)

- ⚠ **原文の行順序は動かさない**。自由配置は**描画位置**の話 ── 行順を動かすと
  分割が壊れ、行差し替えの土台ごと失われる
- 🚫 新しい markdown 方言は足さない(凍結方針)。着手は user の明示 go

### 4 本目(Microsoft Loop 風コンポーネント)

- `pin` を**最初から `readonly number[]`** で受ける(1 個で足りるが配列にしておく)
  ── 常時ライブな部品が N 個になっても、差分台帳が破砕せずスロットが N 個になるだけで済む
- `commitRow(range, text)` を**本文書込の単一口**にする。着地後に todo トグルの
  原文 splice をこの口へ畳めば、本文を disk へ書く経路は **7 本目に増えるのではなく減る**。
  部品が自分で編集して `commitRow` を叩く形が、そのまま Loop 風の書込契約になる
- 塊ごとの「編集能力」を presenter registry に置ける形にしておく(いまは登録しない)

⚠ この 2 つを予約しないまま S5 を着地させると、4 本目の時点で差分台帳と
本文書込口を作り直すことになる。

## 11. 検査の規律(「緑のまま壊れる」を防ぐ)

- **分割の全域性**を代替物で満たせない形で書く ── 「starts が非空」ではなく
  「非空の原文行がちょうど 1 つの塊に属する かつ 重複 0 かつ `fmOffset` が一致」
- **行範囲の往復**: 各塊で `render(原文スライス)` が全文中の塊と一致。
  ⚠ fixture の各次元(表 / fence / 図 / `:::` / 入れ子 / 脚注 / 目次 / 見出し番号 /
  frontmatter)が**非ゼロであることを test 自身に assert させる**
- **確定の input を落とさない**(PR gate の smoke。CDP で「にほん」→「日本」を確定し、
  記録テキストが「日本」であること)。変異: `if (e.isComposing) return;` を足す → 落ちる
- **IME 封印**(smoke)。変換中に外からパッチを起こし ① textarea の**ノード同一性**不変
  ② `activeElement` が当該 textarea ③ composition イベントの回数 ④ 最終 value。
  ⚠ **CONTROL を同じ spec に置く**(パッチを起こさなければイベントが観測できることを
  先に確かめる ── 観測が無音になって空ログを合格と読む事故を実際に踏んでいる)
- **図が生き残る**(smoke。⚠ `tests/smoke` は `dist/` を配るので、変異は `npm run build` を
  挟み `dist/assets/*.js` に届いたことを確かめてから回す)
- **hash の lane 数を pin**し、既知の 32bit 衝突ペアを fixture に固定で持つ
- **PR gate は最小 smoke 2 本(秒オーダー)だけ**。全量は nightly
- 実ブラウザ依存の spec は **2 バイナリ**(`chromium` と `chromium_headless_shell`)で通す

## 12. 測る計画(user 指示 2026-08-03「効くのは定常」に従う)

報告するのは配る量ではなく **① 継続使用の常駐メモリ ② 操作の応答**。

- 既存の P8 ベースライン(JS heap 9.0→9.1MB / 生きている ObjectURL 0 / DOM 226 ノード /
  90 ラウンドで longtask 3 本 / 4ms 心拍の最大の空き 34ms)に対する非退行を、
  `tests/bench/run-app-session.mjs` の作法(persistent profile / 固定ポート / 暖機を捨てて
  前半後半の中央値で傾きを見る)で測る
- ⚠ `performance.memory` は JS heap しか見ない ── 焼いた PNG と IDB の Blob は heap の外。
  **ObjectURL 残高 + DOM 数 + IDB のバイト増分**を必ず併記する
- 対照群は 3 つ: `?pkc-live-off` / **S2 だけ入れたビルド** / S1 だけ入れたビルド
  (S2 は既存バグの修理なので、分離しないと「ライブエディタが速くした」の**誤帰属**が起きる)

### 12.1 🔴 実測(2026-08-05。`tests/bench/run-live-editor.mjs`)

対照群は **同じビルド・同じ本文・同じ打鍵**で `?pkc-live=1` の有無だけを変えたもの
(「何もしない」ではなく「測りたい違いだけが違うもの」)。打つ位置も揃えている
(2 列側は `setSelectionRange` で同じ文字位置へ置く)。fixture は見出し / 段落 / 表 /
箇条書き / コード柵 / 図 1 枚を混ぜたもの。⚠ **添付 0 / 履歴 0 / 関連 0 = 測っていない次元**。

**大きい本文(2000 塊 / 6009 行 / 54.7 KB)・240 打鍵 30ms 間隔・各腕 3 回:**

| | 1 面(live) | 今日の 2 列(split) |
|---|---|---|
| 打鍵中に worker へ飛んだ仕事 | **0 / 0 / 0** | 38 / 28 / 23 |
| 240 打鍵を打ち終わるまで | 8057 / 8162 / 8049 ms | 9399 / 9376 / 9336 ms |
| 反映まで(live=確定後 / split=打ち終わり後) | 169 / 155 / 148 ms | 5 / 17 / 47 ms |
| 常駐 RSS 中央値 | 1180.6 / 1165.0 / 1153.1 MB | 1218.8 / 1183.5 / 1209.4 MB |
| long task(50ms 以上) | 0 件 | 0 件 |

**ふつうの大きさ(60 塊 / 189 行 と 400 塊 / 1209 行)・120 打鍵:**

| | live | split |
|---|---|---|
| 打鍵中の仕事 | 0 / 0 | 1 / 2 |
| 反映まで | 27 / 34 ms | 4 / 3 ms |
| 打ち終わるまで | 3795 / 3839 ms | 3812 / 3934 ms |

**言えること(向きだけ。倍率は書かない):**

1. 🔑 **打鍵中にワーカーへ仕事を出さない**は設計値どおり(0 件、3 回とも)。
   2 列側は 240 打鍵で 23〜38 件 = およそ 8 打鍵に 1 回
2. 🔑 **同じ 240 打鍵を打ち終わるまでが短い**(2 腕の範囲が重ならない)。
   差は 240 打鍵で 1.2〜1.3 秒 ── 打鍵の配送が詰まっている量なので、
   user の言う「もっさり」に直接対応する軸である
3. 🔴 **ただし費用を消したのではなく、移しただけである。** 1 面は確定の瞬間に
   **150ms 前後**(6009 行)を払う。2 列は打鍵中に描き終えているので、打ち終わった
   時点ではほぼ現在の絵になっている。**「1 面のほうが速い」と一律には言えない**
4. ふつうの大きさ(〜1200 行)では**どちらも体感差が出ない**(反映 27〜34ms)。
   分かれるのは 6000 行級から
5. ⚠ **long task では語れない** ── この機械ではどの大きさでも 50ms 超の task が
   0 件だった。「long task が減った」とは**言わない**
6. ⚠ **常駐は向きが弱い**(範囲がほぼ接する:1181 対 1184)。しかも harness の
   RSS は **profile に属する Chromium の全プロセス合計**であって「アプリの使用量」ではない

**この実測が示す次の作業:** 3 の「確定時の 150ms」が S3(keyed 差分)/ S9(worker 側で
差分を取る)の**根拠**である。⚠ ただし markdown の描画は文書全体に依存する
(脚注 / 目次 / 見出しの自動採番)ので、「変わった塊だけ描く」は**そのままでは正しくない**
── 局所描画を先に当てて後から全体描画で直す形(楽観パッチ)は**見た目が一瞬ずれる**
可能性がある。**設計 doc を出して user 裁定を仰いでから**着手する(doc-first)。

### いま測っていないと明記すること

- **確定から画面に出るまでの時間**をブラウザで測っていない(Node 値は向きと比率にだけ使う)
- **postMessage の実コスト**を測っていない。`html` 文字列は transfer 不可なので
  構造化複製が残る(5.6k 行で HTML 453KB)── S9 の前に「往復が軽くなった」と言わない
- **Tab で塊を渡り歩く**操作(確定の連打)── user が最も嫌う軸に直撃する箇所
- **候補窓が開いている最中の layout shift** ── この環境では原理的に測れない
- `browse.render` の無条件 `scrollTop` 読み書き(打鍵ごとの強制レイアウト)が
  本設計で flush 点にならないこと ── 打鍵で DOM を汚さないので増えない見込みだが**未実測**
