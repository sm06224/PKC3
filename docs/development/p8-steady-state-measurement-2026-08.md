# P8: 継続使用(定常)の実測 ── 2026-08-04

> user 指示 2026-08-03(不可侵)
> 「**初回起動が遅くとも、そこは許容 / その後の動作がメモリくったり、もっさりだと
> 嫌なだけです**」
> 「測って報告すべきは配る量ではなく、**継続使用の常駐メモリ**と**操作の応答**である」

## なぜ測ったか

既存の計器 `tests/bench/run-edit-session.mjs` は **storage core だけ**を測る
(`StoreClient` を直に叩く)。P8 で入った**描画・プレビュー・図のラスタ・
ワーカー・ObjectURL** は、一式そろったあとに **1 度も定常を測っていなかった**。

「配る量」は `scripts/check-dist.mjs` が毎 PR で見ているのに、user が実際に
気にしている軸(常駐と応答)には計器が無い、という状態だった。

計器: `tests/bench/run-app-session.mjs`(実アプリを実ブラウザで回す)

## 何をどう測ったか

1 ラウンド = **ノートを開く → 編集に入る → 本文を打ち替える → 確定する**。
user が実際にやる形をそのまま繰り返す。

- **persistent profile**(ephemeral は storage がメモリバックで実 I/O を踏まない)
- **固定ポート 45741**(origin が変われば毎回「初回起動」になる)
- **暖機 10 ラウンドを捨てる**(boot 窓と初回の遅延生成を定常に混ぜない)
- 中央値で前半 / 後半を比べる = **傾き**を見る(1 点の絶対値で語らない)

### fixture の次元(⚠ ゼロの次元は「測っていない次元」)

| 次元 | 件数 |
|---|---|
| ノート | 12 |
| **図(mermaid)** | 4 ── 1 巡で実際に 4 回出たことを測定中に確認 |
| **表(csv)** | 4 ── 同上 |
| revisions | ラウンドごとに 1 版増える(100 ラウンドで 100 版) |
| **添付** | **6 件 × 2.35MB(段㉖ で埋めた。下記)** |

⚠ 図と表が「実際に出た数」を測定の中で数えている。ここが 0 だと
「図があっても増えない」という主張が**自明に通ってしまう**ため。

### 添付の次元を埋めるときに要った 3 つの条件(段㉖)

前の版はここが 0 件で、「添付の定常は測っていない」と本 doc 自身が書いていた。
埋めるにあたって、**素直に足すだけでは測ったことにならない**箇所が 3 つあった。

1. **bytes を件ごとに変える** ── ゼロ埋めだと内容アドレスで 1 件に畳まれ、
   「6 件抱えた」が嘘になる
2. **mime を画像にする** ── preview の分岐は `img/video/audio/pdf` 以外を
   「preview 無し」に落とすので、`application/octet-stream` では
   **`lendObjectUrl` が一度も呼ばれない**。ObjectURL の寿命を見る計器なのに、
   その経路がゼロ件では測っていないのと同じ
3. **ラウンドの中で添付を開く** ── 一覧に並べるだけでは ObjectURL を 1 度も
   踏まないので、「残高 0 のまま横ばい」が**自明に通ってしまう**

⚠ 数える対象も直した。前の版は**一覧全体の件数**(18)を
`attachmentsInList` として出していたが、これは**ノートだけで満たせる**ので
「添付を抱えている」の証拠にならない。いまは
`[data-pkc-archetype="attachment"]` の行だけを数えている。

### 計器そのものの検品(空振り防止)

🔴 **心拍が止まっていても `maxGapMs` は小さい値のまま出る** ── そのまま読むと
「詰まっていない」という**嘘の結論**になる。測る前に**既知の 300ms の詰まり**を
1 度作り、見えることを確かめてから本番に入る(見えなければ計器を落とす)。

この検品で計器の欠陥が 2 件見つかった。**どちらも「0 件」を美点と読み違えさせる**向き:

- **`PerformanceObserver` の callback は非同期に届く** ── 詰まった直後に読むと
  その詰まりがまだ入っていない(304ms の空きは見えているのに long task は 0 件)。
  読む前に 1 手番譲る
- **`page.evaluate` の本体を直に回しても `longtask` は 1 件も出ない** ──
  debugger 由来の評価は frame の task として帰属されない。検品の詰まりは
  **ページ自身が持つ手番**(`setTimeout` の中)で起こす
  - 🔑 逆に言えば、**アプリ自身の仕事は帰属される** ── 本番の
    `longTasks: 0` は計器の欠陥ではなく実測値である

⚠ **fixture を作る手を測定に混ぜない**。canvas のノイズ生成を添付の計測窓に
入れていたときは `maxGapMs: 36`、外に出すと `16` だった ── アプリと無関係な
負荷が「添付が詰まる」の数字に混ざっていた。

## 結果 ①: 添付なし(100 ラウンド / 測定 90 ラウンド)

| | 前半(中央値) | 後半(中央値) |
|---|---|---|
| JS ヒープ | **9.0 MB** | **9.1 MB** |
| 生きている ObjectURL | 0 | 0 |
| DOM ノード数 | 226 | 226 |

- **long task 合計 3 本 / 172ms**(90 ラウンドの編集+確定を通して)
- ページ例外 **0 件**

40 ラウンドの回でも同傾向(ヒープ 9.3 → 9.1 MB、long task 2 本 / 122ms)。

**増えていない。** 90 回ぶんの編集・確定・図の焼き直しを通して、ヒープも DOM も
ObjectURL の残高も横ばい。revisions は 100 版まで積み上がっているので、
「revisions 常駐 0」(設計 doc P5 の DoD)がこの経路でも成立している。

## 結果 ②: 添付を抱えたセッション(段㉖、60 ラウンド / 測定 50 ラウンド)

1 ラウンド = **添付を開く**(preview に ObjectURL を貸す)→ ノートを開く →
編集 → 打つ → 確定。添付は **6 件 × 2.35MB(合計 14.1MB)の PNG**。

⚠ **対照群は「添付以外を全部同じにしたもの」** ── 同じラウンド数・同じ暖機・
同じノート fixture で、添付だけ 0 件にした回を並べる。

| | 添付 6 件(前半 → 後半) | 添付 0 件(前半 → 後半) |
|---|---|---|
| JS ヒープ | **9.3 → 9.2 MB** | 9.2 → 9.1 MB |
| 生きている ObjectURL | **0 → 0** | 0 → 0 |
| DOM ノード数 | **244 → 244** | 226 → 226 |
| 定常の long task | **0 本** | 0 本 |
| 定常の心拍・最大の空き | **53ms** | 55ms |

添付を貼る操作そのもの(6 件を続けて貼る):
**long task 0 本 / 心拍の最大の空き 16ms**。

### 読み方

- **抱えても増えない。** 14.1MB ぶんの添付を抱え、50 ラウンドにわたって
  開いては閉じても、JS ヒープの差は **0.1MB**、DOM は **+18 ノード**
  (= 一覧に増えた 6 行ぶん)だけ。bytes は IDB の Blob に居て
  **heap に載っていない** ── 設計どおりの向きである
- **ObjectURL が残らない。** 添付を開くたびに貸し、次の選択で返す ──
  50 回繰り返して残高は前半・後半とも 0。
  ⚠ この 0 に意味があるのは、**preview が実際に出た**(6 件)ことを
  測定の中で数えているから。画像でない添付だと貸出経路自体を通らず、
  同じ 0 が**何も測らずに**出る
- **貼る操作は詰まらない。** 2.35MB を 6 件続けて貼って long task 0 本・
  最大の空き 16ms。⚠ ただしこれは **PR #61 でハッシュをワーカーへ出した後**の
  数字である(それ以前は同じ経路で 500〜726ms 止まっていた)
- ⚠ 定常の最大の空き **53ms** は long task として計上されていない(境界のすぐ下)。
  添付なしの対照群も **55ms** なので、**添付が持ち込んだものではない**。
  この 50ms 級が何かは未特定 ── 詰まりを詰めるなら次はここ

⚠ **主張の範囲**:
- 絶対値(9MB)は環境依存。意味があるのは**前半と後半が変わらないこと**と、
  **対照群との差**のほう
- `performance.memory` は **JS ヒープだけ**を見る。IDB の Blob や
  ラスタの PNG は heap の外にあるので、この数字には出ない ──
  そちらは ObjectURL の残高と DOM ノード数で間接的に見ている。
  🔑 逆に言えば「heap が増えない」は**「メモリを使っていない」ではない**。
  添付 14.1MB は確かにどこかに居る(IDB)── 言えるのは
  **常駐(タブが抱え続ける量)には効いていない**ことまで

## 未測定(次にやるなら)

- **50ms 級の空きの正体**(添付の有無に関わらず出る。長い方の詰まり)
- **ラスタキャッシュが上限に触れる長さ**(32MB。この長さでは届かない)
- **タブを跨いだ常駐**(writer lease の待機側)
