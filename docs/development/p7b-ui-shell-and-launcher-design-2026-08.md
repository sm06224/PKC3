🔑 P3 の順序(構造を先に固める)としては筋が通っている。**問題は、P7 を

これは P7 設計 doc §0 が「**宣言はあるが実体が無い**」「install できてしまうぶん、

`src/features/flavor/attachment-flavor.ts` は PKC2 の launcher メタを

→ **PKC2 から移行した user は、自分のタイルがデータとして入っているのに
1 つも見えない**。これは「新機能を足す」話ではなく、**取り込んだデータの
到達不能状態**である(凍結方針の対象外だと考えるが、判断は user に仰ぐ)。

## 1. CSS の方針(案)

### 1-1. 何を作るか

`src/styles/app.css` **1 枚**。`main.ts` から `import './styles/app.css'` し、
Vite が hash 付き `.css` として出す(SW の precache は `dist/` を丸ごと拾うので
一覧は自動で追従する)。

| 対象 | 内容 |
|---|---|
| shell | CSS Grid の 2 ペイン(topbar / sidebar / main / notices / status)。狭い画面では 1 カラムへ折る |
| 一覧 | サイドバーの entry 行(選択状態・archetype 印・省略) |
| detail | 見出し・本文・ボタン列・履歴/ゴミ箱パネル |
| markdown | `pkc-md-rendered` 配下(見出し・表の罫線・コード・引用・脚注・目次) |
| かんばん / カレンダー / ファイラ | 列・グリッド・階層のレイアウト |
| 面 | 更新の案内 / 注意 / status footer |

### 1-2. 🔑 PKC2 を**丸写ししない**(user 指示 2026-07-30)

PKC2 の `src/styles/base.css` は **13,801 行 / 398 KB**(Fallout / PIP-Boy 風の
ダークテーマ)。PKC3 が引き継ぐのは**見た目の方向性**であって、
**あの物量ではない**。

| | PKC2 | PKC3 の目標 |
|---|---|---|
| 行数 | 13,801 | **1,000 行以下** |
| バイト | 398 KB | **12 KB 以下**(gzip 3 KB 前後) |
| テーマ | ダーク固定 + scale 変数 2 層 | 下記 §1-3 で裁定 |

⚠ 12 KB は配る量の 0.7% で、cap 残量(772 KB / 32%)から見れば誤差である ──
**削る理由は容量ではなく「次に読む人が読み切れる量に保つ」**ため。

### 1-3. 🔴 裁定してほしいこと(3 点)

| # | 論点 | 案 A | 案 B |
|---|---|---|---|
| 1 | テーマ | **PKC2 の系統(ダーク基調)を継ぐ** | OS 追従(`prefers-color-scheme` で明暗) |
| 2 | 密度 | **情報密度優先**(PKC2 寄り。1 画面に多く) | 余白広め(読みやすさ優先) |
| 3 | 調整口 | **無し(固定)** | `theme.scale` 相当の倍率を 1 つ持つ |

⚠ 3 は見た目より**重い判断**である。確認したところ **PKC3 には flag 機構が
まだ 1 つも無い**(`defineFlag` 相当が 0 件 = 15 枠すべて未使用)。つまり
「倍率を持つ」は**flag 機構そのものを最初に建てる**ことを意味する ──
`settings` と分離する規約(user 指示 2026-07-30)も同時に決めることになる。
**見た目のために機構を建てるのは順番が逆**だと考えるので、案 A(固定)を推す。
倍率が要るとなったら、そのとき flag 機構を単独の段で建てるほうがきれいである。

### 1-4. どう検証するか

- **視覚 smoke を 1 本足す**: 主要ペインが**可視高さを持ち、重なっていない**
  (`elementFromPoint` で覆いを検出)。⚠ 「CSS が読み込まれた」で止めない ──
  読み込まれていてもレイアウトが崩れていれば同じこと
- **既存の 18 件は全部そのまま通ること**(`data-pkc-*` セレクタしか使っていないので、
  CSS を足しても壊れないはず ── **それを確かめるのがこの段の最初の作業**)
- 配る量の増分を検品に出す(cap 残量を報告)

## 2. ランチャーの方針(案)

### 2-1. 何を出すか

`ViewMode` の `launcher` に実体を与え、上部に **ランチャー** ボタンを足す。
面には**タイル**を並べる:

| タイル | 元データ | 押したときの挙動 |
|---|---|---|
| アプリ | `registered_as_app: true` の attachment(HTML) | **新しいタブで開く**(blob URL、`lend`/`dispose` の規律に従う) |
| URL | `launcher_url` を持つ attachment | 同上(PKC2 は referrer 遮断のリダイレクトページを挟む ── §2-3) |

並びは `app_group` でグループ化し、その中を `app_order` → 登録順で安定ソート。
**PKC2 の `tile-order.ts` と同じ意味論**にする(移行後に並びが変わらない)。

### 2-2. 何を**やらない**か(この段では)

- タイルの drag & drop 並べ替え(PKC2 #928)── **見えるようにするのが先**
- 「アプリとして登録」のトグル UI ── 取り込んだデータが見えれば移行の用は足りる
- extension host / pkc-ext 拡張チャネル ── 正本 doc §10 の将来領域

🔑 **見えない状態を解消する最小**に絞る。足りなければ次の段で足せる。

### 2-3. ⚠ URL タイルは**そのままでは移せない**

PKC2 は「オリジンを相手サイトに渡さない」ために**リダイレクト専用の小さな HTML を
attachment 化**し、`window.open('') + document.write` 経由で開く。PKC3 は
Pages 上の PWA(`https://` オリジン)なので、**file:// 前提のこの理屈がそのまま
成り立つか未検証**である。

→ 実装前に「PKC3 のオリジンで開いたとき referrer / opener が実際にどう飛ぶか」を
**測ってから**決める(CLAUDE.md の計測規律)。測るまでは URL タイルは
「開くが、遮断の保証は PKC2 と同じとは書かない」に留める。

## 6. 段⑨ 実装記録(2026-08-03 着地)

`src/styles/app.css` **1 枚**(`main.ts` から import)+ `tests/smoke/layout.smoke.spec.ts`。

| | 目標 | 実測 |
|---|---|---|
| バイト | 12 KB 以下 | **9.75 KB**(gzip 2.22 KB) |

🔑 **既存 smoke 18 件が 1 件も壊れずに通った**。`data-pkc-*` しか機能セレクタに
使わない規約(PKC2 から継承)が効いている ── これを最初に確かめてから中身を詰めた。

#### 🔴 「CSS が読み込まれた」で止めない

`layout.smoke.spec.ts` が見るのは**位置関係**である:サイドバーと本文が横に並ぶ /
かんばんの列が横に並ぶ / status が最下段にある / 面が重ならない /
一覧の行が覆われていない(`elementFromPoint`)/ 表に罫線がある /
狭い画面で 1 カラムへ折る。⚠ 段⑨ 以前の実際の姿(サイドバーが本文の上に縦に流れ、
かんばんの列が縦に積まれる)は**どれもこの spec が落とす**。

#### ⚠ 書いていて自分で踏んだ ── notices と update に**同じ grid area**

両方出ると重なって下の面が読めない。しかも**最初に書いた smoke では捕まらなかった**
── 「既定で出ない」しか見ておらず、重なりは**両方出たときにしか観測できない**。
自然に両方出す(取込の注意 + 待機中の SW)のは高くつくので、
**強制的に出して位置関係だけ**を見る形にした。

変異試験 7 件・生存 0(CSS を読み込まない / grid をやめる / かんばんを縦に積む /
`hidden` を効かなくする / 罫線を消す / 折り返しをやめる / 面を同じ行に戻す)。
⚠ 最後の 1 件は 1 巡目で生き残り、上の観測点を足して落ちるようにした。

## 7. 段⑨b 実装記録 ── 役割メニュー(2026-08-03 着地)

> user 指示 2026-08-03「**メニューは役割ごとにサブメニュー化してください**」

以前は上部に 9 個のボタンがベタ並びで、「見る」「入れる」「出す」「整える」が
**同じ重さ**に見えていた。役割で畳む:

| | 中身 |
|---|---|
| ビュー(**畳まない**) | 詳細 / かんばん / カレンダー / ファイラ |
| **取り込む** | 取込 |
| **書き出す** | バックアップ / 閲覧用 HTML / Markdown |
| **整理** | 添付の整理 |

⚠ **ビューは畳まない** ── 表示の切替は常時使う主軸で、押すたびに開くのは邪魔。
畳むのは「たまに使う・押すと何かが起きる」ものだけである
(`tests/docs-parity.test.ts` が「ビューがメニューに入っていないこと」を pin)。
⚠ **項目の文言は変えない** ── 畳んでも user が読む語は同じ。マニュアルの導線
(「取り込む → 取込」)だけが増える。

実体は `<details>` + `<summary>`(JS で開閉状態を持たない)。`installMenuDismiss` が
**閉じ方と排他**を担う ── 外側クリック / Escape / 項目を押したら閉じる。

#### ⚠ 既存 smoke が 6 件落ちた ── **それが正しい**

畳んだ結果「閉じたメニューの中は押せない」で `clickReal` が落ちた。実際の user も
開かなければ押せないので、**その動線を再現する** `clickMenuItem` を helper に足した
(メニューを開いてから押す。開けるかどうかも観測点になる)。

#### 🔴 変異試験で自分の穴が 3 件

| 変異 | 何が起きていたか |
|---|---|
| 排他をやめる | `name` 属性(ブラウザ native の排他)が **dismiss 側と重複**していて、外しても振る舞いが変わらなかった ── **消した**(test が守れないものは持たない) |
| ビューもメニューに畳む | **変異が発火していなかった**(`void 0;` を足しただけ)── 実際に移す形に書き直したら落ちた |
| 開いているメニューを `pointerdown` で閉じる | **本物の穴**。「閉じた」だけを見ていると、`click` が届かず**メニューは畳まれるのに何も起きない**実装が素通りする → 観測点を「確認ダイアログが出たか」= ハンドラに届いた証拠に変えた |

変異試験 8 件・生存 0。CSS は 10.62 KB(gzip 2.43 KB)、配る量 1638.5 KB
(cap 残量 761.5 KB / 31.7%)。
