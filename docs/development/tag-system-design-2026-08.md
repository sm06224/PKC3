## 1. user の要望(⚠ 要約しない)

> **タグを打つのは本文編集中でも行いたい。というかfrontmatterは本文中に打たれたタグを
> 保存時に重複排除して集約するインボディタグ(自動集約)と文書タグ(frontmatterに直接設定)に分け、
> ユーザーがどの見出しや記事でタグがついたのかわかりやすくすべき**

> **PKC-Markdownの仕様をふやす　「#tag-name #tag-name2」 のように、見出しにならない＝
> 井桁と名前を半角空白で区切らない、タグ同士は半角空白または全角空白で区切る単独行は
> 空白文字種でパースしてその行が存在する見出しレベルのタグとして機能すること。
> そして、タグはバッジ化して表示が必要**

## 3. 段① 記法 ── 本文中のタグ行

### 3.1 規則

**単独行**が、次を満たすときタグ行とする:

1. 行(前後の空白を除く)が **1 個以上のトークン**だけからなる
2. トークン = `#` + 名前。⚠ **`#` の直後に空白を置かない**(置けば見出し)
3. トークンの区切りは **半角空白 / 全角空白 / タブ**(「空白文字種でパースして」)
4. そのタグは、**その行が属する見出しレベル**に付く

⚠ **fence の中は見ない**(preprocessor の既定の作法)。

### 3.3 推薦 ── **タグ名に「数字以外」を 1 文字以上求める**

| 書いたもの | 読み |
|---|---|
| `#買い物 #急ぎ` | ✅ タグ行 |
| `#tag-name #tag-name2` | ✅ タグ行(user の例) |
| `#117 #121` | **本文のまま** |
| `# 見出し` | ✅ 見出し(いままでどおり) |

⚠ 失うのは「数字だけのタグ」だけ(必要なら `#no117`)。得るのは
**番号を並べる書き方が黙って意味を変えられない**こと。

測ったのは **repo の doc = 書き手が 1 人**の corpus である。
🔑 user の実データで同じ走査を回すのが最短の裏取り
(**中身は出さず件数だけ返す**形にできる ── 機密資料の作法と同じ)。

## 4. 段② 2 種類のタグ

| 種類 | 出どころ | 誰が書くか |
|---|---|---|
| **インボディタグ** | 本文のタグ行 | **保存時に自動集約**(重複排除) |
| **文書タグ** | `tags:`(frontmatter) | user が直接 |

### 4.1 🔴 「どの見出しでついたか」を捨てない

user の要件は「**ユーザーがどの見出しや記事でタグがついたのかわかりやすくすべき**」。
⚠ 2 つを 1 つの集合へ潰すと**この要件を満たさない**ので、
インボディタグは **(タグ, 見出しの位置)** を持つ。

### 4.2 ⚠ frontmatter を自動で書き換えるか ── **これが最大の分かれ目**

| 案 | 中身 | ⚠ |
|---|---|---|
| **A. 書き戻す** | 保存時に集約結果を `tags:` へ**書く** | 🔴 **user の本文を機械が触る**。`body-rewrite.ts` の作法が要る。取り消しが効くか要検討 |
| **B. 索引だけ** | `tags:` は user のものだけ。集約は**索引に持つ** | ✅ 本文を触らない。⚠ 「frontmatter は…集約する」という user の字とはずれる |
| **C. 併記** | `tags:` は user のもの、集約は別 key(例 `tags-in-body:`) | 見えるが、key が増える |

🔑 **推薦は B。** 理由:
- user の本文を機械が書き換える経路は、**この repo が最も事故を起こしてきた場所**
  (S3 型のデータ破壊 / 旧ビルドとの互換)
- 集約の目的(探す・集計する・スマートフォルダ)は**索引で全部果たせる**
- ⚠ user の字は「frontmatter は…に分け」であって「frontmatter に書け」とは限らない
  ── ここは**読み違えの可能性があるので裁定をいただきたい**

⚠ **A を選ぶ場合の追加要件**: 書き戻しは**保存の 1 経路だけ**にし(#7 の「同じ判定が 2 か所」)、
旧ビルドが読んでも壊れない形にする(不変条件 5 の双方向互換)。

### 実装の在り処(段②)

| もの | 場所 |
|---|---|
| 集約(判定の 1 か所) | `src/features/flavor/entry-tags.ts` |
| 索引の列 | `entries.body_tags`(`schema.ts` の `ENTRY_ADDED_COLUMNS`) |
| 書くとき | `bindUpsert`(保存の 12 経路が全部ここを通る) |
| 既存 user の埋め戻し | `NEEDS_BACKFILL` + `backfillDerivedColumns` |
| 走査(worker) | `runSmartScan` → `SmartScanRow.bodyTags` → `tagsForMatch` |
| 保存直後の当て直し | `app-state.ts` の `updateSmartHits` |

⚠ **版(`DB_SCHEMA_VERSION`)は上げない** ── 上げると旧ビルドが同じ DB を
**開けなくなる**(`userVersion > DB_SCHEMA_VERSION` で明示 reject)。
判定は「列の実在」なので、上げなくても移行は効く(`task_total` と同じ作法)。

### ⚠ 変異試験が教えた穴 2 件(記録)

1. **`NEEDS_BACKFILL` から `body_tags IS NULL` を外しても緑だった** ──
   test が**いちばん古い形の DB** しか通しておらず、そこでは `task_total` も NULL
   なので**どの項が生きていても**埋め戻しが走ってしまう。⚠ 外れていて困るのは
   **前の版で開いた DB**(= 既存 user 全員)である。門を N 個置いたら
   **N 個目だけが鳴る場面**を作る、の実例。
2. **保存直後の当て直しが `readTags`(先頭だけ)を読んでいても緑だった** ──
   「保存直後だけ当たらず、集め直すと当たる」という**いちばん気づけない食い違い**
   になるところだった。
