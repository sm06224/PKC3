## 0. 何を求められているか(user 裁定 2026-09-13。こちらの解釈)

**予定表を、直感的な操作になるように作り変えること。「選択して、作って、入れて」と
段を踏ませる形はだめ。**

⚠ 私は正本 doc で段を「**A(時間の帯)→ B(直接操作)**」の順に推薦していたが、
この裁定を受けて読みを改める ── 🔑 **B が目的で、A はその前提**である。
A だけ入れても「見えるようになっただけ」で、求められていることを 1 つも満たさない。

**だから A と B は 1 つの束**にし、**束の完成**を段の完了条件にする。

## 1. いま「選択して作って入れて」になっている所(実測 2026-09-13)

予定を **1 つ作る**経路は **4 本**ある(ほかに「作らない」経路が 2 本)。

| | 経路 | 手数 |
|---|---|---|
| ① | 本文に `- [ ] 見積 @2026-08-25` と打つ | 開く → 編集 → 打つ → 保存 |
| ② | 予定タブの「足す」欄 | 打つ → 日付を直す → 「足す」を押す |
| ③ | 束の見出しの「+」 | 「+」→(②の欄に日が入り、焦点が移る)→ 打つ → **「足す」を押す** |
| ④ | 書式帯の「日付」 | 編集に入る → `- [ ] ` を自分で打つ → 「日付」→ 小窓で選ぶ → 「入れる」 |

🔴 **③ に、この設計のいちばん大きい穴が出ている** ── **「+」はその日に予定が
1 件以上ある日にしか出ない**(束の見出しは「予定が在ることの結果」であって
「日付という枠」ではない)。⚠ つまり**空いている日には、押す所が 1 つも無い**。

🔑 **「空いている所を指でなぞって予定を置く」は、いまの一覧型の構造では原理的に
作れない。** これが段 A(時間の帯 = 空いている時間が**面積として在る**)を

## 4. 🔴 先に決めることが 4 つある

### 決 1. 予定を「掴む」のは HTML5 の drag か、Pointer Events か

| | いま |
|---|---|
| 予定の札 | **HTML5 の `draggable`**(`task-card.ts`) |
| 板の塊(移動・伸縮) | **Pointer Events**(`place-drag.ts` ── `pointerdown` / `move` / `up`) |

🔴 **測った(#855 決1 の実装で。2026-09-13)。** 観測点は「掴んで通った先で
`data-pkc-dropping` が立つか」+「保存された本文が書き替わるか」の 2 つ、
測り方は実ブラウザ・CDP の `Input.dispatchTouchEvent`(本物の touch、
50ms 保持でも 600ms 保持でも試した)。

| | 掴んで通った印(`data-pkc-dropping`) | **本文** |
|---|---|---|
| マウス(対照群) | 光る | `@2026-09-13` → `@2026-09-16` に書き換わる |
| 🔴 指(CDP の本物の touch) | **1 度も光らない** | **変わらない** |

**読みは当たっていた** ── `long-press.ts` の節が書いていたとおり、
`card.draggable = true`(HTML5 drag)は指の押下から `dragstart` を起こさない。

🔑 **実装した推薦:予定を掴む口を Pointer Events(`schedule-drag.ts`)へ足した
(`place-drag.ts` と同じ形:`pointerdown`/`pointermove`/`pointerup`)。**

⚠ **ただし「一覧の面だけ HTML5 drag を残す、はやらない」を、そのままの形では
実装しなかった** ── 実装の途中で 2 つの実測が積み重なり、**マウスの HTML5 drag
(`binder.ts`)はそのまま残し、Pointer Events は指・ペン専用にした**(入力の種類で
完全に棲み分ける。`long-press.ts` が並べ替えで既に採っている形)。理由:

1. `document.elementFromPoint` は **happy-dom で常に `null` を返す**(実測)ので、
   Pointer Events 版の「どこへ落ちたか」判定は **unit で検められない** ── マウス側の
   HTML5 drag を消すと、`tests/adapter/schedule-view.test.ts`(`dragTo` ヘルパで
   組んだ、掴んだ日が荷物に無い形の防御まで含む約 900 行)の同等な unit 網が
   **再現不能**になる(smoke だけに頼ることになり、CLAUDE.md「フルスモークの
   使い所」に反する重さになる)。
2. 「掴む」を確定する条件も、依頼どおりの `DRAG_SLOP`(少し動いたら掴む)を
   **実測で作れないと分かった** ── 升目(落とし先)は札の**縦にずっと上**に在り
   (実測 `y` の差 ≈140〜150px)、「動く」を全方向で受けると縦スクロールを
   握り潰す。だから**長押しで確定**(`LONG_PRESS_MS`)にし、確定後だけ全方向で
   受ける形にした(詳細は `schedule-drag.ts` の docstring)。
3. 🔴 実測でもう 1 段落とし穴が在った ── `PointerEvent.preventDefault()` は
   この Chromium で**縦スクロールを止めない**。素の `touchmove`(Touch Events)を
   非 passive で `preventDefault` して初めて止まった(`schedule-drag.ts` に実測込み)。

判定は「誰が問いに答えるか」で 1 本に保っている ──**入力の種類ごとに 1 つの
口**(マウス = HTML5 drag / 指・ペン = Pointer Events)、**落とし先の判定
(`dropTaskCard`)は両方から呼ぶ共通の 1 関数**。⚠ これは決1 の元の推薦
(「口を 2 つ作らない」)を**入力の種類の軸では満たすが、「実装の仕組み」の軸
では満たしていない**(仕組みは 2 つのまま)── 段 B で伸縮 / なぞって新規を
Pointer Events で作るときに、**「掴んで動かす」もマウス側を Pointer Events へ
寄せ切るか**は、あらためて裁定が要る(据え置き)。

**これが分かったら覆る**:一覧の面の drop 先(`data-pkc-drop-date`)を Pointer で
作り直すと、**既存の 5 系統の落とし先**(整理系 4 + 予定 1)と作法が割れる、と分かったとき。

### 決 3. 「14:00 から 15:00」をどう書くか(記法)

🔴 **いまの記法に終わりの時刻は無い。** `..` は**日付の終わり**専用で、
**期間には時刻を付けない**と決めてある(期間の札は複数の日に出るので、
「その時刻がどの日のものか」が決まらないため)。

🔑 **推薦:時刻の尻に `..` を継ぎ足す ── `@2026-08-25 14:00..15:00`。**

⚠ **記法を新しく作らない**という `repeat.ts` の思想どおりである(あちらも
「終わりは既存の `..` が兼ねる」)。⚠ 位置で見分けられる ──
**日付の直後の `..` は期間、時刻の直後の `..` は時間の幅**。
🔑 読み方も既にある形をなぞる:**読み終わった直後の字だけを別に見る**
(`readRepeatTail` と同じ)── 走査の網(`AT_DATE`)は 1 バイトも広げない。

⚠ **実測で確かめたこと**:いまこう書くと `14:00` までが時刻として読まれ、
`..15:00` は**札にそのまま字で残る**(黙って捨てられてはいない)。
つまり**壊れている本文を作らずに足せる**。

**これが分かったら覆る**:総当たりで、`@2026-08-25..2026-08-26`(期間)と
`@2026-08-25 14:00..15:00`(幅)を**取り違える形**が 1 つでも見つかったとき。

⚠ これは正本 doc の**段 C** に置いてあるが、🔴 **段 A/B より先に要る**
── 帯の中の長方形は「長さ」を持つので、長さを書く所が無いと
**画面でしか伸縮できない**(保存すると消える)。

### 🔴 裁定が出た(user 2026-09-13)── **1 回か全部かを選ばせる(Outlook 模倣)**

⚠ **上の推薦は退けられた。** 理由は明らかで、あの案では
**「この回だけずらす」が永久にできなくなる**(記法を増やさないという**こちら側の都合**と、
user の動線を交換していた ── CLAUDE.md「動線をこちらの都合と交換するな」)。

🔑 **落としたときに小窓を 1 つ出す**:

| 押す所 | 本文がどうなるか | 新しい記法 |
|---|---|---|
| **この回だけ** | 落とした日に**行が 1 本増える**(`- [ ] 定例会 @2026-09-22 振替2026-09-20`) | 🔴 **1 つ**(`振替<元の日>`) |
| **全部** | 規則の行の日付が**ずれるだけ**(`@2026-09-13 毎週` → `@2026-09-15 毎週`) | 🟢 無し |
| やめる | 何も起きない | ─ |

#### ⚠ なぜ「除く」を規則の行に足さないか

素直な形は規則の行へ `除く2026-09-20` を足すことだが、**採らない** ──
🔴 **動かした行を消したときに、元の回が戻ってこない**(規則に「除く」だけが残り、
その回は静かに消えたままになる)。
🔑 「振替」を**動かした行のほうに書く**と、**行を消せば元の回がそのまま戻る** ──
取り消しのための仕掛けが要らない(user 裁定 2026-08-23「片道の操作を作らない」)。

#### 🔑 展開の側に新しい分岐は要らない

`repeat.ts` は既に「**同じ字の実体の行がその日に在れば、規則からは出さない**」
(`skip` = 済んだ回の実体)を持っている。🔑 「振替」は**その `skip` に元の日を足すだけ**である。

#### ⚠ これが分かったら覆る

- 「全部」が**ずらす**ではなく**規則そのものを編集する画面**の意味なら、作る物が変わる
- 「**これ以降すべて**」(3 つ目。Google カレンダー式)も要るなら、規則を 2 本に割る形になる
  ── いただいた言葉が「**1 回か全部か**」だったので、**2 択**で作る
