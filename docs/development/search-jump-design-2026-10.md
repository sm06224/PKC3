# 「探す」の結果から、本文の当たった所へ送って塗る(#1102 段①、2026-10-01)

> 出どころ:#1102(提案「検索結果のスニペット表示と本文ヒット位置への自動スクロール」)。
> 裁定:設問 2 つへの答えは **A / A**(#1102 のコメントの設問 1「当たりを本文のどこにどう付けるか」=
> 本文の DOM を変えずに塗る / 設問 2「検索語を本文へどう運ぶか」=「探す」の行から。左の列の行は変えない)。
> 進め方は #1163 の約束事(Gemini の答えで進めてよい)。

## 1. 画面で何が起きるか

| 場面 | 起きること |
|---|---|
| 「探す」の行を押す | これまでどおりノートが**別のウィンドウ**で開く。**開いた本文で、探した語が塗られ、いちばん上の当たりへ送られる** |
| 本文の右上(「目次」の隣) | **「1/4 件 ‹ ›」と ×** が出る。‹ › で前後の当たりへ送り直し、塗りの「いまの 1 つ」が動く。最後の次は最初へ回る |
| × / `Esc` | 塗りも件数も消える。`Esc` は **1 回で 1 段**(次の `Esc` は従来どおりノートを閉じる / 付箋の窓なら窓を閉じる) |
| 畳んだ章の中に当たりが在る | **章を開いてから**送る(目次の `tocJump` と同じ作法) |
| 本文に当たりが無い(題名にだけ当たった) | 帯に「本文に当たった所はありません」。送りは押せない(× は押せる) |
| ノートを変える / 編集を始める | 塗りも帯も消える。編集をやめて戻っても**勝手に再開しない** |
| Custom Highlight を持たないブラウザ | **塗らない**。送りと「n/m 件」だけが動く(帯は出るので無言にならない) |
| すでにそのノートを開いている窓が在る | その窓が前に出て、**同じく塗って送る**(語を落とさない) |
| 出ない所 | 書き出した HTML / 章の別ウィンドウ / 留めた枠 / 左の列の行(B は却下) |

## 2. 作り

### 2.1 塗り方 ── 本文の DOM を 1 バイトも変えない

`CSS.highlights` に Range を登録するだけ(`::highlight(pkc-search-hit)` = 全部の当たり、
`::highlight(pkc-search-hit-current)` = いまの 1 つ)。**節点は 1 つも増えない**ので、
①本文の差分描画(`applyBlocks`)②ライブエディタの行の対応 ③書き出し・印刷 を壊さない。
当たりの数え方は text node ごと(`features/filter/search-hits.ts` の純関数 + `render/search-jump.ts`)。
操作のために差し込んだ字(ボタン・並べ替えの矢印・言語ラベルなど)は数えない。

### 2.2 語の運び方 ── 既存の「探す → 開く」に語を 1 つ足す

```
探す窓の行(data-pkc-find = 結果が返ってきた語)
  → open-note-window(binder)→ services.openNoteWindow(lid, find)
      ├ 新しい窓 : 住所に `find=` を載せて開く(`formatViewDeepLink`)
      │             → 開いた窓の `connectViewDeepLink` が選んだ後に SEARCH_JUMP_START を撃ち、
      │               **使ったらすぐ住所から外す**(栞・F5 に語を焼き付けない)
      └ 開いている窓 : NoteRegistry.raise(lid, find) → 相手の onRaise(find) → SEARCH_JUMP_START
```

URL の断片は**ディープリンクの key の 1 つ**として足した(「クエリを抜け穴にしない」の範囲内)。
語は 200 字で切る。

### 2.3 控えの持ち方

`AppState.searchJump = { lid, query, step, gen }`(DOM を持たない)。
**当たりの数は DOM を数えないと分からない**ので、state は「進んだ回数(step)」だけを持ち、
描く側(`detail.ts`)が当たりの数で畳む(`wrapHitIndex`)。`gen` は START / 送りごとに進む
(同じ語でもう一度でも送り直せる / 描き直しでは跳ねない)。
消えるのは **`reduce()` の外側 1 か所**(`dropStaleSearchJump`):選んでいるノートが違う / `ready` でない
/ 章の欄が開いている ── **結果の形**で見るので、次に選択を動かす case を足した人が忘れられない。

### 2.4 描画

`DetailRenderer`(主の枠だけ)が、本文を描き終わったとき(`PAINTED_ATTR` の後)と控えが動いたときに、
当たりを数え直して塗り、帯を更新する。**送るのは `gen` が変わったときだけ**。
語そのものの高さへ送る(段落を中央に置くと、長い段落の中の 1 語が画面の外に出る)。
画像の読み込みで押し流されたら 1.5 秒だけ追いかける(`scrollSettled` と同じ作法)。

## 3. 範囲外・既知の限界

- 語が**太字やリンクをまたぐ**所は数えない(text node ごとに引くため)。
- **遅れて描く図**(mermaid / グラフ)の中の字は対象外。
- **全角と半角は同じ字として扱わない**(「探す」自身がそう引く。探すで当たらなかった所を、ここだけ当たりにしない)。
- 左の列の行に抜粋を出す案(B)は却下済み。

## 4. 覆る条件

- **Custom Highlight を持たないブラウザで困る声が出たら** → B の `<mark>` を差し込む方式を検討する
  (書き出し HTML と同じ作り。差し込んだ分だけ DOM が変わる = 差分描画・行の対応との突き合わせが要る)。
- 「探す」の結果を押したあと**別のウィンドウではなく本体の中央で開きたい**という要望が出たら、
  `SEARCH_JUMP_START` は窓に依らない(選んでいるノートへ塗る)ので、運び方だけを替えればよい。
