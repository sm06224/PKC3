## 何を測ったか / 測っていないこと

通常版(`npm run build` の `dist/` を `vite preview` で配信)を、実ブラウザで、ノート 3,001 件の入った状態で操作した。
起動の速さは対象外。見たのは、使い続けている間の**操作の応答**と**常駐メモリ**である。

⚠ **限界(読む前に)**
- 合成データである。実際の user のノートの形ではない。**フォルダで整理した fixture** なので、根の行数は 7 行。フォルダを使わず 3,000 件を根に並べている user は、下の「平らに全部出す」と同じ行数を**常に**描く
- Tracing とプロファイルを掛けると時間は 2〜4 倍に伸びる。原因の**配分**だけ読み、絶対値は計器なしの値を使う
- 最初の 3 回(t1〜t3)の a・e は、計測用 script の不備(行の題名の取り方・根へ戻っていない)で無効だった。a・e は t4〜t6 の値だけを使う(b〜d は 6 回とも有効)
- 3,000 件で container.json が 13.6 MB(日本語を `\uXXXX` に escape した合成物)になる zip は、取り込みが `zip の圧縮データを展開できませんでした(container.json): Failed to fetch` で失敗した(`zip-reader.ts` の `Response.blob()`)。8.4 MB に落とすと通った。**この箱の blob 容量の制約か、製品側の上限かは判定していない**(ディスク空きは 1.8 GB だった)
- 「入力 → 描画」の時間は、keydown の `event.timeStamp` から 2 回目の rAF までで測った(合成入力。実機の OS の入力遅延は含まない)

## 重い順の 3 件と原因

### 1. 根から検索すると 1 字ごとに 120〜200 ms(c')

- 1 字ごとに表を `textContent = ''` で**全部壊して作り直す**(`src/adapter/ui/render/filer.ts:876`、行を作るのは `:1039`)。結果が 210〜438 行でも毎回全部組み直す
- プロファイル(5 字、合計 1,159 ms の描画)で、**自己時間 933 ms が `ScrollMemory.use`**(`src/adapter/ui/render/scroll-memory.ts:80` の `el.scrollTop = …`、呼び元 `src/adapter/ui/render/browse.ts:403`)。作り直した直後に `scrollTop` を書くため、**ここで同期レイアウトが走る**(JS の行に見えるが中身はレイアウト)
- Tracing では UpdateLayoutTree 406 ms(3,956 要素)+ Layout 385 ms(dirty 6,162 / 全体 6,385)+ Layerize 242 ms。JS の計算(`filerRows` / `matchesTitle` 等)は合計でも 30 ms 未満
- 同じ検索を**フォルダの中**(63 行)ですると 36〜60 ms になる ── 費用は行数に比例している

### 2. 「中まで全部出す」/ 根に大量に並ぶ一覧(a'・d'・メモリ)

- 3,000 行を一度に作る。仮想化も `content-visibility` も無い(`content-visibility: auto` は `src/styles/app.css:1703` のフォルダ概要の行にだけある。表の `tr` へ効くかは**未確認**)
- 選ぶたび(a')の Tracing 比較(8 回選ぶ間):

  | | 3,000 行 | フォルダ 63 行 |
  |---|---|---|
  | Paint | **1,090 ms**(70 回) | 62 ms |
  | PrePaint | **632 ms** | 24 ms |
  | Layout | 245 ms(全体 42,547 オブジェクト) | 70 ms |
  | HitTest | 332 ms | 5 ms 未満 |

  選択の切り替えは表を作り直さない速い経路(`filer.ts` の「選択だけの変化」)に入っているので、費用は**表が大きいことそのもの**の描画側である。JS 側は 1 選択あたり約 86 ms(`dispatch` 691 ms / 8 回。`inspector.ts:238` の描画 313 ms、`scroll-memory.ts:80` 123 ms など)
- 入れる操作(d')は 3,000 行を 1 回組む。単一 task が最大 924 ms(Tracing 下)
- メモリは +約 98 MB(上の表)。JS ヒープは増えない

### 3. 長いノートを開くと 0.5 秒止まる(e)

- 3,000 行のノートは 74,000 px・約 21,800 節点。開くと**単一のレイアウトが 392 ms**(Tracing。dirty 14,177 / 全体 16,359)
- プロファイルで内訳: `detail.ts:1905` の描画 1,422 ms / 3 回のうち **`restoreScroll`(`detail.ts:2114`)が 1,198 ms**。`this.scroller.scrollTop = …` が同期レイアウトを起こし、本文全体を組む費用がここへ出る(1 と同じ型)。ほかに `applyBlocks`(`apply-blocks.ts:195`)114 ms / `formatBodyStats` / `estimateReadingTime` / `applyHeadingAnchors` が各 20〜40 ms
- 画面に出ない 9 割の段落も含めて組んでいる。メモリも +約 75 MB

### 付随(小さいが全操作に乗る)

- `FilerRenderer.dateSignature`(`filer.ts:625`)は、**選ぶだけの描画でも毎回** 3,000 件分の日付を整形して文字列にする(フォルダの中を選ぶプロファイルで自己時間 95 ms / 8 回 ≒ 12 ms ずつ)。`render` 内の `datesChanged`(`filer.ts:715`)で毎回呼ばれる
- 起動直後の Pss(241〜275 MB)は GC 後(約 200 MB)より約 40〜70 MB 高い。定常ではなく起動の話なので優先度は低い

## 提案する直し方(効く順)

「見た目が変わるか」は、変わるものは**画面の言葉で**書いた。見た目が変わる案は、入れる前に画面で見せる(CLAUDE.md「見え方を変える判断は user のもの」)。

| 順 | 直し | 効く操作 | 規模 | 見た目の変化 |
|---|---|---|---|---|
| 1 | 一覧(`filer-table`)を**画面の外の行を作らない**形にする(窓の分だけ行を作る。上下に空きの高さを置く)。根の大量表示・「中まで全部出す」・検索結果の全部に効く | c'・a'・d'・メモリ(+98 MB の大半) | **L**(範囲選択の reducer・ドラッグ&ドロップ・フォーカス移動・`Ctrl+A`・スクロール位置の記憶が「全行が DOM に在る」前提。`filerRows` が行を決める 1 か所なので、窓は描画側だけで切れる) | 無し(スクロールバーの長さは同じにする)。⚠ ブラウザの検索(Ctrl+F)は窓の外の行を探せなくなる ── 見えるので要確認 |
| 2 | 検索の 1 字ごとの**作り直しをやめて、行を使い回す**(`data-pkc-entry` を鍵に、増える行・消える行だけ触る)。または入力を 100〜150 ms まとめてから描く | c'(1 字 120〜200 ms → フォルダ内と同程度が目標) | **M**(使い回し)/ **S**(まとめる) | 使い回しは無し / まとめるは「打ってから結果が出るまで最大 150 ms 遅れる」(**見える**) |
| 3 | 3,000 行ノートの本文の段落に `content-visibility: auto` + `contain-intrinsic-block-size: auto <見積り>` を付ける(`app.css:1699-1704` のフォルダ概要で、強制レイアウト約 13 ms → 約 1.5 ms を測った型)。読み位置の記憶(`captureReadAnchor` / `installReadAnchorHold`、#1490・#1525)との噛み合わせを先に確かめる | e の 0.5 秒・+75 MB | **M** | 原則無し。⚠ 初めて見える段落の実寸が決まるまで、スクロールバーの長さがわずかに動きうる(`auto` が一度見た高さを憶える) |
| 4 | `ScrollMemory.use` の `scrollTop` 書き込みを、**値が変わるときだけ**・かつ位置の記憶が無い面(新しい面)では書かない。強制レイアウトを描画の後ろへ回す | c'・e・a'(同期レイアウト分。ただし表の大きさが残れば 1 を入れるまで根治しない) | **S** | 無し(戻す位置は同じ) |
| 5 | `dateSignature` を `entryMetas` の参照 + 日付キーで 1 回だけ計算して使い回す | 全操作の描画 12 ms 前後 | **S** | 無し |
| 6 | 「中まで全部出す」を入れる操作を、先頭 200 行を先に出して残りをアイドルで足す | d'(単一 924 ms task → 数十 ms ずつ) | **M** | 入れた直後、下の行が少し遅れて足される(**見える**)。1 を入れれば不要 |

**推薦**:1(窓切り)を本命にする。2 と 3 と 4 は 1 と独立に効くので、先に S の 4・5 を入れて効果を測り(各 1 本の PR)、その後に 3、最後に 1 を段階化して入れる。
覆る条件:4 を入れても c' が 100 ms を切らなければ、強制レイアウトではなく**表の大きさ**が主因と確定する(= 1 を最優先にする)。
