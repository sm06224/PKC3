# P8 段㉗: 図ラスタの上限 ── 実測と、そこで出た欠陥

> user 指示 2026-08-03(不可侵)
> 「**初回起動が遅くとも、そこは許容 / その後の動作がメモリくったり、もっさりだと
> 嫌なだけです**」
> 「**mermaid 図のエクスポートをさせるとき以外は PNG ラスタをキャッシュして、
> GPU レンダリングで表示して欲しい**」

## なぜ測ったか

図のキャッシュには 32MB の上限と LRU の追い出しが P8 段⑰ で入り、段㉑ で
「鍵と中身を対で舐める」へ直した。しかし **上限に触れる長さで動かしたことが
一度も無かった** ── ゼロ件の次元と同じで、触れない長さで回している限り
追い出しは 1 度も走らない。

⚠ この origin の quota は **OPFS の sqlite(ノート本体)と添付 Blob と共用**
である。上限が実効的に効かないことは「無駄が増える」ではなく
**ノート消失に接続する**。

計器: `tests/bench/run-raster-cap.mjs`

## 結果 ①: 上限は守られている

fixture: 40 節の図を 1 枚ずつ持つノートを 200 件、順に作って開く。

| | 値 |
|---|---|
| 図 1 枚の平均 | **181 KB** |
| 追い出しが初めて走った所 | **185 枚目** |
| 観測した最大 | **33,485,480 B**(上限 33,554,432 B の **99.8%**) |
| 上限を超えた標本 | **0** |
| 落ち着いた先 | 29.3 MB / 162 行 |
| 追い出された図を開き直す | **出る**(焼き直しに落ちる) |

⚠ **「触れた」ことを測定の中で確かめている**(`firstEvictionAtDiagram`)。
ここが null なら追い出しは 1 度も走っておらず、「超えなかった」は何も証明しない。

### 一気に焼いたとき ── **上限を 161,573 B 超える**(約 0.5%)

1 枚ずつ焼く分には put の間隔が空くので、`evictDiagramCache` の
`if (evicting) return 0`(走っている間の依頼を取りこぼす門)を**一度も踏まない**。
1 つの文書に図を 40 枚入れて一気に焼かせると踏む:

- 山: **33,716,005 B**(上限 +161,573 B = **+0.48%**)
- そのあと **29.7 MB へ収束**(取りこぼしても後続の put が追いつく)

**図 1 枚ぶん(181KB)の行き過ぎ**であり、収束もする ── 直さない。
⚠ ただし**この数字は図 1 枚の大きさに比例する**ので、上限のすぐそばで
1MB 級の図を焼けば 1MB 行き過ぎる。それを 32MB の側で吸える範囲に保つのが、
下の「焼く大きさの上限」である。

⚠ 最初の測定は burst を 14 枚でやって「はみ出し 0」と出したが、
**そもそも上限に届いていなかった**(31.9MB で止まった)── 追い出しが走ったかを
`burstEvicted` で確かめるようにして、40 枚に増やして初めて踏んだ。

## 結果 ②: 🔴 焼く大きさに上限が無かった(実測 49.8MB)

上限の検証をしている最中に、**上限より桁の大きい確保**が見つかった。
`rasterize` は canvas の大きさを一切 clamp しておらず、
`h = cssWidth × 縦横比 × dpr` がそのまま canvas の高さになっていた。

`cssWidth` は `min(器幅, 図の実寸)` で頭打ちになるが、**縦横比は頭打ちにならない**。
`graph TD` の chain(実データで普通に出る形)で発散する:

| 図 | dpr | PNG 実寸 | canvas の裏バッファ | **画面での幅** |
|---|---|---|---|---|
| 120 節 | 3 | 369 × **35,402** px | **49.8 MB** | **123 px** |
| 40 節 | 3 | 342 × 11,916 px | 15.5 MB | 114 px |
| 10 節 | 3 | 342 × 3,123 px | 4.1 MB | 114 px |

**123px 幅で見せる図のために 50MB 確保していた。**

さらに面積上限(iOS Safari は約 16.7M px)を越えると `canvas.toBlob` が
**null を渡す**ので、その図はその端末で**永久に出ない** ── 鍵が同じなので
再訪しても同じ経路を通る。13.06M px は既にその境界の手前である。

### 直し方と、そこで一度間違えたこと

面積 4M px(裏バッファ 16MB)と辺 32,768px で頭打ちにする。

🔴 **最初は辺を 8,192 にして、別の壊れ方を作った**。それだと
**dpr 1 の縦長の図まで縮む**(123 × 11,801 の図が倍率 0.69 → 表示幅より
小さく焼いて拡大 = ぼける)。効かせたいのはメモリで、それは**面積**で決まる ──
辺は「canvas がそもそも作れない」を避ける帯であって、画質を決める数字ではない。
**面積を主、辺を従**に置き直した。

| 図 | dpr | 直す前 | 直した後 | |
|---|---|---|---|---|
| 10 節 | 1 | 0.4 MB | 0.4 MB | 変わらない |
| 40 節 | 1 | 1.7 MB | 1.7 MB | 変わらない |
| 120 節 | 1 | 5.5 MB | 5.5 MB | 変わらない |
| 40 節 | 3 | 15.5 MB | 15.5 MB | 変わらない |
| **120 節** | **3** | **49.8 MB** | **16.0 MB** | **3.1 倍減** |

縮むのは病的に長い図だけで、その 1 枚も **209px で焼いて 123px で見せる**
(1.7 倍の余裕がある)ので、**ぼけない**。

## 結果 ③: 同時に見つかって直した 3 件

### 🔴 キャッシュが「正しさ」を道連れにしていた

```ts
const hit = await tx(await db(), 'readonly', (s) => s.get(k)).catch(() => null);
```

`await db()` は**引数の位置**なので、後ろの `.catch()` は掛かっていない。
IDB を開けない環境(site data をブロック / DB 破損 / private mode の一部)では
`renderToPng` ごと reject し、**mermaid の描画を一度も試さないまま**
全部の図が原文のまま残る。`dbPromise ??= openDb()` が reject 済みの promise を
保持するので、一度失敗するとその session では二度と回復しない。

この file は 1 か所で「キャッシュは速さの話で、正しさの話ではない」と
宣言していたのに、**読み側と open 側がその宣言を破っていた**。

→ `withCache()` を 1 本置いて全呼び側をそこに通す。**同じ壊し方が書けない形**に
する(段㉔ の `window-close.ts`・段㉕ の `reload-snapshot.ts` と同じ手)。
失敗は memo しない(一時的な失敗なら次の機会に開き直す)。

### 🔴 cache hit のたびに PNG 全体を書き戻していた

LRU の「最後に使った時刻」を更新するのに行ごと `put` していた ──
**時刻 1 個のために平均 181KB(大きい図は 1MB 級)を書き戻す**。
図を 6 枚持つノートを開くたびに 1MB 前後の書込が走る。

→ 5 分の間隔を置く。追い出しは 32MB に触れたときしか走らない(実測 185 枚目)
ので、5 分の粗さは順位に効かない。

### 🔴 図を「消すだけ」の編集で ObjectURL が返っていなかった

段⑲ は `pruneLends()` を `if (applied.inserted.length > 0)` の**外**へ出し、
「塊が**消えるだけ**のときは inserted が空で、そこが一番溜まる」と
コメントまで書いた。にもかかわらず **1 行上の `pruneScopes` は `if` の中に
残っていた** ── **同じ穴を隣同士で片方だけ塞いでいた**。

既存の smoke(`図を打ち替えても、生成した URL が積もらない`)は毎回
**別の図に差し替える**ので `inserted` が常に非ゼロ ── この経路を 1 度も
通っていなかった。図を消すだけの smoke を足した(直す前の実装で実際に落ちる
ことを変異試験で確認)。

## 変異試験

10 件当てて **生存 0**。⚠ 途中 2 件が「生存」に見えたが、**shell の引用の
せいで変異が当たっていなかった**だけだった ── 変異試験の走りを file に出し、
**当たったことを必ず確かめる**ようにした(`当たっていない` を別の判定として出す)。

生き残って直したもの:

- **面積の上限が辺の上限に救われていた** ── 縦長の fixture では辺のほうが先に
  効くので、面積の項を `Infinity` にしても素通りした。**辺は余裕・面積だけが
  効く**大きさの fixture を足した(代替物で満たせる条件を置かない)
- **幅の辺の上限は誰も見ていなかった** ── どの fixture も幅では詰まらなかった
- **片側の丸めを見逃した** ── `Math.floor` を `Math.round` に変えても、
  余裕のある fixture では 1px 増えるだけで上限に届かない(両辺を同時に
  変えたときだけ落ちた)。上限は**不変条件**なので fixture ではなく
  **3,000 通り掃いて**守るようにした。さらに丸めの規則が実装と test の
  2 か所に生えていたので、`rasterSize()` に寄せた(規則を 1 つに寄せる)
