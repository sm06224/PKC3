---

レビュー対象: $ARGUMENTS(未指定なら「直近の commit / いま open な PR の差分」を
1 文で定義してから始める)

`pkc3-reviewer` サブエージェントへ投げてください(プロセス指示「品質はサブエージェント・
スキルで守る:実装 PR は着地前に code review を回す」の実体)。

## 投げる前に

- **差分の範囲を確定する**(`git diff <base>..HEAD` の base を明示)。
  「この PR」だけでは、レビュアーが何を読むか決められない
- **すでに直したものを書く** ── 2 巡目なら「1 巡目の指摘は反映済み。**今回は
  その修正コード自体**を読んでほしい」と明示する。書かないと同じ指摘が戻る
- **自分がやった検証を書く**(typecheck / lint / unit 件数 / smoke / 変異試験の結果)。
  レビュアーが同じことを繰り返さずに済む
- 🔴 **read-only であることを明示する** ── `pkc3-reviewer` の定義にも書いてあるが、
  プロンプト側でも念を押す。書き込み権のあるエージェントを自分の作業ツリーで並行に
  走らせると、編集中の file を変異させられる(2026-08-04 に実際に起きた)

## 受け取ったあと

- 🔴 **鵜呑みにしない。1 件ずつ自分で確かめる。** 2026-08-07 のレビューは 7 件が
  正しく、2 件(「`*{box-sizing}` が落ちている理由」「紙のリンク色は退行」)は
  **前提か結論がずれていた** ── 実測したら片方は「面が揃った」が正解だった
- **CONFIRMED と 未検証 を分けて読む**。未検証の指摘は、まず**自分で測る**
- 🔑 **2 巡目には「片側を直したら対称の反対側」を明示的に見させる** ── PKC3 で最頻の型。
  2026-08-07 は、1 巡目で直した検品の**鏡像**が反対側に残っていた(トークンは出力から
  数えるよう直したのに、規則は需要側の数のまま)
- 直したら**その修正自体をもう 1 巡**回す ── 1 巡目が 7 件見つけた差分の修正コードは、
  まだ誰にも読まれていない(CLAUDE.md「空振りを直したら『今度は何に救われていないか』を問う」)
- 指摘を反映した commit は**理由まで書く**。「レビュー指摘対応」だけでは、
  次に読む人が「なぜこの形なのか」を復元できない
