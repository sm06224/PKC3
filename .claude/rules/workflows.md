# workflow・スクリプト・ビルドを触るときの事故の記録

正本の型の表は CLAUDE.md『検証の規律』。ここは各型の実例。
箱の扱い(`pkill` の代わり・cwd が戻る等)の手順は `.claude/skills/sandbox-hygiene/SKILL.md`、PR の着地は `.claude/skills/pr-landing/SKILL.md`。

## CI と手元で別のものが動いている(型: 環境差)

- 型: 環境差 ── 手元で緑・CI で赤(または逆)。ブラウザのバイナリ・環境変数の効く範囲・速さの向きが食い違っている。
- 見分け方: 「CI だけ落ちる」を見たら、まず**どちらの環境が何を動かしているか**を数える(ブラウザの種類・どの step に env が効くか・所要時間)。
- 直し方: 環境差を語る前に、その環境の挙動を回数つきの数字で持つ。実ブラウザ依存の spec は両方のバイナリで通してから push。観測点を環境差に強い側へ寄せる。
- 未測定: 下の速さの数字は 2026-08-27 時点の観測(CI 4 回 / 手元 7 回)で、いまの値は測り直していない。

- 🔴 **CI と手元で別のブラウザが動いている**(2026-08-05)。`tests/smoke` の config は同梱の
  `/opt/pw-browsers/chromium`(= フル Chromium)を優先し、無ければ playwright 既定に落ちる ──
  **PR gate は後者 = `chromium_headless_shell`**。`window.print()` が chrome では
  `beforeprint` のみ、headless_shell では **`beforeprint` + `afterprint` を同期発火**するため、
  「押した直後に組み上がっている」を見ていた smoke が**手元で緑・CI で赤**になった
  (しかも CI 側が正しい)。🔑 実ブラウザ依存の挙動に触れる spec は**両方のバイナリで通してから
  push**(`PKC3_CHROMIUM=/opt/pw-browsers/chromium_headless_shell-1194/chrome-linux/headless_shell`)。
  🔑 そして観測点を**環境差に強い側**へ寄せる(→ CLAUDE.md『検証の規律』型 4 観測点)── この件では「押した直後」ではなく
  **`beforeprint`(印刷が始まる瞬間)**が、どちらのビルドでも成立する唯一の点だった

- 🔴 **環境差の調査が本物のバグを見つけることがある**(同 2026-08-05)。上の件を headless_shell で
  追ったら `Not allowed to load local resource: blob:null/…` が出た ── **画像の読み込みが
  終わる前に印刷が完了し、`afterprint` の revoke が読み込み中の blob URL を消していた**
  (= 紙から画像が落ちる実バグ)。chrome では `afterprint` が来ないので**永久に露見しなかった**。
  「CI だけで落ちる」を環境のせいにして test 側だけ緩めていたら、バグごと埋めていた

- 🔴 **2026-08-07 追記: この規律は nightly では破れていた。** nightly が probe 用の
  `PKC3_CHROMIUM` を **`$GITHUB_ENV` へ**書いており、以降の全 step ── smoke を含む ── に
  効いていたため、**nightly の smoke だけフル chromium** で走っていた(「両方で通してから
  push」の規律が、**CI 側で静かに裏切られていた**)。いまは probe の step にだけ `env:` で渡し、
  **nightly が smoke を 2 つのブラウザ両方で回す**(突き合わせる場所は nightly しか無い)。
  🔑 **`$GITHUB_ENV` は「以降の全 step」に効く** ── 1 つの step のために書いた値が、無関係な
  step の**検査対象を変える**。step 単位で効かせたいなら `env:` を使う

- 🔴 **「CI は遅いから時間切れになる」は思い込みだった ── 逆に速い**(2026-08-27 実測)。
  録音 smoke が CI でだけ落ちる件を追っていて、当然のように「遅いランナーで待ちが
  足りない」と読んでいた。⚠ **測ったら反対だった**:

  | | 数えた回数 | 所要 |
  |---|---|---|
  | **CI の smoke(全量)** | **4** | 5m27s / 6m31s / 6m38s / 6m50s |
  | **手元のフル smoke** | **7** | 8.3m 〜 9.3m |

  🔑 **CI のほうが 25〜35% 速い。** だから疑うべきは「待ちが足りない」ではなく
  **「物事が早く起きて、順番が入れ替わる」**側である ── 実際その向きで見たら、
  `await` の前後で state が動く穴が見つかった(#490)。
  ⚠ **箱の性能は同じ**(どちらも 4 コア / 16GB)なので、「CI は非力」でもない。
  🔑 一般形:**環境差を語る前に、その環境の速さを数字で持つ。**
  ⚠ 速さの向きを取り違えると、**探す場所が丸ごと反対になる**(遅い前提なら
  「待ちを伸ばす」へ、速い前提なら「順番」へ行く ── 前者は test を緩める方向で、
  CLAUDE.md の「flake に見えるものが製品の穴だった」を踏み抜く)

## shell と CI が「失敗した」を食べる(型: shell と CI)

🔑 次の 2 節(終了コードが消える / 自分の命令行に当たる)は、どちらも**構文が「失敗した」という事実を食べてしまう**同じ罠の顔である。

### 終了コードが「成功」に化ける

- 型: パイプ・複合命令・`&&` `||` の優先順位が、落ちた事実を exit 0 に変える。
- 見分け方: 背景実行の完了通知に「exit code 0」と出ているのに、中身に失敗が在る。
- 直し方: 出力は file に落としてから読む。終了コードは log の中に書き、通知の数字を信じない。CI の条件付き実行は `if … then … fi` で書く。

- 🔴 **`| tail` に通すと、落ちたことが消える**(2026-08-13)。パイプラインの終了コードは
  **最後の命令のもの**なので、`node probe.mjs … | tail -40` は probe が例外で死んでも
  **exit 0** を返す。⚠ 背景実行の完了通知にも「exit code 0」と出るので、**「測れた」と
  読んでしまう**(実際に読みかけた ── 中身に `TimeoutError` が在った)。🔑 出力を絞りたいなら
  **file に落としてから読む**(`cmd > out.log 2>&1; echo "exit=$?"`)。
  ⚠ `set -o pipefail` に頼らない(対話の shell では効いていないことがある)

- 🔴 **`cmd > log 2>&1; echo "exit=$?"` を、複合命令の末尾に置かない**(2026-09-16)。
  ⚠ これは `| tail` の**裏返し**である ── パイプでは最後の命令の終了コードが残るが、
  ここでは**最後に置いた `echo` の終了コード(必ず 0)**が、その塊の終了コードになる。
  実例:背景で `{ npm test > full.log 2>&1; echo "full=$?"; }` を回したところ、
  🔴 **test が 2 件落ちているのに、完了通知は「exit code 0」**と出た
  (`echo` は成功したので当然である)。⚠ `| tail` の件と同じく、
  **「測れた」と読んでしまう**(実際に読みかけた)。
  🔑 **終了コードは log の中に書く。通知の数字を信じない** ── 上の形は
  **log を読むための道具**であって、合否の計器ではない
  (`grep -n "Test Files\|Tests  " full.log` まで見て初めて読んだことになる)。

- 🔴 **`&&` と `||` は同順位・左結合**。CI の条件付き実行を `[ -f X ] && cmd || true` と書くと
  `(([ -f X ] && cmd) || true)` になり、**「無いとき」ではなく「失敗したとき」も飛ばす**。
  実証: 検品が `✗` を出した直後に deploy 行へ到達し **step は exit 0**(不良物を配って job は
  green)。`if [ -f X ]; then cmd; fi` と書く

### `pkill` / `pgrep` / `/proc` の走査が、自分の命令行に当たる

- 型: 探す語を書いた行そのものが、自分の `cmdline` に在るので、包んでいる shell ごと落ちる。
- 見分け方: 出力が 1 行も無く、完了通知が `exit 144` とだけ出る(log file すら作られない)。
- 直し方: 掴んでいる資源(port / cwd)で引く。名前で引くなら `$$` と `$PPID` を除く。できれば**殺さず・待たない**(完了は通知で届く)。

- 🔴 **`pkill -f` のパターンは、自分の命令行にも当たる**(2026-08-17)。
  `pkill -f "vite preview"` と書いた行そのものが `/proc/*/cmdline` に在るので、
  **包んでいる shell ごと落ちる** ── 出力は 1 行も残らず、背景実行の完了通知には
  **exit 144** とだけ出た(log file すら作られていないので「なぜ落ちたか」が消える)。
  ⚠ ここで踏むと**自分の作業を止めた原因が自分だと分からない**。
  🔑 パターンを命令行と一致させない(`pkill -f 'vite prev[i]ew'`)/ できれば
  **port から引く**(`ss -ltnp`)── 名前で殺すより、**掴んでいる資源**で殺すほうが安全。

  - 🔴 **回避は「殺す側」だけでなく「待つ側」にも要る**(2026-09-05、同じ罠の 2 度目)。
    背景で回している待ち受け(`until ! pgrep -f 'playwright'; do sleep 5; done`)は、
    後片付けの `pkill` と**同じ語を命令行に持つ**ので一緒に落ちる。
    ⚠ この日は `pkill` 側だけブラケットで守っており、待ち受けの側が無防備だった。
    ⚠ そして**待ち受けは自分の `pgrep` にも当たる**ので、殺す相手が 1 つも無くなっても
    **永久に終わらない**(実測: playwright 0 本で 72 分回り続けた)。
    🔑 待ち受けにもブラケットを入れる / できれば**待たない**
    ── 完了は通知で届くので、`sleep` で回すこと自体が既に横着である
    (CLAUDE.md「サブエージェントや CI の完了を `sleep` / ポーリングで待たない」)。
    ⚠ 落ちたときに出るのは **`exit 144` の 1 行だけ**なので、
    **待っていた本体まで落ちたと誤読しやすい** ── 結果は待ち受けではなく
    **log file から直接読む**(そうしていれば、この誤読は起きない)。

  - 🔴 **3 度目は `/proc` を自分で走査する形だった**(2026-09-14)。⚠ `pkill` を
    やめて `/proc/*/cmdline` を読む形にしても、**探す語を書いた行そのものが
    自分の `cmdline` に在る**ので、やはり自分ごと落ちる(`exit 144`)。
    ⚠ ブラケット逃れ(`vite[s]t`)は**引数の中の語**にしか効かない ── 自分で
    走査する形では語が**丸ごと**在るので、どう書いても当たる。
    🔑 **`$$` と `$PPID` を除く**、が最小の直しである。
    🔑 そして**そもそも殺さない** ── 背景で回した物の完了は通知で届くので、
    待ちも後始末も要らない。殺すなら**掴んでいる資源で引く**(port / cwd)。
    ⚠ 落ちると出るのは **`exit 144` の 1 行だけ**なので、
    **何を消したのか・どこまで進んだのかが丸ごと消える**。手順は
    `.claude/skills/sandbox-hygiene/SKILL.md`

## 上流と生成物を取り込む場所(型: 上流の取り込み)

- 型: 上流の「入れる物の一覧」「既定値」「スイッチ」を推測で扱い、欠けた物が**無言で空になる**。
- 見分け方: 症状が遠く離れた形(添字 `-1`・範囲外アクセス・ビルド停止)でしか出ない。「入っているはず」で止まっている。
- 直し方: 「コードが読む path」と「配ったものの中身」を全数で突き合わせる。上流は file システムではなく**登録**を読む。上流を触る回転が 2 回を超えたら clone して読む。tripwire は入力ではなく**出力が届いたか**に置く。

- 🔴 **上流の「入れる物の一覧」は、上流自身の変更に遅れる**(2026-08-13、#135 / #144)。
  LibreOffice は表の自動書式を `autotbl.fmt` → `tablestyles.xml` へ移したのに、wasm の
  詰め込み一覧は**古いほうを入れたまま**だった。読み手は開けなければ `SAL_WARN` して
  `return false` ── ⚠ **無言で空になる**ので、症状は「一覧が空 → 添字 `-1` → 範囲外アクセス」
  という**遠く離れた形**でしか出ない。🔑 **上流の成果物を取り込む場所では、「コードが読む
  path」と「配ったものの中身」を全数で突き合わせる** ── 1 件の症状から 1 件だけ直さない
  (数えたら **4 件**欠けており、`share/svx/` と `share/calc/` は**ディレクトリごと**入って
  いなかった)。⚠ 上流の既定値も同じ ── `--with-wasm-module` の既定が `'calc writer'` だった
  ため **Impress は 1 file も入っていなかった**(#145)。「入っているはず」を確かめる

- 🔴 **上流の実物は clone して読む。名前も既定値も、推測で渡さない**(2026-08-14、#158 で
  **7 回転**を溶かした)。日本語 UI を建てるのに `--with-lang` を渡す → `msgfmt` が無い →
  検品の grep が落ちるが**何と食い違ったか 1 行も読めない** → 実物を出す →
  `--disable-wasm-strip-locales` は**上流に無い** → 親スイッチへ、と回り続けた。
  最後に**上流を checkout して全数 grep したら、前提が 3 つとも誤り**だった:
  ① `ENABLE_WASM_STRIP_LOCALES` は **死に変数**(上流全体で一致 1 件 = `config_host.mk.in:265`。
  makefile も C++ も**誰も読まない**)② `--disable-wasm-strip` は **Emscripten では効かない**
  (`configure.ac:1301` が host case で `enable_wasm_strip=yes` を**無条件に上書き**する。
  ⚠ 仮に効いたら `configure.ac:3457-3505` が発火せず `enable_dynamic_loading` まで戻るので、
  **wasm はリンクしない**)③ `WITH_LANG` は**出る file が違う**だけ(`config_host_lang.mk`)。
  ⚠ **決定的な誤りは「空になった変数」を「スイッチが効いた証拠」と読んだこと** ── 実際は
  `--with-wasm-module`(#145)と、`config_host.mk.in` の**右辺が空リテラルの行**によるものだった。
  🔑 **上流を触る回転が 2 回を超えたら、推測をやめて clone する**(実際それで 1 回で片付いた)。
  ⚠ そして真因は下の「「ソースに在る」は「配られる」ではない」の件と**同型**だった ──
  `static/CustomTarget_emscripten_fs_image.mk` が `en-US` を**名指し**で焼き、
  `program/resource/**`(`.mo`)を **1 行も入れていない**。configure のレバーではなかった

- 🔴 **「ソースに在る」は「配られる」ではない**(2026-08-24、#225。**ビルドを止めた**)。
  wasm へ詰め込む `.ui` の取りこぼしを埋めるのに、上流を **`<mod>/uiconfig/**` の実在**で
  数えて 57 件足したら `gb_Deliver_deliver: file does not exist in instdir` で
  **make ごと停止**した。⚠ instdir へ配られるのは `<mod>/UIConfig_*.mk` が
  `gb_UIConfig_add_uifiles` で**登録したものだけ**で、`fileextcheckdialog` は
  `ifeq ($(OS),WNT)` の中 = **Windows 限定**だった。
  🔑 **上流の「入れる物」を数えるときは、file システムではなく登録を読む** ──
  ビルド系は必ず「何を配るか」を宣言している(`*.mk` / `CMakeLists` / manifest)。
  ⚠ そして**登録には条件が付く** ── 条件つきのものは、条件をこちらで評価できないなら
  **足さない**(足りなければ症状で分かるが、足しすぎるとビルドが止まる)。
  ⚠ もう 1 つ重なっていた:**モジュール名 → 配り先の綴りを手書きの対応表で当てていた**
  (`sd` は `modules/simpress` と `modules/sdraw` の**両方**を持つのに前者へ潰していた)。
  🔑 登録を読めば**第 1 引数がそのまま配り先**なので、対応表そのものが要らなくなった ──
  **推測の表を作った時点で、読むべき物を読んでいない合図**である

  - 🔴 **tripwire は「直した所」ではなく「直した結果が届いたか」に置く**(2026-08-24、同じ #225)。
    ⚠ 上の直しには tripwire を **3 つ**置いたのに、⚠ **3 つとも一覧(mk)= 入力の側**しか
    見ていなかった。焼きの検品のほうも**日本語の翻訳しか数えておらず**、
    **ダイアログ資源は 1 件も数えていない** ── つまり
    **`querydialog.ui` が消えても、鳴る計器は 1 つも無いまま**だった。
    🔑 **配る物そのもの**(`soffice.data.js.metadata` = 実際に詰め込まれた目録)を読み、
    一覧と**集合で**突き合わせる(`check-fs-image-uifiles.py`)。
    ⚠ **件数ではなく集合** ── 同じ数だけ取り違えても件数は合う。
    ⚠ **両方向を見る**:「配られていない」は取りこぼし、「**一覧に無いのに配られた**」は
    **こちらの読み方が上流に追随できていない**合図である(黙って通すと、
    読めていない分だけ静かに足りなくなる)。
    ⚠ そのうえで**名指しの錨を別に置く** ── 集合が一致していても、
    **両方から消えていたら症状は戻る**。
    🔑 一般形:**入力を守る検査と、出力が届いたかを見る検査は別物である。**
    前者だけ書くと「直した」という事実が**自己証明**されて固定される

## 配布の検品に、前提が片方にしか無い(型: 複数の場所 ── `pages.yml` の 2 件)

- 型: 同じ検査を 2 か所で回しているのに、前提が片方にしか無い(順番で守っている / 過去の成果物を今の規則で検品する)。
- 見分け方: `release.yml` が足した物を `pages.yml` が展開して再検品する。`pages.yml` の 1 つの job が `/` に過去の release の zip、`/dev/` に main HEAD を置く。
- 直し方: 順番ではなく**規則の側に知らせる**(名前で名指しして除外)。除外したら別立ての門を置き直す。過去の成果物に効く新しい要求は**旗で opt-in** にし、焼きたてを見る経路が全部立てる。
- 関連: 同じ問いに答える口が 2 つ在る型は `.claude/rules/src-invariants.md`。

- 🔴 **「順番で守っている」ものは、その順番を守れない読み手が居ると破れる**
  (2026-08-29、**本番配布を止めた**)。⚠ `.claude/rules/src-invariants.md` の「同じ問いに答える口が 2 つ」とは別で、
  こちらは**同じ検査を 2 か所で回していて、前提が片方にしか無い**形である。
  実例:`portable-template.html`(持ち歩ける 1 枚の雛形、実測 7051.7 KB)は
  **アプリの一部ではない**ので precache にも配る量にも数えてはいけない ── それを
  「**検品の後に足す**」という順番だけで守っていた。⚠ ところが `release.yml` が
  検品の後に zip へ足したものを、**`pages.yml` は展開してもう一度検品する**ので、
  v3.2.0 の本番配布が「precache に載っていない生成物がある」+「cap を 6563.8 KB 超過」で
  落ちた(run 33256868235)。
  ⚠ **一度も通っていなかった**(CLAUDE.md『検証の規律』型 2 未実行の経路)── v3.1.0 の `release.yml` にこの step は無い
  (144 行 / `portable` 0 件)ので、**この経路は追加から今日まで 1 度も走っていない**。
  🔑 検算は 1 つ:**「順番で守っている」と書いたら、その順番を守れない読み手を数える**
  (ここでは「zip を展開して検品する側」が居た)。居るなら、順番ではなく
  **規則の側に知らせる**(名前で名指しして除外する)。
  ⚠ そして**除外したら、外したぶんの門を置き直す** ── アプリの cap から外した瞬間、
