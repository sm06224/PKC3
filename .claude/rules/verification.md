## 1. 検査が空振りする ── 緑が「別の理由」で成立している

🔑 **ガードは代替物で満たせない条件にする**。「それらしいものが在るか」ではなく**「参照されているものが実在するか」**で書く。以下は全部その顔違いである。

### 1.1 代替物に満たされる(救い手が変わっただけ)

- **型**: 条件を満たす「代替物」が、外だけでなく測っている物の内側にも居る。
- **見分け方**: 本体を消す変異を当てても緑のまま。満たしているのは別の file・別の項・測っている物自身の初期値(豆腐・0・既定値)。
- **直し方**: 空振りを直したら「今度は何に救われていないか」を問う。「無いときに何が返るか」を 1 度実測してから条件を書く。

**実例**

- **救い手が変わっただけ**(2026-08-02、P7 段① で 2 ラウンド連続)。1 巡目「`.js` が
  1 件でもある」は `sw.js`(public の静的コピー)に救われ、**アプリ本体を消しても緑**だった。
  「index.html の参照を突合」へ直したら、2 巡目は**空振り防止のガード自体**が
  `manifest.webmanifest` / `icon.svg`(Vite が書き換えない public の静的参照)に満たされ、
  `--base /` にすると**やはり本体を消しても緑**。🔑 **空振りを直したら「今度は何に
  救われていないか」を問う** ── 条件は「参照が 1 件でもある」ではなく
  「**hash 付き生成物への参照が 1 件でもある**」

- **「書体そのものの豆腐」に満たされた**(2026-09-11、#770 段①。
  ⚠ **下の 1.3「また自分の解説コメントだった」の件を直した同じ turn で踏んだ**)。
  「配る woff2 に、その絵が本当に入っているか」を実ブラウザで見る門を新設し、
  **送り幅が 1em であること**と**素の書体と幅が違うこと**の 2 つで見た。
  ⚠ 変異(目録の `print e8ad` → 書体に無い `e999`)を当てたら **SURVIVED**。
  🔴 真犯人は**この書体自身の `.notdef`(豆腐)**である ──
  fontTools で測ると `.notdef` の送り幅も **960/960 = 1.0em** なので、

  | 測ったもの | 絵が在るとき | 🔴 無いとき(豆腐) |
  |---|---|---|
  | 送り幅 | 16.0px | **16.0px** |
  | serif との差 | 違う | **違う**(豆腐 16.0 ≠ serif 12.4) |

  ⚠ **2 つの門が、どちらも同じ物に満たされていた** ── 在る / 無いで
  **1 ビットも動かない**計器で「40 種とも出ている」と書いていた。
  ⚠ しかも spec のコメントには「**『幅が 0 でない』では足りない ── 豆腐にも幅が在る**」と
  **正しく警告が書いてあった**(警告を書いた本人が、その警告どおりに外した)。
  🔑 直しは **豆腐そのものを対照群にする**:書体に**必ず無い**符号位置を 1 つ描き、
  **画素の指紋が同じかどうか**で見る(送り幅では言えないので画素にする)。
  ⚠ 指紋の**値は pin しない**(環境で変わる)── 見るのは**同じ回の中での違い**だけ。
  🔑 一般形:**「代替物で満たせない条件にする」の「代替物」は、外ではなく
  測っている物の内側にも居る。** 書体は自分で豆腐を持ち、DB は自分で 0 を返し、
  CSS は自分で初期値を持つ ── **「無いときに何が返るか」を 1 度実測してから**
  条件を書く(本節冒頭の「今度は何に救われていないか」の、いちばん近い所版)

### 1.2 成り立たない主張・未確認の期待

- **型**: 検査の主張そのものが成り立たない、または確かめる前の期待を assert に固めている。
- **見分け方**: 守れない条件(user が書けば必ず破れる)を要求している / 落ちたとき「実装が悪いのか期待が間違いか」が区別できない / 注釈に書いた因果が外しても壊れない。
- **直し方**: 先に「その条件が成り立ちうるか」を確かめ、実害の形へ書き直す。未確認は assert ではなく診断(値の印字)で出し、通ったのを見てから昇格させる。「これが無いと壊れる」と書くなら、外して壊れるのを 1 度見る。

**実例**

- **主張そのものが成り立たない**(= 検査の「主張そのもの」が間違っている。2026-08-08)。
  🔑 **空振りを直す前に、その条件が成り立ちうるか**を確かめる。ヘルプ smoke が「document 内に
  **id の重複が 0 件**」を要求していたが、面は `hidden` で同一 document に常駐するので、
  **user がマニュアルと同じ見出しを書けば必ず重複する** ── 守れない条件だった(しかも
  ノートを 1 件も作っておらず**空振りでもあり、だから緑だった**)。🔑 **実害の形へ書き直す**:
  重複は許し「`#slug` が**本文の面**に当たること」を見る。
  ⚠ 「重複 0 件」のような**きれいな条件**ほど、成り立たないまま素通りしやすい

- **後条件は、確かめた事実の上にだけ書く**(2026-08-14)。⚠ 上と**近縁だが別**である ──
  あちらは**論理的に成り立ちえない**条件、こちらは**経験的に未確認**の条件を、確かめる前に
  固定したもの。`--disable-wasm-strip` を渡せば locale の剥がしが止まる**はず**という期待を
  そのまま `grep -q '^export ENABLE_WASM_STRIP_LOCALES=$' config_host.mk` に固め、
  `tests/workflow-steps.test.ts` で**字面ごと pin** した。
  ⚠ 落ちたとき「**実装が悪いのか、期待が間違いか**」が区別できない ── 実際 3 回とも
  「ビルドが失敗した」と読み、**期待の側を疑うのが毎回最後**だった(`WITH_LANG` に `ja` →
  存在しない option `--disable-wasm-strip-locales` → 本件)。
  🔑 **未確認は assert ではなく診断で出す**(値を印字して次の回転で読む)。**通ったのを
  見てから**後条件へ昇格させる。⚠ 1 度の実験が **2 つを主張していた**のも効いた ──
  `--with-lang` と `--disable-wasm-strip` を同じ configure で渡したので、どちらが効いたか
  単独では読めない。§「回すものの粒度」の**「1 job = 1 主張」の実験版**である。
  - ⚠ **コメントに書いた因果も、検査の主張と同じく間違う**(2026-08-14)。`min-height: 0` に
    「これが無いと本文が縮まず、面が 30vh を超えて見出しごと押し出される」と書いていたが、
    **外しても本文は h=0 まで縮んだ**(実測値まで一致)── 同じ規則の `overflow: auto` が
    flex の automatic minimum size を 0 に解決するので、その 1 行は **no-op** だった
    (`src/styles/app.css`)。🔑 **「これが無いと壊れる」と書いたら、外して壊れることを
    1 度は見る。** 見ないなら書かない

- **「これが無いと壊れる」と書いた規則が no-op だった**(2026-08-20)。
  `[data-pkc-region='kanban-cards'][hidden] { display: none }` に「`display: flex` が
  UA の `[hidden]` を上書きするので要る」と**コメントまで書いた**が、**外しても
  実ブラウザで畳めた**(変異試験が SURVIVED で教えた)── 同じ file の 500 行下に
  `[hidden] { display: none !important; }` が既に在った。
  ⚠ **2026-08-14 の `min-height: 0` と同じ型を、戒めを読んだうえで踏んだ。**
  🔑 だから規律を言い換える:**「これが無いと壊れる」と書く前に、外して壊れるのを見る。**
  変異試験に掛ければ 1 回で分かる(no-op は必ず SURVIVED になる)

### 1.3 範囲が広すぎて、無関係な散文・別の面に満たされる

- **型**: file 全体・document 全体・名前の一部一致で探した検査が、注釈・別の面・別物に満たされて常に真になる。
- **見分け方**: 条件を裏返す変異を当てても緑(SURVIVED)/ 製品が正しいのに「不具合」に見える。
- **直し方**: 見るのは自分が書き換えた行・実行する行そのもの・その面(region)の中。CSS / yml / 原文を `toContain` で見る検査を書いたら、必ず注釈を落として範囲を絞る(思い出すのではなく手順にする)。file 名は path の頭と尻を両方留める。

**実例**

- **範囲が広すぎて無関係な散文に満たされる**(2026-08-13、CI で同じ日に 2 度)。
  ①「頼んだときだけ `SAFE_HEAP` が入る」を **file 全体**(`mark in text`)で見ていたが、上流に
  `# avoid -s SAFE_HEAP=1 …` という**コメントが実在** ──「頼んでいないのに在る」が常に真で、
  ⚠ **配布ビルドを焼くたびに落ちる**状態だった。② 順序の guard を
  `indexOf('qtbase-patch-*.py')` で書いたら **cache 鍵のほうに当たっていた**(鍵は file の
  上に在るので、step をどこへ動かしても常に「前」になる)。🔑 見るのは**自分が書き換えた行**
  (①なら `INITIAL_MEMORY` の行)、位置を採るなら**実行する行そのもの**で採る

  - **CSS を読む検査でも踏んだ**(2026-08-14)。CSS を読む test で
    `indexOf(selector + ' {')` と書いたら**版面の `grid-area` の規則**に当たって落ち、
    直した 2 稿目は `"${sel} {"` で探したので**選択子リスト**(`A,\nB {`)に書いた規則を
    **1 つも拾えなかった**。⚠ **同じ file の 40 行上の test がまさにこれを戒めていた**
    (`tests/adapter/announce.test.ts`)。🔑 CSS は**構文で拾う** ── `選択子 { 宣言 }` を
    全部読み、選択子リストを `,` で割って**丸ごと一致**を見る。⚠ `@media` の中まで拾うと、
    印刷や狭い版面だけの規則で**画面の規則を消しても緑**になる ── 最初の `@media` で切る

  - **この教訓を書いている最中に、自分の解説コメントに満たされた**(2026-08-14)。「効かない
    `--disable-wasm-strip` が戻っていない」を **yml 全体**で `not.toContain` したところ、
    **直上に書いた自分の解説コメントに満たされて**必ず落ちた ── `SAFE_HEAP` の件と
    **同じ罠**である。🔑 見るのは**実行する行** ── heredoc を抜き出し、その中だけを見る
    (空振り防止に「抜き出せていること」も併せて assert する)

  - **「別の面の文字」に満たされた**(2026-08-17)。
    ① 2 枚目のタブの帯を **root 全体**の `textContent` で探したら、**お知らせのカード**
    (「保存は本体タブ経由ですと画面下に出ます」)に満たされて**常に真** ──
    昇格して帯が消えても「消えていない」と読み、**製品の不具合に見えた**
    (実際は製品が正しく、観測点が広すぎた)。状態の行(`[data-pkc-region="status"]`)
    だけに絞ったら解けた。② 同じ日に `[data-pkc-entry]` を **document 全体**で数えて
    いた probe が、情報ペインの**ボタン 3 つ**に満たされて **13 晩 nightly を赤に**
    していた。🔑 **面(region)へスコープする** ── 「その面の中で」を書かない検査は、
    別の面の文字で満たされる。⚠ しかも①は**自分が足した検査**で、足したその日に踏んだ

  - **「同じ名前の別物 3 つ」に満たされた**(2026-08-24、#225)。
    「この一式は非 ODF を保存できるか」を **`cui/ui/querydialog.ui` が入っているか**で
    見分けようとし、古い一式で `grep -c "querydialog.ui"` したら **1 件ヒット**したので
    「この印は使えない」と読みかけた。⚠ 実際は `vcl/ui/querydialog.ui` /
    `recalcquerydialog.ui` / `safemodequerydialog.ui` という**別物**に満たされていた
    ── **`/cui/ui/querydialog.ui"`(閉じ引用符まで)で完全一致**を取れば、
    古い一式 4 つは **0 件**・直した一式は **1 件**ときれいに分かれる。
    🔑 **file 名で見分けるときは、path の頭と尻を両方留める** ── 尻だけ留めると
    前に伸びた名前(`recalc…`)に、頭だけ留めると後ろに伸びた名前(`….bak`)に当たる。
    ⚠ この誤りは**印を捨てる方向**へ効くので、「使えないと分かった」の顔で残る
    (使えるのに使わない ── 誰も検算しない)

- **`grep` の語は「その器が持つ属性を全部」数え上げる**(2026-09-11、#770 段①。同じ件)。
  着地前レビューは「`data-pkc-icon` を読む残骸は **0 件**」と断定し、私はそれを
  信じて着地させた。⚠ **実ブラウザの smoke が 2 本落ちて分かった** ──
  残骸は `[data-pkc-chip] svg path` と `[data-pkc-chip="folder"] svg` で、
  **`data-pkc-icon` の字を 1 つも含んでいない**(同じ span が属性を 2 つ持つ)。
  🔑 **器を替えたら、その器に付いている属性を全部 grep する**
  (`data-pkc-icon` / `data-pkc-chip` / `data-pkc-symbol` / `data-pkc-field`)。
  ⚠ 「0 件でした」は**探した語の範囲でしか成り立たない** ── 語を書かずに
  「漏れ無し」と読むと、この形で必ず抜ける

- **また自分の解説コメントだった**(2026-09-11、#770 段①)。
  ⚠ 2026-08-14 の解説コメントの件とまったく同じ形である ── `font-display: block` を CSS **file 全体**で
  見る検査を書き、`swap` へ変える変異を当てたら **SURVIVED**。
  真犯人は**すぐ上に書いた自分の注釈**(「⚠ `font-display: block` ── 届くまでは
  何も出さない」)で、規則を裏返しても**その 1 行が条件を満たしていた**。
  🔑 直しは 2 手で足りる:**注釈を落とす** + **`@font-face` の塊だけに絞る**
  (どちらか片方では、別の宣言に満たされる余地が残る)。
  ⚠ **その戒めは読んでいた**のに踏んだ ── 覚えているのは「コメントに
  満たされる」という**話**であって、**書いている今がその場面だ**とは気づかない。
  🔑 だから機械的な合図にする:**「CSS / yml / 原文を `toContain` で見る検査を
  書いたら、必ず注釈を落として範囲を絞る」**(思い出すのではなく、手順にする)

### 1.4 数えている対象が、名前と違う

- **型**: 数字が出る(空振りに見えない)が、数えている対象が名前の主張と違う。
- **見分け方**: 出た値は本物だが対象だけが違う。空の状態を作って 0 が返るかを見ていない。
- **直し方**: 「何を数えているか」を 1 度は実測する ── 空の状態を作って、0 が返ることを見る。

**実例**

- **数えている対象が、名前と違うことがある**(2026-08-20、#297 ── **user のアプリが
  起動不能になった**)。「索引が空なら組み直す」の判定を
  `SELECT count(*) FROM entries_fts === 0` で書いていたが、⚠ **外部内容の FTS5
  (`content='entries'`)は全走査すると内容表のほうを読む** ── 索引が空でも
  `entries` の行数が返る。実測:索引 0 件 / entries 3 件 → `count(*) FROM entries_fts`
  は **3**、影表 `entries_fts_docsize` は **0**。つまりこの判定は
  **配った初日から一度も真になっていなかった**(既存 user の本文検索は静かに 0 件)。
  ⚠ この顔が厄介なのは、**数字が出る**こと ── 空振りに見えない
  (2026-08-17 の「計器の名前が範囲より広い」と同型で、**出た値は本物、対象だけが違う**)。
  🔑 **「何を数えているか」を 1 度は実測する** ── 空の状態を作って、0 が返ることを見る。
  ⚠ そして**この空振りは救済経路だった** ── 別の欠陥(下記 §2)が索引を壊したとき、
  これが直すはずだったのに一度も走らず、**自分で自分の逃げ道を塞いでいた**

### 1.5 検査の守る範囲が、題名より狭い

- **型**: file 名指し・名前だけ・上限だけ・材料の欠落など、守っている範囲が検査の題名の主張より狭い。
- **見分け方**: 別の面に同じ物を生やしても / 縮む方向に壊しても / 中身を空にしても緑のまま。
- **直し方**: 全数走査して等値で pin する。上限だけでなく下限も置く。材料が実際に届いていることを pin する。検品する側・test する側も変異試験の対象にする(→ 3)。

**実例**

- **guard を file 名指しで書かない**(2026-08-08)。「版は 1 か所」を守るはずの検査が
  **`settings.ts` に `APP_VERSION` が無いこと**しか見ておらず、他のどの面に生やしても素通り
  ── 題名は「2 か所に出ていない」なのに、守っていたのは「settings.ts に出ていない」だけ。
  **面の file を全数走査して等値で pin する**形に直したら、`main.ts` に**2 か所目が既に在った**
  (`(dev)` と「(開発版)」の 2 系統が同時に出ていた)

- ⚠ **「名前が在るか」の検査は、中身が空でも通る**(2026-08-08)。`repo-hygiene` の
  「受け手のいない `data-pkc-action` が無い」は**名前を消す変異は殺すが、ハンドラの中身を
  空にする変異は殺さない** ── 非対称である(中身は別の test が見る)。⚠ 逆に**等値 pin の
  既知リスト**(`KNOWN_DEAD`)は良く効いた ── 直したら消さないと落ちるので**忘れられない**

- **tripwire は上限だけでなく下限も置く**。取り違え・欠落は**縮む方向**にも起きる ──
  size cap しか無いと、entry chunk を **0 バイト**にしても「配る量が減った」だけで通る(実証)。
  **件数を数える検査も同型** ── `--sourcemap inline` は `.map` を 1 件も出さないので、
  4.3MB の map を出荷しながら「map 0 件」と報告した

- **壊れを検出する材料を捨てない**。`content_hash` のような照合材料を落とすと、誤りが
  **自己証明されて固定される**(書込側が計算し直すので以後の検査も通る)。⚠ **検査を書いた
  だけでは足りない** ── 材料が実際に届いていることを pin する(optional な field は writer が
  代入を落としても tsc が黙る = 全件で無効化される)

- 🔑 **検品する側・test する側も変異試験の対象**にする(→ §3)── 検品が壊れると
  「通った」という事実だけが残る

### 1.6 画面の字が、実在しない物を指す(安心の字を含む)

- **型**: 断り文・案内が指す字(ボタン名)が画面に無い、または「何も消えていません」が偽になる経路が在る。
- **見分け方**: 期待値に字を手で書いている(ボタン名を変えた日に実装も検査も古い字のまま緑)/ 「ここへは来ない」と注釈で宣言しているだけ。
- **直し方**: 期待値は画面の label 一覧から引く(一覧は左の列と設定の両方)。user に押させる字を書いたら `src` を 1 回 grep する。安心させる字は文ではなく作りで真にする(偽になる経路をそこへ来ない形にする)。

**実例**

- ⚠ **文言は「押した場所」と対で pin する**(2026-08-08)。断り文に「編集」が含まれるか
  だけ見ていたので、**呼び名(`ノート` / `リンク先`)を取り違える変異が生き延びた**。
  行を押したのに「リンク先を開いてください」と出ると、user は**別のものを探す**
  - **その先がある ── 「押してください」と書いた物が、画面に実在するか**
    (2026-09-16、#996)。⚠ 上は**呼び名の取り違え**だが、こちらは
    **そもそも無い物を指していた**。実例:「1 枚に焼けません」の断り文が
    **2 本とも**「代わりに **一式を書き出す** を押してください」と言っていたが、
    🔴 **その字は画面のどこにも無い**(`commands.ts` の label は「**バックアップ**」)。
    ⚠ **いちばん助けが要る場面で、断り文がそのまま行き止まり**になっていた ──
    しかも**配布済みのお知らせ 1 件**にも同じ字が載っていた。
    🔑 **門は「画面の字から引く」**:`COLLECTION_COMMANDS` / `SETTINGS_COMMANDS` から
    label を引いて、断り文がその字を含むことを見る
    (`tests/features/image-export-limit.test.ts`)。
    ⚠ **期待値を手で書かない** ── 書くと、**ボタン名を変えた日に両方そのままで緑**になる。
    ⚠ **一覧は両方見る**(左の列 / 設定)── 片方だけだと、命令が引っ越した日に
    「在るのに見つからない」で落ちる。
    🔑 検算は 1 つ:**user に押させる字を書いたら、その字を `src` で 1 回 grep する**
    (1 秒である)。⚠ 0 件なら、それは**案内ではなく行き止まり**である
    - **2 日前に自分で割った口を指していた**(2026-09-18、#1011)。
      「壊れていないか調べる」の結果は **3 か所とも**「**拾えるだけ取り出す**」を
      押させていたが、🔴 その字は **2026-09-16(#986)に画面から消えている**
      (口が 2 つに割れた)。⚠ つまり **DB が本当に壊れた人にだけ出る 1 行が、
      2 日間そのまま行き止まり**だった ── **いちばん助けが要る場面**で。
      🔴 **そして検査がその行き止まりを pin していた** ── 期待値に
      `'拾えるだけ取り出す'` を**手で書いて**いたので、実装も検査も同じ古い字のまま緑。
      🔑 門は**画面から引く**形にした:断りの字の中の **「…」を全部抜いて**、
      `buildSettingsCommands()` が**描いたボタンの字**と突き合わせる
      (`tests/features/db-rescue.test.ts`)。⚠ **どこが壊れたか分からなかった枝**も
      見る ── そこも 3 つ目の行き止まりだった。
      🔑 一般形:**口を割ったら、その口の名前を書いている所を全部 grep する。**
      ⚠ 割った本人は「割った」ことを覚えているので、**案内のほうを見に行かない**

- **画面に出す「安心させる字」は、願いで書かず、作りで担保する**
  (2026-09-18、#1006。**着地前レビュー 2 本が独立に同じ所を指した**)。
  ⚠ 呼び側の `catch` に「**何も消えていません**」と書き、注釈で
  「ここへ来たのは zip を落とす前だから言える」と**理由まで添えて**いた。
  🔴 ところがその前提は**①で落ちたときにしか成り立たない** ── 捨てる②・開き直す③が
  裸で、そこで落ちても**同じ catch へ来る**。②が通った後なら **DB はもう無い**ので、
  **いちばん安心させる字が、いちばん嘘**になっていた。
  ⚠ しかも例外の枝は**読み込み直さない**ので、terminate 済みの接続を握ったまま
  画面が残る(以後の保存が全部落ちるのに、画面は何も言わない)。
  🔑 **直しは字ではなく構造である** ── ②以降を**丸ごと try で覆い**、落ちても
  **結末として返す**(投げない)。これで `catch` が意味するのは「①で落ちた」だけになり、
  **その字が作りとして真**になる。
  🔑 検算は 1 つ:**その文が偽になる経路を 1 つ書けるか。** 書けるなら、
  文を直すのではなく、**その経路がそこへ来ない形**にする ──
  ⚠ 注釈で「ここへは来ない」と宣言するのは、**来ないことを保証していない**

### 1.7 async にした瞬間に、同期の test が空振りする

- **型**: 時間の型 ── assert は走るが、実装がまだそこへ到達していない。
- **見分け方**: 直す前も直した後も緑。答えが true でも false でも結果が同じ。
- **直し方**: 関数に `async` を付けたら、呼んでいる test を grep で数え上げ、数えた数だけ `await` を足す。対照群を同じ it に置く。製品コードの呼び側の seam にも変異試験を当てる。

**実例**

- **`async` にした瞬間、それを呼ぶ同期の test は全部空振りになる**(2026-08-21、#299)。
  ⚠ 他の空振りは「条件が別物に満たされる」型だが、これは**時間**の型である
  ── assert は走るが、**実装がまだそこへ到達していない**。
  実例: `launchTile` を async にしたら、`confirmSameOrigin` の `await` が
  `window.open` より**前**に来た。同期の `it` から呼ぶと、答えが `true` でも `false` でも
  `opened` は必ず空 ── **「断ったら窓すら開けない」という、同一オリジンで開く経路の
  唯一の門が、12 時間ほど何も見ていなかった**(着地前レビューが拾った)。
  ⚠ 恐ろしいのは**その test が落ちないこと** ── 直す前も直した後も緑である。
  🔑 **関数に `async` を付けたら、その関数を呼んでいる test を `grep` で数え上げ、
  数えた数だけ `await` を足す。** そして**対照群を同じ it に置く**
  (「受けたら 1 枚開く」)── 置かないと「`await` を足したのに、別の理由で空だった」を
  次に見抜けない。⚠ 同じ型は**製品コード**にも出る(`await` を落としても `Promise` は
  常に truthy なので tsc が黙る)── 呼び側の seam ごとに変異試験を当てる。

### 1.8 「強制する」規則・論理式の片側が効いていない

- **型**: `A || B` の片方の項を丸ごと外しても緑 ── もう一方の項が、どのみち true で救っている。
- **見分け方**: 守っていたのは「結果が出ること」であって「強制していること」ではない。門を N 個置いたのに N 個目だけが鳴る場面が無い。
- **直し方**: `B` が false になる形で見る。対照群も同じ場面で置く。門を N 個置いたら、N 個目だけが鳴る場面を N 通り作り、どの門が鳴ったかを文言で見分ける。

**実例**

- **「強制する」規則は、強制しなければ false になる場面で見ないと空振りする**
  (2026-08-22、#178。変異試験 N5 が SURVIVED で教えた)。
  `checkpoint = diskAhead || (freshLid !== lid && baseline !== seed)` と書いて
  「別の窓の版を必ず履歴へ積む」を足したが、**普通のノートは右辺がどのみち true** なので、
  ⚠ **`diskAhead ||` を丸ごと外しても test は緑**だった ── 守っていたのは
  「積まれること」であって「**強制していること**」ではない。
  🔑 **`A || B` を足したら、`B` が false になる形で見る** ── この件では
  「新規ノートの初回 commit」(`freshLid === lid` なので普通は積まない)が唯一の場面で、
  そこで見たら 1 発で殺せた。⚠ **対照群も同じ場面で置く**(「別の窓が書いていなければ
  積まない」= 規則そのものが生きていること)── 置かないと、右辺を壊しただけの変異と
  区別がつかない。
  ⚠ これは 1.1「救い手が変わっただけ」の**論理式版**である ── 救い手は
  別の file ではなく、**同じ式のもう一方の項**だった

  - **同じ形が「空振り防止」の test にも出る**(2026-08-24、#225 の後条件)。
    下限(floor)を**一覧と目録の両方**に置いたのに、test は**両側を同時に小さくする**
    fixture 1 本しか持っていなかった ── ⚠ **片方の下限を殺しても、もう片方が救って
    落ち続ける**(変異試験 2 件が SURVIVED で教えた)。
    🔑 **門を N 個置いたら、N 個目だけが鳴る場面を N 通り作る。**
    そして**どの門が鳴ったのかを文言で見分ける** ── 「落ちた」だけを見る assert は、
    門が 1 つ死んでも緑のままである

### 1.9 検査の向きを裏返したら、作法も裏返る

- **型**: 「無い」ことの主張を「在る」ことの主張へ書き換えたのに、前処理・範囲が前のまま。
- **見分け方**: 受け口をコメントアウトしても緑(注釈が検査を満たす)。
- **直し方**: 主張の向きを変えたら前処理・範囲・空振り防止を全部見直す(同じ検査の続きではなく、別の検査を書いていると考える)。

**実例**

- **検査の向きを裏返したら、作法も裏返る**(2026-08-18、#250)。「ドラッグ&ドロップを
  **受けない**」を pin していた検査は、実装した瞬間に落ちて役目を果たした ── そこで
  「**受ける**」側へ書き換えたが、⚠ **コメントを落とす前処理(`codeOnly`)を通し忘れた**。
  「無い」ことの主張では**広く拾うほうが安全**(コメントで誤検知して落ちるのは見逃すより
  よい)だが、「在る」ことの主張では**注釈が検査を満たす** ── 受け口を**コメントアウト
  しても緑**になる。⚠ その file 自身の `codeOnly` の docstring がまさにこれを戒めていた。
  🔑 **主張の向きを変えたら、前処理・範囲・空振り防止を全部見直す**(同じ検査の続きではなく、
  **別の検査を書いている**と考える)

### 1.10 期待値が実装と同じ盲点を共有する

- **型**: 期待値を「実装と同じ文法の別の綴り」や「実装の配列そのもの」から組んでいて、実装が間違う形で期待値も同じく間違う。
- **見分け方**: 集約した値(配列・1 か所へ寄せた規則)を壊すと、検査のループも同時に縮んで「一致している」が最後まで成り立つ。
- **直し方**: 期待値は別の観測(実装を参照しない不変量 / user に配る正本)から作る。一致の前提はその場で assert し、崩れたら「前提が崩れている」と読める文言で落とす。

**実例**

- **期待値を「実装と同じ文法の別の綴り」で組むと、同じ盲点を共有する**
  (2026-08-22、#284/#318 の 3 巡目レビュー)。「修理した結果が、**user が閉じを
  書き足した理想形**と一致する」という検査を書き、⚠ **理想形は
  `frontmatterRunLength` を 1 度も呼ばないから独立だ**と説明まで添えた。
  実際は**同じ規則を test 側で書き直しただけ**で、実装が間違える形では
  **理想形も同じように間違える** ── 実測:`tags:` + 空行 + `- 牛乳` は
  両辺が揃って `- 牛乳` を frontmatter と読み、**一致してしまった**
  (その裏で user の買い物リストが閉じの内側へ隠れて画面から消えていた)。
  🔑 **期待値は「別の綴り」ではなく「別の観測」から作る** ── この件で効いたのは
  実装の綴りを 1 行も参照しない不変量だった:
  **「隠した行は、必ず誰かが読んでいる」**(= 修理後の frontmatter 領域の実のある行は、
  **その行を消すと `meta` が変わる**。変わらないなら隠してはいけない)。
  ⚠ 同型の弱さは**比べる対象の粒度**にも出る ── `meta` だけ比べる検査は
  「本文から行が消えた」を原理的に見られず、**byte の生存**だけ見る検査は
  「閉じの内側へ移って画面から消えた」を見られない
  - **配列版 ── 期待値が、実装の配列そのものをループの種にしている**
    (2026-09-18、#1006 の変異試験で 1 件だけ生き延びた)。
    戻らない物の呼び名を `REBUILD_LOST` の 1 か所へ集めたのは正しい(§7)。
    ⚠ ところがそれを検める test が**全部**
    `for (const lost of REBUILD_LOST) expect(文).toContain(lost)` の形だった ──
    🔴 **配列から 1 つ落とすと、窓の字も、見に行くループも、同時に縮む**ので、
    「一致している」は**最後まで成り立つ**。
    ⚠ 空振り防止に置いた `length > 0` も、**3 → 2 の縮みには反応しない**
    (0 件ではないので)。
    🔑 直しは「assert を足す」ではなく**期待値の出どころを変える**こと ──
    **マニュアルの表**(その配列を 1 行も参照しない、user に配る正本)と
    **等値**で比べる形にしたら、同じ変異が 1 発で KILLED になった。
    ⚠ **お知らせは使わない** ── 配ったら書き換えない約束なので、後で 1 つ足す日に
    **直せない側**を期待値にしてしまう。
    🔑 一般形:**「1 か所へ集めた」ことが、そのままテストの死角になる。**
    集約した値を検めるときは、**集約先を見ない観測**を 1 つ用意する

- **一致を主張する検査は、前提を検算してから比べる**(2026-08-22、#284/#318)。上の検査は
  自前の総当たり 2662 形のうち **36 形で成り立たなかった**(値のある key の直後の
  `- item` で走が止まる形)。⚠ **前提を書かない一致の主張は、成り立たない条件**
  (本節 1.2)である。🔑 前提は**その場で assert する** ── 崩れた形が来たら
  「一致しなかった」ではなく「**前提が崩れている**」と読める文言で落とす。
  ⚠ 前提の判定も**読み手と同じ文法**で書く(ここでも行末コメントの剥ぎ忘れで
  1 度落ちた ── **同じ罠が test 側にも出る**)

### 1.11 挙動を変えたのに、test が前も後も通る

- **型**: 台が作った状態が、両方の実装で同じ結果になる。
- **見分け方**: 直す前の実装に戻しても test が落ちない。
- **直し方**: 直す前の実装に戻して落ちるかを見る(変異試験の R1)。台を「2 つの実装が分かれる 1 点」まで進める。

**実例**

- **挙動を変えたのに、test が前も後も通るなら、それは守っていない**(2026-08-27、#490)。
  ⚠ 他の空振りは「条件が別物に満たされる」型だが、これは
  **台が作った状態が、両方の実装で同じ結果になる**型である。
  実例:「書けないときに**捨てる**」を「**預かる**」へ変えたのに、既存の test は
  **どちらでも緑**だった ── 台が `keepLock: true` で**錠を永久に握る**ので、
  捨てても預かっても「追記は飛ばない」「理由を言う」が成り立つ。
  ⚠ しかも台のコメントには「**実物では effect 層が錠を解く**」と書いてあった ──
  つまり **test が再現していたのは、製品に存在しない状態**である。
  🔑 検算は 1 つ:**直す前の実装に戻して、その test が落ちるか。**
  落ちないなら、守っているのは自分が思っている物ではない
  (変異試験の R1 として回せば 1 回で分かる)。
  🔑 直し方は「assert を足す」ではなく **`錠を解いて、入ることまで見る`** ──
  **2 つの実装が分かれる 1 点**まで台を進めること

## 2. 経路が「一度も通っていない」── 弱いのではなく走っていない

🔑 空振り(§1)は**条件が別物に満たされる**、こちらは**そもそも実行されない**。生き延びた・緑だったときは、まず**通っているか**を疑う。

### 2.1 その行・その分岐を 1 度も通っていない

- **型**: test がその行(分岐・経路・環境の道)を実行していない。
- **見分け方**: 変異が当たったのに生き延びた / 壊す代わりに `throw` を置いても落ちない / 環境が持たない道(happy-dom に無い API)の fallback ばかり通っている。
- **直し方**: assert を足す前に「通っているか」を疑う。分岐を書いたら分岐の数だけ「実際に走らせた記録」を持つ。環境が持たないから代わりに動く道は、本物と同じ意味論かを確かめる。判断は取り出せば test できる。

**実例**

- **`SURVIVED` の半分は「弱い」ではなく「通っていない」**(2026-08-07)。変異は当たったのに
  **test がその行を 1 度も実行していない**ことがある ── 履歴パネルのガードを消す変異が
  生き延びた原因は assert ではなく、`render()` が**指紋(当時 4 項: selectedLid / body / phase /
  revisionPanel。いまは 6 項、`detail.ts` の `render()` 冒頭)が同じなら何もせず返る**ことで、test は `entryMetas` だけ動かしていたため
  **その関数に入っていなかった**。🔑 生き延びたら **assert を足す前に「通っているか」を疑う**
  ── 壊す代わりに `throw` を置いて、落ちなければ**誰も通っていない**。
  手順は `.claude/skills/mutation-testing/SKILL.md`

- **「両方向を検めている」と書いた検査が、片方向しか走っていない**(2026-08-13)。§1 の
  `SAFE_HEAP` の後条件は「頼んだのに入らない」も見るつもりで書いたが、**実際に走ったのは
  `=1` の側だけ**だった ── 最初に回した調査ビルドが `safe_heap=true` で、**配布側の経路は
  1 度も通っていなかった**。⚠ **変異試験 7 件が KILLED でも突けない**(変異が当たる場所と、
  経路が通っていない場所が別である)。🔑 **分岐を書いたら、分岐の数だけ「実際に走らせた記録」を
  持つ** ──「両方向」「N 通り」と書いた瞬間が、その全数を**手で通す**合図である
  (この件は上流の実 file を落として 4 通り当てたら 5 分で片付いた)

- **本命の分岐を、unit は 1 度も通らないことがある**(2026-08-18、#250)。
  `insertText` は `document.execCommand('insertText')` を使い、**駄目なら手で splice** する
  形だが、**happy-dom に `execCommand` は無い** ── つまり unit は**必ず fallback を通る**。
  帰結は 2 つ。① `execCommand` 側は unit で 1 度も走らない(そこに置いた `focus()` を
  消す変異が生き延びた ── 実ブラウザ smoke を足して初めて殺せた)② **fallback が本物と
  違う振る舞いをすると、その差は test から永久に見えない**(実際 `input` を撃たず caret も
  進めておらず、2 列では**画面に見えているのに保存された本文には無い**形だった)。
  🔑 **「環境が持たないから代わりに動く道」を書いたら、そちらが本物と同じ意味論かを
  必ず確かめる**(§3「stub は本物の意味論を真似る」の**製品コード版**である)

- **どの test からも実行されない file に、判断を書かない**(2026-08-08)。`src/main.ts` は
  **原文を `readFileSync` で読む test しか無い** ── 配線をそこへ直書きしたら、「設定を切った
  だけの user を既読にする」型の取り違えが**全 2385 tests 緑のまま**通った。🔑 **取り出せば
  test できる**(`update-card.ts` が同じ理由で取り出されている前例)。⚠ 取り出せないもの
  (boot の呼び出し順)は原文 pin で妥協するが、**弱いと自覚して使う**

- **worker は node で動く**(`tests/adapter/storage-worker.test.ts` の手法: `self` /
  `postMessage` を差して実物を dynamic import、`:memory:` fallback)。「worker の中だから
  unit では届かない」は誤り ── smoke 1 本に頼ると、向き・題名・上限の変異が誰にも守られない

### 2.2 fixture の次元が、0 件・1 つに潰れ・端数・古さ不足

- **型**: fixture の次元(旧さ・件数・散らし・差・打ち方)が、書いたつもりより狭い。
- **見分け方**: 非ゼロの assert を素通りする(1 つに潰れている / 差が 1px 未満)/ 旧い形のはずが最初から新しい / 打ち方(日本語入力)が全部半角。
- **直し方**: その次元が非ゼロ・N 通り・余裕つきで出ていることを test 自身に assert させる(`>= N`、差そのものを assert)。「旧い」は版ごとに数え上げる。入力を受ける機能は日本語入力で打った形を 1 つ持つ。組み合わせが有限なら全数当てる。

**実例**

- **「旧い形」の fixture が、ここまで古くないことがある**(2026-08-20、#297)。
  migration の test は「旧い DB を自分で作って通す」形で正しく書かれていたが、
  その旧 DB は **FTS の表と trigger を落としていなかった** ── 行を入れた時点で
  trigger が索引を埋めるので、**「索引が空のまま UPDATE が走る」という当の経路を
  12 日間 1 度も通っていなかった**(その間に起動不能が配られた)。
  🔑 **「旧い」は 1 つではない。** 何を足す前の姿かを**版ごとに数え上げ**、
  fixture がどの版を再現しているのかを書く。⚠ 「後から足した列」だけ落として
  「後から足した**表**」を落とし忘れる、が実際の形だった

- **fixture のゼロ件の次元は「測っていない次元」**。本文が短いと逆向きパッチが一度も
  生まれず、パッチ経路を壊す変異が素通りした。🔑 **その次元が非ゼロか**を test 自身に
  assert させる(`expect(chain.some((r) => r.kind === 'patch')).toBe(true)`)
  - **ゼロではなく「1 つに潰れている」形もある**(2026-08-23、予定の probe)。
    ⚠ こちらは**非ゼロなので上の assert を素通りする** ── 実際 `groupCount > 1` を
    満たしていたので**緑のまま**だった。fixture のコメントには「**3 日ぶんに散らす**」と
    書いてあり、実際は **2 日にしか散っていなかった**。
    原因は散らす式:チェックリストを持たせるのは `i % 10 === 0` のノートだけで、
    それは**必ず偶数**なので `i % 2` は**常に 0** ── 🔑 **散らすなら「選ばれた側の
    連番」で割る**(`(i / 10) % 3`)。
    🔑 だから規律を 1 段強める:**「N 通りに散らした」と書いたら、実際に N 出ることを
    test 自身に assert させる**(`>= N`)。⚠ 「1 件以上ある」では、**書いたつもりより
    狭い次元**を検出できない。
    ⚠ そして気づけたのは**回したから**である ── 張り替えた probe を「張り替え済み」と
    報告して終えていたら、fixture の嘘は台帳に残ったままだった
    (§「test は使い所を選ぶ」の「**回さなすぎのほうが害が大きい**」の実例)
  - **次元は在るが「端数で」しか在らない**(2026-09-11、夜の検査が
    2 件落ちた)。⚠ 上の 2 つは *0 件* と *1 通りに潰れている* だが、こちらは
    **差が 1px 未満**である ── 非ゼロだし通りも複数あるので、**どちらの assert も
    素通りする**。実測:「表が器より広い」を見る 2 本が、
    **1034.81px 対 1036px(差 1.19px)** と **超過 0px(器 374px)** で成り立っていた。
    ⚠ つまり fixture は「広い」を**字 1 つ分にも満たない差**に賭けており、
    `playwright` の更新でブラウザが字幅を数 % 変えた日に**両方まとめて裏返った**
    (製品は無傷 ── 落ちたのは前提のほうである)。
    🔑 **差は桁で稼ぐ** ── 列を 6 → 9 / 8 → 12 に増やしたら、内容は器の 1.5 倍を
    超え、字幅が動いても向きは変わらなくなった。
    🔑 そして**その差自体を assert する**(「升が折れている」/「超過 > 24px」)──
    ⚠ 幅の引き算だけを見ると、裏返った日に「**1px 足りない**」としか出ない。
    **「前提が崩れている」と読める形で落とす**(値も文言に入れる)。
    ⚠ 一般形:**比較で成り立つ前提は、成り立ち方の「余裕」まで書いて初めて次元になる。**
    余裕を書いていない比較は、外の都合(ブラウザ・font・DPR)で静かに向きが変わる

- **「打ち方」の次元を fixture に 1 つも持っていなかった**(2026-09-07、#764。
  **user 報告で判明**)。⚠ その場で計算の test も smoke も**全部半角で打っていた** ──
  ところが user は**日本語入力のまま**打つので `２＋３＝` になり、**何も起きなかった**
  (「発火していない気がする」)。🔑 fixture のゼロ件次元(§2)の**入力版**である:
  **入力を受ける機能は、日本語入力で打った形を fixture に必ず 1 つ持つ**
  (全角の数・演算子・`＝`・全角の空白)。⚠ ASCII だけで組んだ corpus は、
  **日本語で書く user の経路を 1 度も通っていない**。

- **表に載っている件数は「誰かが数えた分」でしかない**(2026-08-07 ── 未実行の**全数版**)。
  ライブエディタの釣り合いは `ok:false` が **4 件**と記録されていたが、外 14 形 × 内 8 形を
  **全数**当たると **48 / 112 通り**壊れていた ── 数えていなかったから記録も無かった。
  🔑 「既知の欠陥は N 件」を出発点にしない。**組み合わせが有限なら全部当てる**
  (当てた表がそのまま回帰 test になる)

## 3. 変異試験そのものの罠 ── 「殺せた / 生き延びた」を信じる前に

### 3.1 変異が当たったかを確かめる(NOT-APPLIED と偽の NOT-APPLIED)

- **型**: 変異が適用されていないのに「生存」と読む / 印が消えて偽の「届いていない」と読む。
- **見分け方**: 結果を 3 値(KILLED / SURVIVED / NOT-APPLIED)で出していない / smoke の変異に build を挟んでいない / 変えた物と探す物が揃っていない。
- **直し方**: 走りは file に出し、置換前に元の文字列が在ることを assert する。smoke は `npm run build` を挟み、印は実行時の副作用にする。変えたのが条件なら、探すのは文言ではなくその条件が効いた結果(test の赤緑)。

**実例**

- **結果は `KILLED` / `SURVIVED` / `NOT-APPLIED` で出す**(時間切れは `TIMEOUT`、計器が
  立たなかったら `INFRA` ── 計 5 値。`.claude/skills/mutation-testing/SKILL.md` §2.1)
  (= **「当たらなかった変異」と「生き延びた変異」を区別する**。2026-08-04、1 セッションで
  2 度踏んだ)。変異が**適用されていない**とき、結果は「生存」と見分けがつかない ──
  **空振りを合格と読む**。① shell の引用で python が SyntaxError になり変異が当たらなかった
  ② `  armDpr();` という置換文字列が、狙った初回呼び出しではなく `onDpr` の中の
  **4 字下げの別行に部分一致**して先にヒットした。🔑 走りは**その場の shell ではなく file に
  出す**/置換前に「元の文字列が在ること」を assert して**当たったことを確かめる**。
  ⚠ 置換文字列は**前後を含めて一意にする**(`  x();` のような短い断片は必ず別行に刺さる)

- **smoke に変異を当てるには build が要る**(2026-08-05 ── 上の**別の顔**。当たらない原因は
  shell のクォートだけでなく、**検査対象が生成物であること**もある)。`tests/smoke` は
  `vite preview` で **`dist/` を配信**するので、source を書き換えただけでは**一切届かない**。
  印刷 CSS の変異 6 件が全部「SURVIVED」に見えて「@media print は誰も守っていない」と
  読み違えかけた(真相は 6 件とも NOT-APPLIED)。🔑 **`npm run build` を挟み、
  `dist/assets/*.js` に「変異後の文字列が在り、変異前の文字列が消えた」ことを確かめてから**
  test を回す
  - **その「印」自体が消えることがある**(2026-08-18、#253 で 2 回)。上の確かめ方は
    **印が dist に残る**ことを前提にしているが、①**型注釈に混ぜた印**
    (`'idle' as T & { __mut?: true }`)は**コンパイルで消える** ②**文字列リテラルの
    `.slice(0, 4)`** は**畳まれて消える**(minifier の定数畳み込み)。どちらも
    「dist に届いていない = NOT-APPLIED」と出るが、⚠ **変異そのものは効いている**ので
    **偽の NOT-APPLIED** である(合格と読みかけた)。🔑 印は**実行時の副作用**にする
    ── `(globalThis as unknown as Record<string, unknown>)['__mutX'] = 1;` は畳めない
  - **「印が、自分が変えた物ではなかった」**(2026-08-22、#178)。上の 2 つは
    *印が消える*話だが、こちらは**印が最初から的外れ**である ──
    `...(diskAhead ? { error: '別の窓の…' } : {})` の**条件**を `false` に変えたのに、
    「届いたか」を**文言の grep** で見た。文言は**死んだ枝の中に残る**ので `1 件` と出る
    (私の判定は「0 なら届いている」だった = **届いていないと読む**)。⚠ 実際には
    変異は効いており、smoke は **KILLED** だった ── 判定を信じていれば
    「NOT-APPLIED だから測り直し」と**1 回転捨てていた**。
    🔑 **「何を変えたか」と「何を探すか」を揃える** ── 変えたのが**条件**なら、
    探すのは文言ではなく**その条件が効いた結果**(= test の赤緑)である。
    ⚠ dist の grep が答えられるのは「**その文字列が在るか**」だけで、
    「変異が効いたか」ではない(2026-08-17「計器の名前が範囲より広い」と同型)

- ⚠ **変異自体を疑う**。発火しない形で当てて素通りしたことがある

### 3.2 ハーネスが作業ツリーを壊す・終わらない

- **型**: 変異試験は作業ツリーを触る操作である ── 巻き戻す・変異が残る・固まる。
- **見分け方**: スイープの最後に修正前のコピーが書き戻される / timeout で殺されて `finally` が届かない / 同期ループで test の timeout も発火しない。
- **直し方**: バックアップは変異を当てる直前に取り直す。戻しをハーネスの `finally` と signal(`SIGINT` / `SIGTERM` / `exit`)に閉じ込め、`timeout -k` で確実に殺し、`124` / `137` を `HUNG` として出す。スイープの後に typecheck / lint / test と `git status` を見る。

**実例**

- **着地前に変異試験を回す**。実装を意図的に壊し、test が落ちることを確かめる
  (`cp` でバックアップ、`git checkout` は使わない)。落ちなければ、その test は**その機構を
  守っていない**。実績: 1 PR あたり 1〜3 件が生き残り、その多くが「既に壊れているのに
  鳴っていない」だった。⚠ **検品する側・test する側も対象**にする(§1)
  ⚠ **2026-08-14 にこの戒めそのものを踏んだ** ── 変異試験の**後始末**に `git checkout` を
  使い、未 commit の workflow 変更を失った(入れ直した)。⚠ CLAUDE.md と
  `.claude/skills/mutation-testing/SKILL.md` の**2 か所に書いてあって止まらなかった**。
  🔑 文言を 3 か所目にせず、**戻しをハーネスの `finally` に閉じ込める**(手で戻す手順を残さない)

- **ハーネスが、直したばかりの実装を巻き戻すことがある**(2026-08-10)。バックアップ用の
  ディレクトリを**使い回した**ため、スイープの最後に**修正前のコピーが書き戻され**、その状態の
  まま commit して CI が赤くなった(typecheck 3 件 + flags の全数検査)。手元では
  **スイープの前**に緑を見ていたので「通ったのに落ちた」に見える。🔑 ① バックアップは
  **変異を当てる直前に取り直す**(使い回さない・終わったら消す)② **スイープの後にもう一度**
  typecheck / lint / test を回してから commit する ── 変異試験は**作業ツリーを触る操作**である
  - **「殺されて `finally` が届かなかった」**(2026-08-22、#178)。上は
    *バックアップの使い回し*だが、こちらは**ハーネスごと落とされる**顔である ──
    2 分の timeout で殺され、`finally` が走らず**変異が作業ツリーに残った**。
    ⚠ 恐ろしいのは**次の走り**である:残った変異入りの版を `orig` として読むので、
    その変異は「元の文字列が 0 件」= **NOT-APPLIED** と出て、しかも
    **以後の復元が全部「変異入りの版」を書き戻す** ── スイープ全体が無意味になる。
    🔑 ① ハーネスは **`SIGINT` / `SIGTERM` / `exit` でも復元する**
    (`process.on` で戻す ── `finally` だけでは足りない)
    ② **`NOT-APPLIED` を合格と読まない**(3.1 の 3 値の規律)── この件で
    気づけたのは**字面を目視した**からで、読み飛ばしていれば
    **無限ループのコードをそのまま push していた**
    ③ スイープの後は**必ず `git status` と字面**を見る(緑だけ見て commit しない)
  - **「変異が固まった」**(2026-09-11、#215)。⚠ 上の 2 つは
    *バックアップの使い回し* と *殺されて `finally` が届かない* だが、こちらは
    **変異そのものが終わらない**顔である ── 門を 1 つ外したら配線が
    **無限に回り**、同期のループなので **test の timeout すら発火しない**。
    ⚠ そして `$(timeout 120 npx vitest …)` は**効かない** ── `timeout` が
    `npx` を殺しても、**子が stdout を握っている限り `$( )` は返らない**。
    ハーネスは 2 度とも**ぶら下がったまま**で、殺したら(上の「殺されて `finally` が届かなかった」と同じく)
    変異が作業ツリーに残った。
    🔑 ハーネス側:**`timeout -k` で確実に殺す** / **各変異の直後に必ず戻す**
    (`trap` だけに頼らない)/ **`124` / `137` は `HUNG` として出す**(ハーネスの出力名は `TIMEOUT`)
    (`SURVIVED` と混ぜない ── 3 値の規律に 4 つ目が要る)。
    🔴 **製品側のほうが本題である** ── 門が 1 つ消えただけで固まるなら、
    **門の置き方が悪い**。この件の輪は「`onState` の中から `dispatch` する」
    ことで閉じており、⚠ **再入を弾く形の門では止まらなかった**
    (`Dispatcher` が drain 中の dispatch を**待ち行列に積む**ので、
    入れ子ではなく**順番に**回り続ける)。
    🔑 効いたのは**送る条件のほう**:回り続ける理由は「押すたびに時刻が動く」
    ことなので、**時刻だけの違いでは送らない**(並べ替えが見るのは順番だけ)。
    これで輪が**構造から消え**、同じ変異は 1 秒で `KILLED` になった。
    ⚠ 一般形:**`SURVIVED` より `HUNG` のほうが重い** ── 生き延びたのは
    「検査が弱い」だが、固まるのは「**製品が壊れうる形をしている**」である

### 3.3 変異が殺す範囲 ── 置いた門にしか当てていない

- **型**: 「N 件 KILLED」は置いた門が効いていることしか言わない(置き忘れた門・下流の結果・印の数では見えない形)。
- **見分け方**: 別経路が救って変異を見逃す / stub が実装より正しい / 受ける側の端を総当たりしていない。
- **直し方**: 壊れる当の振る舞いを直接見る。stub は判定ごと本物の意味論を写す。実装が受ける / 受けないを分ける軸を数え上げ、端を総当たりする。判定関数を直に当てる test を別に置く(空振り防止つき)。

**実例**

- ⚠ 「添付が ZIP に入るか」のような**下流の結果**だけを見る test は、別経路が救って変異を
  見逃す。**壊れる当の振る舞い**(書き換えが起きるか等)を直接見る

- **stub は本物の意味論を真似る**。stub が実装より正しいとバグが隠れる(fake の
  `getRevision` が保存形をそのまま返し、本物が materialize する食い違いを隠していた ──
  「鎖のまま往復する」test が壊れた実装でも通った)

- **変異を「自分が足した門」にしか当てていない**(2026-09-07、#764)。
  ⚠ 14 件すべて KILLED で着地させたのに、着地前レビューが**実測で 11 例の欠陥**を出した
  ── `md5=` → `md5=5` / `2^3=` → `2^3=3`(**8 ではない**)/ `1,200+800=` → `1000`
  (**正しくは 2000**)/ 既にある行の途中で答えが 2 つ。
  🔑 原因は 1 つ:**変異させたのは自分で書いた門だけ**で、**門を置かなかった形**は
  1 つも試していない。⚠ 「N 件 KILLED」は**置いた門が効いている**ことしか言わない
  ── **置き忘れた門については何も言わない**。
  🔑 検算:実装が「受ける / 受けない」を分ける**軸を数え上げ**、受ける側の端を総当たりする
  (この件では「`=` の直前に何が来るか」── 数字・ASCII の語・日本語・記号・行頭)。

- **印の数では見えない門がある**(2026-09-07、#749。2 件が SURVIVED)。
  ⚠ 焼く側(描画)を数える test は、**読み手がそもそもその形を描かないとき**
  門の有無に関わらず **0 個**を返す ── 引用の中の囲み / 区切りの行だけ引用の深さが違う表。
  🔑 割れるのは**書く側だけ**なので、**判定関数を直に当てる** test を別に置く
  (空振り防止つき)。⚠ 「corpus で数えているから守れている」は、
  **描かれる形についてしか言えない**

## 4. 観測点の選び方 ── 何を見れば「届いた」と言えるか

### 4.1 観測点が「信号」になっていない

- **型**: 放っておいても変わる / 増減が相殺する / 量が動かない相手を、「届いた」の証拠にしている。
- **見分け方**: 何もしていないキーでも「変わった」と出る / 効いているのに「効かなかった」と出る。
- **直し方**: 間隔をあけて数枚撮り、集合ごと入れ替わったときだけ「変わった」と言う。増減が同時なら数ではなく個体(題名 / id)で見る。量は複数の面から採る。手順の先頭に「効くはずの一手」を対照群として置く。

**実例**

- **観測点が「放っておいても変わる」なら、変化は届いた証拠にならない**(2026-08-13)。
  canvas しか無い相手(LO wasm)で「絵の hash が変わったか」を届いた判定に使ったが、Writer には
  **点滅するカーソル**が在るので、**何もしていないキー**でも `landed: true` になった。
  🔑 **間隔をあけて数枚撮り、集合ごと入れ替わったときだけ**「変わった」と言う。⚠ 逆側も要る
  ── **手順の先頭に「効くはずの一手」を対照群として置く**(この件では「ただの文字を打つ」)。
  それが届いていない回は、**以降の判定が全部無意味**である。実際これが無ければ
  「ダイアログが開かないのは LO wasm の制限だ」と**存在しない結論**を書いていた
  (真相は合成 focus では入力先が決まらないこと)
  - ⚠ **逆向きも同じ**(2026-08-14)。窓の**枚数**で「命令が効いたか」を見たら、
    メニューが閉じる(−1)とダイアログが開く(+1)が**相殺して 0** になり、効いているのに
    「効かなかった」と読んだ(`build/office-wasm/io-layer-probe.mjs`)。
    🔑 **増減が同時に起きる相手では、数ではなく個体**(題名 / id)**で見る。**
    ⚠ そして観測点の生死は**窓ごとに違う** ── 同じ `textContent` が、LO の主窓では
    `Enable Screen Reader` 固定なのに、Qt のダイアログ窓では題名が読める。
    「この観測点は死んでいる」と書くときは**どの面でか**まで書く

- **「増えたか」を観測点にすると、増えない相手を取りこぼす**(2026-08-24、#225)。
  9 形式の保存を「file の大きさが増えたか」で見ていたが、**`.xls` は 1 バイトも動かない**
  ── BIFF は区画の大きさが決まっているので、1 文字ぶんの変更では総量が変わらない。
  ⚠ **大きさだけを見ていたら「保存できない」と報告していた**(実際そう書きかけた)。
  🔑 **「起きたこと」を複数の面から採る** ── この件では **mtime が動いたこと** +
  実装側の印(`medium:commit`)+ **下流が受け取ったこと**(PKC が保存を取り込んだ)の
  3 点にしたら、11 形式が同じ規則で読めた。
  ⚠ 「量」で見るなら**量が動かない相手が居ないか**を先に問う(圧縮・固定長・
  パディング・sector 境界 ── どれも「変えたのに同じ」を作る)

### 4.2 対照群が届かない回を、結果として読む

- **型**: 対照群が落ちた回・崩れた回・「判定不能」と書いた同じ文で、観測値を解釈している。
- **見分け方**: 壊れた計器が数字と真偽を返して「測れている顔」をしている / 「取れない」と書くのに数えた経路が 2 つだけ。
- **直し方**: 対照群が落ちたら、まず「その道具はそもそも動くのか」を測る。判定不能とは 1 つも主張しないこと(続けてよいのは次に測る物だけ)。判定規則は回す前に書く。「できない」と書くなら数えた経路を書く。

**実例**

- **対照群が届かない回は「判定不能」と書く。結果を読まない**(2026-08-17、#225)。
  `.docx` の書き出しが落ちる層を割るため `--convert-to` の probe を書いたが、
  **対照群(native の `.odt`)も 120 秒で 0 バイト**だった ── つまり命令行の変換経路
  そのものがこの一式で動かない。⚠ 対照群を先頭に置いていなければ
  **「docx が落ちた」と誤って書いていた**(そして存在しない層を追っていた)。
  🔑 **推薦した 1 手が空振りしたら、その線は取り下げる** ── 「出なかった」ではなく
  「**出ないことが分かった**」として台帳に残し、次の手(実機)へ渡す
  - 🔑 **ただし「判定不能」で終わらせる前に、道具の欠品を疑う**(2026-08-17、#238)。
    user のバグレポ「書き出した docx が LO で開けない」を native の `soffice` で確かめたら
    **PKC の docx も、LO 自身が作った docx も、ただの `.txt` すら**開けなかった。
    ⚠ ここで結果を読んでいたら「PKC の書き出しは壊れている」と**存在しない不具合**を
    報告していた。真因は箱に **`libreoffice-core` しか入っておらず Writer の filter が無い**
    ことで、`libreoffice-writer` を入れたら**対照群が通り**、PKC の docx は 2 本とも
    PDF になった(= **ファイルは正常**、残る層は LO wasm 側)。
    🔑 **対照群が落ちた回は、まず「その道具はそもそも動くのか」を測る** ── 直せるなら
    直したほうが速い(この件は 1 回の `apt-get install` で**判定不能が決着に変わった**)
  - **「取れない」で終わらせる前に、取り方を数え上げる**(2026-08-17。CLAUDE.md §4『取り方を数え上げる』(user 指摘 2026-08-17)を参照)。Office 一式を「この箱では**原理的に**
    取れない」と書いたが、⚠ 数えたのは **2 経路だけ**(Pages / repo の中身)で、
    しかも **CA bundle を渡さずに 1 回叩いた**だけだった。実際は
    **release 資産が `curl -sSL --cacert /root/.ccr/ca-bundle.crt` で 1.4 秒で落ちる**
    (`github.com/.../releases/download/...` → `release-assets.githubusercontent.com` へ追従)。
    ⚠ この誤りは**引き継ぎ doc に「原理的に立てられない」と書いてしまい**、
    次に読む人が**試さなくなる**形で残るところだった ── 「できない」は
    **できることより強い主張**なので、**数えた経路を書く**(書けないなら言い切らない)。
    🔑 手順は `.claude/skills/office-oracle/SKILL.md`

- **計器の対照群が崩れた回を、結果として数えない**(2026-08-24、#225)。同じスイープで
  `.odt` / `.rtf` / `.pptx` の 3 つが「保存できない」に見えたが、**3 つとも
  最初の打鍵が版面に届いていない回**だった(`.pptx` は probe ごと時間切れで殺され、
  `Target page … has been closed` が出ていた)。回し直したら 3 つとも保存できた。
  🔑 分かれ方が**形式ではなく計器と一致**していた ── 打鍵が届いた回は **8/8** で保存でき、
  届かなかった回は **3/3** で保存されない。**この一致を見たら、まず計器を疑う**。
  ⚠ ただし**判定規則を結果の後から緩めない** ── 「届かなかった回は判定不能」は
  スイープを回す**前**に書いておく(後から書くと、都合の良い回だけ採ったことになる)。
  🔑 非対称でよい:**保存が走った証拠(印 + 下流)は、どの打鍵が効いたかに依らず読める**
  が、**走らなかったことは、入力が届いた対照群が無いと言えない**

- **「判定不能」と書いた同じ息で、結果を読んでしまう**(2026-08-23、#199 で 1 時間溶かした)。
  ⚠ §4 の「**対照群が届かない回は『判定不能』と書く。結果を読まない**」は
  **半分しか守れない** ── 私は「対照群が無いので判定不能」と正しく書きながら、
  同じ文で「**落ちている LO でも真になる**(= だから昇格させない)」という
  **結果由来の主張**を並べ、それを根拠に**実装の名前と test の pin を裏返した**。
  🔑 **判定不能とは「1 つも主張してはいけない」ということである。**
  「測れなかった」の後に続けてよいのは**次に何を測るか**だけで、
  観測された値の解釈は 1 つも書けない。
  ⚠ 実測で覆った(動く計器で測り直したら**開いた回と開かない回が完全に分かれた**)
  ── つまり嘘の結論を**製品と test の両方へ**入れていた。
  - **原因は「自分の戒めを読まなかった」こと**である。
    `.claude/skills/office-oracle/SKILL.md` の冒頭には
    **「⚠ 『この箱では確かめられない』と書く前に必ずここを読む」**と書いてあり、
    §4 に版面の byte 数という**動く観測点**が、§7 に**どの文書が開くかの実測表**が
    在った。⚠ 私はその一文をまたいで「確かめられない」と 2 つの issue に書いた。
    🔑 **戒めは「読む条件」で引く** ── 「確かめられない」「原理的に無理」「判定不能」と
    **書こうとした瞬間**が、その skill を開く合図である(書いた後ではない)。
  - ⚠ **壊れた計器は、無い計器より悪い。** 私の probe は対照群すら開かないのに
    数字と真偽を返していたので、**測れている顔**をしていた。
    🔑 だから消した ── 直せない計器を「参考」として残さない

### 4.3 一致の件数を、因果の証拠にする

- **型**: 「7/7 で一致」のような一致を確定として扱う。
- **見分け方**: 一致が別の現象を数えている / 件数の強さが対照群から来ている。
- **直し方**: 次に測るのは「仮説が真なら必ず壊れる 1 手」。既存の記述と一致したことを補強に数えない。

**実例**

- **一致の件数は、因果の証拠ではない**(2026-08-14)。#117 の fault と「メニューの項目が
  効かない」が **7/7 で一致**したので、「fault が LO の命令発行を殺している」を**確定として
  扱い**、その線で probe を 2 本書いた。⚠ ところが user の実機では `Cmd+A` と `Cmd+B` が
  **両方効いた** ── **7/7 は別の現象を数えていた**。⚠ しかも支える側は **fault 有り 2
  サンプル**しかなく、「7/7」の見かけの強さはほとんど**対照群 5 回**のほうから来ていた。
  🔑 一致を見たら、次に測るのは**「仮説が真なら必ず壊れる 1 手」**である。
  ⚠ **既存の記述と一致した**ことを補強に数えない ── その記述自体が同じ推測から
  生まれていることがある

### 4.4 測った対象が、主張の範囲と違う

- **型**: 数字は本物だが、測った量が user の見る量・主張の範囲と違う(客域だけ / heap だけ / 配った先が違う / 別の面の出力)。
- **見分け方**: 実測を添えているのに主張が的を外している。
- **直し方**: 計器の名前を主張として読み、その主張を満たす範囲を測っているかを確かめる。直した対象ではなく user が見る面を測る。「焼けた」と「届いた」の間に何段あるかを数える。probe には「どう測ったか」を出させる。揺れの主因が測りたい物でないなら観測点をそこから外す。

**実例**

- **自分が測った量と、user が見る量が違うことがある**(2026-08-12)。Office の窓を
  「器いっぱいにした」と実測つきで報告したが、測っていたのは**客域(canvas)だけ**だった ──
  Qt はその**外側に**枠 8px と疑似タイトルバー 22px を描くので、**窓全体は 30px はみ出し、
  LO のステータスバーが画面外に落ちていた**。数字は正しく、主張が的を外していた。
  🔑 **「直した対象」ではなく「user が見る面」を測る** ── 内寸を直したなら**外寸**を、
  1 経路を直したなら**画面に出る最終形**を。⚠ 実測を添えると説得力が出るぶん、
  **的を外した実測は嘘より始末が悪い**(こちらも相手も「確かめた」と思ってしまう)
  - **「配った先」でも同じ型が起きた**(2026-08-14)。Impress を焼いて PKC3 の prerelease
    `lo-wasm-dev` に出し、「user に Impress が届きます」と報告した ── ⚠ **user が取る先は
    そこではない。** アプリが読むのは同一 origin の `/office-pack/pack.json` で、
    **GitHub の release 資産は CORS で原理的に取れない**(ACAO 0 件 / OPTIONS 405 を実測)。
    しかも配布 Pages を組む `make-pages-bundle.mjs` は **PKC3 の CI から 1 度も呼ばれていない**
    ── **配布は 2 段**で、2 段目は別 repo(`sm06224/office-pack`)の Pages である。
    ⚠ 露見したのは外部の検証レポートが**古い目録のまま**だったからで、こちらの計器は
    1 つも鳴らなかった。🔑 **「焼けた」と「届いた」の間に何段あるかを数えてから報告する。**
    ⚠ 根は**名前**に在った ── workflow 自身が `lo-wasm-dev` を「**配布 tag**」と呼んでいる。
    **取れない先を配布と呼ぶと、次に読む人も同じ読み違えをする**

- **計器の名前が、計器の見ている範囲より広いことがある**(2026-08-17、#114)。
  `run-app-session.mjs` は題名も docstring も「**継続使用の常駐メモリ**」と書いてあるのに、
  実際に読んでいたのは `performance.memory` = **メインの realm の JS heap だけ**だった ──
  PKC3 でいちばん大きい確保元(**sqlite の wasm メモリ**)は storage worker の中に在るので、
  **1 バイトも数えていなかった**。実測すると **heap 10MB に対しプロセス木の Pss は 514MB**。
  ⚠ この形は空振り(§1)と違って**数字が出る**ので気づけない ── 出た数字は本物で、
  **測っている対象だけが違う**(2026-08-12 の「客域だけ測って外寸を見なかった」と同型)。
  🔑 **計器の名前を主張として読み、その主張を満たす範囲を測っているか**を確かめる。
  worker を持つアプリで「常駐」を言うなら、観測点は**プロセス木**(`smaps_rollup` の Pss)。
  ⚠ `Rss` は同じ共有ページをプロセスごとに数えるので、**プロセス数が動く比較では
  「増えただけ」で重く見える** ── 比べるなら Pss

- **揺れの主因が「測りたい物」でないなら、観測点をそこから外す**(2026-08-22。元の文は「同日」で、直前の #178 の項と同じ日)。
  同じ 2 群を、編集セッション(添付 2MB のラスタ込み)で測ると **±8MB 揺れて符号も反転**し
  **分解不能**だったが、**renderer だけ・静止時**へ寄せたら **6 組とも同じ向き・範囲が
  重ならない**(−3.9MB)。⚠ n を増やす前に**何が揺らしているか**を見る ── 揺れの出所が
  測定対象と無関係なら、n を 10 倍にしても分解能は上がらない。
  ⚠ ただし「静止時に寄せた」は**主張の範囲も狭める** ── 語れるのは「idle worker の常駐」で
  あって「編集中の体感」ではない(そちらは分解できなかった、と書く)

- **器の比で押す probe は、面ごとに別の場所を指す**(2026-08-25、#154。**3 回続けて
  嘘の結論を書きかけた**)。同じ `0.4 / 0.35` を Writer と Impress で使い回したが、
  Writer は版面が器のほとんどを占めるのに対し、**Impress は左にスライド一覧、
  右にサイドバー**が在るので、同じ比が**枠の外**に落ちる。⚠ そこで打っても字は
  入らないが、それは **LO の話ではなく座標の話**である。
  ⚠ **実測 2 本が揃って false になった** ── それらしいので、そのまま
  「Impress には入力が届かない」と書くところだった(枠がスライド全面を覆う
  fixture で押し直したら **true**)。
  🔑 **「同じ手順で回した」は「同じ物を触った」ではない。** 比・座標・キーの意味は
  面ごとに違う ── 揃えるのは**手順の字面**ではなく**触る対象**である。
  🔑 だから probe には**どう測ったかを出させる**(押した比 / 入り方)──
  それが出ない数字は、後から読めない。
  ⚠ 入り方も同じ:Writer は 1 クリックで本文に入るが、**Impress は
  ダブルクリック**が要る(1 回は枠を選ぶだけ)── そのとき版面は変わるので、
  「変わった = 字が出た」と読むと**二重に間違える**。

- **`page.on('console')` は子 frame の分も上がる ── 計器に「どの面か」を書かせる**
  (2026-08-29、#561)。html / svg の囲みを **sandbox の `srcdoc`** で描くので、
  **箱の中でブラウザが出したエラー**が**アプリの例外と同じ 1 行**になっていた。
  実測すると出所は `about:srcdoc`(`lineNumber: 0`)= **箱の中**で、製品は無傷だった。
  ⚠ 出所を書かない計器は、**製品の不具合と fixture 自身の出力を取り違えさせる** ──
  本節 4.4「計器の名前が範囲より広い」の**面版**である。
  🔑 直したら**外し方の順番**に気をつける:等値の名指し(`KNOWN_CONSOLE_NOISE`)は
  **飾る前**に当てる ── 順番を変えれば「飾ると外れなくなる」は起きない
  (⚠ 1 稿目のコメントは「だから console は飾れない」と書いていた。**両立できた**)

### 4.5 環境の性質を、アプリの挙動と読み違える

- **型**: 環境(ブラウザのビルド)で到着時期や値が変わる物を、「飛んだ / 止まった」やアプリの不具合の判定に使っている。
- **見分け方**: ビルドによって assert が先に上がる / 永遠に来ない。
- **直し方**: 観測点はアプリ自身の信号 + 応答が返らないことの 2 つにする。アプリが制御している値(属性そのもの)を見る。主張が違えば観測点も違う。

**実例**

- **ネットワークの event を「飛んだ / 止まった」の判定に使わない**(2026-08-06、外部画像の
  同意で踏んだ ── 環境差(§5)と同じ型)。CSP が止めた試行も `page.on('request')` に
  **上がる**(直後に `requestfailed { errorText: 'csp' }` が続き、応答は 1 度も返らない =
  bytes は出ていない)。ところが**その到着の時期がビルドでまるで違う**:
  `chromium_headless_shell` は assert より先に上がり、`chromium` は 5 秒待っても上がらない
  ことがある ── `request` を数えれば**「外へ飛んだ」という誤った読み**、`requestfailed` を
  待てば**永遠に来ない**(どちらに寄せても片方のブラウザで落ちる)。🔑 観測点は
  **①アプリ自身の信号**(この件では「確認の帯が出たこと」= 箱の中で違反が実際に起きた証拠)
  + **②応答が返らないこと**の 2 つにする。⚠ ②だけでは**空振りでも通る**(箱の script が
  動かなくても応答は来ない)── だから①が要る。⚠ 逆に「試行そのものが起きない」を主張する
  test(`src` を持たない `<img>`)では `request` が正しい観測点である ──
  **主張が違えば観測点も違う**

- ⚠ **環境の性質をアプリの不具合と読み違えない**。この headless Chromium は**非 ASCII の
  `<a download>` 名を丸ごと捨てて `"download"` にする**。実データの題名はほぼ日本語なので、
  `download.suggestedFilename()` を観測点にすると必ず詰まる ── **アプリが制御している値**
  (属性そのもの)を見る

### 4.6 測らずに書いた主張(深刻度・「動いている」・「無防備」)

- **型**: 緊急度・「もう動いている」・「無防備」を、読んだだけで書いている。
- **見分け方**: 「消える」と「見えなくなる」を区別していない / 上流の印の数だけ見て下流(保存)を通していない / 経路が既に持つ防御を読んでいない。
- **直し方**: 通して測る(10 行の test で足りることが多い)。「動く」の観測点は下流まで(押せる → 打てる → 保存される)。範囲は狭まっても深刻度は狭まらない ── 訂正は「頻度の見積もりが違った」と書く。

**実例**

- **「消える」と「見えなくなる」は別の主張である ── severity は読まずに通して測る**
  (2026-08-22、#178)。動線レビューも issue も私のコメントも
  「別窓の書込が**黙って消される**」と書いていたが、**実物の worker で窓 2 枚の物語を
  通したら消えていなかった** ── `COMMIT_EDIT` は既存ノートで `checkpoint: true` なので、
  履歴へ積まれるのは `old.body` = **ディスク上の値 = 別窓の版**である。
  🔑 **緊急度が変わると、作る物が変わる** ── 「消える」なら**楽観検査で断る**
  (= user が打った字を捨てさせる)機構が要るが、「見えなくなる」なら
  **知らせるだけ**でよい。実際、推薦していた対策は**2 つとも要らなくなった**。
  ⚠ **10 行の test で決着した**(`storage-worker.test.ts`)── 読んで severity を
  書くのは、**測れるのに測っていない**ということである
  (2026-08-19「事故の報告ほど、範囲を実測してから書く」の**深刻度版**)。
  🔑 そして**前提を assert しておいたのが効いた** ── 1 稿目の fixture は
  「新規行には `old` が無いので `maintainChain` が呼ばれない」を踏んでおり、
  `expect(await metasOf(...)).toHaveLength(1)` が
  **「一致しなかった」ではなく「前提が崩れている」**で落ちたので即座に直せた
  - ⚠ **「無防備」と書く前に、その経路が既に持っている防御を読む**(2026-08-22、#178)。
    追記を **🔴 無防備**と issue に書いたが、実装の docstring が
    **その問題を既に見越していた** ──「本文は event に載っていない。ここで disk から
    読み直す ── 画面が持つ本文を基底にすると、別経路の書込(**別タブ**)を巻き戻す」。
    つまり**わざと読み直している**ので、残っていたのは
    **`getBody` と書込の間(数ミリ秒)**だけだった。
    🔑 **範囲は狭まるが、深刻度は狭まらない** ── そこで重なれば本文は消え、
    履歴にも残らない。**変わるのは頻度であって、起きたときの結果ではない**。
    ⚠ だから訂正は「軽微だった」ではなく「**頻度の見積もりが違った**」と書く

- **「もう動いている」を、印の数で判断しない**(2026-09-07、#749 → #775)。
  issue のコメントに「csv の囲みは引用の中で**既にちゃんと動く**」と書いたが、
  見たのは**焼かれた印の数(4)だけ**で、**書ける経路を 1 度も通していなかった** ──
  実測すると **4 件とも保存されず、打った字が消えていた**。
  🔑 「動く」の観測点は**下流まで**通す(押せる → 打てる → **保存される**)。
  ⚠ 上流だけ見た「動いている」は、**次の判断の前提**として使われるので害が長く残る
  (この誤りは issue のコメントに書かれ、そのまま設計の根拠にされかけた)。
  - **逆向きの顔 ── reducer が通すことは、画面に押す道が在ることではない**
    (2026-09-27、#1051)。`UNDO_MOVE` を lid で通すようにし、smoke とお知らせに
    「**編集中に留めた枠の塊を動かして、元に戻せる**」と書いた ── 実ブラウザで回すと、
    **編集中は留めた枠の ⠿ が出ず、その場面は画面に無かった**(⠿ を #1081 で直して
    初めて届いた)。⚠ unit は reducer に直接 dispatch するので、**押す道が無くても緑**になる。
    🔑 お知らせ・マニュアルに「〜できるようになりました」と書く前に、**その操作を
    実ブラウザで 1 回押して通す**。通らないなら、字を書き直すか、押す道を先に直す

### 4.7 CI の計器と再現

- **型**: 計器が古い値を返す / 再実行で唯一の証拠が消える / 再現しないのを「起きない」と読む。
- **見分け方**: 同じ id を 2 度引いて 1 バイトも違わない / 再実行後に `failed_jobs: 0` / 回数を増やしても出ない。
- **直し方**: 同じ id を 2 度引いて同じなら別の口(一覧)から引き直す。再実行の前に落ちた job のログを丸ごと控える。回数を増やす前に条件の軸(間を空けたか)が合っているかを疑う。タイムアウトを超えて見えることを異常の証拠に数えない。

**実例**

- **計器が「古い値」を返すことがある ── 動いていないと読む前に、一次情報を見る**
  (2026-08-23、#346 で 1 往復溶かした)。CI の check-run が `in_progress` のまま
  **14 分**動かないので「自分の smoke が CI を止めている」と読み、原因を
  `window.print()` だと**断定して test を弱く書き換えた**。⚠ ところが
  ① **その版は CI で緑だった**(run を直に引いたら `status: completed /
  conclusion: success`、**15:47:52 に終わっていた**)② 手元で `headless_shell` に
  当てて**再現も取れなかった**(1.1 秒で通る)。
  🔑 **「止まっている」は観測ではなく解釈である** ── `in_progress` が意味するのは
  「**この計器がまだ完了を知らない**」であって「走り続けている」ではない。
  ⚠ しかも**タイムアウトを超えて**いたことが「異常だ」という確信を強めた
  (実際は計器が遅れていただけ)。
  🔑 順番は **①一次情報を引く**(check-run ではなく **run / job**)
  **②手元で再現する** ── どちらか一方でも先にやっていれば、この往復は無かった。
  ⚠ そして**再現しない原因を書いてはいけない** ── 書き換えた test には
  「CI をハングさせて学んだ」という**起きていない出来事**を注釈に残しかけた
  (CLAUDE.md「事故の報告ほど、範囲を実測してから書く」の**原因版**)
  - **上の「run / job を引け」は、実測で不足だった**(2026-08-27、#481)。
    ⚠ 同じ症状(smoke が `in_progress` のまま **13 分**、job の timeout は **10 分**)で
    書いてあるとおり一次情報を引いたが、🔴 **`get_workflow_job` も
    `get_workflow_run` も同じ凍った記録を返した** ── run の `updated_at` は
    **`13:50:11` のまま**で、以後 1 度も更新されていなかった。
    ⚠ つまり「一次情報」と思って引いた先が**同じキャッシュ**だったので、
    2 度引いても**同じ嘘**が返る(1 回目と 2 回目のレスポンスが 1 バイト違わない、
    が唯一の手掛かりだった)。
    🔑 **効いたのは `list_workflow_jobs`(run の id で job を一覧する)**である ──
    こちらは **`completed / success`、13:57:23 終了**を返した(smoke は **6m36s**、
    timeout の内側)。
    🔑 **だから引き方を 1 つ増やす:同じ id を 2 度引いて同じなら、
    別の口(一覧)から引き直す。**
    ⚠ そして**タイムアウトを超えて見えることを「異常の証拠」に数えない** ──
    2026-08-23 と今日で **2 度**、それが「止まっている」という確信を強めた。
    ⚠ 今日は危うく「自分の PR が CI を 10 分の門にぶつけた」と読み、
    **落ちてもいない smoke を分割しかけた**(#480 の実測 7m14s と並べていれば
    余裕は読めたのに、超過の見かけが先に立った)

- **落ちた job を再実行すると、唯一の証拠が消える**(2026-08-29、#561)。
  間欠の赤を「一度きりの flake」と読んで再実行し、緑にしてから調べ始めたら、
  `get_job_logs` は **`failed_jobs: 0`** を返した ── ⚠ **再実行はログを上書きする**ので、
  落ちた回の出力は**もうどこにも無い**。手元に残っていたのは、私が issue へ写した
  **1 行の断片**だけだった(しかもそれで足りた ── 断片が無ければ調査ごと不能だった)。
  🔑 **再実行は「証拠を捨てる操作」である** ── 押す前に**落ちた job のログを丸ごと控える**。
  ⚠ CLAUDE.md は「flake に見えても 1 回だけ再実行してよい」と書いているが、
  **その 1 回の前に控える**ところまでが手順である。

- **再現しないのは「起きない」ではなく「条件を外している」ことがある**
  (2026-08-29、#561)。間欠の赤を **21 回**回しても出ず(通常 15 回 + 打鍵を遅くして 6 回)、
  「再現しない」と書きかけた。⚠ 遅くした群も出なかったのは、**等間隔で打つと
  debounce が一度も発火しない**からで、**打鍵を途中で 1.2 秒止める**形にしたら
  **1 発で出た**(対照群 = 止めない群は 0 件)。
  🔑 **「速い / 遅い」ではなく「間を空けたか」で条件を作る** ── 下書きを描く相手は
  **止まった瞬間**に描くので、等間隔の打鍵は**いちばん再現しない打ち方**である。
  ⚠ 一般形:**回数を増やす前に、条件の軸が合っているかを疑う。**
  21 回はコストであって証拠ではない
