# 検証の規律（`tests/**` を触るときのチェックリスト）

正本の 10 型は `CLAUDE.md` §6。ここはテストを書く・直すときの具体的な要点。

## 1. 検査が空振りする（緑が別の理由で成立している）

- **1.1 代替物に満たされる**:
  - 静的ファイル（`sw.js` / `icon.svg`）、DB の初期値 `0`、CSS の初期値、フォントの `.notdef`（豆腐）など、本体が壊れていても条件を満たす代替物に注意する。
  - 「無いときに何が返るか」を 1 度確かめ、代替物と区別できる条件（hash 付き生成物への参照、豆腐との画素比較など）で assert する。
- **1.2 成り立たない主張・未確認の期待**:
  - 「document 内に id 重複 0 件」のように user の入力次第で破れる条件ではなく、「`#slug` が本文ペインに当たること」のように実害を防ぐ条件を書く。
  - 「これが無いと壊れる」とコメントに書くなら、実際に外して壊れることを確認する。
- **1.3 範囲が広すぎてコメントや別領域に満たされる**:
  - ファイル全体や document 全体に対する部分一致（`toContain` / `indexOf`）は、解説コメントや別ペインの要素にマッチして常に真になりやすい。
  - CSS・YAML・ソース文字列を検査するときは**コメントを剥がし、対象の選択子・実行行・`[data-pkc-region]` の内側**に絞って検査する。
- **1.4 数えている対象が名前と違う**:
  - 空の状態（0 件）を作って実際に `0` が返ることを確かめる。
- **1.5 守る範囲が狭い / 上限しかない**:
  - 上限だけの検査は 0 バイトに縮む退行を通すため、下限とセットで置く。
  - ただし UI のボタン追加や CSS 規則追加で既存の件数・上限テストに当たったときは、**機能を削るのではなく、追加した事実に合わせてテスト側の件数・上限を更新する**。
- **1.6 画面の文言と実体の不一致**:
  - エラー文や案内文が指すボタン名・ラベルは、画面に実在するラベルと一致させる。
- **1.7 非同期化の空振り**:
  - 関数を `async` に変えたら、呼び出し側のテストすべてに `await` が付いているか `grep` で確認する（`await` なしだと Promise オブジェクトのまま素通りする）。
- **1.8 複合条件の片側**:
  - `A || B` のガードは、片方が `false` の状態でテストしないと他方に救われて空振りする。
- **1.9 検査の向きを反転させたとき**:
  - 「無いこと」の検査を「在ること」に書き換えたら、前処理と探索範囲も見直す。
- **1.10 期待値が実装と同じ盲点を持つ**:
  - 実装と同じ正規表現やヘルパーで期待値を作らない。独立した不変量または固定の期待値と突合する。
- **1.11 修正前後とも緑**:
  - バグ修正のテストは、修正前の実装に戻したときに必ず赤くなること（R1）を確認する。

## 2. 経路が一度も通っていない

- **2.1 未実行の分岐**:
  - happy-dom に無いブラウザ API の fallback 枝ばかり通っていないか確認する。重要な判定ロジックは純粋関数として切り出して直接テストする。
- **2.2 fixture の次元不足**:
  - テストデータの件数が 0 件や 1 件、ASCII のみ、最新スキーマのみに偏っていないか確認する（日本語入力・複数件・旧形式からの変換を含める）。

## 3. 変異試験の注意点

- **3.1 NOT-APPLIED と SURVIVED の区別**:
  - 置換対象の文字列が複数箇所（特にインデント違い）にないか確認し、置換前に元文字列の一意性をチェックする。smoke で見る変異は `build` を挟む。
- **3.2 作業ツリーの保護**:
  - 変異ハーネスは `try ... finally` とシグナルハンドラで必ず元ファイルを復元し、終了後に `git status` が clean であることを確認する。
- **3.3 振る舞いを直接見る**:
  - フラグや内部変数の値だけでなく、下流の出力（DOM・保存結果・描画結果）が変わることを assert する。

## 4. 観測点の選び方

- **4.1〜4.3 信号と対照群**:
  - 合計件数だけでなく集合の中身（どの要素が入れ替わったか）を見る。対照群（修正前・無効化時）で確実に差が出る計器を使う。
- **4.4〜4.7 測定範囲と再現性**:
  - 「ビルドできた」と「画面に届いた」の間の段を飛ばさない。フレークに見える失敗はテストを緩める前に製品側の競合（非同期の追い越し・DOM 再生成）を疑う。
