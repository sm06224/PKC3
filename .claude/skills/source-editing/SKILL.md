# ソースを書き換えるときの作法(PKC3)

## 🔴 1. 制御文字を書いたつもりが**生バイト**になる

`Write` / `Edit` に `\u0000` のような escape を書いても、**実際のファイルには生の
制御バイトが入ることがある**(2026-08-07 に 3 回踏んだ)。CLAUDE.md は生バイトを
禁じており、`tests/repo-hygiene.test.ts` が機械的に止める。

```bash
# 書き換えた直後に必ず走らせる(1 行も出ないのが正しい)
perl -ne 'while (/([\x00-\x08\x0b\x0c\x0e-\x1f])/g) { printf("RAW 行 %d: U+%04X\n", $., ord($1)) }' <file>
# 生バイトが入っていたら escape へ直す
perl -i -pe 's/\x00/\\u0000/g' <file>
```

⚠ **そもそも制御文字を避けられるなら避ける。** マスク用の目印なら**私用領域**
(``)を使う ── eslint の `no-control-regex` にも当たらない。
実例: `build/body-css.ts` の minify は `` で引用符区間を退避している。

## 🔴 2. template literal の中にバッククォートを書かない

`src/features/export/pkc3-html.ts` の `viewer()` が返すのは巨大な template literal である。
中の CSS コメントに ``` `.b` ``` のようなバッククォートを書くと**リテラルが早期終了し、
tsc が意味不明な位置でエラーを出す**(この file で **5 度**踏んだ)。

```bash
# リテラルの範囲にバッククォートが無いことを確かめる(0 行が正しい)
awk '/^  return `$/{s=1;next} /^<\/script>`;$/{s=0} s && /`/ {print NR": "$0}' \
  src/features/export/pkc3-html.ts
```

🔴 **2026-08-14 まで、この検査は 1 行も検めていなかった。** 開始アンカーが
`^const VIEWER = ` のままだったが、実体は `function viewer()` の中の `return` へ
移っている ── **当たらないので常に 0 行 = 常に合格**だった。
🔑 **「0 行だから安全」と読む前に、わざと 1 個入れて鳴ることを見る。**
実際に当てた対照群(2026-08-14):

```bash
sed '300i\  /* `.b` */' src/features/export/pkc3-html.ts > /tmp/inj.ts
# 新アンカー → 1 行(鳴る) / 旧アンカー → 0 行(死んでいる)
```

⚠ 開始アンカーの**出現数が 1** であることも併せて見る(`grep -c` が 0 なら、
その検査は何も見ていない)。これは CLAUDE.md §1「ガードは代替物で満たせない条件にする」の
**アンカー版**である ── file の構造が変わると、検査は落ちるのではなく**黙る**。

⚠ 同じ理由で、`${…}` を**文字として**書きたいときも工夫が要る ── **書かないのが正解**
(散文で言い換える)。

### ⚠ template literal の中では、正規表現のバックスラッシュを二重にする

`` `…replace(/\s+/g, ' ')…` `` と書くと `\s` が**リテラルに食われて `s`** になり、
「**文字 s の連続**」を置換する別物になる(2026-08-14、`build/office-wasm/io-layer-probe.mjs`
で実害)。⚠ **出力が変わらないことが多い**ので、走らせても気づけない ── この件は
たまたま窓の題名に `s` の連続が無く、**eslint が拾わなければ永久に露見しなかった**。

```bash
# template literal の中の一重バックスラッシュを洗う(意図的な一重が無いことを確かめる)
grep -n '\\[sdwbSDWB]' build/office-wasm/*.mjs
```

⚠ **注記そのものが罠を踏む** ── 2026-08-14 は、この罠をコメントに書く途中で
バッククォートを入れて構文エラーにした。

### ⚠ DOM の `append` は「追加」ではなく「移動」である

器を移す編集では、**元の `append` を消したか**を必ず見る。`ParentNode.append` は
`insertBefore` 意味論なので、既に別の親に付いているノードは**移動する**。
実例(2026-08-14): `src/adapter/ui/render/announce.ts` で「閉じる」を見出しへ移したのに、
下の `acts.append(close, mute)` が残っていて**元へ戻っていた**。
🔑 捕まえるのは包含の pin(`tests/adapter/announce.test.ts` の `head.contains(close)`)──
**移した先を assert する test を、移すのと同じ commit で書く**。

## 🔴 3. 整形ツールを既存 file に掛けない

`npx prettier` を掛けて `main.ts` を全面リフォーマット(302 行差分)し、リポジトリで
唯一 double quote の file にしたことがある。**diff が読めなくなり、次に触る PR が
全部 conflict する**。⚠ 触るのは**自分が足した行だけ**。

## ⚠ 4. 置換のアンカーに全角括弧・全角記号を含めない

この repo のコメントは日本語で、`(` `)`(全角)と `(` `)`(半角)が混在する。
コメント行をアンカーにすると照合に失敗し、**変異試験なら `NOT-APPLIED`、
一括置換なら黙って何もしない**。**コードの行**をアンカーにする。

## ⚠ 5. perl の `\Q…\E` は変数補間を止めない

```perl
perl -i -pe 's/\Q${BODY_CSS}\E/…/'   # ✗ $BODY_CSS が補間されて空になる
```
`\Q` はメタ文字の解釈を止めるだけで、**補間は止まらない**。`$` を含む文字列を
置換するなら **python を file に出して**やる(2026-08-07 に、これで A/B 計測が
「変異が当たっていないのに同じ数字」になった)。

🔑 **置換したら「当たったか」を必ず確かめる** ── 期待する字面が消えた / 現れたことを
`grep -c` で見る。**当たっていない置換は、何も起きていないのと区別がつかない**。

## ⚠ 6. Edit が失敗したら、まず全角・半角を疑う

`Edit` の `old_string` が「見つからない」とき、たいていは:
1. コメント中の全角括弧の食い違い
2. 直前の別の編集で内容が変わっている(`Read` し直す)
3. escape と実文字の食い違い(ツールが両方試すが、それでも外れることがある)

**アンカーを短く・コードだけにする**と通る。

## 🔴 7. 1 つのスクリプトに複数の編集を入れるなら、assert を**全部先に**済ませる

**症状**(2026-08-21): 1 本の python に「① action の handler を足す ② 型に 1 行足す」を
入れ、②の `assert` が(字下げ違いで)落ちた。⚠ **例外は書き込みの前に飛ぶので、
①の編集も一緒に消える** ── ところが typecheck は通る(型を足していないだけ)ので、
**「①は入った」と思ったまま次へ進む**。露見したのは `repo-hygiene` の
「受け手のいない `data-pkc-action` が無い」が落ちたときだった。

🔑 **順番を固定する: 全部の `assert` → 全部の `replace` → 1 回だけ `write`。**

```python
a = "…"; b = "…"
assert s.count(a) == 1, a          # ← 先に全部確かめる
assert s.count(b) == 1, b
s = s.replace(a, A, 1).replace(b, B, 1)
io.open(p, 'w', encoding='utf-8').write(s)   # ← 書き込みは 1 回
```

⚠ **落ちたスクリプトを「何も起きなかった」と読まない。** 部分適用が起きていないことは、
**書き込みが 1 回であること**でしか保証されない。
🔑 迷ったら、直後に `grep` で**当たったこと**を確かめる(編集の後条件を書く)。

## 検算の一括コマンド

```bash
# 書き換えたあと、commit の前に
perl -ne 'print "RAW: $ARGV 行 $.\n" if /[\x00-\x08\x0b\x0c\x0e-\x1f]/' $(git diff --name-only)
npm run typecheck && npm run lint
```

## 🔴 テンプレート literal の中で 2 度踏んだ(2026-08-17)

**HTML / script を `` ` `` で組む file(probe の中の page など)では、2 つが即死する。**

1. **バッククォート**を中のコメントに書くと、そこで文字列が終わる ──
   `lint` が `Parsing error: ',' expected` を出す(build も落ちる)。
   🔑 中のコメントでは **`` ` `` を使わない**(語を素で書く)
2. **`${'X'}` は「その場で評価される」** ── 差し込みの目印のつもりで書いても、
   テンプレートが組まれた時点で文字列 `X` になり、後段の
   `.replace(/\$\{'X'\}/g, …)` は**1 度も当たらない**。
   🔑 目印は **`__X__` のような素の字面**にして `replace` する

⚠ 2 の実害は**静か**である ── #225 の probe は `/work/INPUT`(拡張子なし)を
変換させており、**出力の名前が違うだけ**なので「変換が動かない」と読めてしまった。
🔑 **入力が実在することを、その場で一覧して確かめる**(`FS.readdir('/work')`)。


## ⚠ 全角の空白(U+3000)も生バイトで入る(2026-09-07)

制御文字と U+FEFF の走査は `tests/repo-hygiene.test.ts` に在るが、
**全角の空白はその分類の外**である ── 捕まえたのは **lint**
(`no-irregular-whitespace`)だった。

🔑 だから**書き換えたら lint も回す** ── `npm test` だけでは出ない。

```bash
npm run lint          # 見えない字はここで出る
grep -n $'\u3000' <file>   # 手で確かめるならこれ
```

⚠ 日本語の文面(お知らせ・マニュアル・test の fixture)を扱う日は必ず踏む。
コメントの中の例示に全角の空白を書きたくなったら、**言葉で書く**
(「`合計` の後ろの全角の空白」)か `\u3000` の escape にする。

## 🔴 `python3 -c "…"` の中のバッククォートは、**shell に食われる**(2026-09-13)

```bash
# 🚫 こう打った
python3 -c "
s = s.replace(old, '// ⚠ この file は `lend` しか使わない …')
"
```

出たのは `/bin/bash: line 11: lend: command not found` の **1 行だけ**で、
**python は最後まで走り、`ok` と印字した** ── そして file には

```ts
  // ⚠ この file は  しか使わない …
```

と、**語が 1 つ消えた**まま書かれた。⚠ lint も typecheck も test も**全部緑**
(注釈なので当然である)。

🔑 原因は **`"…"` の中では `` `…` `` が命令置換になる**こと。
⚠ 置換の結果は空文字なので、**消えたことが出力に出ない**
(唯一の手掛かりが `command not found` の 1 行で、しかも**成功の印字に紛れる**)。

🔑 **だから heredoc で渡す**(`<< 'PY'` … `PY`)── 引用符を `'PY'` にすれば
shell は中身を**1 文字も解釈しない**:

```bash
python3 - << 'PY'
s = s.replace(old, '// ⚠ この file が使うのは `lend` だけ …')
PY
```

⚠ この repo の注釈は**識別子をバッククォートで囲む**書き方なので、
**注釈を書き換えるときに必ず当たる**。
🔑 検算は 1 つ:**書き換えた行を `sed -n` で読み返す**(緑を見ても、消えた語は言わない)。

## 🔴 正規表現で「まとめて消す」書き換えをしない(2026-09-16)

⚠ CLAUDE.md §9 は「**index で切って繋ぐ書き換えをしない**」(2026-08-23、527 行が消えた)と
戒めているが、⚠ **正規表現でも同じことが起きる** ── しかも**もっと静かに**起きる。

実例:お知らせの既知表(`tests/adapter/announce.test.ts`)から **1 行**消すつもりで
貪欲な正規表現を当てたところ、🔴 **表ごと 558 行が消えた**。

```python
# 🚫 これで表の中身が丸ごと消えた(`.*` が次の `];` まで食う)
s = re.sub(r"\['2026-09-13-x'.*\];", "];", s, flags=re.S)
```

⚠ 今回は**構文が壊れて parse error** になったので気づけた ── 🔴 **壊れていなければ
緑のまま消えていた**(検査が消えれば、当然その検査は落ちない)。

🔑 **手順は 3 つで 1 組。どれか 1 つでも欠けると、この事故は静かに通る**:

1. **消す範囲を「開始と終了の両方」の文字列で名指しする**(正規表現の `.*` を使わない)
   ```python
   drop = "    ['2026-09-13-x', 'e84c7520'],\n"   # 行末の改行まで含めて 1 件に確定させる
   assert s.count(drop) == 1, s.count(drop)        # ⚠ 2 件なら止まる
   s = s.replace(drop, "")
   ```
2. **書き換えの前後で行数を数え、差が読みどおりか見る**
   ```python
   before = s.count('\n');  ...;  print('lines', before, '->', s.count('\n'))
   # 足し 1 / 引き 1 なら差 0。想定と違ったら**その場で止まる**
   ```
3. **`git diff --stat` を commit の前に読む** ── 558 行の削除は 1 行で見える

⚠ **`re.S`(`DOTALL`)を付けた瞬間が危険の合図**である ── `.` が改行をまたぐので、
**閉じの記号が次にどこへ出るか**を人間は読み切れない。
🔑 どうしても範囲で消すなら、**終端を否定文字クラスで留める**(`[^\]]*?` のように、
**食われては困る字を `.` に含めない**)。

### ⚠ これは「test file だけ」の話ではない

同じ形は**登記表・目録・既知リスト**すべてで起きる ── ⚠ どれも
「**消えても何も落ちない**」構造をしているので、気づく計器が**件数しかない**。
🔑 **表から行を消したら、その表の件数を assert している所が在るかを先に見る**
(この repo では `announce.test.ts` の `KNOWN` が `NOTICES.length` と等値である)。

## 🔴 `Write` の前に「その path は本当に無いか」を確かめる(2026-09-21、#1029 段 C)

⚠ `Write` は**既存 file を黙って丸ごと置き換える**。⚠ しかも成功の返事は
「新規作成」と「全面上書き」で**区別が付かない**ので、⚠ **消したことに気づけない**。

実例:段 C の実装で `tests/adapter/inspector-action-groups.test.ts` を
**新しい test だと思って `Write`** したところ、それは**段 B(4 日前)で作られていた
file** で、既に在った **4 件の検査(塊の名前の等値 / 操作が塊の外に漏れていない /
塊の間が CSS で広い / 切れ目は器が持つ)を消していた**。
🔑 気づけたのは `git log -1 -- <path>` を打ったからで、⚠ 打たなければ
**検査が 4 件消えたまま緑**である(CLAUDE.md §9「test file を切り落としても suite は緑」)。

🔑 **手順は 1 つ**:

```bash
# 🔑 `Write` を打つ前に。file が在れば history が出る(無ければ何も出ない)
git log -1 --oneline -- <path>; ls -l <path> 2>/dev/null
```

⚠ **「新しく作る」と思っているときほど打つ** ── 既存だと疑っているときは
そもそも `Edit` を使うので、事故は**新規だと思い込んでいる側**でしか起きない。
🔑 復元は `git show <sha>:<path>`(この件はそれで原文を取り出し、新しい検査と統合した)。
