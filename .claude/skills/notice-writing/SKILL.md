# お知らせを書く(PKC3)

user 指示 2026-08-07:
> 「**PKC3 にも PKC2 のようにお知らせポップアップをつけてください /
> お知らせ掲載内容は過去のお知らせとして、最大 10 件を…ヘルプ画面から
> 参照できるようにしてください**」

## 置き場

| もの | 場所 |
|---|---|
| 登記表(本体) | `src/features/notice/notice-log.ts` の `NOTICES` |
| 起動時の帯 | `src/adapter/ui/render/announce.ts` |
| 過去の一覧 | `src/adapter/ui/render/help.ts`(ヘルプの面) |
| 既読(id の集合) | `src/adapter/platform/notice-store.ts` |
| **落ちた分の受け皿** | `CHANGELOG.md`(repo の根。**アプリには入らない**) |
| 決まりの test | `tests/adapter/help-pane.test.ts` / `tests/adapter/announce.test.ts` / `tests/docs-parity.test.ts` |

## 足し方

`NOTICES` の**先頭**に 1 件足す。それだけ。表示件数を切るのは `recentNotices`
**1 か所**なので、面ごとに `slice` を書かない。

```ts
{
  id: '2026-08-08-flags-and-help',   // YYYY-MM-DD-slug
  title: 'フラグ画面とヘルプ画面ができました',
  items: [
    '開発中の切り替えは、これまで URL に直接打ち込む必要がありました。左の列の「フラグ」から切り替えられます。',
  ],
},
```

## 🔴 上限に達しているときは、**落とす分を CHANGELOG へ移す**

登記表は `NOTICE_KEEP_MAX`(**30 件** = `NOTICE_SHOW_MAX` と同じ)で頭打ちで、
**古い方から静かに落ちる**。
⚠ 受け皿を作る前は、**配った 42 件のうち 22 件が既に消えていた**
(git の履歴からしか読めない状態だった。2026-08-18 に復元して `CHANGELOG.md` にした)。

🔴 **2026-08-29 に 20 → 10 へ揃えた**(#596 E)。⚠ それまでは表示の 2 倍を持っており、
理由は「**原本は残す**」だったが、その役目は 2026-08-18 から `CHANGELOG.md` が担っている
── 11 件目より後ろは**原本でもなく画面にも出ない、配るだけの重り**だった(実測 10 件)。
🔑 揃えたので不変条件が 1 つ増えた:**登記表 = 画面に出るもの**
(`announce.test.ts` の「登記表と画面のずれ」が 0 件を見る)。

🔴 **2026-09-08 に 10 → 30 へ増やした**(#751)。⚠ 実測(2026-09-06)で在庫 10 件が
**全部 2 日ぶん**で、9 月 5 日だけで **11 件**が押し出されていた ── つまり
「**昨日の変更を読み逃したら、アプリの中には二度と出てこない**」状態だった。
⚠ この skill は **2026-09-12 までこの数を 10 のまま書いていた**(4 か所)──
数を 2 か所に書くと、片方だけが腐る(CLAUDE.md §7)。
🔑 **迷ったら定数を読む**:`src/features/notice/notice-log.ts` の `NOTICE_SHOW_MAX` が正本で、
この表の値はその写しである。

**足すときの手順は 3 つで 1 組**:

1. `NOTICES` の**先頭**に 1 件足す
2. **30 件を超えるなら、いちばん古い 1 件を削る**(⚠ 超えたまま置くと、
   その 1 件は**アプリのどこからも読めない**ので test が落ちる)
3. 🔴 **削った 1 件を `CHANGELOG.md` に残す** ── 日付の節に `### 題名` +
   items を箇条書きで。**同時に `tests/docs-parity.test.ts` の `DROPPED` へ題名を 1 行足す**

⚠ 3 を忘れると **CI が落ちる**(`docs-parity` が「登記表 + 落ちた分 = CHANGELOG」を
**等値**で見る)。⚠ 数だけで縛ると**受け皿が登記表のコピーでも通る**ので、
`DROPPED` は**身元の既知リスト**にしてある(`announce.test.ts` の `KNOWN` と同じ作法)。
⚠ 新しく足した 1 件も CHANGELOG に要る(**落ちる前から**入れておく ──
落ちてから足す運用にすると、落とした人が気づかない)。

🔴 **`KNOWN`(`tests/adapter/announce.test.ts`)から行を落とすときは、その行に付いていた
注記も一緒に消す**(2026-09-02)。落とした行の「⚠ 訂正(…)」「⚠ この entry は main に在る…」
という注記だけが**185 行**残り、10 行の表を覆い隠していた ── 訂正の経緯は CHANGELOG と
git の履歴に在るので、表には**いま在る行の注記だけ**を置く。

⚠ **CHANGELOG の文面は書き換えない。** 誤りが見つかったら、その行の下に
`⚠ 訂正(日付)` を足す ── 何を配ったかと、何が正しいかの両方を残す。

## 🔴 「もう配ったか」は **main** で見る(2026-09-08。user 報告で判明)

> 「**そもそもマニュアル分割が dev 版に反映されてないが? ヘルプのお知らせにも載ってない**」

既に配った entry へ item を足しても、**帯には 1 行も出ない** ──
`unreadNotices` は **id の集合**だけで既読を見る(中身を見ない)。
だから足す前に必ず「**この id はもう配ったか**」を判定する。⚠ そこを間違えた:

| | 何に答える計器か |
|---|---|
| 🚫 `git show v3.2.0:src/features/notice/notice-log.ts \| grep "id: "` | **本番の tag に在るか**だけ |
| ✅ `git log --oneline origin/main -S"<id>" -- src/features/notice/notice-log.ts` | **main に入ったか** = `/dev/` に配ったか |

⚠ 🔴 **`main` ではなく `origin/main` と書く**(2026-09-08 に踏みかけた)── session の作業ツリーは
feature branch だけを持っていることがあり、そこで `git log main …` を打つと
**`unknown revision` か空**が返る。⚠ **空 = 「未配布」に見える**ので、
この誤りは**当の間違いをそのまま再生産する**。🔑 打ったら `origin/main` の側で
1 件は当たることを確かめる(全部空なら、引く先を間違えている)。

🔑 **user が読んでいるのは `/dev/`(main HEAD)である。** merge した瞬間に配布済みで、
本番の tag は関係ない。⚠ 2026-09-07〜08 に、この取り違えで**既配布の 3 件**へ
新しい話を足した(`2026-09-06-help-manual-first` / `-primary-action` /
`-table-convert-touch` ── どれも 2026-09-06 に main へ入っていた)。
⚠ 誤りは**「未配布だから束ねてよい」という理由づけ**の形で 8 か所に増殖していた ──
同じ観測点を写して回したためである。

🔑 **判定は 2 択で、途中が無い**:

- **main に入っていない** → その entry の文面を直してよい(`KNOWN` の digest を pin し直す)
  - 🔴 **2026-09-15(#930)に、この判定を機械へ寄せるのをやめた。** `KNOWN` には
    「配布済み」を表す 3 つ目の印が在ったが、**手で付ける物なので merge の瞬間から腐る**
    ── 実測で **30 件中 27 件**が「まだ配っていない」と**嘘を言っていた**(危ない側)。
    🔑 いまは印が無く、文面が変わると **`git log … -S"<id>"` の 1 行がその場に印字される**。
    ⚠ **打つのは人である** ── 計器は「配ったかどうか」を知らないので、言わない
- **main に入っている** → 🔴 **新しい id を作る。** 枠が満杯なら
  **いちばん古い 1 件を落とす**(user 裁定 2026-09-06「古い順に出す」)。
  ⚠ 「同じ主題だから束ねる」は**配る前だけの手**である

⚠ 既配布の entry から**行を消す**のは、`announce.test.ts` の docstring の②
(**届かなくてよい訂正**)に当たる ── 既読の user には届かないと認めたうえで、
**これから読む人に嘘を出さない**ときだけ使う(例: 新しい波で偽になった 1 文)。

## 書式(数で持つ ── 散文の規律にしない)

| 決まり | 値 | 定数 |
|---|---|---|
| 帯・ヘルプに出す件数 | 30 件 | `NOTICE_SHOW_MAX` |
| 登記表に残す件数 | **30 件**(= 表示件数) | `NOTICE_KEEP_MAX` |
| 1 件の項目数 | 6 まで | `NOTICE_ITEMS_MAX` |
| 1 項目の字数 | 4〜120 | `NOTICE_ITEM_CHARS_MIN/MAX` |

⚠ PKC2 は上限を持たず、**1 entry 22 項目・1 項目 200 字超**の壁ができた。
「短く書こう」という注意書きは効かなかったので、**数で持つ**。

## 🔴 禁止

1. **記法を書かない**(`**強調**` / `` `コード` `` / `[題名](url)`)。
   描画は `textContent` なので、**アスタリスクがそのまま見える** ── PKC2 が
   実際にそうなっていた。test が落とす。
2. **「これから〜します」を書かない。** 掲示した約束は取り消せない ── PKC2 は
   掲示済みの挙動が後の既定変更を縛った。**「〜できるようになりました」**だけ書く。
3. **起きていないことを書かない。** user は同じ画面で嘘に気づく。
4. **id を変えない。** id は**既読の鍵**である。直すなら文面だけ ── id を変えると
   「読んだお知らせ」がもう一度出る。
5. **日付の field を作らない。** 日付は id から引く(`noticeDate`)── PKC2 は
   `date` を宣言して**一度も読まなかった**。
6. 🔴 **内部の語を書かない**(2026-09-21)。実例:題名「型ごとの 6 節に組み替わりました」
   →「6 つの節に組み替わりました」へ直した。「型」「領域」「realm」「区画」は**設計の語彙**
   であって画面の語彙ではない ── `src/features/ui-terms.ts` の `BANNED_TERMS` を
   `notice-log.ts` にも当てる門(`tests/features/ui-terms.test.ts`)が在るので、
   使わない語を書くとその場で落ちる。

## 文面の型

- **何ができるようになったか**を、user の言葉で 1 文
- **どこにあるか**を書く(「左の列の『フラグ』から」)── 探させない
- 詳しい話はマニュアルに書く。お知らせは**気づかせる**のが仕事

## お知らせを足す PR でやること

1. `NOTICES` の先頭に 1 件足す
2. **マニュアルも同じ commit で直す**(`docs/manual.md`)── お知らせは気づかせる
   だけで、正本はマニュアルである。`tests/docs-parity.test.ts` が食い違いを落とす
3. 🔴 **決まりの test を 4 つとも回す** ── `tests/adapter/announce.test.ts` /
   **`tests/adapter/help-pane.test.ts`** / `tests/docs-parity.test.ts` /
   🔴 **`tests/features/manual-refs.test.ts`**

   ⚠ **2026-09-13 に、3 つのうち 2 つしか回さずに CI を赤くした。**
   直した後に `announce`(文面の pin)と `docs-parity`(CHANGELOG との等値)だけを
   回して緑を見たが、**項目数と字数の門は `help-pane.test.ts` に在る** ──
   1 件に 7 項目書いていたことに、CI で落ちるまで気づかなかった。
   🔑 **上の表は 3 つ並べて書いてあった**(情報は在った)── 足りなかったのは
   「**3 つとも**回す」という手順のほうである。⚠ 迷うくらいなら `npm test` を回す。

   🔴 **同じ日に、その「3 つ」でも足りなかった**(2026-09-13。**1 日で 2 度**)。
   ⚠ 落ちたのは **4 つ目**(`manual-refs`)で、原因は**どちらの回も同じ** ──
   マニュアルに **`(→「節の名前」)`** と書いたが、**その節が無かった**
   (1 度目「アプリの一覧」/ 2 度目「アプリの一覧を並べ替える」。
   実在は「ランチャー」と「指で並べ替える(並べ替えモード)」)。

   🔑 **合図は「お知らせを足したか」ではなく「`docs/manual.md` を触ったか」である** ──
   だから条件をそちらへ移す:**マニュアルを 1 文字でも書き換えたら `manual-refs` を回す。**
   ⚠ 節の名前は**記憶で書かない** ── `grep -n '^#\{2,4\} ' docs/manual.md` で
   実在を見てから書く(1 秒である)。
   ⚠ この門は**増える側しか見ない**わけではない ── 節を**消した / 改名した**ときも
   落ちるので、「参照を足していないから関係ない」と読まないこと。

⚠ **user に見える変更なのにお知らせを書かない**、が既定の失敗である。
UI・挙動・既定値が変わったら 1 行足す。

### 🔴 足す前に、既存 spec が「最新のお知らせの題名」を pin していないか grep する(2026-09-21)

登記表の**先頭**に 1 件足すと、`最新のお知らせ` を等値で見ている spec の pin が
壊れる(実例: `system-toc.smoke.spec.ts` が前回の最新題名を等値で持っていた)。

🔑 足す前に `grep -rn "<いままでの最新の題名>" tests/` を打ち、当たった pin を
**同じ commit で新しい題名へ**張り替える。


## 🔴 お知らせに**鍵の綴り**を書かない(2026-09-04、#689 の動線レビュー)

書きかけた字:

> 「その窓で読み込み直す(**F5**)と…」「**Ctrl+D** で作るブックマークも…」

⚠ **スマホに `F5` も `Ctrl+D` も無い**(2026-09-03 に指で触る端末の手当てを
配ったばかりで、user はスマホで読む)。⚠ Mac では `Command+R` / `Command+D` である。

🔑 **起きることで書く** ── 「**読み込み直しても**、いま見ているノートが出ます」
「**ブックマークに登録すると**、いま見ているノートを指します」。

⚠ 画面のボタンは `applyShortcutHints` が鍵の字を組む(mac では `⌥`)ので
この問題を持たないが、**お知らせは素のテキスト**なので**そのまま出る**。

### ⚠ 同じ理由で「戻る」も曖昧である

PKC には左の列に **`‹ 戻る`(前に見ていたノートへ戻る)**が在るので、
「戻る」とだけ書くと**2 つのものを指す**。ブラウザのほうを指すなら
**「ブラウザの『戻る』」**と書く。

### ⚠ カードの並びは「読む順」で決める

同じ日に 2 件足すと、登記表の並び = 画面に出る順である。
⚠ 「**A のアドレスが…**」を「**A が開けるようになりました**」より先に出すと、
1 枚目を読んだ user は **A が何なのか分からない**。
🔑 **「できるようになったこと」が先、「その細部」が後**。
