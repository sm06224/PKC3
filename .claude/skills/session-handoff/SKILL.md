# セッション引き継ぎ（PKC3）

> **user 指示（PKC2 から継承）**:
> 「セッション引き継ぎはセッション引き継ぎ用の PR を作成して、その PR を渡すことで完成させます。PR には引き継ぎ事項のほかに最初の仕事の有無を含めてください」

## 1. 最初の仕事の有無（PR 本文の冒頭に必須）

| 区分 | 書き方 |
|---|---|
| **あり** | 「**最初の仕事: あり**」+ 何を・どこから・完了条件。次セッションは確認せず直ちに着手する |
| **なし（指示待ち）** | 「**最初の仕事: なし。user の指示を待つ**」 |
| **裁定待ち** | 「**最初の仕事: なし。user の裁定待ちが N 件**」+ 具体的な選択肢と推薦 |

## 2. 引き継ぎ PR・doc に入れるもの

1. **現在の状態（実測してから書く）**:
   - `main` の HEAD（SHA と 1 行要約）、open PR の有無、作業ブランチの状態。
2. **着地したもの**:
   - このセッションで `main` に入った PR 番号・SHA・1 行要約。
3. **残件（正確に書く・隠さない）**:
   - 🔴 **未実装の項目やサブ項目を「完了 `[x]`」と偽ったり、勝手に間引いて台帳から消してはならない**。
   - 束（バンドル）の中で一部でも未実装の項目がある場合は、どの項目が未実装かを明記して残件に残す。
4. **裁定待ち**:
   - 本当に user の判断が必要な項目のみ（不具合修正や合意済み項目の UI 調整を「過去の決定に触れる」として裁定待ちに逃がさない）。

## 3. 手順

1. **状態を実測する**: `git log --oneline -5`、open PR、CI の状態、未 push の有無を確認する。
2. **知見の整理（必要な場合のみ）**: 新しい技術的罠があった場合のみ `.claude/skills/knowledge-reflection/SKILL.md` の上限規律に従って簡潔に反映する（反省文の追記はしない）。
3. **引き継ぎ doc を書く**: `docs/development/session-handoff-YYYY-MM-DD.md` を作成し、PR 本文からリンクする。
4. **導線の検算**:
   doc や PR 本文に書いた `.claude/...` パスや `#NNN` が実在するか確かめる:
   ```bash
   grep -hoE '(PKC2:)?\.claude/[A-Za-z0-9./_-]*' <file> | grep -v '^PKC2:' \
     | sed 's/[.,)。]*$//' | sort -u \
     | while read p; do [ -e "$p" ] && echo "ok   $p" || echo "無い $p"; done
   ```
5. **commit → push → PR 作成（または merge）** し、作業ツリーが clean であることを確かめる。
