## 「無い」と書く前に、その file を最後まで読む

- **型**:`grep` は当たったのに、file の冒頭だけを読んで「無い / 未着手」と書いた。
- **見分け方**:issue や索引に「無い」と書いた根拠が、file の**冒頭の要約**だけではないか。
- **直し方**:`wc -l` で行数を見て、最後まで読んだかを問う。中身を足したら冒頭の要約も直す(次に読む人が同じ誤読をする)。

🔴 **`grep` は当たったのに、`file` を最後まで読まなくて外した**(2026-08-29)。
⚠ 同じ日に **8 件**「在る物を無いと思いかけた」が、**7 件は 1 grep で止まり、
この 1 件だけ止まらずに issue へ嘘を書いた**。差は 1 つ ──
**file を最後まで読んだかどうか**である。
実例:`.claude/agents/pkc3-ux-reviewer.md` の **先頭 12 行(`description`)だけ**を
読んで「動線の欠陥しか見ていない = 未着手」と書いた。⚠ 実際は **148 行あり、
その 3 分の 1 が当の「良くできる所を探す」節**だった。
🔑 原因は**冒頭が古かった**こと ── `description` は founding のままで、
**中身だけが育っていた**。⚠ 「その file が何をするか」を**冒頭の要約で判断しない**。
🔑 機械的な検算:**「無い」と書く前に、その file の行数を見て、最後まで読んだかを問う**
(`wc -l` は 1 秒である)。⚠ そして**育てた側の責任**でもある ──
中身を足したら**冒頭の要約も直す**(直さないと、次に読む人が同じ誤読をする)

## issue の本文が古い(着手の前に 1 件 1 grep)

- **型**:起票した後も issue の本文は古くなる。「まだ在る仕事」の顔をしているので、古いほど信じられる。
- **見分け方**:着手しようとした issue の本文の主張(「無い」「0 件」「未着手」)が、いまの実装と食い違う。
- **直し方**:着手の前に本文を 1 件 1 grep で検算する。検算して分かったことは**その場で issue に書く**。

🔴 **同じ腐り方は、既に open な issue にも起きる**(2026-08-22。1 巡で **5 件**)。
上は**起票のとき**の規律だが、⚠ **起票した後も本文は古くなる** ── しかも
issue は「まだ在る仕事」の顔をしているので、**古いほど信じられてしまう**。
実測(open issue を 1 件 1 grep で当たった結果):
① **#292** 段①は**着地済み**なのに `[ ]` の顔で open
② **#251**「変換が **1 つもありません**」→ **4 種のうち 3 種が実装済み**
③ **#178**「別窓の書込は黙って**消える**」→ **履歴に残っていた**(CLAUDE.md「検証の規律」§4)
④ **#180** 台帳の落差の表「探す = 題名の絞り込みのみ」→ **全文検索は在る**
(ほか **8 件**が既に実装済みだった)
⑤ **#179** 原因が「タブか窓か」→ 実測すると「**誰が開いたか**」
🔑 **無い物を作りかけたのが 5 回**である。着手の前に**その issue の本文を
1 件 1 grep で検算する** ── 「着手する」は「本文を信じる」ではない。
⚠ 検算して分かったことは**その場で issue に書く**(次に読む人のために ──
自分の頭の中に置くと、同じ 5 分をもう一度誰かが払う)

## 直したのに閉じていない

- **型**:仕事そのものは終わっているのに、issue が open のまま残る。
- **見分け方**:PR を merge した後も issue が open。実体も test も main に在る。
- **直し方**:直した PR を merge したら、その場で issue を閉じる。

🔴 **腐り方はもう 1 つある ── 直したのに閉じていない**(2026-08-24、#160)。
⚠ こちらは**本文が古い**のではなく、**仕事そのものが終わっている**。
#160 は 2026-08-23 に着地(PR #351、実体も test も main に在る)していたのに
open のままで、**私は今日そこから着手しかけた**。
🔑 **直した PR を merge したら、その場で issue を閉じる** ── 閉じ忘れた issue は
「まだ在る仕事」の顔で台帳に残り、⚠ **同じ物を二度作らせる**
(「無い物を作りかけた」の別経路である)

## 着地の記録が PR にしか無い

- **型**:PR には丁寧に書いたが、issue に 1 行も戻していない。
- **見分け方**:issue のコメントが 0 件 / 本文が「作ります」で止まっているのに、PR は merge 済み。
- **直し方**:merge の直後に issue へ観測点つきで 1 行書き、閉じるか残りを書き直す(後述「判定は 1 つ」)。

🔴 **3 つ目の腐り方 ── 着地の記録が PR にしか無い**(2026-08-27。**1 日で 3 件**)。
⚠ 上の 2 つは「本文が古い」「閉じ忘れ」だが、こちらは
**issue に 1 行も戻ってきていない**形である ── PR には書いたので
「書いた気」になり、issue を読む人には**未着手にしか見えない**。
実測(棚卸し 1 巡):
① **#426** 段①が着地したのに**コメント 0 件**で、本文の「PKC3 は 0 件」が嘘のまま
② **#433**「測る口を**作ります**」で止まっていたが、**PR #435 で配り済み**
③ **#403**「**次の PR で直す**」の 2 件が、**既に直っていた**
🔴 **3 件とも、そこから着手しかけた。**

## 索引そのものが腐る

- **型**:「止まっているものの一覧」(#604)のような索引 issue は、本体より速く腐る。
- **見分け方**:索引に載っている推薦・待ちが、本体 issue の現状(閉じた / 配り済み)と食い違う。
- **直し方**:索引を更新するときは、`list_issues` の open 一覧と 1 件ずつ突き合わせてから投稿する。

🔴 **4 つ目の腐り方 ── 索引そのものが腐る**(2026-09-09。1 回の更新で 3 行)。
⚠ 「止まっているものの一覧」(#604)のような**索引 issue** は、
**本体より速く腐る** ── 本体が動いても索引は誰も直さないからである。
実測(1 回の突き合わせ):
① **#811** は「止める」を**推薦したまま**載っていたが、実際は
「取れなくても開く」で**配り済み**だった(推薦と実装が正反対)
② **#678 #679** は**閉じている**のに「着手してよいか」として載っていた
③ **#681** は**段①② が着地済み**なのに「足しますか」のままだった
🔑 **索引を更新するときは、必ず `list_issues` の open 一覧と 1 件ずつ
突き合わせる** ── 足す行だけ見て投稿しない(私は 1 度目にそれをやり、
同じ turn の 30 分後に 2 件の腐りを見つけて出し直した)。
⚠ 索引の腐りは**本体の腐りより害が大きい** ── user はそこだけを読んで
決めるので、**間違った推薦のまま裁定を求めることになる**。

## 索引に「無い」と書いて、実は在った

- **型**:索引を書くその場で、`ls` を打たずに「まだ〜していません」と書いた(書いた嘘)。
- **見分け方**:索引・issue に「まだ〜していません」「無い」「0 件」と書いた文。
- **直し方**:書く前にその物を `ls` / `grep` で 1 回引く(1 秒)。

🔴 **5 つ目の腐り方 ── 索引に「無い」と書いて、実は在った**(2026-09-16)。
⚠ 上の 4 つは*古い / 閉じ忘れ / 戻していない / 索引が追いつかない*だが、
こちらは**その場で書いた嘘**である。#604 に「#529 の設計 doc は**まだ書けて
いません**」と書いたが、🔴 **`docs/development/whiteboard-bucket-design-2026-08.md`
が 19 日前から 159 行で在り**、先頭に「user の裁定待ち」と書かれたまま止まっていた。
⚠ **自分が書いた doc を、自分で「無い」と書いた** ── 覚えていないのではなく、
**索引を書くときに `ls` を 1 度も打たなかった**。
🔑 検算は 1 秒:**「まだ〜していません」「無い」「0 件」を索引に書く前に、
その物を `ls` / `grep` で 1 回引く。**
⚠ そして**待ちが 19 日空振りしていた**ことにも、索引を書いた日まで気づいていない ──
「裁定待ち」と書いてあると、**待っている側も待たせている側も検算しない**
(上の「待ちが 1 回でも空振りしたら、待つのをやめて doc 自身の推薦から着手する」の
実例である)。

## 判定は 1 つ ── 「その issue を読んだ人は、いま何をすべきだと思うか」

- **型**:上の 5 つの腐り方に共通する、台帳の読み手から見た判定。
- **見分け方**:PR 本文にどれだけ丁寧に書いても、issue に戻していなければ台帳は動かない。
- **直し方**:merge の直後に ①issue へ観測点つきで 1 行 ②閉じるか、残りを書き直す、までを 1 つの作業にする。

🔑 **判定は 1 つ:「その issue を読んだ人は、いま何をすべきだと思うか」。**
⚠ PR 本文にどれだけ丁寧に書いても、**issue に戻さなければ台帳は動かない** ──
merge の直後に **①issue へ観測点つきで 1 行 ②閉じるか、残りを書き直す**
までが 1 つの作業である(⚠ 「あとで棚卸しする」は、その棚卸しが
**同じ 5 分をもう一度払う**ことを意味する)

## 裁定を「待っている」ものも起票する

- **型**:裁定待ちの項目を doc の中に置いた(どこにも積まれない)。
- **見分け方**:doc の形で「`[ ]` を `[x]` にして返してください」と並べた一覧。open issue を数えても残件が見えない。
- **直し方**:待っている項目も issue にする。待ちが 1 回でも空振りしたら、待つのをやめて doc 自身の推薦から着手する。

🔴 **裁定を「待っている」ものも起票する**(2026-08-15。user 指摘で判明)。
移植候補の doc(削除済み。中身は #180 と個別 issue へ移した)は **22 件**を
「`[ ]` を `[x]` にして返してください」の形で並べた doc だが、**11 日間 1 件も
動かず**、その間 open issue を数えても PKC 本体の残件は**2 件しか見えなかった**
(16 件が Office)。⚠ **doc に置いた仕事は、待っている限りどこにも積まれない** ──
「裁定待ち」は状態であって、**台帳から消えてよい理由ではない**。
🔑 待ちが 1 回でも空振りしたら、**待つのをやめて doc 自身の推薦から着手する**
(止まっているほうが害が大きい)。台帳は #180

## 実体を作ってから導線を書く(番号の書き順)

- **型**:作る前の issue の番号を、コメントや本文に書いた(壊れたポインタ)。
- **見分け方**:「#NNN へ切り出しました」「#NNN に起票しました」と書く文を、`issue_write` より先に書いた。
- **直し方**:番号を返す呼び出しを先に単独で出し、返った番号を使って書く。番号が要るときはリンクを書きたくなった瞬間に先に stub を作る。

⚠ **実体を作ってから導線を書く。** 逆順は壊れたポインタになる(#69 で 1 度失敗)

⚠ **2026-08-23 に 2 度目**:issue のコメントに「**#344 へ切り出しました**」と書いてから
#344 を作った。**番号はたまたま一致した**が、間に誰かが 1 件起票していれば
**別の issue を指す壊れたポインタ**になっていた。
🔑 **「たまたま当たった」を「大丈夫だった」と記録しない** ── 記録すべきは
**手順が逆だったこと**である(結果が無事だと、次も同じ順で書く)

🔴 **2026-09-16 に 3 度目。しかも「次も同じ順で書く」と書いた当の場所を踏んだ** ──
#971 のコメントに「**#999 に別立てで起票しました**」と書いてから #999 を作った
(⚠ **また番号は一致した**)。
🔑 **2 度書いた戒めが効かなかったのだから、文言を 3 か所目にしない ── 手順を変える。**
⚠ 逆順になる理由は毎回同じである:**長い本文を書いている最中にリンクが要る**ので、
「後で作ればいい」と**書きながら決めてしまう**(起票しに行くと、書いている文が途切れる)。
🔑 だから**順番を固定する**:**リンクを書きたくなった瞬間に、先に起票する。**
⚠ 中身が固まっていなくてよい ── **題名だけの stub を作って番号を取り**、
本文は後から `issue_write` の `update` で入れる(**番号は 1 度取れば動かない**)。
⚠ そして**書いた後に検算する**:投稿した本文の `#NNN` を**全部引いて**、
題名が意図どおりかを見る(⚠ 「たまたま合っていた」と「合わせた」は別である)
