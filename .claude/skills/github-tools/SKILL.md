# GitHub を道具として叩く(PKC3)

> ⚠ **これは PR の着地とは別の主題である**(2026-09-05 に `pr-landing` から切り出した ──
> 1 枚 1 主題)。ここに在る罠は**起票・棚卸し・調査**でも同じように踏む。
> 着地の手順そのものは `.claude/skills/pr-landing/SKILL.md`。

## 0. 🔴 何で叩くか

- 🚫 **`https://api.github.com` への直 curl は塞がれている** ── `GH_TOKEN` は env に
  在るのに、返るのは `{"message": "GitHub access is not enabled for this session. ..."}`
- 🚫 **`gh` CLI は無い**(2026-09-05 に再確認: `gh: command not found`)
- 🟢 **MCP の github tool を使う**(`actions_list` / `pull_request_read` /
  `issue_write` / `add_issue_comment` / `list_workflow_jobs` ...)

⚠ **「読む手段が無い」と書く前に、MCP tool の一覧を見る。**
🔑 それでも無いなら、**無い経路を数えて書く**(CLAUDE.md §4「取れないで終わらせる前に、
取り方を数え上げる」)。

## 🔴 監視ループは「想定外の応答」を必ず 1 行吐かせる

⚠ 上の塞がった curl を **poll ループに入れて 6 分捨てた**(2026-08-13)。
書いたのはこういう形:

```bash
st=$(curl … | python3 -c "…print(d.get('status'), d.get('conclusion'))")
case "$st" in
  "completed "*) echo "CI 完了"; exit 0 ;;
  poll-error)    echo "poll-error" ;;      # ← ここに来ない
esac
```

エラー JSON にも `status` キーが**無いだけで parse は通る**ので、
`None None` が出て**どの case にも当たらず、黙って次の周回へ行く**。
⚠ **「何も鳴らない」が「まだ走っている」と見分けられない。**
🔑 poll ループは **想定外の応答を必ず 1 行吐かせる**(`*) echo "想定外: $st" ;;`)。
「成功の合図だけを grep する監視は、crash と hang に対して沈黙する」の同型である。


## 🔴 引いた識別子と状態は、書く前に確かめる

規律の正本は `CLAUDE.md`(「渡す URL は、渡す前に実在と中身を確かめる」/
「同じ検算を『状態』にも当てる」)。手順としてはこれだけ:

- **番号**(PR / issue / run / commit / tag)は **branch や id から引いてから**書く ──
  「その番号を、いま自分はどこから読んだか」を言えないなら書かない
- **「着地した」「済んだ」は観測点を 1 つ挙げてから**書く
  (`pull_request_read` の `merged` / `origin/main` の log)

🔴 **「引く」を面倒にしない ── 1 回で出る形を持っておく**(2026-09-14。
issue #854 の段①② に **#869 / #877** と書いたが、**2 つとも実在しなかった**)。
⚠ 私は「調べれば分かる」と思って**調べずに書いた** ── 引くのに何を打つか
**その場で考えないといけない**と、書くほうが速いので書いてしまう。
🔑 だから**打つ物を決めておく**:

```
# その issue / 主題に紐づく merged な PR を全部出す(番号と題名が 1 回で並ぶ)
search_pull_requests  q: "repo:sm06224/PKC3 is:pr is:merged <番号や語> in:title"

# branch から引く(いま自分が押した PR を確かめるとき)
list_pull_requests    head: "sm06224/<branch>"  state: "all"
```

⚠ **commit の題名から引けないことがある** ── この repo の merge には
`(#NNN)` が付く物と付かない物が混ざっているので、`git log --grep` では
**番号の無い行が返って空振りする**(実際この日それで 1 手溶かした)。
🔑 番号の出どころは **GitHub 側**に置く。

### 🔴 **まだ無い番号を書かない ── 実体を作ってから導線を書く**(2026-09-13 で **3 度目**)

⚠ 上の 2 つは「**在る物**を引いてから書く」話だが、こちらは
**これから作る物の番号を、作る前に書いてしまう**形である。

| いつ | 何をしたか |
|---|---|
| 2026-08-04(#69) | 実体を作る前に導線を書き、**壊れたポインタ**にした |
| 2026-08-23 | コメントに「**#344 へ切り出しました**」と書いてから #344 を作った ── **たまたま一致** |
| 🔴 2026-09-13 | コメントに「**#878 に起票しました**」と書いてから #878 を作った ── **またたまたま一致** |

🔴 **2 度「たまたま当たった」ので、2 度とも実害が出ていない。** ⚠ だから止まらない ──
**結果が無事だと、次も同じ順で書く**(記録すべきは結果ではなく**手順が逆だったこと**)。
⚠ 間に誰かが 1 件立てていれば、**別の issue を指す壊れたポインタ**になる。
しかも番号はそれらしく見えるので、**読み手は疑わない**。

🔑 **手順を 2 手に割る**(「気をつける」は 2 度効かなかった):

1. **先に `issue_write` で作る** ── 返ってきた番号を控える
2. **その番号を使って**コメント / 本文を書く

⚠ 書きながら「あとで作る」と思った瞬間が合図である ── **その文を書くのをやめて、先に作る。**
🔑 どうしても順序を変えられないなら、**番号を書かずに用件だけ書く**
(「別件として起票します」)── ⚠ 未来形は嘘にならない。

- 🔴 **4 度目は「作る」と「使う」を同じ 1 回の呼び出しに並べた形だった**(2026-09-26、#1067)。
  `create_pull_request` と `subscribe_pr_activity` を**並列で**出し、監視には
  **まだ返っていない PR 番号を推測で**渡した(また**たまたま一致**)。
  ⚠ 並列の呼び出しは**互いの結果を見られない** ── 片方の出力を使う呼び出しは、
  **同じ block に入れた時点で推測**である。
  🔑 **番号を返す呼び出し(`create_*` / `issue_write` の `create`)は単独で出し、
  結果を読んでから次を出す。**

## 🔴 「よそを直した」を、いま書いている場所に書かない

⚠ すぐ上の「済んだは観測点を挙げてから」は**外の事実**(merge / run / 番号)向けで、
**自分の手で これから やる作業**には効かなかった ── **同じ嘘を 3 日あけて 2 度**書いた
(2026-09-09「実機確認は **#438 Q8 として足しました**」→ #438 に Q8 は無い /
同日「お知らせの文面を**直してあります**」→ source はその字のまま /
🔴 2026-09-12 ── **後者を自分で見つけて書き上げた同じコメントの中で**、前者をもう一度)。

🔑 **なぜ毎回ここで出るか**: 主語が**別の場所**なので、**投稿は何の抵抗もなく通る**。
コメントは「書いた」ことしか確かめず、**書いた内容が指す先は誰も見ない**。

### 直し方(手順を 2 手に割る ── 「気をつける」は 2 度効かなかった)

1. 🔴 **報告は、直した場所に書く。** 「Y を直した」を X に書かず、
   **Y にコメントし、X からは指す** ── GitHub が参照を両側に出すので X 側は 1 行で足りる。
   🔑 この形なら**書くこと自体が作業**なので、**嘘になりようがない**。
2. X にまとめるしかないときは、**Y の観測点を同じ文へ貼る** ──
   `add_issue_comment` が返した **comment URL** / commit の **sha** / 本文なら **`updated_at`**。
   ⚠ **貼る物が無い文は、時制を「〜します」へ変える**(未来形は嘘にならない)。

### ⚠ 投稿の直前に、過去形だけを抜き出して読む

```
しました / 済ませました / 直してあります / 足しました / 移しました / 外しました / 閉じました
```

🔑 1 行ずつ「**その証拠を、いまこの画面から引けるか**」を言う。言えない行は消す。

- ⚠ **「済ませたこと」という見出しを、書く前に作らない** ── 欄の名前が過去形だと、
  中身は**観測ではなく意図で埋まる**(2026-09-12 はその欄で外した)
- 🔴 **直す前を測った労力を、直した事実と数えない** ── 同じ投稿に
  「移す前は #438 に 0 件だった」と**pre 条件の実測まで書いてある**。
  測ったのは前だけで、**後は一度も見ていない**(CLAUDE.md「後条件は、確かめた事実の上にだけ書く」)

## 🔴 計器が凍ることがある ── 同じ id を 2 度引いて同じなら、別の口から引く

`get_workflow_run` / `get_workflow_job` が**同じ凍った記録**を返し、
`updated_at` が何分も動かないことがある(2026-08-27、#481。job の timeout は 10 分
なのに 13 分 `in_progress` に見えた)。⚠ **2 度引いても同じ嘘が返る**ので、
「一次情報を引いた」だけでは足りない。

🔑 **`list_workflow_jobs`(run の id で job を一覧する)から引き直す** ──
このときは `completed / success` が返った(実所要 6m36s)。
⚠ **タイムアウトを超えて見えることを「異常の証拠」に数えない**(2 度誤った)。

## 🔴 落ちた job を再実行すると、唯一の証拠が消える

`get_job_logs` は**再実行で上書きされる**(2026-08-29、#561 で `failed_jobs: 0` が
返った)。🔑 **再実行を押す前に、落ちた job のログを丸ごと控える。**
⚠ 「flake に見えても 1 回だけ再実行してよい」は、**控えたあとの話**である。

## ⚠ issue にコメントするつもりで**本文を上書きしない**

`issue_write` の `method: "update"` に `body` を渡すと、**本文がまるごと置き換わる**。
2026-08-13 に #134 の症状表を消した(復元済み)。
🔑 コメントは **`add_issue_comment`**。`update` を使うのは題名を変えるときと、
**本文そのものを書き直すと決めたとき**だけである。

🔴 **同じ日に 2 度目 ── 踏むのは「閉じるとき」である**(#145)。
`state: "closed"` を渡すのに `issue_write` を使うので、**ついでに結末も `body` へ
書きたくなる**。そこが罠で、調査の記録がまるごと消える。
🔑 **閉じるのは 2 手に分ける**: ①結末を `add_issue_comment` ②`issue_write` で
`state` **だけ**(`body` を渡さない)。⚠ 1 回目の教訓を書いた本人が踏んだので、
「気をつける」ではなく**手順を 2 手に割る**ことで止める。

🔴 **3 度目は「コメントするつもり」のほうだった**(2026-09-21、#1017)。
上の 2 つは *閉じるついで* だが、こちらは**ただコメントを足したかっただけ**である ──
`add_issue_comment` を使うべき所で `issue_write` の `update` を打ち、
**本文を `PLACEHOLDER` で丸ごと上書きした**。
⚠ **原文は戻せなかった** ── 復元の口を全部当たって全滅である:

| 当たった先 | 結果 |
|---|---|
| GitHub の GraphQL(`userContentEdits` = 編集履歴) | 🔴 **この箱から塞がれている**(proxy が「REST を使え」と返す) |
| REST | 本文の履歴を返す口が**無い** |
| メールの控え(GitHub の通知) | **0 件**(自分が立てた issue の通知は届かない ── CI の通知だけ在った) |
| repo の中の複製 | **0 件** |

🔑 だから復元は「**組み直し**」になる ── 設計 doc・コメント・CLAUDE.md から書き直し、
**本文の先頭に「原文そのものではない」と明記する**(黙って埋めると、次に読む人が原文だと思う)。

🔴 **文言を 3 か所目にせず、門にした**(CLAUDE.md「戒めを 3 か所目にしない」)。
`.claude/hooks/guard-issue-body.mjs` + `.claude/settings.json` の `PreToolUse` が、
**`method: "update"` に `body` を渡す呼び出しを exit 2 で止める**
(`create` と、`body` を渡さない `update` は通す)。
🔑 禁止が解ける条件:**`PKC3_ALLOW_ISSUE_BODY_UPDATE=1`** ──
塞ぎたいのは**惰性**であって、本文を書き直す操作そのものではない。
⚠ そのときも**先に `issue_read` で現在の本文を控える**。

⚠ **門は「置いた session」では効かないことがある** ── 設定の監視は
**session が始まった時点で settings file が在った場所**しか見ないので、
新しく置いた `.claude/settings.json` は次の session(か `/hooks` を開くまで)効かない。
🔑 だから**置いた日は自分の手で守る**(2026-09-21 に実測:試し打ちが門を素通りして API まで届いた)。

## 🔴 短い sha を、40 桁へ「伸ばして」書かない(2026-09-15)

`merge_pull_request` の `expectedHeadSha` は **40 桁ちょうど**を要求する。
⚠ 手元に在ったのは `git log --oneline` の **7 桁**だったので、私は残りを
**それらしい 16 進で埋めた** ── 当然それは実在しない sha である。

🔑 **助かったのは API が形を検めたから**(1 回目は「40 桁でない」、
2 回目は `409 Head branch was modified`)── ⚠ **もし偶然 40 桁の形に
整っていたら、409 は「誰かが押した」と読めてしまう**(実際そう読みかけた)。

🔑 **手順は 1 つ:`git rev-parse HEAD` か `git ls-remote origin <branch>` で引く。**
⚠ CLAUDE.md の「**渡す識別子は、渡す前に実在と中身を確かめる**」は
PR 番号 / run 番号 / commit の話だが、**桁を補う**のも同じ罪である ──
**引いていない字を書いた**ことに変わりはない。

## 🔴 CI の完了を待つ ── ポーリングせずに、1 回だけ起きる(2026-09-21)

CLAUDE.md は「**CI の完了を `sleep` / ポーリングで待たない**」と定めている。
⚠ ところが **merge は緑を見てからしかできない**ので、「待たない」と「着地させる」が
正面からぶつかる ── この日は同じ check-run を **7 回**引いて溶かした。

🔑 **待ち方は 2 つある。どちらも「1 回だけ起きる」形である**:

| 手 | 使う所 | 書き方 |
|---|---|---|
| **背景で 1 回だけ寝る** | 完了見込みが読める(CI の実測が在る) | `Bash` を `run_in_background` で `sleep 150; echo wake` ── 完了通知で起きる |
| **自分宛の check-in** | 見込みが外れても拾いたい / session をまたぐ | `send_later`(`delay_minutes`)で「緑なら merge して閉じるところまで」を自分へ送る |

⚠ **`sleep` を前景で打つのは塞がれている**(ハーネスが止める)。
🔑 **両方を張ってよい** ── 背景の 1 回で拾えたら、check-in は `delete_trigger` で畳む
(CLAUDE.md「理由が消えた仕掛けは、消えた時点で外す」)。
⚠ **通知が来る前に何度も引かない** ── `verify` の実測はこの repo で **約 4.5 分**
(型 20 秒 → lint 18 秒 → `npm test` 約 3 分 → build 5 秒 → 検品 1 秒)。
🔑 **押してから 4 分は引く意味が無い。**

### ⚠ 「凍っている」の見分けは、**step の時刻**で付く

CLAUDE.md は「同じ id を 2 度引いて同じなら、別の口(job の一覧)から引き直す」と
書いてあるが、⚠ **一覧が返すのは status だけではない** ──
`actions_list` の `list_workflow_jobs` は **step ごとの `started_at` / `completed_at`**
を返すので、「**どの step で、いつから**動いていないか」が読める。

| 読み方 | 意味 |
|---|---|
| いちばん後ろの step が `in_progress` で、その `started_at` が**数分前** | 🟢 **本当に走っている**(引き直す必要は無い) |
| `in_progress` なのに、その step の `started_at` が**十数分前**で、次が `pending` のまま | 🔴 凍っている疑い ── ここで初めて再実行を考える |

🔑 だから**引くなら `list_workflow_jobs`** ── check-run の 1 行(`in_progress`)には
この情報が無く、「止まっている」という**解釈**しか作れない。
