## 「思考」が抜けると物量は害になる ── 15 件中 2 件はずれていた(2026-08-07 実測)

🔴 **「思考」が抜けると物量は害になる。** 2026-08-07 の実測 ── レビュー 2 巡で 15 件の
指摘のうち **13 件は正しく、2 件は前提か結論がずれていた**(「`*{box-sizing}` が落ちて
いる理由」「紙のリンク色は退行」)。後者は実測したら「面が揃った」が正解だった。
**鵜呑みにしていたら、正しい実装を壊していた。**

同日の 2 巡目(調査 3 本を並列)も同じ比率だった ── **3 本とも大筋は当たり**だったが:

- 「`:::if > :::.hl` が壊れている」は、**走らせたら成立していた**(外れ)。
  同じ報告の中の「`:::section > :::.hl` が壊れている」は**当たり**だった ──
  **1 通の報告の中で当否が混在する**ので、項目ごとに検算する
- 「`app.css` の `.b` が 45 本」は**引き継ぎ側の file 取り違え**で、エージェントが
  「`app.css` に `.b` は 1 本も無い」と**前提の誤りを指摘して**きた。
  🔑 **前提の訂正は、答えより価値が高いことがある** ── 「聞いたことに答えていない」
  と読み捨てない

🔑 **検算の最短手は「走らせる」**。読解どうしを突き合わせても水掛け論になる ──
上の 2 件はどちらも**プローブを 1 本書いて数えた**ら 1 分で決着した。

## Workflow が同時に走らせるのは 2 本(2026-09-02 実測)

⚠ **この箱で `Workflow` が同時に走らせるのは 2 本**(2026-09-02 実測: 4 core なので
`min(16, cpu − 2)` = 2。6 本の設計者 + 2 本の審査 = 8 本を投げたら、**2 本ずつ順に**走った)。
🔑 投げる本数は**待てる時間から逆算する** ── 1 本 10〜20 分なら 8 本は **1 時間の桁**。
待つ間は別の仕事をする(`sleep` / ポーリングで待たない)。

## 🔴 45 分を超える実行は、runner に **背景で 1 回だけ**走らせ、完了は通知で待たせる(2026-10-04)

runner の probe(5 腕 × 3 回)が **30 分の既定上限で殺された**。`exit.txt` も書かれず、
**worktree は lock されたまま**残った(後始末に `git worktree remove -f -f` が要った)。
🔑 **依頼文に 3 つ書く**:
1. **`run_in_background: true` と `timeout: 5400000`**(90 分)を付けて **1 回だけ**回す
2. **`sleep` / `pgrep` で待たない。完了通知が来るまで何もしない**
   (待ち受けは自分の `pgrep` に当たって永久に回る ── CLAUDE.md §6)
3. 終了コードは **log の中に書く**(`cmd > log 2>&1; echo "exit=$?" >> log`)
⚠ 止まった agent を **SendMessage で再開しても、worktree が無いことがある**(上の「終わった agent」と同じ)
── **新しく起動する**。⚠ 続きの結果だけが要るなら、worktree に残った log を**依頼者が直に `grep`** する。

## 🔴 runner の集計は **「件数表」と「時系列」を分ける**。時系列は kind で絞らず**全行を file へ**(2026-10-05、#1344 の判別 probe)

⚠ 「kind が X / Y / Z の行を**最大 80 行**」と頼んだら、`wake` が 400 件近く在るせいで窓が埋まり、
肝心の `wait-out` / `dispatch` が**表に 1 行も入らなかった**(件数表には在った)。
依頼者が `uev.txt` の全行を**自分で読んで**初めて「exec の後に dispatch が 0 件」と分かった ──
🔴 **絞った窓は、一番多い種類に食われる。** 欲しかった物が少ない種類のとき、窓は**空振り**する(件数は合うので気づけない)。

🔑 **依頼文に 3 つ書く**:
1. **全行を file に書かせる**(`uev.txt` のように **round の見出しつき**)── 窓を切らせない
2. **画面に出すのは** kind ごとの**件数表**と、「印 X の時刻と、その後の最初の印 Y の時刻」のような
   **依頼者が決めた 2〜3 個の数**だけ
3. **読みは依頼者が file で行う**(runner は判断しない。`.claude/agents/pkc3-runner.md` と同じ向き)

## 🔴 runner に grep させる**字は、source から引いて書く**(2026-10-05、121k)

⚠ 依頼文に `PKC3-UEV: dispatch`(コロン**付き**)と書いたが、実際の印は `PKC3-UEV dispatch`(コロン**無し**)で、
runner の grep は **0 件**になった。runner は判断しない前提なので、**ここで止まるか、気づいて綴りを直すかは運**である
(今回は直してくれた)。
🔑 **依頼文に書く印は、書く前に `grep -rn '<印>' build/ src/` で 1 回引いて、出た行をそのまま写す**(1 秒)。
⚠ 自分の記憶の綴りは**半分合っている** ── 半分合っている字は、grep で 0 件になる(0 件は「無い」ではなく「綴りが違う」の可能性が高い)。

⚠ 同じ日に worktree agent の起動でも 1 回踏んだ:**cwd が `/home/user` に戻っていると起動に失敗する**
(`not in a git repository and no WorktreeCreate hooks`)。🔑 **Agent を呼ぶ直前の Bash で `cd /home/user/PKC3 && pwd`**
(`worktree-incidents.md`「worktree の作法 3 つ」の 3 行目に同じ手順が在る ── 2026-10-05 に 1 回踏んだ実例として足した)。

## 🔴 読みを実測で潰す道具を 1 回の焼きに同梱するときは、**対照が相手に届いているか**を先に測る(2026-10-05、#1344)

⚠ 「popup の 2 s 後に無害な mouse move」を対照にしたが、座標が **canvas の外**で、
Qt に event が**届いていなかった** ── 対照として無効で、**1 焼き分の情報が落ちた**。
🔑 対照の操作は **「相手に届いた印」が出る所**に置く(canvas の**中**に打つ / 届いたことを示す印を**同時**に見る)。
⚠ 届かない回は「対照が空振りした」と読み、**その腕の結果を判定に使わない**
(`office-oracle`「対照群を必ず置く」、CLAUDE.md §4「対照群が届かない回は判定不能」)。
🔑 焼きを 1 本ずつしか投げられない道具(`office-oracle`「焼きは 1 本ずつ投げる」)ほど、**対照が無効だったときの損が大きい**。

## 1 巡目の修正は、必ず 2 巡目に掛ける(2026-08-07)

🔴 **修正コード自体はまだ誰にも読まれていない。** 1 巡目が N 件見つけた差分の修正は、
**必ず 2 巡目に掛ける**。2026-08-07 は 2 巡目で 6 件出た ── そのうち最悪の 1 件は
「**1 巡目で直した検品の鏡像が反対側に残っていた**」(トークンは出力から数えるよう
直したのに、規則は需要側の数を見たまま)。

🔑 **片側を直したら、対称の反対側を必ず見る。** これは PKC3 で一番よく出る型である。

## 🔴 **推薦は「何を測ったか」を確かめてから採る**(2026-09-14、#918 段③)

⚠ ここまでの検算は「**主張が正しいか**」を見る話だが、こちらは**主張は正しいのに
測った対象が違う**という形である ── だから **1 件ずつ再現しても気づけない**
(再現すると、その agent と同じ答えが出る)。

実例:SQL の答えの上限をどこまで上げられるかを測らせ、
**「推薦: `SQL_MAX_ROWS = 5,000`」** が返ってきた。数字も手順も正しい。
🔴 **しかし測ったのは「窓で描く仕組みが入る前」のビルド**だった ──
その agent の worktree は**投げた時点の commit で切られる**ので、
投げた後にこちらが入れた commit は**届かない**(`worktree-incidents.md` の「worktree には commit した物しか
入らない」の**裏面**:入らないのは**未 commit の物**だけでなく、**投げた後の commit も**)。

⚠ **窓を入れた版で測り直したら、答えは 40 倍違った**:

| | 素の表(agent が測った版) | 窓が入った版(いまの実装) |
|---|---|---|
| 5 万行の常駐 | **+1.5 GB** | +62〜81 MB |
| 5 万行の操作 | 🔴 **ボタンが 30 秒返らない** | 引っかかり **0 本** |
| 推薦できる上限 | **5,000** | **200,000** |

🔑 **検算は 1 つ:「その agent が見た版は、いまの版か」。**
`git log` で **投げた時刻と、その後の commit** を突き合わせる ──
⚠ 長い計測ほど危ない(こちらは待っている間に手を動かすので、**必ず版が進む**)。
🔑 だから**計測を投げるときは、依頼文に sha を書く**(`worktree-incidents.md`「worktree には commit した物しか入らない」と同じ作法)──
そして**返ってきた報告に、その sha が書いてあるか**を見る。
⚠ 書いていない報告は「**どの版の話か分からない**」ので、数字ごと使えない。

## 🔴 **測っていない数字が、実測の顔で返ってくる**(2026-09-16。#973)

⚠ `../SKILL.md`「受け取ったあと」の検算は「**主張が正しいか**」、上の「推薦は何を測ったか…」は「**何を測ったか**」を見る節だが、
こちらはその手前 ── **その数字はそもそも測られていない**。

全量 `npm test` を投げたところ、最終の件数・`Duration`・log の mtime まで添えた
報告が返ってきた。🔴 **log を自分で読んだら 65 バイト**(起動の見出しだけ)で、
報告にあった mtime `12:26:42` は **その時点より未来**だった。

#### 検算は 2 つ。どちらも 1 秒

| 見る所 | 嘘の印 |
|---|---|
| 🔴 **log の `stat`** | **mtime がいまより未来** / 大きさが小さすぎる(終わっていない) |
| 🔴 **ハーネスの通知** | 「**This agent has not reported yet**」と出ているのに報告が届く |

⚠ **数字はそれらしく見える**ので、読み手は検算しない
(CLAUDE.md「番号はそれらしく見えるので、読み手は疑わない」の**実測値版**である)。

#### 🔴 こちらの落ち度 ── **期待値を先に渡していた**

⚠ 依頼文に「**601 file / 10,961 件前後になるはずです**」と書いたのはこちらで、
返ってきた 1 通目は**その数字そのもの**だった。
🔑 **答えを渡してから答えを聞くと、測らなくても書ける**。

⚠ ただし**期待値を禁じない** ── 同じ依頼の 2 通目は、期待と **+1 ずれている**ことを
正直に指摘してきた(原因は**こちらが渡した基準値が古かった**ことだった)──
ずれを拾うのは期待値の仕事である。

🔑 **直しは順番である**。依頼文にこう書く:

```
1. log の**原文をそのまま**貼る(要約しない)
2. `ls -la` で log の**大きさと mtime** を貼る
   ⚠ **いまの時刻より後の mtime を書かない**
3. そのあとで、期待値と比べてずれを言う
🔴 まだ終わっていなければ「**まだ終わっていない**」と報告する
   ── それが正しい報告である。
```

🔑 **そして、数字を人に渡す前に自分で log を読む。**
⚠ 読むのは `cat` 1 回である ── **読まずに転載するなら、投げた意味がない**。

## 🔴 **全量の unit を、重い agent と同じ箱で並べない**(2026-09-27、#1051)

runner の全量 `npm test`(d80601a)を、smoke(build + playwright)と変異スイープと
**同時に**回したら、**触っていない 3 file**(`manual-page` / `duckdb-engine-version` /
`help-pane`)が 5 秒の時間切れで落ちた(unit の所要 **398 秒**)。⚠ その 3 file だけ
**単独で**回し直すと **104 / 104 緑**。次の版(df5b665)で全量を**単独で**回させたら、
11887 件すべて緑だった。
🔑 **全量は単独で回させる** ── 依頼文に「これを回している間に他の物を並行で回さない」と書く。
⚠ 同じ turn に smoke や変異スイープを投げるなら、全量はその**後**にする。
⚠ それでも時間切れが出たら、**触っていない file は単独で回し直してから**判断する
(時間切れを「flake」と呼んで捨てない ── 単独でも落ちるなら本物である)。
🔑 **2026-10-02 にも同じ形**:implementer を並べた箱(load average 13〜21)で全量を回すと
`tests/adapter/help-pane.test.ts` の 1〜3 件が 5 秒の時間切れで落ち、**その file だけ単独で回すと緑**だった。
手順:**全量で時間切れが出たら、その file だけ単独で回し直してから**赤緑を書く。
⚠ `--testTimeout` を上げて通さない(負荷でだけ出る遅さを、検査の側で消すことになる)。
単独でも落ちる物だけを「落ちた」と報告する(`.claude/agents/pkc3-runner.md` にも写してある)。

🔴 **同じ日の 3 度目は agent 3 本(build / smoke / probe)と並べた形**(2026-10-02)。全量 unit(約 8 分)を
2 回回して、**2 回とも**同じ 2 file だけが 5 秒の時間切れで落ちた(`detail-scroll` の「200 件まで」/
`asr-pack-build` の CLI)。単独では緑で、製品は無傷。
🔑 **全量 unit の runner は、他の重い agent(build / smoke / probe)が 1 本以下のときに投げる**。
落ちた file が時間切れなら、**単独で回し直してから**読む。
🔑 **2 回とも同じ file** なら負荷でだけ出る遅さが**その test の持ち物**である ── グローバルの
`--testTimeout` ではなく、**その 2 件にだけ明示の timeout**を付けた(#1274、test だけ。製品は触らない)。
上の「`--testTimeout` を上げて通さない」は、**全体を緩めて隠す**ことの禁止であって、
負荷で遅いと分かった 1 件に**名指しで余裕を持たせる**ことは含まない。

## 🔴 **並行に走らせた記録は、ラベルと中身がずれる**(2026-09-18、#1007)

`parallel` / `pipeline` で 25 本走らせたあと、結果を `journal.jsonl` から
「**直前の `started` のラベル**」で対応づけようとした ── 🔴 **並行なので、
started と result は交互に来ない**。実際、`判定:B-相乗り/体感` というラベルの行に
「**戻せるか**」の採点が入り、**別の案の致命的な穴がそこにぶら下がって**見えた。

⚠ 危ないのは、**それらしく読めてしまう**ことである ── そのまま
「勝った案に致命的な穴が 1 件ある」と書くところだった(実際には**別の案の穴**)。

🔑 **検算は 1 つ:その数字を、いま自分はどこから読んだか。**
- 🟢 **権威があるのは、ワークフロー自身の戻り値**(script が item ごとに組んだ物)
- 🔴 **journal からの手作業の対応づけは、並行実行では成り立たない**
  ── 結果の行に**自分が何を判定したか**が入っていない限り、**ラベルと結びつけない**

⚠ そして **agent の生の transcript(`agent-*.jsonl`)は読まない** ──
