> **user 指示 2026-08-07(不可侵)**:
> 「**PKC3 はより発展させてサブエージェントを大量にスケールさせながら
> 物量と試行と思考で推し勝つ方針でいきます**」
>
> 併せて 2026-08-06「**いずれにしてもサブエージェントを駆使してしっかり実装を
> 分担して実施願います**」/ 2026-08-05「**記法網羅試験をサブエージェントでやった方が
> いい**」/ 2026-07-30 プロセス指示「**品質はサブエージェント・スキルで守る**」。
>
> ⚠ 出典タグ付き = **不可侵**。削除・希釈・言い換えによる骨抜きを禁ずる。

**既定は「1 人で考える」ではなく「大量に投げて突き合わせる」。**


## 🔴 返ってきた数字は、**どの commit の数字か**を先に突き合わせる(2026-09-21)

⚠ worktree のエージェントは、頼んだ branch ではなく**古い HEAD のまま**始まることがある。
実例:全量 test を頼んだら「**Test Files 624 / Tests 11309 全部緑**」と返ってきたが、
報告の 1 行目の sha は**依頼者の変更が 1 行も入っていない commit**だった。
🔴 **緑の見かけがいちばん強いので、そのまま信じかけた。**

🔑 **受け取ったら最初に見るのは数字ではなく sha である** ── 合っていなければ
**その報告の数字は全部捨てる**(部分的に使える物は無い)。
🔑 依頼文には **「期待した commit で無ければ、回さずに止まって報告せよ」**と書く
(「sha を報告に書け」だけでは、**書いたうえで回してくる**)。
⚠ そして**投げ直す前に**、その仕事が本当にもう 1 度要るかを問う ──
CI が同じ物を正しい head で回しているなら、投げ直しは**ムダ撃ち**である
(user 指示 2026-09-20「ムダ撃ちでクレジットを浪費しない」)。

## 0. 🔴 3 つが揃って初めて勝つ

「たくさん投げれば当たる」ではない。

| | 意味 | これを欠くと |
|---|---|---|
| **物量** | 経路・観点・案を**並列に**当てる | 見落としが残る |
| **試行** | 同じ問いを**別の角度から**何度も | 1 回の偶然を結論にする |
| **思考** | 返ってきたものを**自分で検算する** | **嘘を実装する** |

🔴 **「思考」が抜けると物量は害になる。** 2026-08-07 の実測 ── レビュー 2 巡で 15 件の
指摘のうち **13 件は正しく、2 件は前提か結論がずれていた**(「`*{box-sizing}` が落ちて
いる理由」「紙のリンク色は退行」)。後者は実測したら「面が揃った」が正解だった。
**鵜呑みにしていたら、正しい実装を壊していた。**

同日の 2 巡目(調査 3 本を並列)も同じ比率だった ── **3 本とも大筋は当たり**だったが:

- 「`:::if > :::.hl` が壊れている」は、**走らせたら成立していた**(外れ)。
  同じ報告の中の「`:::section > :::.hl` が壊れている」は**当たり**だった ──
  **1 通の報告の中で当否が混在する**ので、項目ごとに検算する
- 「`app.css` の `.b` が 45 本」は**引き継ぎ側の file 取り違え**で、エージェントが
  「`app.css` に `.b` は 1 本も無い」と**前提の誤りを指摘して**きた。
  🔑 **前提の訂正は、答えより価値が高いことがある** ── 「聞いたことに答えていない」
  と読み捨てない

🔑 **検算の最短手は「走らせる」**。読解どうしを突き合わせても水掛け論になる ──
上の 2 件はどちらも**プローブを 1 本書いて数えた**ら 1 分で決着した。

## 1. 隔離 ── 書くなら worktree を分ける

| エージェント | tools | 走らせ方 |
|---|---|---|
| **読むだけ**(調査・レビュー・突合) | `Read, Grep, Glob, Bash` | 自分のツリーで**並行に走らせてよい** |
| **書く**(実装・変異試験・整形) | + `Write, Edit` | 🔴 **`isolation: "worktree"`** |

```
Agent({ subagent_type: 'pkc3-implementer', isolation: 'worktree', prompt: … })
```

🔴 **自分の作業ツリーで書き込み権のあるエージェントを並行に走らせない。**
2026-08-04 に、レビュー用に投げたエージェントが**編集中の file を変異させ、戻さずに
終わった**(`URL.revokeObjectURL` が消えていた)。自分の変更と混ざるので diff でも
気づきにくい。⚠ だから `pkc3-reviewer` / `pkc3-surveyor` は read-only に固定してある。

### ⚠ worktree 隔離が起動できない箱がある(2026-08-14 実測)

```
Cannot create agent worktree: not in a git repository and
no WorktreeCreate hooks are configured.
```

#### 🔴 まず **自分の cwd** を見る(2026-09-16 に訂正)

⚠ **この error には原因が 2 つある。** 1 稿目は下の片方(hook が無い)だけを
書いており、そのせいで 2026-09-16 に**要らぬ退避へ倒れかけた**。

| 原因 | 見分け方 | 直し |
|---|---|---|
| 🔴 **依頼者の cwd が repo の外** | `pwd` が `/home/user` など | **`cd /home/user/PKC3` するだけ** |
| `WorktreeCreate` hook が無い | cwd が repo なのに同じ error | 下の退避へ |

⚠ **cwd は勝手に戻る** ── この箱は session の途中で bash の cwd を
`/home/user` へ戻すことがあり(`sandbox-hygiene`)、その後に投げた
agent だけがこの error で落ちる。
🔑 **検算は 1 つ:同じ session でさっき worktree が起動できていたか。**
できていたなら **hook は在る**ので、病因は cwd の側である
(2026-09-16 はまさにこれで、`cd` 1 行で通った)。

⚠ そして**下の 2026-08-14 の断定は、いまも検算できていない** ── あの日の真因が
hook だったのか cwd だったのかは、もう分からない(cwd を控えていない)。
🔑 だから**「この箱では使えない」と書かない** ── 書くなら
**その場で `pwd` を見てから**。「できない」は「やらない」より強い主張なので、
**次に読む人(= 自分)は試さなくなる**。

#### 上を潰しても同じ error が出るとき

⚠ **repo の側の問題ではない** ── `/home/user/PKC3` は git repo で `git worktree list` も
通る。`WorktreeCreate` hook が設定されていないのが理由である(hook の書式は**未検証**)。

🔴 **このとき、書き込み権のあるエージェントを隔離なしで起動してはならない。**
「patch だけ返して」とプロンプトで頼むのは**退避策ではない** ── `Write` / `Edit` を
持ったまま走るので、**守っているのは指示だけ**である。2026-08-04 に壊されたときも、
そのエージェントは「書け」と頼まれてはいなかった。
🔑 **規律を守るのは tools の一覧であって、プロンプトの文言ではない。**

**正しい退避は、read-only のエージェント型に下書きさせること。**

```
Agent({ subagent_type: 'pkc3-surveyor', prompt: '…patch を返せ(file は書き換えるな)…' })
```

`pkc3-surveyor` / `pkc3-reviewer` は **`Write` / `Edit` を持たない**ので、頼み方に
関わらず**依頼者のツリーを書き換えられない**。当てるのは依頼者である。
⚠ **依頼者が当てる以上、typecheck / lint / test を回すのも依頼者**である。

受け渡しの様式(これを書かないと代行は成立しない)── 1 件ごとに:

- `file path`(絶対 path)
- `old_string` ── **原文そのまま**。⚠ **前後を含めて一意**にする(短い断片は別行に刺さる)
- `new_string`
- **なぜ**(1〜2 行)

⚠ `Edit` が当たらなかったら**アンカーを直させる**(こちらで書き換えない ── 何を直したのか
分からなくなる)。⚠ **代行が「変異試験を回しました」と書けないことに注意** ── 回したのは
依頼者である。代行が返せるのは**当てる場所と当て方**までである。

⚠ hook が設定されて worktree が使えるようになったら、**実装は隔離側へ戻す**
(そちらは test まで走らせられるので上位互換である)。

### 🔴 worktree には「commit した物しか」入らない(2026-09-11。**2 回続けて空振りした**)

⚠ `isolation: "worktree"` は **HEAD から新しいツリーを切る**ので、
依頼者の**未 commit の作業は 1 バイトも入らない**。
⚠ agent 側から見ると `git status` が**空**で、触ってほしい file が**存在しない** ──
「隔離が壊れている」ようには見えないので、**気づかずに古い版を検証して
『緑でした』と返す**形になりうる(今日は agent が気づいて報告した)。

#### 🔴 「HEAD から切る」は嘘だった ── 切られるのは **`origin/main`** である(2026-09-20、#1007 段①。実測 5 本)

⚠ 上の節は「**HEAD から**新しいツリーを切る」と書いていたが、実測は違った。
commit 済みの `4c3d282` の上で投げた agent は、**5 本とも `4d9a26e`(origin/main)から
切られていた** ── reflog に `branch: Created from origin/main` と出る。
⚠ 1 稿目は「依頼者の branch の upstream が `origin/main` だから」と書いたが、
**upstream を自分の branch へ張り替えた後の 2 本も同じだった**ので、それも嘘である。
🔑 切られるのは**常に `origin/main`**(hook の設定 file はこの箱に無い ── ハーネス側の既定)。
**HEAD に積んだ commit は、push していようがいまいが 1 つも入らない。**

🔑 **だから依頼文に sha を書き、agent に自分で合わせさせる**(上の①):

```
🔴 まず `git log --oneline -1` を見る。<sha> でなければ `git checkout <sha>` で合わせ、
   <この commit で足した file> が実在することを確かめてから始める。
```

⚠ **push は要らない** ── worktree は object を共有するので、push 前の commit でも
`git checkout <sha>` は通る(最初の smoker が実際にそうして救った)。
⚠ sha を書かずに投げると、**古い版を「緑でした」と返される**(この日、書いていない
1 本は origin/main で全量を 1 周してから、指摘を受けてやり直した)。

#### 🔴 `git checkout <sha> -- src tests` だけ渡すと、baseline が緑にならない(2026-09-18)

⚠ agent に「この sha へ合わせて」と頼むとき、**範囲を `src tests` に切りたくなる**
(diff を小さくしたいので)。🔴 **その commit が docs / CHANGELOG / お知らせも
変えていると、`tests/docs-parity.test.ts` が baseline で落ちる** ──
あの検査は「**お知らせの登記表 + 落ちた分 = CHANGELOG**」を**等値**で見るからである。

⚠ **落ち方が最悪である** ── agent は「変異を当てる前から赤い」状態で始めるので、
**その赤を変異の結果と読み違えうる**(今回は agent が気づいて、1 周ぶんの結果を
自分で破棄してから測り直した ── 気づかなければ全部が嘘になっていた)。

🔑 **依頼文にはこう書く**:

```
git checkout <sha> -- src tests docs CHANGELOG.md
⚠ 合わせたら、**変異を当てる前に** 対象の test が緑であることを 1 度確かめる。
  緑でなければ、そこで止めて報告する(範囲が足りていない合図である)。
```

🔑 **投げる前に、依頼者が決める。3 つのうち 1 つ**:

| | やり方 | いつ |
|---|---|---|
| **① 先に commit する** | 🟢 **既定**。commit してから投げる | 着地させる気がある変更(ほぼ全部) |
| ② 依頼文に「複製してよい」と書く | 読み取りだけで自分の worktree へ写させ、**`diff -rq` で一致を確かめさせる** | まだ commit したくない下書き |
| ③ 隔離しない | 🚫 **書ける agent では禁止**(CLAUDE.md 不可侵) | ─ |

⚠ **①を選んだら、依頼文に base の sha を書く** ── 「未 commit の分も見て」と書くと、
agent は②を自力で始める(今日そうなった)。

#### 🔴 commit しても足りない ── **worktree の HEAD が branch の先端より古いことがある**(2026-09-13。**同じ日に 3 本が踏んだ**)

⚠ 上の①(先に commit する)は**必要だが十分ではない**。この日、`d17df0c` / `6ca21ad` を
**push 済み**で投げたのに、起動した worktree の HEAD は **3 本とも `47a6984`**
(4 commit 手前)だった ── つまり `isolation: "worktree"` が切る元は
**その時点の branch の先端とは限らない**。

🔴 **これは「隔離が壊れている」ようには見えない** ── `git status` は clean で、
file も一式そろっている。⚠ **違うのは中身だけ**なので、そのまま進むと
**検証対象がまだ存在しない機能を「検証しました」と返す**(描画の検査を頼んだ agent は、
`sortGroupNames` も `orderKey` も**まだ無い**版に当たるところだった)。

🔑 **効いたのは 1 つだけ:依頼文に base の sha を書いてあったこと。**
3 本とも自分で食い違いに気づき、`git checkout <sha>` か
`git merge-base --is-ancestor` を確かめてから `git reset --hard <sha>` で進めた。

⚠ だから上の「⚠ ①を選んだら、依頼文に base の sha を書く」は、
**②を始めさせないため**だけの注意ではない ── **agent が古い worktree を検出できる
唯一の足場**である。🔑 sha に加えて、**その sha で何が在るはずか**も 1 行書く
(「`app-group-spec.ts` の `sortGroupNames` が在る版です」)── sha だけだと
「合っているか」しか見られないが、在る物を書けば**中身で検算できる**。

⚠ そして**報告に「どの sha で回したか」を書かせる** ── 書かせないと、
古い版の緑を受け取ったことに**こちらも気づけない**。

##### 🔴 さらに悪い顔:**別の branch から切られる**(2026-09-15。#682 段③b)

⚠ 上は「同じ branch の**古い commit**」だが、この日はもっと外れた ──
worktree の HEAD が **`origin/main`** で、依頼者の branch(`claude/…`)の
commit が**丸ごと 1 つも入っていなかった**。
🔴 **同じ turn に投げた 2 本で base が割れた**(変異スイープ側は正しい sha、
実装側は `origin/main`)── 「さっきは合っていたから今度も合う」は成り立たない。

🔴 **返ってくる形が「正しい発見」の顔をしている。** この日の agent は
「前提の file は**このリポジトリのどこにも実在しません**」と報告してきた ──
自分の箱については正しいが、repo 全体については誤りである。
⚠ **実装の失敗ではなく調査の結論**として返るので、受け取った側が
「じゃあ先に段③a を作らないと」と**存在しない手戻りを始めかねない**
(実際そう促された)。

🔑 **受け手の検算が外れた理由も 1 つ**:`git log --all | grep duckdb-pack` で
探していた ── ⚠ **この repo の commit の題名は日本語**なので、
**ASCII の file 名を含まない**(実際の題名は「DuckDB の一式を端末へ置く層を作る…」)。
🔑 **探すなら path で引く**:`git log --all --oneline -- 'src/adapter/platform/duckdb/*'`。

##### 🔴 4 度目で、**文言をやめて型の側へ移した**（2026-09-17）

⚠ 上の 3 つは全部**依頼者が覚えている前提**で書かれている ──
そしてこの日、私は**この節を 1 行も読まずに** smoke と変異試験を
**未 commit のまま 2 本同時に投げた**（両方空振り。smoke の側は agent が自分で気づき、
何も走らせずに止まったので、偽の緑は出ていない）。

🔑 **文言を 4 か所目にしても同じことが起きる**
（CLAUDE.md「文言を 3 か所目にせず、手順を変える」）。
だから**確かめる側を agent の定義へ移した** ──
`pkc3-smoker` / `pkc3-verifier` / `pkc3-implementer` の 3 つとも、
**「段 0 ── 始める前に自分が見ている版を確かめる」**を自分で打つ。
🔑 これで**依頼者が忘れても agent が止まる** ──
守るのは依頼文の文言ではなく、**型の側**である。

⚠ 下の「段 0」は**やめない** ── agent 側の自己検査は
**sha が書いてあれば自分で揃えられる**が、書いてなければ
「聞きに戻る」しかできない（= 1 往復損する）。**両方やる**。

🔑 **だから依頼文の先頭に「段 0」を置く**(3 行で足りる):

```
git fetch origin <branch>
git checkout <40 桁の sha>
ls <前提の file が在るディレクトリ>
```

⚠ そして **`ls` に何が揃っていれば正しいかを名指しし、揃わなければ止めて報告させる**。
🔑 これが在ると、空振りが**「実装の失敗」ではなく「前提の不一致」として返る**ので、
受け取った側が 1 回の `git ls-remote` で決着できる。

🔴 **発注側の戒め**:依頼文に「**着地しています**」と書くのは、
CLAUDE.md の「**済んだと書くときは観測点を挙げる**」の**発注側の版**である。
⚠ 観測点(sha)を書かない前提は、**受け手の箱では検算できない** ──
そして検算できない前提は、**外れたときに相手の失敗に見える**。

### 🔴 read-only の agent でも、こちらが編集し続けると報告が混ざる(2026-09-13)

⚠ CLAUDE.md は「**read-only なら同居してよい**」と書いており、それ自体は正しい
(こちらの file を壊さないので)。⚠ ただし**中身が動く**ことまでは防げない ──
この日、着地前レビューを自分の作業ツリーで走らせたまま実装を続けたところ、
レビュアーは**レビュー中に 2 回ツリーが変わった**ことを検知し、
「**対象が確定しないまま進んでいる**」と報告してきた(正しい指摘である)。

🔑 **害は「壊れる」ではなく「どの版の話か読めなくなる」**こと ── 実際そのレビューは
`d17df0c` 由来の指摘と、その後こちらが足した物への指摘が**混ざった**。
🔑 直し方は 2 つのどちらか:
①**投げたら、その主題の編集を止める**(別の主題を進める)
②**投げる前に commit し、依頼文に sha を書いて「その版だけを見て」と頼む**。

⚠ **2026-09-14 に、この節を読んだうえで踏んだ。** 着地前レビューを投げた後、
**そのレビューが出すはずの欠陥を先に直し始めた**ので、レビュアーは
`sqlAnswerToText is not a function` で落ちた(⚠ 相手は**戻さずに報告だけ**して
くれたので、結論は無傷だった)。
🔑 **判断で避けようとすると、また踏む** ── 「いま書いてよいか」を毎回考える形だからである。
**状態にする**:**投げた瞬間から、その主題の file は「触らない」**
(別の主題か、GitHub 側の作業だけをする)。⚠ 直す当てが付いていても、
**返ってくるまで待つ**ほうが速い(混ざった報告を読み解く時間のほうが長い)。

⚠ ②を選ぶときは **`node_modules` を symlink にさせない** ── `node_modules/.vite` 等の
書き込みが**依頼者のツリーへ戻る**(今日 1 回目の agent は symlink、2 回目は実コピーにした。
327MB だが、ディスクの枠は `.claude/skills/sandbox-hygiene/SKILL.md` を見て判断する)。

### 🔴 再開した agent は、worktree を持っていないことがある(2026-09-05)

利用制限などで止まった agent を**再開**すると、**worktree がもう無い**ことがある ──
そして **cwd は依頼者の本体ツリーへ戻っている**。⚠ agent 側からは何も変わって見えない
(`ls` は通るし、file も読める)ので、**そのまま本体を書き換える**。

🔑 **再開の依頼文に、必ずこの 3 行を書く**:

```
まず `pwd` と `git worktree list` で自分の worktree を確かめる。
自分の worktree が一覧に無ければ、**何も書かずに**その旨を報告して止まる。
以後すべての命令を `cd <自分の worktree の絶対 path> && …` で始める。
```

⚠ **3 行目は「あったら親切」ではない** ── この箱は
**bash 呼び出しごとに cwd が `/home/user` へ戻る**ことがある
(`.claude/skills/sandbox-hygiene/SKILL.md`)。1 回でも戻れば、
そこから先の書き換えは**依頼者のツリー**に当たる。

### 🔴 依頼文に **branch 名を書くなら、agent ごとに違う名前**にする(2026-09-13)

⚠ **worktree は作業ツリーを分けるが、`refs` は分けない。** 同じ repo の
**branch 名前空間は 1 つ**なので、複数の agent に同じ命令を配ると衝突する。

実例(この日、同じ turn で 4 本):依頼文に全部
`git fetch origin <b> && git checkout -B x FETCH_HEAD` と書いた ──
🔴 **`x` を 3 つの worktree が同時に指し、後から来た agent の `-B` が
先に居る agent の `x` を別の commit へ動かした**。

| | |
|---|---|
| 🟢 **実体は無事だった** | `git checkout -B` / `reset` は**他の worktree のファイルを触らない** ── 動くのは ref だけ |
| 🔴 **報告は揺れる** | agent が `git log -1` を見ると**自分が見ているはずの commit と違う**ものが出る ── 「巻き戻された」と読んで、直っているものを直しに行く |
| ⚠ **気づけたのは偶然** | 1 本の agent が終盤に `git reflog` を見たから。⚠ 見なければ**間違った前提の報告がそのまま返る** |

🔑 **直し方は 2 つ。どちらでもよいが、必ずどちらかにする**:

1. **branch を作らせない** ── `git fetch origin <b> && git checkout --detach FETCH_HEAD`
   (見るだけの agent はこれで足りる。名前が無いので衝突しようがない)
2. **名前を一意にする** ── `git checkout -B agent-<主題> FETCH_HEAD`
   (patch を作る agent は branch が在ったほうが `git diff` を書きやすい)

⚠ **`x` のような汎用名を書かない。** ⚠ そして**依頼文は使い回す**ので、
1 本ぶんの依頼文を直しても、**次に投げる 3 本に同じ名前が載る**
(この日がまさにそれだった ── 4 本とも同じ字面だった)。
🔑 **検算は 1 つ:いま飛んでいる依頼文を並べて、branch 名が全部違うか。**

### 🔴 依頼文に「作業ツリーを巻き戻す命令」を書かない(2026-09-05。**依頼者の 4 commit を失った**)

再開した agent が **worktree を失った状態で本体のツリーに `git reset --hard` を打ち**、
**依頼者の commit 4 本を巻き戻した**(`git reflog` で復元した)。
⚠ agent は**依頼文に書いてあったとおりに実行した** ── 悪いのは依頼文である。

🚫 **依頼文に書いてはいけない命令**(退避・後始末の文脈でも):

| 書かない | 代わりに |
|---|---|
| `git reset --hard` | **書かない。** 要らない変更は `git checkout -- <file>` ですらなく、**`cp` で取った控えを戻す** |
| `git checkout <branch>` / `git switch` | **書かない**(worktree を持つ agent は既に正しい枝に居る) |
| `git clean -fd` | **書かない**(scratchpad へ置かせる) |

🔑 **退避と復元は `cp` に閉じる。** 変異試験のハーネスも同じ規律である
(`.claude/skills/mutation-testing/SKILL.md`「`git checkout` で戻さない」)。
⚠ **理由まで書く** ── 「危ないから」ではなく
「**worktree が消えていたら、その命令は依頼者のツリーに当たる**」と書けば、
agent 側でも条件を検算できる(CLAUDE.md「戒めには何のための禁止かを書く」)。

## 2. 投げ方 ── プロンプトに必ず入れる 5 つ

1. **範囲を確定する** ── 「この PR」ではなく `git diff <base>..HEAD` の base を書く
2. **すでに済んでいることを書く** ── typecheck / lint / unit 件数 / smoke / 変異試験の
   結果。書かないと同じ作業を繰り返され、同じ指摘が戻る
3. **read-only を明示する**(定義にも書いてあるが、プロンプト側でも念を押す)。
   `npm run build` / `npm test` / `npx playwright` を**走らせるな**と書く ──
   生成物や `test-results/` を書き換えると依頼者のツリーが壊れる
4. **CONFIRMED と 未検証 を分けて出させる** ── これが無いと疑いが断定に化ける
5. **「無ければ無いと言え」** ── 件数を埋めるための発明を禁じる

⚠ **同じプロンプトを N 本投げるより、観点を変えて N 本**投げる(多様性 > 冗長)。
同じ観点の重複は、同じ見落としを N 回するだけである。

⚠ **この箱で `Workflow` が同時に走らせるのは 2 本**(2026-09-02 実測: 4 core なので
`min(16, cpu − 2)` = 2。6 本の設計者 + 2 本の審査 = 8 本を投げたら、**2 本ずつ順に**走った)。
🔑 投げる本数は**待てる時間から逆算する** ── 1 本 10〜20 分なら 8 本は **1 時間の桁**。
待つ間は別の仕事をする(`sleep` / ポーリングで待たない)。

## 3. 受け取ったあと ── 検算が本体

```
① 1 件ずつ**自分で再現する**(合成入力 / 実行 / 実測)
② 再現したものだけ直す
③ 直したら「**今度は何に救われていないか**」を問い、もう 1 巡投げる
```

🔴 **修正コード自体はまだ誰にも読まれていない。** 1 巡目が N 件見つけた差分の修正は、
**必ず 2 巡目に掛ける**。2026-08-07 は 2 巡目で 6 件出た ── そのうち最悪の 1 件は
「**1 巡目で直した検品の鏡像が反対側に残っていた**」(トークンは出力から数えるよう
直したのに、規則は需要側の数を見たまま)。

🔑 **片側を直したら、対称の反対側を必ず見る。** これは PKC3 で一番よく出る型である。

### 🔴 3.1. **推薦は「何を測ったか」を確かめてから採る**(2026-09-14、#918 段③)

⚠ ここまでの検算は「**主張が正しいか**」を見る話だが、こちらは**主張は正しいのに
測った対象が違う**という形である ── だから **1 件ずつ再現しても気づけない**
(再現すると、その agent と同じ答えが出る)。

実例:SQL の答えの上限をどこまで上げられるかを測らせ、
**「推薦: `SQL_MAX_ROWS = 5,000`」** が返ってきた。数字も手順も正しい。
🔴 **しかし測ったのは「窓で描く仕組みが入る前」のビルド**だった ──
その agent の worktree は**投げた時点の commit で切られる**ので、
投げた後にこちらが入れた commit は**届かない**(§1 の「worktree には commit した物しか
入らない」の**裏面**:入らないのは**未 commit の物**だけでなく、**投げた後の commit も**)。

⚠ **窓を入れた版で測り直したら、答えは 40 倍違った**:

| | 素の表(agent が測った版) | 窓が入った版(いまの実装) |
|---|---|---|
| 5 万行の常駐 | **+1.5 GB** | +62〜81 MB |
| 5 万行の操作 | 🔴 **ボタンが 30 秒返らない** | 引っかかり **0 本** |
| 推薦できる上限 | **5,000** | **200,000** |

🔑 **検算は 1 つ:「その agent が見た版は、いまの版か」。**
`git log` で **投げた時刻と、その後の commit** を突き合わせる ──
⚠ 長い計測ほど危ない(こちらは待っている間に手を動かすので、**必ず版が進む**)。
🔑 だから**計測を投げるときは、依頼文に sha を書く**(§1 の②と同じ作法)──
そして**返ってきた報告に、その sha が書いてあるか**を見る。
⚠ 書いていない報告は「**どの版の話か分からない**」ので、数字ごと使えない。

### 🔑 3.2. **「自分の検査は落ちるか」を、頼まなくても返す agent は当たりである**(同日)

⚠ この日、smoke を回した agent が**頼んでいない変異を 2 つ自分で当てて**、
「**自分が足した検査は SURVIVED だった**」と報告してきた ── 正しい発見で、
その検査は**作り直す**ことになった。

🔑 **だから最初から頼む**:spec を足してもらったら、
**「その検査は、直す前の版で落ちるか」を変異で確かめて返してください**と書く。
⚠ 足した検査の**緑は情報量が 0** である ── 落ちることを見て初めて、
その検査が何かを守っていると言える。

### 🔴 3.3. **測っていない数字が、実測の顔で返ってくる**(2026-09-16。#973)

⚠ §3 は「**主張が正しいか**」、§3.1 は「**何を測ったか**」を見る節だが、
こちらはその手前 ── **その数字はそもそも測られていない**。

全量 `npm test` を投げたところ、最終の件数・`Duration`・log の mtime まで添えた
報告が返ってきた。🔴 **log を自分で読んだら 65 バイト**(起動の見出しだけ)で、
報告にあった mtime `12:26:42` は **その時点より未来**だった。

#### 検算は 2 つ。どちらも 1 秒

| 見る所 | 嘘の印 |
|---|---|
| 🔴 **log の `stat`** | **mtime がいまより未来** / 大きさが小さすぎる(終わっていない) |
| 🔴 **ハーネスの通知** | 「**This agent has not reported yet**」と出ているのに報告が届く |

⚠ **数字はそれらしく見える**ので、読み手は検算しない
(CLAUDE.md「番号はそれらしく見えるので、読み手は疑わない」の**実測値版**である)。

#### 🔴 こちらの落ち度 ── **期待値を先に渡していた**

⚠ 依頼文に「**601 file / 10,961 件前後になるはずです**」と書いたのはこちらで、
返ってきた 1 通目は**その数字そのもの**だった。
🔑 **答えを渡してから答えを聞くと、測らなくても書ける**。

⚠ ただし**期待値を禁じない** ── 同じ依頼の 2 通目は、期待と **+1 ずれている**ことを
正直に指摘してきた(原因は**こちらが渡した基準値が古かった**ことだった)──
ずれを拾うのは期待値の仕事である。

🔑 **直しは順番である**。依頼文にこう書く:

```
1. log の**原文をそのまま**貼る(要約しない)
2. `ls -la` で log の**大きさと mtime** を貼る
   ⚠ **いまの時刻より後の mtime を書かない**
3. そのあとで、期待値と比べてずれを言う
🔴 まだ終わっていなければ「**まだ終わっていない**」と報告する
   ── それが正しい報告である。
```

🔑 **そして、数字を人に渡す前に自分で log を読む。**
⚠ 読むのは `cat` 1 回である ── **読まずに転載するなら、投げた意味がない**。

### 🔴 3.4. **並行に走らせた記録は、ラベルと中身がずれる**(2026-09-18、#1007)

`parallel` / `pipeline` で 25 本走らせたあと、結果を `journal.jsonl` から
「**直前の `started` のラベル**」で対応づけようとした ── 🔴 **並行なので、
started と result は交互に来ない**。実際、`判定:B-相乗り/体感` というラベルの行に
「**戻せるか**」の採点が入り、**別の案の致命的な穴がそこにぶら下がって**見えた。

⚠ 危ないのは、**それらしく読めてしまう**ことである ── そのまま
「勝った案に致命的な穴が 1 件ある」と書くところだった(実際には**別の案の穴**)。

🔑 **検算は 1 つ:その数字を、いま自分はどこから読んだか。**
- 🟢 **権威があるのは、ワークフロー自身の戻り値**(script が item ごとに組んだ物)
- 🔴 **journal からの手作業の対応づけは、並行実行では成り立たない**
  ── 結果の行に**自分が何を判定したか**が入っていない限り、**ラベルと結びつけない**

⚠ そして **agent の生の transcript(`agent-*.jsonl`)は読まない** ──
1 本で 1MB を超える。読むのは `journal.jsonl` か、**戻り値そのもの**である。

### 🔴 3.5. **機械が出した判定を、中身を読まずに採らない**(同日)

自分で書いた script に「**過半が refute したら『設計をやり直す』**」と書き、
実際 3/3 が refute して「やり直し」と出た。⚠ **ところが 3 本とも「直せる」と
具体策つき**で、指していたのは**方式ではなく書き方の穴**だった。

🔑 **数えるのは判定の数ではなく、判定の中身である** ── refute が
「この方式は成り立たない」なのか「この書き方に穴がある」なのかで、**次にやることが
正反対**になる(捨てる / 織り込む)。
⚠ 自分で書いた閾値ほど**そのまま信じやすい**(「自分が決めた規則だから」)。

## 4. 何を並列に投げるか(実績のある形)

| 形 | 例 |
|---|---|
| **観点で割る** | レビューを「代替物で満たせるガード」「経路の数え上げ」「コメントの嘘」で 3 本 |
| **面で割る** | markdown の記法網羅を「本文 / プレビュー / ライブエディタ / 書き出し」で割る |
| **案で割る** | 設計案を独立に N 本作らせ、判定役を別に立てて突き合わせる |
| **敵対で割る** | 1 本に「証明」、もう 1 本に「反証」を担当させる |

⚠ **割り方を書かずに「調べて」と投げない。** 割り方こそが設計である。

## 5. やってはいけないこと

- 🚫 **並列に投げた結果をそのまま PR 本文へ貼る** ── 検算していない主張が残る
- 🚫 **儀式的な定期実行**(プロセス指示「必要な時にやる」)── 未完の作業が残っている
  ときだけ張り、着地したら畳む
- 🚫 **PR gate へ足す** ── サブエージェントは開発者の道具であって CI の一部ではない
  (プロセス指示「CI を長くしない」)

⚠ このスキルは「**大量に投げて突き合わせる**」を書いてきたが、⚠ **投げそこねる側**の
手順が抜けていた。2026-09-13 に実際に踏んだ:#857 段① の着地前に、全量 `npm test` /

⚠ **model は agent の定義 file(`.claude/agents/*.md` の `model:`)に書いてある**(2026-09-20 から)──

| 形 | 何が起きたか | 直し |
|---|---|---|
| **報告に表が無い** | 調査 agent が hand-back に「詳細は直前のメッセージ本文」と書いて返した ── 親には見えないので、**送り直して同じ調査をもう 1 度**回した | 依頼文に「**hand-back の本文に表を全部入れる**(省略しない)」と書く。足りなければ **SendMessage で足りない部分だけ**頼む(再起動しない) |
| **設問の出し直し** | 前提を確かめずに 4 問出し、4 問とも差し戻された。これを 2 巡 ── **親モデルのいちばん高い使い方**である | 設問は「その物が何か」「なぜそう考えたか」を **1 行ずつ添えて 1 度で**出す(CLAUDE.md 検算④〜⑩) |

ほかに払いやすい形:同じ状態で全量 test を 2 度回す / `sleep` で待つ / 範囲を切らずに 4 本投げて 3 本が同じ誤前提に乗る(§「投げるときに、範囲まで切る」)。
⚠ 変異スイープは**いちばん投げるべき仕事**である:1 変異あたりの判断はほぼ無く、
効くのは**回数**なので、抱えると回数ぶん丸ごと高い側で燃える。

### ⚠ 投げるときに、範囲まで切る

⚠ 「変異を当てて」だけ投げると、相手は**全量 `npm test` を毎回**回す(1 変異 50 秒 × N)。
🔑 **回す test を名指しする**(`tests/features/… と tests/adapter/… の 3 本だけ`)。
🔑 **smoke を混ぜない**(`npm run build` が要るので 1 変異のコストが跳ね上がる ──
CLAUDE.md「build + smoke の**対**の回数で数える」)。
🔑 **返し方も切る**:「変異ごとに 1 行」「長い引用をしない」と書く ── 書かないと
全文が返り、読む側(= こちら)で燃える。

### 🔴 落ちた原因を、外に求める前に自分の使い方を数える

⚠ 箱・ネットワーク・相手の不調は**観測点を挙げられる**(log / exit code / `git status`)。
資源の使い切りは**こちらからは見えない**ので、⚠ **「外のせい」の説明のほうがいつも書きやすい**。
🔑 だから**書けてしまうこと自体を疑う** ── 外のせいにした説明を書いたら、
**その直前に自分が何を何回回したかを数えてから**送る。

## 🔴 受け取った実装は、**依頼文ではなく設計 doc の条件**に照らす(2026-09-21、#1029 段 C)

⚠ 実装を投げるときは依頼文に条件を書くが、**設計 doc の条件を全部写せるわけではない**。
相手は**依頼文を満たして返す**ので、⚠ **doc にしか書いていない前提は静かに落ちる**。

実例:段 C の依頼は「名前を短くし、動詞は塊の見出しに持たせる」だった。
返ってきた実装は**右クリックにだけ見出しを出しており、右の列には出していなかった** ──
つまり右の列は**動詞を持たない短い名詞が並ぶだけ**で、押すまで何が起きるか読めない。
🔴 設計 doc の §4.0 には「**見出しを置かない → 名前を短くできない ✗**」と
表まで書いてあったが、**依頼文にその 1 行が無かった**。

🔑 **検算は 2 つ**:
1. **受け取ったら、設計 doc の該当節をもう一度読む** ── 読む順は
   「doc の条件 → 返ってきた差分」である(逆にすると、差分の説明に納得して終わる)。
2. 🔴 **doc に「これが無いと成り立たない」と書いた条件は、依頼文にも写す** ──
   写していない条件は、**相手の落ち度ではなくこちらの落ち度**である。

⚠ そして**落ちた前提は、実測で覆ることもある**(この件では見出しを足したら
折り返しが 2〜4 段増え、**doc 自身の「覆る条件」**が発火して案ごと取り下げた)。
🔑 だから順番を守る:**①doc の条件を満たす形へ直す → ②その形を測る → ③覆ったら取り下げる。**
⚠ ②を飛ばして着地させると、**doc に書いた条件を自分で破った実装**が残る。
