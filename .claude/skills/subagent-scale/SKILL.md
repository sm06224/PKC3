# サブエージェントを大量にスケールさせる

> **user 指示 2026-08-07(不可侵)**:
> 「**PKC3 はより発展させてサブエージェントを大量にスケールさせながら
> 物量と試行と思考で推し勝つ方針でいきます**」
>
> 併せて 2026-08-06「**いずれにしてもサブエージェントを駆使してしっかり実装を
> 分担して実施願います**」/ 2026-08-05「**記法網羅試験をサブエージェントでやった方が
> いい**」/ 2026-07-30 プロセス指示「**品質はサブエージェント・スキルで守る**」。
>
> ⚠ 出典タグ付き = **不可侵**。削除・希釈・言い換えによる骨抜きを禁ずる。

**既定は「1 人で考える」ではなく「大量に投げて突き合わせる」。**

## 0. 🔴 3 つが揃って初めて勝つ

「たくさん投げれば当たる」ではない。

| | 意味 | これを欠くと |
|---|---|---|
| **物量** | 経路・観点・案を**並列に**当てる | 見落としが残る |
| **試行** | 同じ問いを**別の角度から**何度も | 1 回の偶然を結論にする |
| **思考** | 返ってきたものを**自分で検算する** | **嘘を実装する** |

🔴 **「思考」が抜けると物量は害になる。** 2026-08-07 の実測 ── レビュー 2 巡で 15 件の
指摘のうち **13 件は正しく、2 件は前提か結論がずれていた**(「`*{box-sizing}` が落ちて
いる理由」「紙のリンク色は退行」)。後者は実測したら「面が揃った」が正解だった。
**鵜呑みにしていたら、正しい実装を壊していた。**

同日の 2 巡目(調査 3 本を並列)も同じ比率だった ── **3 本とも大筋は当たり**だったが:

- 「`:::if > :::.hl` が壊れている」は、**走らせたら成立していた**(外れ)。
  同じ報告の中の「`:::section > :::.hl` が壊れている」は**当たり**だった ──
  **1 通の報告の中で当否が混在する**ので、項目ごとに検算する
- 「`app.css` の `.b` が 45 本」は**引き継ぎ側の file 取り違え**で、エージェントが
  「`app.css` に `.b` は 1 本も無い」と**前提の誤りを指摘して**きた。
  🔑 **前提の訂正は、答えより価値が高いことがある** ── 「聞いたことに答えていない」
  と読み捨てない

🔑 **検算の最短手は「走らせる」**。読解どうしを突き合わせても水掛け論になる ──
上の 2 件はどちらも**プローブを 1 本書いて数えた**ら 1 分で決着した。

## 1. 隔離 ── 書くなら worktree を分ける

| エージェント | tools | 走らせ方 |
|---|---|---|
| **読むだけ**(調査・レビュー・突合) | `Read, Grep, Glob, Bash` | 自分のツリーで**並行に走らせてよい** |
| **書く**(実装・変異試験・整形) | + `Write, Edit` | 🔴 **`isolation: "worktree"`** |

```
Agent({ subagent_type: 'pkc3-implementer', isolation: 'worktree', prompt: … })
```

🔴 **自分の作業ツリーで書き込み権のあるエージェントを並行に走らせない。**
2026-08-04 に、レビュー用に投げたエージェントが**編集中の file を変異させ、戻さずに
終わった**(`URL.revokeObjectURL` が消えていた)。自分の変更と混ざるので diff でも
気づきにくい。⚠ だから `pkc3-reviewer` / `pkc3-surveyor` は read-only に固定してある。

### ⚠ worktree 隔離が起動できない箱がある(2026-08-14 実測)

```
Cannot create agent worktree: not in a git repository and
no WorktreeCreate hooks are configured.
```

⚠ **repo の側の問題ではない** ── `/home/user/PKC3` は git repo で `git worktree list` も
通る。`WorktreeCreate` hook が設定されていないのが理由である(hook の書式は**未検証**)。

🔴 **このとき、書き込み権のあるエージェントを隔離なしで起動してはならない。**
「patch だけ返して」とプロンプトで頼むのは**退避策ではない** ── `Write` / `Edit` を
持ったまま走るので、**守っているのは指示だけ**である。2026-08-04 に壊されたときも、
そのエージェントは「書け」と頼まれてはいなかった。
🔑 **規律を守るのは tools の一覧であって、プロンプトの文言ではない。**

**正しい退避は、read-only のエージェント型に下書きさせること。**

```
Agent({ subagent_type: 'pkc3-surveyor', prompt: '…patch を返せ(file は書き換えるな)…' })
```

`pkc3-surveyor` / `pkc3-reviewer` は **`Write` / `Edit` を持たない**ので、頼み方に
関わらず**依頼者のツリーを書き換えられない**。当てるのは依頼者である。
⚠ **依頼者が当てる以上、typecheck / lint / test を回すのも依頼者**である。

受け渡しの様式(これを書かないと代行は成立しない)── 1 件ごとに:

- `file path`(絶対 path)
- `old_string` ── **原文そのまま**。⚠ **前後を含めて一意**にする(短い断片は別行に刺さる)
- `new_string`
- **なぜ**(1〜2 行)

⚠ `Edit` が当たらなかったら**アンカーを直させる**(こちらで書き換えない ── 何を直したのか
分からなくなる)。⚠ **代行が「変異試験を回しました」と書けないことに注意** ── 回したのは
依頼者である。代行が返せるのは**当てる場所と当て方**までである。

⚠ hook が設定されて worktree が使えるようになったら、**実装は隔離側へ戻す**
(そちらは test まで走らせられるので上位互換である)。

## 2. 投げ方 ── プロンプトに必ず入れる 5 つ

1. **範囲を確定する** ── 「この PR」ではなく `git diff <base>..HEAD` の base を書く
2. **すでに済んでいることを書く** ── typecheck / lint / unit 件数 / smoke / 変異試験の
   結果。書かないと同じ作業を繰り返され、同じ指摘が戻る
3. **read-only を明示する**(定義にも書いてあるが、プロンプト側でも念を押す)。
   `npm run build` / `npm test` / `npx playwright` を**走らせるな**と書く ──
   生成物や `test-results/` を書き換えると依頼者のツリーが壊れる
4. **CONFIRMED と 未検証 を分けて出させる** ── これが無いと疑いが断定に化ける
5. **「無ければ無いと言え」** ── 件数を埋めるための発明を禁じる

⚠ **同じプロンプトを N 本投げるより、観点を変えて N 本**投げる(多様性 > 冗長)。
同じ観点の重複は、同じ見落としを N 回するだけである。

## 3. 受け取ったあと ── 検算が本体

```
① 1 件ずつ**自分で再現する**(合成入力 / 実行 / 実測)
② 再現したものだけ直す
③ 直したら「**今度は何に救われていないか**」を問い、もう 1 巡投げる
```

🔴 **修正コード自体はまだ誰にも読まれていない。** 1 巡目が N 件見つけた差分の修正は、
**必ず 2 巡目に掛ける**。2026-08-07 は 2 巡目で 6 件出た ── そのうち最悪の 1 件は
「**1 巡目で直した検品の鏡像が反対側に残っていた**」(トークンは出力から数えるよう
直したのに、規則は需要側の数を見たまま)。

🔑 **片側を直したら、対称の反対側を必ず見る。** これは PKC3 で一番よく出る型である。

## 4. 何を並列に投げるか(実績のある形)

| 形 | 例 |
|---|---|
| **観点で割る** | レビューを「代替物で満たせるガード」「経路の数え上げ」「コメントの嘘」で 3 本 |
| **面で割る** | markdown の記法網羅を「本文 / プレビュー / ライブエディタ / 書き出し」で割る |
| **案で割る** | 設計案を独立に N 本作らせ、判定役を別に立てて突き合わせる |
| **敵対で割る** | 1 本に「証明」、もう 1 本に「反証」を担当させる |

⚠ **割り方を書かずに「調べて」と投げない。** 割り方こそが設計である。

### 🔴 「よその repo を学ぶ」ときの割り方(2026-08-22、PKC2 で実証)

user 指示「**お前はまだまだ PKC2 を学ぶ必要がある**」を受けて 4 本並列で投げ、
**私の思い込みを 3 つとも壊せた**。割り方はこうだった:

| 本 | 問い | これで壊れた思い込み |
|---|---|---|
| **経緯** | なぜ凍結されたのか。時系列で | 「storage が遅かった」→ 実は **boot 22.9s の 85.6% は renderer**。storage が直せなかったのは**メモリと OOM** |
| **物語** | 1 人の user が続けてやる一連の作業を 5〜8 本 | 「機能の集合」→ 実は「**入口は多く、判定は 1 か所**」という作り |
| **面の動線** | 窓とペインはどう開き、どう閉じるか | 「窓の間で状態を渡せない」→ **2117 行の protocol と親子窓の実績**が在った |
| **生死** | 使われている物と、使えない物を証拠つきで | 「在る = 使える」→ **多窓は flag OFF で 1 種類しか届いていなかった** |

🔑 **「機能の一覧を作るな」と明示的に禁じる。** 放っておくと機能表が返る ──
それは**こちらが既に持っている形**であって、学びにならない。
🔑 **「物語」を要求する**:「user は〈…〉をしたくて、〈…〉を開き、〈…〉を押し、
〈…〉になる」を file:line つきで。⚠ これが**動線を読む唯一の形**である。
🔑 **「生死」の本を必ず 1 本混ぜる。** user 指示 2026-08-22
「**使っていないものや使えないものまでを実装再現するのは間違えている**」──
学ぶ相手が万能機であるほど、**死んだ枝も多い**。
⚠ そして生死の判定は **flag・マニュアル・test の三点では足りない** ── PKC2 には
三点が揃っていて**動かない**例(`Ctrl+\` が別コマンドに横取りされる)が在った。
**四点目は実機**である。

⚠ **1 本ずつ順に投げない。** 4 本は互いの前提を壊し合うので、**同時に投げて
突き合わせる**ほうが速く、かつ「先に返った 1 本に引きずられる」ことがない。

## 5. やってはいけないこと

- 🚫 **並列に投げた結果をそのまま PR 本文へ貼る** ── 検算していない主張が残る
- 🚫 **儀式的な定期実行**(プロセス指示「必要な時にやる」)── 未完の作業が残っている
  ときだけ張り、着地したら畳む
- 🚫 **PR gate へ足す** ── サブエージェントは開発者の道具であって CI の一部ではない
  (プロセス指示「CI を長くしない」)
