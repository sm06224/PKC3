# サブエージェントを大量にスケールさせる

> 方針の正本は CLAUDE.md「進め方の方針」(user 指示 2026-08-07。不可侵)。併せて 2026-08-06 / 2026-08-05 / 2026-07-30 の指示も CLAUDE.md に在る
> (末尾の注記「この節は 2026-08-07 まで…」)。**ここは手順だけ**を持つ。
>
> 事故の記録(日付・issue つき)は 2 本:
> [`reference/worktree-incidents.md`](reference/worktree-incidents.md)(worktree と依頼文)/
> [`reference/dispatch-incidents.md`](reference/dispatch-incidents.md)(投げ方・受け取り・計測)。

**既定は「1 人で考える」ではなく「大量に投げて突き合わせる」。**

## 3 つが揃って初めて勝つ

| | 意味 | これを欠くと |
|---|---|---|
| **物量** | 経路・観点・案を**並列に**当てる | 見落としが残る |
| **試行** | 同じ問いを**別の角度から**何度も | 1 回の偶然を結論にする |
| **思考** | 返ってきたものを**自分で検算する** | **嘘を実装する** |

🔑 「思考」が抜けると物量は害になる(2026-08-07 の実測でレビューの指摘 15 件中 2 件が前提か結論のずれ。
→ `dispatch-incidents.md`「「思考」が抜けると物量は害になる」)。検算の最短手は**走らせる**こと
(プローブを 1 本書いて数える)── 読解どうしの突き合わせは水掛け論になる。

## 隔離 ── 書くなら worktree を分ける

| エージェント | tools | 走らせ方 |
|---|---|---|
| **読むだけ**(調査・レビュー・突合) | `Read, Grep, Glob, Bash` | 自分のツリーで**並行に走らせてよい** |
| **書く**(実装・変異試験・整形) | + `Write, Edit` | 🔴 **`isolation: "worktree"`** |

```
Agent({ subagent_type: 'pkc3-implementer', isolation: 'worktree', prompt: … })
```

🔴 **自分の作業ツリーで書き込み権のあるエージェントを並行に走らせない。**
2026-08-04 に、レビュー用に投げたエージェントが**編集中の file を変異させ、戻さずに
終わった**(`URL.revokeObjectURL` が消えていた)。自分の変更と混ざるので diff でも
気づきにくい。⚠ だから `pkc3-reviewer` / `pkc3-surveyor` は read-only に固定してある。

⚠ read-only の agent でも、投げた主題の file を**こちらが編集し続けると報告が混ざる**。
**投げた瞬間から、その主題の file は触らない**(別の主題か GitHub 側の作業をする)。

## 依頼文の頭に書くこと(段 0)

隔離した worktree は**まっさらな checkout**で、**依頼者の HEAD からではなく `origin/main` から**切られる
(未 commit の物は 1 バイトも入らない)。依頼文の先頭にこの 3 行を置く:

```
段 0: git rev-parse HEAD の先頭が XXXXXXXX でなければ git checkout --detach XXXXXXXX で揃える。
      この commit で足した物(関数名 / file 名)が 1 grep で在ることを確かめる。
      0 件なら何もせず報告して終える(揃えても無いときだけ止まる)。
```

| 起きること(型) | 依頼文に書く / 依頼者がやる | 記録(`reference/worktree-incidents.md`) |
|---|---|---|
| 起点が違う(`origin/main` / 先端より古い commit / 別 branch)。**緑の見かけがいちばん強い** | **先に commit** し、sha は `git rev-parse` の出力を貼る(作文しない)。**「在るはずの物」を 1 つ**書く。branch 名で checkout させない。範囲を `src tests` に切るなら `docs CHANGELOG.md` も(お知らせ・CHANGELOG の突合が baseline で赤くなる)。合わせたら**変異の前に対象 test が緑**であることを見る。agent の定義(smoker / verifier / implementer)にも同じ段 0 が入っている(両方やる) | 「worktree には commit した物しか入らない」 |
| 返ってきた報告の sha が依頼と違う | **受け取って最初に見るのは数字ではなく sha**。合っていなければ数字は全部捨てる(投げ直す前に、CI が同じ物を回していないか問う)。走っている最中は `git worktree list` で agent の HEAD が見える | 「返ってきた数字は、どの commit の数字か」/「runner / smoker の依頼文には期待する sha を必ず書く」 |
| `node_modules` が無い | `ln -s /home/user/PKC3/node_modules node_modules`(🔴 commit しない)。vite の dev server を立てるなら `server.fs.allow` を足した config を worktree の中に置く | 「worktree の作法 3 つ」 |
| `git` を含む複合コマンド / heredoc + パイプを断られる | 素の 1 本ずつに割る。割れない物は **script file に書いて `sh <file>`** | 同上 |
| `isolation: "worktree"` が `not in a git repository` で落ちる | **まず `pwd`**(原因は cwd が repo の外のことが多い)。`Agent` を投げる直前の Bash で `cd /home/user/PKC3 && pwd`(cwd が戻る性質そのものは `sandbox-hygiene`「bash の cwd が `/home/user` へ戻ることがある」)。cwd が repo なのに同じ error のときだけ hook を疑う。**そのとき書ける agent を隔離なしで起動しない**(read-only の型に下書きさせ、依頼者が当てる) | 「worktree 隔離が起動できない箱がある」 |
| scratchpad / 変異試験の backup dir / `vite preview` の port は**兄弟の agent と共有**される | 作業 file は `scratchpad/<issue 番号>/` の固有 dir、短い名前(`edit1.py`)を使わない、実行前に `cat`。backup は `<file>.mutbak` の隣置きか `mktemp -d`。`PKC3_SMOKE_PORT=N` は **N / N+1 / N+2 を握る**ので 10 刻みで割り、立たなかったら INFRA として読む(`ss -ltnp` で回す前に確かめる) | 「worktree を分けても共有される物が 3 つ」「smoke の port は 3 つ使う」「scratchpad は兄弟の agent と共有される」 |
| branch の名前空間(`refs`)は共有 | 見るだけの agent は `git checkout --detach FETCH_HEAD`、patch を作る agent は `-B agent-<主題>`(汎用名 `x` を書かない)。**飛んでいる依頼文を並べて、branch 名が全部違うか**見る | 「依頼文に branch 名を書くなら、agent ごとに違う名前」 |
| worktree の置き場所の取り違え | 場所を名指しし、**作る前に在るか確かめる**(`test ! -e <path> \|\| …`)。命令は絶対 path。投げた後に `git worktree list` で、**投げた担当の数だけ依頼文どおりの行が在るか**見る | 「worktree の置き場所も agent ごとに違う名前にし…」 |
| 依頼文の「後始末」が依頼者のツリーを巻き戻す | 🚫 `git reset --hard` / `git checkout <branch>` / `git switch` / `git clean -fd` を**書かない**。退避と復元は `cp` に閉じる。理由まで書く(worktree が消えていたら、その命令は依頼者のツリーに当たる) | 「依頼文に「作業ツリーを巻き戻す命令」を書かない」 |
| 再開(SendMessage)した agent の worktree が消えている(利用制限で止まった agent も、**正常に終わった agent** も) | 再開の依頼文に 3 行:`pwd` と `git worktree list` で自分の worktree を確かめる / 無ければ**何も書かずに**報告して止まる / 以後の命令を `cd <自分の worktree の絶対 path> && …` で始める。頼む前に `git worktree list` で残っていることを見る。続きの結果だけなら worktree の log を依頼者が直に `grep` | 「再開した agent は、worktree を持っていないことがある」 |
| worktree 隔離の agent は GitHub から file を落とせない | **親が落とす**(scratchpad へ `curl`、sha256 を確かめ、path を依頼文に書く)。止められたら止められた字をそのまま返させ、回避させない | 「worktree 隔離の agent は GitHub から file を落とせない」 |
| 書き込み担当が `git checkout --` / `git reset --hard` を、禁じても打つ | **専用の作業ツリー**で走らせる(失うのはそこの未 commit 分だけ)。戻ってきたら依頼者が `git status --short` と `git diff --stat` を**作業ツリーで**見る | `dispatch-incidents.md`「禁じても、書き込みエージェントは…」 |

## 投げ方 ── プロンプトに必ず入れる 5 つ(+ レビューのとき 6 つ目)

1. **範囲を確定する** ── 「この PR」ではなく `git diff <base>..HEAD` の base を書く
2. **すでに済んでいることを書く** ── typecheck / lint / unit 件数 / smoke / 変異試験の
   結果。書かないと同じ作業を繰り返され、同じ指摘が戻る
3. **read-only を明示する**(定義にも書いてあるが、プロンプト側でも念を押す)。
   `npm run build` / `npm test` / `npx playwright` を**走らせるな**と書く ──
   生成物や `test-results/` を書き換えると依頼者のツリーが壊れる
4. **CONFIRMED と 未検証 を分けて出させる** ── これが無いと疑いが断定に化ける
5. **「無ければ無いと言え」** ── 件数を埋めるための発明を禁じる
6. 🔑 **レビューには「この差し替えが壊しうる物」を 3〜5 個、名指しで書く**(2026-10-02)。
   今日の着地後レビュー 3 本が当たったのは、依頼文に「2 本目の接続 / 関数の寿命 /
   事前呼び出しの副作用 / `as` で黙らせた所」と**仮説を列挙した**ときだった。reviewer は
   変異をそこへ当てる ── 書かないと「test が弱い」の一般論が返り、**送り直し**(ムダ撃ち)になる。
   ⚠ 仮説は**当てさせる的**であって、**結論ではない**(「壊れているはず」と書かない)

⚠ **同じプロンプトを N 本投げるより、観点を変えて N 本**投げる(多様性 > 冗長)。
同じ観点の重複は、同じ見落としを N 回するだけである。

🔑 **本数は箱から逆算する**:`Workflow` が同時に走らせるのは 2 本(4 core)。build / test を回す
implementer は **3 本まで**(`uptime` の load average が core 数 4 の 3 倍 = 12 を超えていたら増やさない。8 本同時で 23 に達して箱が再起動した)。
読むだけの agent は本数に数えない。待つ間は別の仕事をする(`sleep` / ポーリングで待たない)。

| 長い走り・大きな返り | 依頼文に書くこと(`reference/dispatch-incidents.md`) |
|---|---|
| 45 分を超える実行(probe など) | `run_in_background: true` と `timeout: 5400000` を付けて **1 回だけ**。完了通知まで何もしない。終了コードは log の中に書く(`cmd > log 2>&1; echo "exit=$?" >> log`)。「45 分を超える実行は、runner に背景で 1 回だけ走らせ…」 |
| 時系列を集計させる | **全行を file へ**(round の見出しつき)。画面に出すのは件数表と、依頼者が決めた 2〜3 個の数だけ。読みは依頼者が file でする。「runner の集計は「件数表」と「時系列」を分ける」 |
| grep させる字 | 書く前に `grep -rn '<印>' build/ src/` で 1 回引き、**出た行をそのまま写す**(記憶の綴りは半分合っていて 0 件になる)。「runner に grep させる字は、source から引いて書く」 |
| 焼きに対照を同梱する | **対照が相手に届いたか**を先に測る(届かない回は判定に使わない)。「読みを実測で潰す道具を 1 回の焼きに同梱するときは…」 |

## 受け取ったあと ── 検算が本体

```
① 1 件ずつ**自分で再現する**(合成入力 / 実行 / 実測)
② 再現したものだけ直す
③ 直したら「**今度は何に救われていないか**」を問い、もう 1 巡投げる
```

🔴 **修正コード自体はまだ誰にも読まれていない。** 1 巡目が見つけた差分の修正は、**必ず 2 巡目に掛ける**。

🔑 **片側を直したら、対称の反対側を必ず見る。** これは PKC3 で一番よく出る型である。

| 受け取った物 | 検算(1 秒〜1 分) | 記録(`reference/dispatch-incidents.md`) |
|---|---|---|
| 差分の「user 報告」「user 指示」「user 裁定」 | `git diff \| grep -n 'user 報告\|user 指示\|user 裁定'` で拾い、行ごとに issue / CLAUDE.md の元の字を引く。引けない物は出どころ(台帳の行 id など)に書き換える(発言を作らない) | 「受け取った差分の「user 報告」は、出どころを 1 件ずつ引く」 |
| 推薦・計測の数字 | **その agent が見た版は、いまの版か**(`git log` で投げた時刻と、その後の commit を突き合わせる)。依頼文に sha を書き、報告に sha が無ければ数字ごと使わない | 「推薦は「何を測ったか」を確かめてから採る」 |
| 「自分の検査は落ちるか」 | spec を足してもらったら**直す前の版で落ちるかを変異で確かめて返す**ことを最初から頼む(足した検査の緑は情報量 0) | 「「自分の検査は落ちるか」を、頼まなくても返す agent は当たりである」 |
| 全量 test の報告(件数・Duration・mtime) | **log の `stat`**(mtime がいまより未来 / 小さすぎる)と、ハーネスの「has not reported yet」。数字を人に渡す前に**自分で log を `cat`**。期待値を渡すなら、報告は log の原文 → `ls -la` の大きさと mtime → 期待値との差、の順で書かせる(答えを先に渡すと測らなくても書ける。期待値は禁じない ── ずれを拾うのは期待値の仕事) | 「測っていない数字が、実測の顔で返ってくる」 |
| 全量 unit が時間切れ | 全量は**単独**で回させる(他の重い agent が 1 本以下のとき)。触っていない file が 5 秒の時間切れで落ちたら、その file だけ単独で回し直してから読む。`--testTimeout` を上げて通さない(2 回同じ file なら**その test にだけ**明示の timeout) | 「全量の unit を、重い agent と同じ箱で並べない」 |
| 並行実行の journal / 戻り値 | 権威があるのは**ワークフロー自身の戻り値**。journal の「直前の started のラベル」で結果を結びつけない。agent の生の transcript(`agent-*.jsonl`)は読まない | 「並行に走らせた記録は、ラベルと中身がずれる」 |
| 機械が出した判定(閾値) | 数えるのは判定の数ではなく**判定の中身**(refute が「方式が成り立たない」か「書き方に穴」か)。自分で書いた閾値ほどそのまま信じやすい | 「機械が出した判定を、中身を読まずに採らない」 |
| 受け取った実装 | **依頼文ではなく、設計 doc の条件**に照らす(読む順は「doc の条件 → 返ってきた差分」)。doc に「これが無いと成り立たない」と書いた条件は依頼文にも写す。①条件を満たす形へ直す → ②その形を測る → ③覆ったら取り下げる(②を飛ばさない) | 「受け取った実装は、依頼文ではなく設計 doc の条件に照らす」 |

⚠ ワークフロー(`parallel` / `pipeline`)を組むとき:
- **同じ作業ツリーで `npm run build` する段を並べない**(`dist/` を空にしてから書き直す)。build する段は直列にし、後の段は「前の段が焼いた `dist/` を使う」と書く。並べたいなら作業ツリーを分け、smoke のポートも分ける。単体テスト(`vitest`)は並べてよい。
- 箱が作り直されてワークフローが消えたら、**最初から投げ直さない**:`git worktree list` と各作業ツリーの `git log -1` → `…/workflows/<run id>/journal.jsonl` の `"type":"result"` 行 → 残りだけ新しく回す(失われるのは報告と未実行の段だけのことが多い)。「箱が作り直されてワークフローが消えたら、最初から投げ直さない」
- 止まった implementer の再開は `SendMessage` で「**まず `git status` と字面で、変異の残りが無いことを確かめてから続きを**」(変異試験の最中に止まった agent は変異入りの版を `orig` と読む)。「同時に走らせる implementer は 3 本まで」

## 何を並列に投げるか(実績のある形)

| 形 | 例 |
|---|---|
| **観点で割る** | レビューを「代替物で満たせるガード」「経路の数え上げ」「コメントの嘘」で 3 本 |
| **面で割る** | markdown の記法網羅を「本文 / プレビュー / ライブエディタ / 書き出し」で割る |
| **案で割る** | 設計案を独立に N 本作らせ、判定役を別に立てて突き合わせる |
| **敵対で割る** | 1 本に「証明」、もう 1 本に「反証」を担当させる |

⚠ **割り方を書かずに「調べて」と投げない。** 割り方こそが設計である。
🔑 よその repo を学ばせるときは「経緯 / 物語 / 面の動線 / 生死」で 4 本同時に割り、**「機能の一覧を作るな」と明示的に禁じ、「物語」と「生死」を要求する**
(`dispatch-incidents.md`「「よその repo を学ぶ」ときの割り方」、2026-08-22)。
⚠ **1 本ずつ順に投げない。** 互いの前提を壊し合うので、同時に投げて突き合わせる。

## やってはいけないこと

- 🚫 **並列に投げた結果をそのまま PR 本文へ貼る** ── 検算していない主張が残る
- 🚫 **儀式的な定期実行**(プロセス指示「必要な時にやる」)── 未完の作業が残っている
  ときだけ張り、着地したら畳む
- 🚫 **PR gate へ足す** ── サブエージェントは開発者の道具であって CI の一部ではない
  (プロセス指示「CI を長くしない」)

## 何を投げ、何を自分で持つか ── 基準は「速さ」ではなく「繰り返し」

方針の正本は CLAUDE.md「重い作業を自分で抱えない」(user 指示 2026-09-13。#857 段① の着地前に全量 test・build・smoke・変異スイープを
自分で回して予算を使い切り、原因を「箱が作り直された」と外のせいにした件)。機械的に振り分ける:

| 誰が | 何を | 目安 |
|---|---|---|
| 🟢 **自分** | 直した層だけの unit / typecheck / lint / grep / file の読み書き | **秒**で終わる |
| 🔴 **サブエージェント**(model は下の 3 段) | 全量 `npm test` / `build` / 実ブラウザ smoke / **変異スイープ** / 全数調査 | **分**かかる、または**同じ手順を何十回も当てる** |

🔑 **検算は 1 つ:「この作業は、同じ形を 3 回以上繰り返すか」。** 繰り返すなら投げる。
⚠ 落ちた原因を外に求める前に、自分の使い方を数える(CLAUDE.md の同じ節)。
⚠ **model は agent の定義 file(`.claude/agents/*.md` の `model:`)に書いてある**(2026-09-20 から)── 起動時の指定に頼らない。定義に無い型(`general-purpose` / `Explore`)を使うときだけ `model` を明示する。

### モデルの選び方 ── 3 段

方針は CLAUDE.md「サブエージェントは「適切なモデル」でコストを最適化する」(user 裁定 2026-09-20「3 段で分ける」)。

| 段 | 何に | agent |
|---|---|---|
| **haiku** | **機械的な作業** ── 回して結果を返す / 数える:全量 `npm test` / `build` / 名指しの spec の smoke / grep の全数と件数 / 変異スイープの実行 | `pkc3-runner` / `pkc3-verifier` |
| **sonnet** | **file:line で根拠を読む仕事** ── 調査 / レビュー(実装・動線)/ 実装の分担 / smoke の範囲を切る | `pkc3-surveyor` / `pkc3-reviewer` / `pkc3-ux-reviewer` / `pkc3-implementer` / `pkc3-smoker` |
| **親** | **設計の判断と user とのやり取り**だけ | ── |

🔑 検算:「この作業に**判断**は要るか」。要らなければ haiku。要るが**根拠を読むだけ**なら sonnet。
⚠ 親で回してよいのは秒で終わる物だけ(上の表)。

### ムダ撃ち ── 同じクレジットを 2 度払わない(CLAUDE.md の同じ節、user 指示 2026-09-20)

| 形 | 直し |
|---|---|
| 報告に表が無い(「詳細は直前のメッセージ本文」)── 送り直して同じ調査をもう 1 度 | 依頼文に「**hand-back の本文に表を全部入れる**(省略しない)」と書く。足りなければ **SendMessage で足りない部分だけ**頼む(再起動しない) |
| 設問の出し直し | 設問は「その物が何か」「なぜそう考えたか」を **1 行ずつ添えて 1 度で**出す |

(実際に払った 2026-09-20 の記録は `dispatch-incidents.md`「ムダ撃ち」。)

### ⚠ 投げるときに、範囲まで切る

⚠ 「変異を当てて」だけ投げると、相手は**全量 `npm test` を毎回**回す(1 変異 50 秒 × N)。
🔑 **回す test を名指しする**(`tests/features/… と tests/adapter/… の 3 本だけ`)。
🔑 **smoke を混ぜない**(`npm run build` が要るので 1 変異のコストが跳ね上がる ──
CLAUDE.md「build + smoke の**対**の回数で数える」)。
🔑 **返し方も切る**:「変異ごとに 1 行」「長い引用をしない」と書く ── 書かないと
全文が返り、読む側(= こちら)で燃える。

## 自己点検(投げる前に)

- [ ] 書き込み権のある担当は `isolation: "worktree"`、依頼文の頭に**段 0**(sha と「在るはずの物」)が在る
- [ ] sha は `git rev-parse` の出力を貼った(作文していない)。branch 名・作業ツリーの path が**担当ごとに違う**
- [ ] `git reset --hard` / `git checkout <branch>` / `git clean -fd` を依頼文に書いていない
- [ ] 範囲(base の sha)・済んだこと・read-only・CONFIRMED と未検証・「無ければ無いと言え」を書いた
- [ ] 回す test を名指しし、返し方(表・1 行ずつ・数)を切った。期待値を渡すなら報告は log の原文が先
- [ ] build / test を回す担当は 3 本以内。全量 unit は他の重い担当が 1 本以下のときに
- [ ] 投げた主題の file を、返るまで触らない
- [ ] 受け取ったら sha → 数字 → 1 件ずつ再現、の順で読む
