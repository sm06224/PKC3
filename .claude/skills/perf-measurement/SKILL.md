# 測って示す(PKC3)

> **規律の正本は `CLAUDE.md`**(「計測規律は PKC2 から継承」+「検証の規律」)。
> 本スキルは**手順と道具**である。

## 0. 何を主張するのかを先に書く

測る前に、紙に 1 行で書く。**書けないなら測っても読めない。**

| 主張の型 | 要る道具 |
|---|---|
| **速くなった** | 対照群つきのベンチ(§1) |
| **消しても見た目は変わらない** | 差分ハーネス(§2) |
| **重くなっていない** | 対照群だけ(前後で動かないことを示す) |

⚠ **「配る量が減った」は主張として弱い**(user 指示 2026-08-03「配る量は気にしない。
効くのは定常」)。測って報告すべきは**常駐メモリ**と**操作の応答**である。

## 1. 対照群 ── 「何もしない」ではない

> **対照群 = 測りたい操作**以外**を全部同じにしたもの**(CLAUDE.md)

🔴 **2026-08-07 に間違えた実例。** 「本文に無い記法の段を素通りさせる」効果を測るとき、
対照群を「**記法が少し在る本文**」にした。ところがその本文にも**目印の無い記法**が
大量にあり、**対照群でも素通りが効いていた** ── 前後で 22.3 → 13.5 ms と動いてしまい、
そのまま読めば効果を**過大に見積もる**ところだった。

**正しい対照群は「目印を全部含む本文」**である。そこでは素通りが 1 段も効かないので、
**前後で動かないこと**が「効くべきでないときに何もしていない」証拠になる。

```
記法なし(素通りが全段で効く)   20.6 ms → 10.5〜11.8 ms   ← 主張したい側
目印を全部含む(対照群)         134.6 ms → 129.8〜132.4 ms ← 動かないことが証拠
```

🔑 **対照群は「効かないはずの条件」で組む。** 「効きが薄いはずの条件」では足りない ──
薄くても効いていたら、差の出どころが分からなくなる。

## 2. 差分ハーネス ── 「消しても見た目は変わらない」を示す

読んで「この規則は死んでいる」と判断しない。**両方作って全プロパティを突き合わせる。**

型(2026-08-07、書き出し HTML の `.b` 規則 38 本の削除で使った):

1. 削除**前**の生成物を出す
2. 削除して生成物を出す
3. 実ブラウザで両方を開き、**対象配下の全要素 × 全 computed プロパティ**を読む
4. **面を変えて繰り返す** ── 画面 light / 画面 dark / **紙**(`@media print`)。
   ⚠ 紙を落とすと `@media print` の規則の退行を丸ごと見逃す

### ⚠ 「相違 0 点」は、そのままでは何も意味しない

**2 つのガードを先に置く。** どちらも 2026-08-07 に実際に必要だった。

**(a) 被覆を数える** ── 消した規則の**当たり先が fixture に実在するか**を数える。
1 巡目は 129,081 点を突き合わせて「相違 0」だったが、**10 次元が空**だった
(縦書き / 物理寄せ / 式 / 外部画像 / 見つからない添付 …)。
CLAUDE.md「fixture のゼロ件の次元は測っていない次元」。**37 / 37 にしてから測り直す。**

```js
// 消した規則の選択子を並べ、当たり先が 0 件のものを出す
for (const s of SELECTORS) if (root.querySelectorAll(s).length === 0) console.log('0 件:', s);
```

**(b) 感度を確かめる** ── **生きていると分かっている値**を変えて、差分が出ることを見る。
⚠ **死んでいる規則で試してはいけない** ── 0 点が返るが、それは
「ハーネスが鈍い」のか「その規則が死んでいる」のか区別できない。
実例: `.b th{background}` を変えても 0 点(= 死んでいた)。
`.b{max-width:46em}` → `20em` で **698 点**動いて、初めて感度が確かめられた。

## 2.5. 🔴 計器そのものに自己検査を持たせる(2026-09-04、#685)

⚠ **「0 件」は、そのままでは 2 通りに読める** ── 「速い」のか「**見ていない**」のか。
実例:付箋を 5 枚開いても long task が **0 件**だったので「重くならない」と書きかけたが、
その前に**わざと 300ms 詰まらせても 0 件**だった ── 🔑 そこで**計器が死んでいる**と
読みかけ、実際は**観測を登録した同じタスクの中で詰まらせていた**だけだった
(1 フレーム挟んだら鳴った)。つまり**計器も、こちらの試し方も、両方疑う必要がある**。

🔑 だから**計器の先頭で自己検査する** ── わざと 1 フレーム詰まらせ、
**鳴らなければ「判定不能」で落とす**:

```js
w.__probeSelfCheck = async () => {
  w.__probe.armed = true;
  await new Promise((r) => window.requestAnimationFrame(r)); // ⚠ フレームを挟む
  const t = Date.now();
  let spin = 0; while (Date.now() - t < 250) spin += 1; void spin;
  await new Promise((r) => setTimeout(r, 600));
  return w.__probe.longTasks.length;   // 0 なら計器が死んでいる
};
```

⚠ `PerformanceObserver.supportedEntryTypes` に `longtask` が**載っていても**、
実際に鳴るかは別である ── **一覧は約束ではない**。

### ⚠ 観測点が「自分の待ち」に支配されていないか

同じ回で 2 つ目の誤りを踏んだ。打鍵の実時間を測るのに、間に入れた `sleep`(2.4 秒)を
**足したまま**数えていたので、0 枚 **3084ms** / 5 枚 **3074ms** ── 🔴 **分解能が 0** で、
どんな差も出ない数字だった。打っている間だけ数えたら 679ms / 675ms になり、
初めて「差が無い」と言える形になった。

🔑 **出た数字を見る前に「この数字は何に支配されているか」を問う。**
⚠ 待ち・起動・取り込みが測定対象より大きいなら、その観測点は**主張を支えられない**。

## 3. 主張してよい範囲

- 🔴 **差し引きで出た値は向きのみ信頼し、倍率は書かない**(CLAUDE.md)
- 🔴 **百分率は分母を書く**(「どの実行の何に対する比率か」)
- 🔴 **boot 窓だけで定常を語らない**(user 指示 2026-07-27
  「boot 直後とか測ってない?意味ないからね、ソレ」)
- ⚠ **測った場所を書く。** node の `renderMarkdown` を測ったなら、それは
  **実機の体感ではない**。long task / 入力から反映までの時間は別に測る
- ⚠ **暖機してから測る**(JIT)。回数を書く
- 🔴 **`Worker.terminate()` は、worker の中の同期の `VACUUM` を止めない**(2026-10-02、#1218)。
  「止めた」を「書き終えた」と読まない ── 大きな書込の**途中でタブを殺す**と、**DB が開けなくなる**ことが在る
  (#1218)。目的:**殺す / 止める操作を、書込の完了の観測に使わない**こと
  (probe・smoke・変異試験で「タブを閉じた / worker を止めた」後に DB を読むとき)。
  🔑 検算:止めた後に**DB を開き直して整合を見る**(開けるか / 書いたはずの件数が在るか)。
  開き直せなかった回は、**製品の不具合か、途中で殺した計器の副作用か**を分けてから書く
  (同じ手順で「殺さずに書き終わるまで待つ」群を対照にする)。

## 4. 道具

| 何を測るか | 置き場 |
|---|---|
| 実ブラウザの挙動・computed style | `tests/smoke/`(Playwright。`smoke-testing` スキル) |
| 大きな DOM / 打鍵 / 保存 | `tests/probe/run-*.mjs`(nightly が回す) |
| 一時的なベンチ・差分ハーネス | **repo 直下に置いて、測り終えたら消す** |

⚠ 一時ハーネスは `npx tsx` で動かすと `src/` の TS をそのまま import できる。
⚠ ハーネスを repo 直下に置いたら **commit しない**(`git status` で確かめる)。
⚠ `@playwright/test` を import するハーネスは **repo 直下**に置く ── `/tmp` から
だと `node_modules` を解決できない。

## 6. 🔴 測ってから作る ── 順番を逆にすると、段を 2 つ捨てる(user 指摘 2026-10-09)

user の問い(解釈):**最近、実装がやたらに遅い。原因は何か。**
数えたら原因は 5 つで、うち 3 つは**この skill の手順を飛ばしていた**ことだった(#1467 段 3-e / 3-g):

| 何が起きていたか | どう直すか |
|---|---|
| **直してから測った**。「forced layout の読み手を外せば速くなる」を読みで決めて 2 段作り、A/B で**差が出なかった**(2,581 → 2,565〜2,730 ms / 2,381 → 2,537 ms)。1 段は閉じ、1 段は効果無しで着地 | 🔴 **trace で「どの行が何 ms か」を見てから作る**。読みは仮説であって計測ではない ── 段 3-h(`:has()` を属性へ)は trace の StyleInvalidator 18,654 件から入り、1 回で 3,085 → 2,375 ms |
| 全量 `npm test` を **1 PR で 2 回**(レビュー前と後) | **最終の sha で 1 回**。途中は触った層だけ |
| A/B を**他の重い物と同じ箱で**回した(全量 unit / smoke が同時に走り、timeout と flake が混ざった) | 🔴 **測る間は箱を静かにする**(load 3 未満を各 run の前に見る)。seed(20,000 行で約 6 分)は **1 回**で済ませ、before / after を**交互に**回す |
| 機械的なエージェントを 3 本同時に起動(箱は 4 コア) | **同時は 2 本まで**。3 本目は待ちの間に次の調査を書く |
| 待ち時間を待ちで使った | 待ちの間に**次の段の trace を読む / 依頼文を書く**(完了は通知で届く) |

🔑 検算は 1 つ:**作り始める前に「いま測った数字で、この段が効く理由」を 1 行で書けるか。**
書けないなら、先に trace を 1 回回す(5 分)── 作って測って捨てる(2 段で 1 日)より安い。
