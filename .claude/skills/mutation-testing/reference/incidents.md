## SURVIVED の型: 実装としては違うのに、user から見た結果が同じ(2026-08-08)

`SURVIVED` の型: **実装としては違うのに、user から見た結果が同じ**。

**実例**: 「編集中はノートを移らない」の `return` を消す変異が生き延びた ──
`SELECT_ENTRY` は reducer が編集中に捨てるので、**素通りしても選択は動かない**。
1 巡目の fixture は**居るノート**しか試しておらず、差が出なかった。

🔑 **差が出る入力を探す。** 居ない lid なら、素通りすると理由が
「見つかりません」で**上書きされる** = user が**直せない指示**を読む。
そこを assert したら殺せた。

⚠ 「差が本当に無い」なら、それは**冗長なコード**である ── test を足すのではなく
**消す**ほうが正しいこともある。どちらかを選ぶ(放置しない)。

## SURVIVED の型: 壊した行に一度も入っていない ── 生き延びたら、まず「通っているか」を疑う(2026-08-07)

🔴 **`SURVIVED` には 2 つの意味がある。** 順に潰す ── 逆順でやると、届いてもいない
test に assert を足し続けることになる。

| 見かけ | 実態 | 直し方 |
|---|---|---|
| `SURVIVED` | test は**壊した行を実行している**が、assert が弱い | assert を足す / 観測点を変える |
| `SURVIVED` | test が**壊した行に一度も入っていない** | **入力を変えて経路に入れる** |

**実例(2026-08-07)**: 履歴パネルの作り直しを止めるガードを消す変異が生き延びた。
assert は正しかったが、`DetailRenderer.render()` は
**(selectedLid, body, phase, revisionPanel) の指紋が同じなら何もせず返る**(当時 4 項。いまは 6 項) ──
test は `entryMetas` だけ動かしていたので、**`renderPanel` に 1 度も入っていなかった**。
本文を変える入力(= 履歴を開いたまま追記した形)に替えたら殺せた。

**見分け方**: 壊す代わりに **`throw new Error('reached')` を置いて test を回す**。
落ちなければ、その行は**誰も通っていない**。

⚠ これは §「`NOT-APPLIED` を合格と読まない」の**別の顔**である ── 変異が届かない
原因は「アンカーが外れた」「生成物を検査している」だけでなく、
**test の入力がその分岐に入らない**こともある。

そのうえで「assert を足す」より先に「**この assert は何に救われているか**」を問う。
CLAUDE.md「空振りを直したら『今度は何に救われていないか』を問う」。

## SURVIVED の型: 「差が出る入力」を作らないと殺せない変異がある(2026-08-17、#1222 は 2026-10-02)

**同じ結果になる 2 つの実装は、変異試験では区別できない。** 2 件連続で踏んだ:

- 「知らない器の中へ降りる」の fixture が **段落 1 つ**だった ── 降りない実装でも
  同じ 1 段落になるので、**降下を消す変異が生き延びた**。見出し + 段落にしたら殺せた
- 行の lid 解決を `selectedLid` 固定にする変異が **smoke では生き延びた** ──
  情報ペインでは「行の lid」と「選択中の lid」が**必ず一致する**ので差が出ない。
  **差が出る入力**(行の lid ≠ 選択)を unit で作ったら殺せた
- 🔴 **`null` 同士の `toBe` は緑になる**(2026-10-02、#1222)。「同じノードを指す」を
  `expect(a.querySelector(x)).toBe(b.querySelector(x))` で見たら、**両方が `null`** でも通った
  (どちらの selector も当たっていなかった)。目的:**比べる 2 つが両方とも「無い」で救われない**こと。
  🔑 比べる前に **`expect(a.querySelector(x)).not.toBeNull()` を置く**(片側だけでよい)。
- 🔴 **fixture が、その変異で差の出る形か**を回す前に 1 行で言う(2026-10-02、#1222)。
  留めた枠が**何も選んでいない** / 孫が**無い**fixture で、初回の変異 **4 件が SURVIVED**
  (差が出ない入力なので、壊しても同じ結果になる)。目的:SURVIVED を「検査が弱い」と
  読み違えて assert を足しに行かないこと。🔑 手順:変異ごとに
  「**この変異で結果が変わる入力は、fixture のどの要素か**」を書き、書けなければ fixture を足す。

🔑 生き延びたら「assert が弱い」の前に **「この入力で差が出るのか」**を問う。
⚠ 本当に差が出ないなら、それは**冗長なコード**である ── test を足すのではなく
消すほうが正しいこともある(どちらかを選ぶ。放置しない)。

## SURVIVED の型: 別の処理が結果を戻していた(2026-08-20)

「通っているか」の節は「その行に入っていない」、「差が出る入力」の節は「入力で差が出ない」。こちらは
**test はその行を通り、差も出るのに、後続の別処理が壊れた状態を元へ戻す**形。

**実例**: 全文検索の索引が「一部だけずれている」ことを検知するか見る test で、
「空のときだけ組み直す」へ壊す変異が**生き延びた**。理由は、同じ起動処理の中で
**派生列の埋め戻しが全行を UPDATE し、その trigger が索引を埋め直していた**から ──
検査したい判定を**通ってはいたが、結果が別経路に救われていた**。

🔑 **見分け方**: 変異を当てたまま、**その test だけを回して最終状態を印字する**。
期待どおりの値になっているなら、**それを作ったのは自分の検査対象ではない**。
🔑 **直し方**: 救い手が走らない前提を test 側で作る(この件では派生列を**先に埋めて**
UPDATE が 1 行も走らない形にした)。⚠ 製品を変えるのではなく **fixture を変える**。

## SURVIVED の型: 観測点が「開始」と「完了」を取り違えている(2026-08-22)

ここまでの型は「通っていない」「差が出ない」「救われた」。こちらは
**test はその行を通り、差も出て、救い手も居ないのに、assert が両方の場合に真**という形。
= §1 の空振りが**時間の軸**で出たもの。

**実例**: 「DB の 2 本を**並行**に投げる」を守る test で、直列へ戻す変異が生き延びた。

```ts
// ❌ 1 稿目 ── 直列でも真になる
entryLids: async () => { entryStarted = true; await gate; return [...]; },
revisionLids: async () => { if (entryStarted) parallel = true; return [...]; },
```

直列(`await a(); await b();`)でも、b が走る時点で a は**開始済み**なので
`entryStarted` は真。⇒ **並行かどうかを 1 ミリも見ていなかった。**

```ts
// ✅ 直した ── 「解決する前に走ったか」を見る
entryLids: async () => { await gate; entryResolved = true; return [...]; },
revisionLids: async () => { if (!entryResolved) parallel = true; return [...]; },
```

🔑 **並行・順序・排他を主張する test は、「相手を止めたまま自分が進めるか」で書く。**
片方を gate で止め、microtask を進め、**止まっている間に相手が走ったか**を見る。
⚠ 「開始した」「呼ばれた」を観測点にすると、**直列でも必ず真**になる。

🔑 見分け方は「別の処理が結果を戻していた」の型と同じ形で言える ── **変異を当てたまま、その assert が
「変異前と変異後で違う値になるか」を印字して確かめる**。同じなら観測点が誤っている。

## SURVIVED の型: 同じ物を守る網が 2 枚あって、互いに救い合う(2026-09-09、#681 段③)

「別の処理が結果を戻していた」の型は「別の処理が戻していた」だが、こちらは**自分が意図して置いた 2 枚目**である。
どちらを壊しても**もう 1 枚が同じ結果を作る**ので、**2 つとも SURVIVED になる**。

**実例**(temp の表を作り直す所):

| 網 | 役目 |
|---|---|
| 作る前の `DROP … IF EXISTS` | 前の回の中身を引かせない(**鮮度**) |
| 走り終わりの `finally` の `DROP` | 常駐メモリを返す(**解放**) |

⚠ 「本文を直したら新しい側が出る」の test は**どちらか 1 枚が生きていれば通る** ──
だから 1 枚ずつ壊しても落ちない。

🔑 **直し方は 2 つで 1 組**:

1. **その網だけが鳴る場面を、網の数だけ作る** ── 上の例なら「解放」は
   **`sqlite_temp_master` に前の回の表が残っていないか**で見る(「引けるか」では
   見えない ── 引く字を打てば作り直されるので、残っていても同じ答えが出る)
2. 🔴 **それでも殺せない網は、殺せないと注記する** ── 上の「鮮度」の側は、
   `finally` が働いている限り**振る舞いが 1 つも変わらない**。⚠ そこで
   「これが無いと壊れる」と書くと嘘になるので、**2 枚目であること・残す理由
   (`finally` の落としは例外を飲む)・test では殺せないこと**をコメントに書く
   (CLAUDE.md「『これが無いと壊れる』と書く前に、外して壊れるのを見る」)

⚠ **後始末(close / free / revoke)の変異は、ほぼこの形になる** ── 守っているのは
メモリであって振る舞いではないので、外から観測する口が無い。
🔑 だから**最初から「これは殺せない」と分けて数える**:報告は
「20 件中 18 件 KILLED、残る 2 件は**振る舞いを変えない後始末**」と書く
(「2 件 SURVIVED」とだけ書くと、次に読む人が test を足そうとして時間を溶かす)。

## SURVIVED の型: 実装の穴 ── 変異が実装の穴を出したら、それは test の話ではない(2026-09-09、#681 段③)

⚠ 変異試験の報告は「test が弱い / 強い」で終わりがちだが、この日は
**3 件とも製品の穴**だった:

| 生き延びた変異 | 実際に見つかったもの |
|---|---|
| 名前の無い囲みを表にする | test の fixture が**そのノートを走査すらしていなかった**(粗い絞りが `name=` なので、`name=` を持たない本文は読まれない = §1 の空振り) |
| 組み立ての順番を入れ替える | 断った回に、**そこまでに作った物が落ちていなかった**(戻り値で渡していたので、投げると呼び側へ届かない) |
| 断りの側の後始末を消す | **外しても誰も落ちない行**だった(前段が既に同じことをしている)⇒ 消した |

🔑 だから `SURVIVED` を見たら、**test を足す前に「実装はこれで正しいか」を 1 度読む**。
⚠ 「test が弱い」と決めて assert を足すと、**穴を埋めたまま緑にする**ことになる。

## SURVIVED の型: 当てた変異が、直したい欠陥を再現していない(2026-09-09。同じ日に 2 回)

⚠ これは「網が 2 枚」の型とも「実装の穴」の型とも違う ── **test も実装も正しく、
変異のほうが的を外している**。⚠ 結果は「SURVIVED」なので、そのまま読むと
**在りもしない弱さを直しに行く**(1 回転まるごと無駄になる)。

| 当てた変異 | なぜ再現しなかったか |
|---|---|
| 窓ごとの合言葉を作る行を、乱数の**別の枝**へ倒した | ⚠ その枝も**一意な値を返す** ── 直したい欠陥は「合言葉が同じになる」ことなので、まったく起きていない |
| `if (this.storage === null) return this.fallback;` を `void 0;` に置き換えた | ⚠ すると次の行が `this.storage.getItem(...)` を**素で呼んで例外を投げる**ので、`catch` が控えを返して**正しく動いた** ── 直す前の綴りは `this.storage?.getItem(...)` で、**投げない**のが欠陥の本体だった |

🔑 **検算は 1 つ:「この変異を当てた版は、直す前の版と同じ振る舞いか」。**
⚠ 「行を消す」「条件を `false` にする」は、**直す前の姿とは限らない** ──
とくに **`?.` を `.` にする / 早期 return を消す**ような変異は、
**別の経路(例外・既定値)が拾って結果が変わらない**ことがある。

🔑 だから **直す前の綴りをそのまま復元する**変異を 1 本持つ(`git show` で引ける)。
⚠ これは §「R1 ── 直す前に、新しい test を『直す前の dist』で回して赤を見る」と
**同じ主張の変異試験版**である ── 守っているのが本当に「直した物」かを見る。

## SURVIVED の型: 手順が「肝心の場面」を作っていない(2026-09-14、#918 段③)

⚠ 「当てた変異が、直したい欠陥を再現していない」の型は*変異*が的を外す話だが、こちらは **test の手順**が的を外す ──
**assert は正しく、変異も正しく、それでも落ちない**。

実例:「**器が広がったら窓も広げる**(白い帯を残さない)」を実ブラウザで見る段を足した。
手順は「**打つ欄に複数行を打って伸ばす → 打った字を消して縮める**」。
⚠ 変異を 2 つ当てたら **両方 SURVIVED** だった。

🔴 **理由は手順に在った** ── 「伸ばして**戻す**」は、戻した先が**元の大きさ**である。
そのときの窓は**元から足りている**ので、途中で描き直さなくても最後には間に合う。
🔑 つまりこの手順は「**器が過去最大より大きくなる**」という**当の場面を 1 度も作っていない**。

🔑 直し方は assert ではなく**手順**である ── **1 度も無かった大きさにする**
(この件では窓そのものを縦 2 倍にした = `page.setViewportSize`)。
そうしたら同じ変異が **2 件とも KILLED** になり、
**白い帯 230px** という数字まで出るようになった。

⚠ **検算は 1 つ:「この手順は、直したい欠陥が起きる状態を通るか」。**
🔑 言い換えると **「初めての値」を作っているか** ── 元へ戻す / 同じ値をもう一度 /
既に通った範囲を往復する、は**どれも新しい場面を作らない**。

⚠ そして**これを見つけたのは、回した agent 自身**だった(頼んでいない変異を
自分で当てて報告してきた)── `subagent-scale/reference/dispatch-incidents.md`「『自分の検査は落ちるか』を、頼まなくても返す agent は当たりである」に「最初から頼む」と書いた。

## SURVIVED の型: 正しい値を残したまま、偽物を足しただけ(2026-09-16、#996)

⚠ 「当てた変異が、直したい欠陥を再現していない」の型は「変異が直す前の姿を再現していない」だが、こちらは**もっと単純**である ──
**門が `toContain`(含むか)なのに、変異が『足す』方向だった**。

実例:断り文が**実在するボタンの名前**を含むことを見る門を足し、変異を当てた:

```ts
// 直した版
`…は「持ち歩ける 1 枚」に入れられません。` + `代わりに 左の列の バックアップ …`
// 🔴 1 稿目の変異 ── 偽の名前を**足した**(正しい名前はそのまま)
`…に入れられません(一式を書き出す へ)。` + `代わりに 左の列の バックアップ …`
```

🔑 **門は正しく通る** ── 正しい名前は**まだ在る**のだから当然である。
⚠ ここで「門が弱い」と読むと、**在りもしない弱さを直しに行く**。
🔑 直しは 1 つ:**`toContain` の門には「置き換える」変異を当てる**
(正しい名前を**消して**偽物にする)── 当て直したら 1 回で `KILLED` になった。

⚠ 一般形:**変異の向きを、門の向きに合わせる。**

(判断の表は [`../SKILL.md`](../SKILL.md)「門の向きと変異の向き」)

## SURVIVED の型: 門が「その file に字が在るか」を見ていて、字は別の所にも在った(2026-09-21、#1032)

⚠ 「偽物を足しただけ」の型は*変異の向き*の話だが、こちらは**門の見ている場所**である ──
`readFileSync` で source を読み、**その名前が file のどこかに在るか**で守ったつもりになる形。

実例:「左の列の 3 つの器(`filer-table` / `dual-table` / `entry-list`)を
**1 つ残らず**判定に入れる」を守る門を、こう書いた:

```ts
const src = readFileSync('src/adapter/ui/actions/binder.ts', 'utf-8');
for (const region of ['filer-table', 'dual-table', 'entry-list']) {
  expect(src.includes(`[data-pkc-region="${region}"]`)).toBe(true);  // 🔴 弱い
}
```

🔴 **判定から `entry-list` を落としても緑**だった ── その字は
**同じ file の別の所**(行を掴む判定・焦点の行を引く所・D&D)にも在るからである。
⚠ 変異試験で **SURVIVED** が出て初めて分かった(CLAUDE.md §1「範囲が広すぎて
無関係な所に満たされる」の、**同一 file 版**)。

🔑 **直しは「assert を足す」ではなく、正本を 1 つ作ること**:

```ts
// 製品側 ── 字を 1 か所へ置き、読む所は全部ここから引く(§7)
export const ROW_HOST_REGIONS: readonly string[] = ['filer-table', 'dual-table', 'entry-list'];
export const ROW_HOST_SELECTOR = ROW_HOST_REGIONS.map((r) => `[data-pkc-region="${r}"]`).join(', ');

// test ── **配列そのもの**を等値で pin する(file の字面を探さない)
expect([...ROW_HOST_REGIONS]).toEqual(['filer-table', 'dual-table', 'entry-list']);
```

同じ変異(配列から 1 つ落とす)は **1 発で KILLED** になった。

⚠ そして**寄せる先を間違えない** ── この件では「行を掴む判定」と「余白を押したら
閉じる判定」が**同じ 3 つを名指し**していたので 1 か所へ寄せられたが、
🔴 後から実測で**押す側の器は別物**(`browse-host`)だと分かった。
🔑 **同じ字だからといって同じ物とは限らない** ── 寄せる前に「この 2 か所は
**同じ問いに答えているか**」を 1 行で言えるか確かめる(言えないなら 2 つの定数にする)。

## SURVIVED の型: 場面が「入れ子」しか無く、普段の経路を 1 度も通っていない(2026-10-05、#1344 v2)

⚠ 「手順が肝心の場面を作っていない」の型は*肝心の場面を作っていない*だが、こちらは**肝心の場面は作ったが、普段の場面を作っていない**。

実例:Qt の入れ子 suspend を LIFO で起こす JS の patch(`qtbase-patch-asyncify-nested.py`)。実装者は変異 **5 件を KILLED**
にして出したが、着地前レビュー(read-only)が**別の台で**同じ JS に当てたら、**実害のある変異が 2 件 SURVIVED** だった:

| 変異(from → to) | 何が起きるか |
|---|---|
| tick 頭の `armed = false` を「stack が空なら return」の**後**へ動かす | 空 tick が `armed` を立てたまま終わり、**次の wake で永久停止** |
| `if (!top.wake) return;` を `s.length > 1` のときだけに | 入れ子でない**普段の loop が tick ごとに空転**(常駐 CPU) |

🔴 **なぜ 5 件が殺せて 2 件が残ったか**:実装者の場面は **(a) 1 回だけ** と **(b)(c) 入れ子**で、
**「1 つが起きて、再予約の空 tick が回り、また suspend する」= LO の main loop の普段の形**を 1 度も通していなかった。
変異 5 件は**全部「入れ子で破れる」物**だった(= 自分が置いた門ばかり狙った。下の「置いた門ではなく、
置き忘れた門を狙う」の実例)。

🔑 **検算**:**「普段の経路(入れ子でも例外でもない、1 本が何度も往復する形)を、再予約・idle の tick を回したうえで N 周」**を
場面に**必ず 1 つ**持つ。⚠ **状態 flag(`armed`)を持つ機構は、何もしない tick の後に次の操作が通るか**を見る。
🔑 **直し**:新しい unit test 2 本(各 20 行)。変異を**自分でも当て直して**落ちることを見た
(`tests/office-asyncify-nested-patch.test.ts` の「③ v2: 再予約の空 tick を回した後も…」「③ v2: 単独の entry が起きて再 suspend しても…」)。

⚠ **レビュアーが台を自分で作って当てたから見つかった** ── 実装者の `it.each(MUTANTS)` の**表を読むだけでは出ない**
(表は実装者が選んだ変異しか載っていない)。🔑 レビュー依頼には**「生き延びる変異を 2 つ以上、from → to で挙げる」**を入れる
(`.claude/agents/pkc3-reviewer.md` §② が「最低 3 つ、そのまま適用できる diff で」と**既に定めている**ので定義は触らない。
`subagent-scale/SKILL.md`「投げ方」の 6 つ目の**仮説の名指し**と併せて依頼文に写す)。

## SURVIVED の型: 閾値・数え直し・向きのような「定数と符号」を 1 つも pin していない(2026-10-05、#1344 v3)

⚠ 「普段の経路を 1 度も通っていない」の型の翌日、同じ patch で同じ形を踏んだ。実装者は変異 **9 件を KILLED** にして出したが、着地前レビュー(read-only)が
**4 件 SURVIVED** を出した ── 全部「**数**と**符号**」だった:

| 変異 | なぜ生き延びたか |
|---|---|
| 診断の閾値 `=== 250` → `=== 1`(`=== 2` / `=== 100` / `=== 600` も) | test は「600 周の後に診断 1 件」しか見ておらず、**249 周で 0・250 周で 1** を見ていない |
| 1 ずつ数える `+ 1` → `+ 2` | 同上(125 周で鳴っても 600 周の後は 1 件) |
| 待ちごとに数え直す `= 0` を外す | test は **1 回の待ち**しか無く、短い待ちが**累積して鳴る**形を作っていない |
| 門の符号 `!==` → `<` | 台は sp が**下がる**場面(上に frame が生きている)しか持たず、**上がる**場面(巻き戻し)が無い |

🔑 **検算**:実装に **数(閾値・周期・上限)と符号(`<` / `!==` / `>=`)** が在れば、その数の**両隣**(249 / 250)と符号の**裏側**
(上がる / 下がる)を場面に 1 つずつ持つ。「N 周で鳴る」は **N−1 周で鳴らない**ことまで書いて初めて pin である。
🔑 **数え直し(reset)は、閾値に届かない短い episode を 3 回並べて「鳴らない」で pin する** ── 長い episode の後に短い episode を
置いても、counter は閾値を 1 度しか跨がないので(2 回目以降は `===` に当たらない)、reset の有無で結果が変わらない。
⚠ **符号の変異は、台に「その向きの場面」が無いと NOT-APPLIED と見分けがつかない** ── レビューの掃引で「1 failed」と出た変異が、
実は `from` の字が別の変異で既に変わっていて NOT-APPLIED だった(値で読む ── [`../SKILL.md`](../SKILL.md)「結果は 5 値で読む」)。

### 🔴 台の模型が「起きた frame の止まり直し」を新しい frame として押していた(同日、同じ patch)

shadow stack を模した台(`sp -= 16` で押す / JS へ戻れば戻す)で、場面 B(内側が起きて**もう一度 suspend**)が v3 でも「門なし」でも
落ちた ── 模型が **B → B2 を新しい frame として 1 段押していた**ので、戻ったときの sp が外側の sp と一致しなかった。
実物では「起きた frame が `then` の中で再 suspend する」のは **同じ frame が同じ深さで止まり直す**こと(押さない / 戻すときの値は元の frame から引き継ぐ)。
🔑 **模型が「門なし」でも落ちたら、実装ではなく模型を疑う**(門を外しても落ちる = 門の話ではない)。
🔑 模型を直すときは **実物の規則を 1 行で書いてから**書く(「新しく JS から入った frame だけが押す」)。

### 🔑 同じ日の 3 度目(#1344 (a')、PR #1358)── 場面は「重なり」と「裏側」を**最初から**持たせる

promise_await の門(`tests/office-promise-await-guard.test.ts`)は「普段の経路」「定数と符号」の型を読んだうえで書いたので、実装者の 5 件は KILLED だったが、
着地前レビューが **場面の欠け**を 2 つ出した(変異ではなく「この場面が無い」の指摘):
① **await が 2 本重なる**(外側が待っている間に、上に積んだ計算も await に入り、外側の promise が**先に**解決する)──
門は外側を起こしてはいけない(内側 → 外側の順)。台の `getPromise` が **1 本しか持てない**形だったので、id で持つ形に直して場面 D を足した。
② **sp が控えより高い**(`dir=unwound`)── 「定数と符号」の型の「符号の裏側」そのもの。場面 E を足したら、変異 ⑦「`===` を `>=` にする(上だけ見る)」が初めて殺せた。
🔑 **検算**:待ち/起こしの門には、**(a) 同じ資源を待つ物が 2 つ重なる場面**と **(b) 符号の裏側**を、変異を当てる前に場面として持つ。
⚠ 「変異 N 件 KILLED」は置いた場面の範囲でしか言えない(§「置いた門ではなく、置き忘れた門を狙う」)── 場面の一覧を先に書く。

## SURVIVED の型: 1 回しか呼ばない台 ── 「N 回目も効くか」を当てる(2026-09-04、#689)

⚠ 台が **1 回しか呼ばない**購読・ハンドラでは、「**初回だけ動いて以後は固まる**」
変異が生き延びる。

```js
// 生き延びた変異(#689 の着地前レビューが実際に出した形)
+ let armed = true;
  const off = wiring.onSelectedEntry((cid, lid) => {
-   if (lid === null) return;
+   if (lid === null || !armed) return;
+   armed = false;
    target.setEntry(cid, lid);
  });
```

🔴 **user から見た症状は「半分だけ直っている」**である ── 「2 件目までは
付いてくるのに、3 件目から固まる」。⚠ 全部壊れるより**報告されにくい**ので、
台帳には「直った」と書かれたまま残る。

🔑 **台で 2 回以上呼び、2 回目の結果まで assert する。**
⚠ 「1 回呼んで正しい」を見た検査は、**繰り返しについて何も言っていない**。

🔑 当て所の数え方:`grep -c '<台の呼び口>('` で**台が何回呼んでいるか**を数える。
1 回しか呼んでいない購読は、この変異が必ず生き延びる場所である。

## SURVIVED の型: 置き忘れた門 ── 置いた門ではなく、置き忘れた門を狙う(2026-09-07、#764)

⚠ 変異は**自分が書いた行**にしか当てられないので、**書かなかった行**については

🔑 **変異を並べる前に、実装が「受ける / 受けない」を分ける軸を数え上げる。**
軸ごとに**受ける側の端**を総当たりし、**答えが出てしまう形**を探す。

(軸の表は [`../SKILL.md`](../SKILL.md)「変異の選び方」)

## SURVIVED の型: 印の数では見えない門がある(2026-09-07、#749)

## SURVIVED の型: 経路が別 ── SURVIVED が「経路が別」を意味することがある(2026-08-18)

**smoke が唯一の門**である(この件は smoke で KILLED になった)。
