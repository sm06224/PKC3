# 変異試験(PKC3)

> **通っている test は、何も保証していないかもしれない。**(CLAUDE.md)

実装を意図的に壊し、**test が落ちることを確かめる**。落ちなければ、その test は
その機構を守っていない。実績: **1 PR あたり 1〜3 件が生き残り、その多くが
「既に壊れているのに鳴っていない」**だった。

## 手順

### 1. ハーネスを file に出す(その場の shell に書かない)

```bash
cp .claude/skills/mutation-testing/templates/mutate.py /tmp/mut-<主題>.py
# MUTATIONS を編集してから
python3 /tmp/mut-<主題>.py            # 全件
python3 /tmp/mut-<主題>.py M1 M3      # id を指定
```

🔴 **その場の shell に書かない。** shell の引用で python が SyntaxError になり、
**変異が当たらないまま「生存」と読んだ**ことがある(2026-08-04)。
テンプレートは置換前に「元の文字列がちょうど 1 件あること」を assert し、
置換後に「変異後の字面が在ること」を確かめる。

⚠ **「挿入」型の変異では「元の字面が消えたこと」を要求できない**(2026-08-08 に
ハーネスが 2 回止まった)。`before` を残したまま前後に足す変異
(`import X;` の前に 1 行挿す等)では `after` が `before` を**含む**ので、
`assert before not in now` が必ず落ちる。判定はこう書く:

```python
assert after in now, f'{mid}: 置換後の字面が入っていない'
if before not in after:                       # ⚠ 置換型のときだけ
    assert before not in now, f'{mid}: 元の字面が残っている'
```

🔑 **同梱テンプレートは既にこの形**(「置換後の字面が在るか」だけを見る)──
**手書きすると踏む**。`templates/mutate.py` をコピーして `MUTATIONS` だけ書き換える。

⚠ **アンカーは前後を含めて一意にする。** `?pkc-flag=editor.live` は同じ file に
3 回出て `NOT-APPLIED` になった ── `ARM === 'live' ? '?pkc-flag=editor.live' : ''`
のように**式ごと**掴む。

### 2. 結果は 3 値で読む

| | 意味 | やること |
|---|---|---|
| `KILLED` | test が落ちた = 守られている | 次へ |
| `SURVIVED` | test が通った = **守られていない** | test を足す / 書き直す |
| `NOT-APPLIED` | **変異が当たっていない** | アンカーを直して**やり直す** |

🔴 **`NOT-APPLIED` を合格と読まない。** 当たっていない変異は「生存」と見分けが
つかない ── これを 1 セッションで 2 度踏んだ(2026-08-04)。

### 2.5. 🔴 生き延びたら、「差が user に見えるか」を先に問う(2026-08-08)

`SURVIVED` の 3 つ目の顔: **実装としては違うのに、user から見た結果が同じ**。

**実例**: 「編集中はノートを移らない」の `return` を消す変異が生き延びた ──
`SELECT_ENTRY` は reducer が編集中に捨てるので、**素通りしても選択は動かない**。
1 巡目の fixture は**居るノート**しか試しておらず、差が出なかった。

🔑 **差が出る入力を探す。** 居ない lid なら、素通りすると理由が
「見つかりません」で**上書きされる** = user が**直せない指示**を読む。
そこを assert したら殺せた。

⚠ 「差が本当に無い」なら、それは**冗長なコード**である ── test を足すのではなく
**消す**ほうが正しいこともある。どちらかを選ぶ(放置しない)。

### 3. 生き延びたら、まず「**通っているか**」を疑う(2026-08-07)

🔴 **`SURVIVED` には 2 つの意味がある。** 順に潰す ── 逆順でやると、届いてもいない
test に assert を足し続けることになる。

| 見かけ | 実態 | 直し方 |
|---|---|---|
| `SURVIVED` | test は**壊した行を実行している**が、assert が弱い | assert を足す / 観測点を変える |
| `SURVIVED` | test が**壊した行に一度も入っていない** | **入力を変えて経路に入れる** |

**実例(2026-08-07)**: 履歴パネルの作り直しを止めるガードを消す変異が生き延びた。
assert は正しかったが、`DetailRenderer.render()` は
**(selectedLid, body, phase, revisionPanel) の指紋が同じなら何もせず返る** ──
test は `entryMetas` だけ動かしていたので、**`renderPanel` に 1 度も入っていなかった**。
本文を変える入力(= 履歴を開いたまま追記した形)に替えたら殺せた。

**見分け方**: 壊す代わりに **`throw new Error('reached')` を置いて test を回す**。
落ちなければ、その行は**誰も通っていない**。

⚠ これは §「`NOT-APPLIED` を合格と読まない」の**別の顔**である ── 変異が届かない
原因は「アンカーが外れた」「生成物を検査している」だけでなく、
**test の入力がその分岐に入らない**こともある。

そのうえで「assert を足す」より先に「**この assert は何に救われているか**」を問う。
CLAUDE.md「空振りを直したら『今度は何に救われていないか』を問う」。

### 3.5. probe に変異を当てる(2026-08-17 に確立)

**`tests/probe/run-*.mjs` は vite dev(`--port 45731`)に向く**ので、smoke と違って
**build は要らない** ── `src/**` を書き換えたら、次の page 読み込みでそのまま届く。
⚠ ただし watcher が拾うまで一拍あるので、当てた直後に **1.5 秒待つ**。

```python
if kind.startswith("probe:"):
    time.sleep(1.5)                      # vite の watcher が拾うのを待つ
    r = run(kind[len("probe:"):], timeout=900)
```

🔴 **判定は「exit code」だけに頼らない。** probe は `ok: false` を出しても
`process.exitCode` を立て忘れることがあるし、**bench は落ちない作り**である
(数字を出すのが仕事なので)。実例(#223):「live の行確定を外す」変異は
bench の**出力の中身**(`observed.diagram` が 0 件)でしか捕まらなかった。

```python
killed = r.returncode != 0 or '"diagram": 0' in out    # 中身も見る
```

### 3.6. 🔴 「差が出る入力」を作らないと殺せない変異がある(2026-08-17)

**同じ結果になる 2 つの実装は、変異試験では区別できない。** 2 件連続で踏んだ:

- 「知らない器の中へ降りる」の fixture が **段落 1 つ**だった ── 降りない実装でも
  同じ 1 段落になるので、**降下を消す変異が生き延びた**。見出し + 段落にしたら殺せた
- 行の lid 解決を `selectedLid` 固定にする変異が **smoke では生き延びた** ──
  情報ペインでは「行の lid」と「選択中の lid」が**必ず一致する**ので差が出ない。
  **差が出る入力**(行の lid ≠ 選択)を unit で作ったら殺せた

🔑 生き延びたら「assert が弱い」の前に **「この入力で差が出るのか」**を問う。
⚠ 本当に差が出ないなら、それは**冗長なコード**である ── test を足すのではなく
消すほうが正しいこともある(どちらかを選ぶ。放置しない)。

## 変異の選び方

**壊れる当の振る舞い**を狙う。下流の結果だけ見る test は別経路に救われる。

| 型 | 例 |
|---|---|
| 値の取り違え | `find('dark')` → `find('light')`(名前しか見ない検査を素通りする) |
| 順序 | 生成物の一部を前後へ移す(詳細度・cascade・listener 登録順) |
| 落とす | 集合の最後の 1 件を落とす / 文脈(`@media`)を落とす |
| 緩める | `every` → `some` / 境界チェックを外す / 判定を常に真にする |
| 検品を骨抜き | 検査関数が常に合格を返す / `this.error` を消す |
| 渡し忘れ | 複数経路のうち 1 つだけ引数を落とす(**経路ごと**に 1 件ずつ) |

⚠ **検品する側・test する側も変異の対象**にする(CLAUDE.md)。検品が壊れると
「通った」という事実だけが残る。

## 落とし穴(全部この repo で踏んだ)

### 🔴 置換文字列は前後を含めて一意にする

`  armDpr();` のような短い断片は、狙った行ではなく**4 字下げの別行に部分一致**する。
テンプレートは出現回数が 1 でなければ `NOT-APPLIED` を返す。

### 🔴 smoke に当てるなら build が要る

`tests/smoke` は `vite preview` で **`dist/` を配信**する ── source を書き換えた
だけでは検査対象に**一切届かない**。印刷 CSS の変異 6 件が全部「SURVIVED」に
見えて「誰も守っていない」と読み違えかけた(真相は 6 件とも NOT-APPLIED)。

テンプレートの `kind="smoke"` は `npm run build` を挟み、**`dist/assets/` の生成物に
変異後の字面が在り、変異前の字面が消えたこと**を確かめてから test を回す。

#### 🔴 CSS を壊す変異は、印を **custom property** で置く(2026-08-14)

CSS の変異に**コメントで印を書くと minify が消す** ── dist に 1 つも残らないので、
**当たっているのに `NOT-APPLIED`** になる(実測: 出荷 css のコメントは **0 件**、
custom property は残る)。`--mut-a: 1` を足して、それを探す。

⚠ **`*.js` だけを見ない。** `app.css` は `dist/assets/` へ**別 file** で出る
(実測 js **105 件** / css **1 件**)── テンプレートの `dist_assets()` は両方読む。

```bash
# 変異を当てて build したあと。印が無ければ NOT-APPLIED(SURVIVED と読まない)
grep -rq -- "--mut-a" dist/assets/
```

⚠ **規則ごと消す変異にも印を残す** ── 消すだけだと「当たったこと」を dist から
確かめられない。消した規則の代わりに `--mut-x: 1` を置くと、当たりが見える。

#### 🔴 TypeScript を壊す変異の印は、**実行時の副作用**にする(2026-08-18、#253)

CSS のコメントと同じ罠を、TS で **2 通り**踏んだ ── どちらも
「dist に届いていない」= **偽の NOT-APPLIED**(変異自体は効いている)になる:

| 印の置き方 | どうなるか |
|---|---|
| **型注釈に混ぜる**(`'idle' as T & { __mutS1?: true }`) | ❌ `tsc` が**型を消す**ので 1 バイトも出ない |
| **文字列リテラル + `.slice`**(`'idle__mutS1'.slice(0, 4)`) | ❌ minifier が**畳んで** `'idle'` にする |
| **実行時の代入** | ✅ 残る |

```ts
// 変異の中に 1 行足す ── 畳めない・消せない
(globalThis as unknown as Record<string, unknown>)['__mutS1'] = 1;
```

⚠ 印が出ないときに**「当たらなかった」と読んで先へ進まない** ── まず
**印の置き方**を疑う(1 度目は本当に届いていない、2 度目はたいてい印の側である)。

### ⚠ 全角の括弧・記号をアンカーに含めない

この repo のコメントは日本語で、`(` `)`(全角)と `(` `)`(半角)が混ざる。
コメント行をアンカーにすると照合に失敗して `NOT-APPLIED` になる。
**コードの行**をアンカーにする。

### 🔴 片側を直したら、対称の反対側を必ず疑う

2026-08-07 の最悪の 1 件がこれだった ── 検品を「出力の文字列を見る」形に直したのに、
**トークンだけ直して規則は需要側の数を見たまま**だった。組み立てのループを消すと
検品が合格し、**規則が 1 本も入っていない CSS が出荷される**(実測)。

🔑 **1 巡目の修正は、2 巡目の対象である。** 変異の一覧を作るとき、「今回直した箇所の
**鏡像**はどこか」を必ず 1 行足す。

### ⚠ perl の `\Q…\E` は変数補間を止めない

`$` を含む字面(`${BODY_CSS}` など)を perl で置換すると**補間されて空になる** ──
`\Q` はメタ文字の解釈を止めるだけ。当たらないまま A/B して「同じ数字」を得た。
**python を file に出して**置換する。

### 🔴 `git checkout` で戻さない ── **後始末も含めて**

作業ツリーの他の変更ごと消える。テンプレートは `cp` でバックアップし、
`finally` で必ず戻す(test が落ちても・例外でも)。

⚠ **2026-08-14 に、変異の「後始末」でこれをやって未 commit の workflow 変更を失った。**
CLAUDE.md と本 skill の**2 か所に書いてあって止まらなかった** ── スイープ本体では
守れていたのに、終わったあと手で片付けようとして踏んだ。
🔑 **文言を 3 か所目にしない。手で戻す手順を残さないこと**が対策である ──
バックアップと復元は `finally` の中だけに置き、外から `git` を触らせない。

⚠ **バックアップは変異を当てる直前に取り直す**(使い回さない・終わったら消す)。
2026-08-10 に使い回して、スイープの最後に**修正前のコピーが書き戻され**、その状態で
commit して CI が赤くなった。⚠ **スイープの後にもう一度** typecheck / lint / test を
回してから commit する ── 変異試験は**作業ツリーを触る操作**である。

### ⚠ build が落ちたら、それは `KILLED` である

下限 tripwire(検品)が効いた形。テンプレートはそう扱う。

## 報告の形

```
○ KILLED       M1 焼いた CSS を style から外す
    Error: 配った HTML の見た目がアプリと違う
🔴 SURVIVED    M2 …
⚠ NOT-APPLIED  M3 元の文字列が 0 件(1 件でない)

KILLED 10 / 10
```

PR 本文には **KILLED した件数と、何を壊したか**を書く。⚠ 「変異試験を回した」
だけでは意味がない ── **何が生き延びて、どう直したか**が中身である。

## 🔴 変異は「自分の直し」にも当てる(2026-08-18)

レビューの指摘を直したあと、**その直し自体**に変異を当てると、**直しの副作用**が出る。
実例(#261、同じ日に 2 件):

| 直したつもり | 何が壊れていたか |
|---|---|
| タスクの印を「`<li>` の**直下**だけ見る」へ縮めた | **loose な GFM リスト**(`<li><p><input>`)の印を**丸ごと落とす** |
| 置けなかった理由を**その場で** `OP_FAILED` に出した | `state.error` は **1 枠**なので、直後の件数の総括に**上書きされて消える** |

🔑 **主張の向きを変えたら、反対側で何が壊れるかを 1 度は見る**(CLAUDE.md §1 の
「検査の向きを裏返したら、作法も裏返る」の**実装版**)。
🔑 **1 巡目の修正は、2 巡目の対象である。**

## ⚠ SURVIVED が「経路が別」を意味することがある(2026-08-18)

`store-port` が `parent` を落とす変異は **unit 全部が緑**だった ── worker の test は
worker を直に叩き、reducer の test は store-port を通らないので、**その層を誰も通らない**。
🔑 層をまたぐ配線は、**どの test がその層を通るか**を先に数える。通る test が無いなら、
**smoke が唯一の門**である(この件は smoke で KILLED になった)。
